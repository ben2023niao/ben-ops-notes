运维就绪不是“能部署一次”，而是项目上线后具备可恢复性：能部署、能回滚、能观测、能审计、能恢复数据、能处理故障。

本规范是公共框架底线。项目可以在 docs/project/** 或 ADR 中加严，但不能低于本文要求。

1. 分级

级别 适用阶段 必须具备
mvp 内测、试运营、小流量 环境说明、部署步骤、回滚步骤、基础日志、health check、密钥不进 Git。
growth 增长期、付费或稳定用户 监控告警、备份恢复、staging 验收、队列/缓存/数据库指标。
scale 大流量、多服务、多团队 SLO、灰度、限流、熔断、压测、容量评审、故障演练。
enterprise 企业级、合规、强审计 变更审批、密钥轮换、权限隔离、审计报表、灾备演练。

Scale Profile 来自 project.config.json。公共框架默认 mvp，但项目一旦启用真实支付、真实用户、后台处罚、账本、视频通话或高价值数据，至少要按 growth 检查。

2. 环境

每个项目必须维护环境矩阵：

docs/qa/test-environments.md

至少说明：

  1. local、dev、staging、production 的用途。
  2. 每个环境的基础 URL、数据库/存储、部署或启动命令。
  3. 哪些环境允许 mock、fixture、测试 key。
  4. 哪些环境禁止真实支付、真实短信、真实第三方回调。
  5. 哪个环境是上线前验收环境。

规则：

  1. local 不能作为上线验收依据。
  2. staging 未配置时，不能声明生产可上线。
  3. production 禁止未登记 mock/fallback/fixture。

3. 部署

部署策略记录在：

docs/operations/deployment-strategy.md
infra/deploy/README.md

必须说明：

  1. 每个 app/service 的构建命令、产物和启动命令。
  2. Nginx/Gateway/静态资源/API/Worker/Realtime 的部署边界。
  3. 端口、健康检查路径、日志路径。
  4. 数据库迁移执行顺序。
  5. 部署后 smoke test 和关键链路检查。

推荐部署后检查：

health check -> 静态资源 200 -> API 鉴权 -> DB/Redis 连通 -> Worker 心跳 -> 关键业务接口 -> 日志/监控可见

4. 回滚

每次上线前必须知道如何回滚：

  1. 前端静态资源回滚到上一构建产物。
  2. API 服务回滚到上一 image/commit/tag。
  3. Worker 先暂停消费，再回滚，再恢复消费。
  4. Realtime 服务回滚时必须考虑连接重连和兼容协议。
  5. 数据库变更优先向前兼容，避免依赖数据库回滚。
  6. 配置和第三方开关必须可回退。

破坏性 migration、协议变更、数据清理、权限模型变更必须写 ADR 或发布计划。

5. 配置与密钥

密钥规范见：

docs/operations/secrets-management.md

底线：

  1. 真实 secret 不进 Git。
  2. .env.example 必须列出必需变量、用途、是否 secret、默认值策略。
  3. dev/staging/production 密钥必须分离。
  4. 第三方服务必须区分测试 key 和生产 key。
  5. 密钥 owner、轮换策略和泄漏处置必须明确。

6. 备份与恢复

备份恢复规范见：

docs/operations/backup-restore.md

底线：

  1. 数据库必须有备份策略。
  2. 对象存储、上传文件、审计日志、账本流水必须明确是否备份。
  3. 必须说明 RPO/RTO。
  4. 必须有恢复演练或恢复步骤。
  5. 高风险上线前必须确认最近一次备份可用。

7. 观测

观测基线见：

docs/architecture/observability-baseline.md

最低要求：

  1. 每个服务有 health check。
  2. 每个请求有 request id 或 trace id。
  3. 访问日志、错误日志、后台审计日志分层。
  4. 登录、支付、账本、通话、消息、审核等关键业务有业务指标。
  5. Worker 有队列积压、失败、重试、死信指标。
  6. production 告警必须绑定责任人和 runbook。

8. 故障处理

故障响应规范见：

docs/operations/incident-response.md
docs/templates/ops-runbook-template.md

每类高风险服务至少需要 runbook：

  1. API 5xx 或 502/504。
  2. 数据库连接、慢查询、锁等待。
  3. Redis/缓存故障。
  4. Worker 积压或死信。
  5. 第三方回调失败。
  6. 证书、域名、磁盘、内存、CPU。
  7. 支付/账本/审核/权限异常。

9. 上线准入

上线前至少满足：

  1. npm run check 通过。
  2. npm run check:ops 通过。
  3. 测试环境矩阵有 staging 和 production 说明。
  4. 部署、回滚、密钥、备份恢复、故障响应文档齐全。
  5. 高风险数据变更有备份和回滚策略。
  6. 运行时日志、监控、告警可见。
  7. Agent 日志写明运维影响和验证结果。

10. 不允许完成的情况

以下情况不能声明“上线完成”：

  1. 只在本机跑通，没有 dev/staging/production 说明。
  2. 只有部署步骤，没有回滚步骤。
  3. 真实 secret 写在代码、README、日志或 PRD 中。
  4. 数据库有破坏性变更但没有备份和恢复方案。
  5. production 仍依赖未登记 mock/fallback/fixture。
  6. 没有 health check、日志或基本故障排查入口。
