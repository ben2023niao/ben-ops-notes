AI 框架技术价值模型

本文件定义公共 AI 工程框架是否真正产生“可复用、可规模化技术价值”的判断标准。框架不是为了沉淀漂亮文档，而是为了让下一个项目更快、更稳、更少返工。

1. 核心判断

一次实践只有同时满足以下条件，才算沉淀为框架资产：

  1. 可复用：不绑定单一项目、业务名、接口、设计图或服务器。
  2. 可配置：可以通过 framework.config.json、project.config.json 或模板变量适配新项目。
  3. 可验证：有脚本、CI、测试或清单证明规则被执行。
  4. 可迁移：项目通过 .ai-framework 升级或初始化后能指导开工，而不是只解释单个项目历史。
  5. 可规模化：能支撑多人、多 Agent、多端、多服务、多技术栈协作。

如果一条经验只解决当前项目问题，但没有抽象为配置、模板、脚本或流程，它只能算项目经验，不能算框架技术价值。

2. 框架资产类型

类型 说明 合格证据
规则 Agent 和工程成员必须遵守的工作方式 写入 AGENTS.md 或 docs/agents/rules/**，且能由框架版本复用
文档模板 新项目可通过框架获得的任务、日志、ADR、验收结构 位于 docs/templates/**，无项目硬编码
契约结构 OpenAPI、事件、错误码、DTO 的组织方式 位于 packages/contracts/**，不包含旧项目业务接口
公共包边界 前端、Go、PHP、UI、生成物的分层规则 例如 docs/architecture/package-boundaries.md 和 scripts/validate-package-boundaries.py
校验器 把软规则变成失败门禁的脚本 位于 scripts/validate-*.py，加入 npm run check
CI/CD 规则 多人协作时自动执行的质量检查 位于 .github/workflows/** 或 infra/ci/**
技术栈适配器 某类技术栈的目录、命令、测试和部署约束 例如 docs/architecture/backend-stack-go-gin-laravel.md
Web surface 适配器 官网、PC 站、H5、后台和 App 下载页的目录与验收规则 例如 docs/architecture/web-surface-strategy.md
Web 技术栈适配器 Nuxt 4 + Tailwind CSS v4 的目录、配置、共享 UI、测试和部署约束 例如 docs/architecture/web-stack-nuxt-tailwind.md
Scale Profile MVP、增长、大流量、企业级的演进规则 例如 docs/architecture/scaling-strategy.md
项目 Overlay 当前项目启用模块、技术栈、第三方、验收强度和例外 例如 project.config.json、docs/project/** 和 docs/architecture/project-overlay.md
Playbook 处理常见任务的操作剧本 有输入、步骤、验收和风险说明

3. 不算框架价值的内容

以下内容默认属于项目资产，不直接算公共框架价值：

  1. 某个产品的 PRD。
  2. 某个产品的 OpenAPI 具体业务接口。
  3. 某个产品的设计图、图片素材、机器人数据。
  4. 某台服务器、某个域名、某个第三方密钥。
  5. 某次临时修复，但没有提炼为规则或门禁。

这些内容可以作为实践证据，但必须经过抽象，才能进入公共框架。

4. 复用评分

每次框架改动必须按以下 5 项自评：

维度 问题 通过标准
参数化 是否去掉项目名、路径、业务接口、服务器硬编码？ 使用模板变量、framework.config.json 或 project.config.json
跨项目 新项目是否能不理解旧项目业务也能使用？ 文档只描述通用方法和配置
可执行 是否有脚本/CI/测试约束？ 有 scripts/validate-* 或明确检查命令
可观察 失败时是否能告诉 Agent 哪里不合格？ 脚本错误信息或验收清单明确
可维护 是否有 owner、日志和后续补齐项？ CODEOWNERS、Agent 日志、风险与待办齐全

低于 4 项通过时，只能标记为“项目经验”，不能标记为“框架能力”。

5. 规模化评分

框架要支持规模化，至少要覆盖：

  1. 多 Agent 并行：任务边界、日志、红蓝对抗、交接。
  2. 多端协作：apps、services、packages、docs、infra 的目录职责。
  3. 多技术栈：当前 P0 为 Go Gin + Laravel，后续技术栈必须通过适配器和项目 Overlay 接入。
  4. 多 Web surface：移动 App、官网落地页、PC/H5、后台和 Web 预览都有明确目录和验收规则。
  5. 多 Web 技术栈：当前默认 Nuxt 4 + Tailwind CSS v4，后续 Web 栈必须通过适配器接入。
  6. 多公共包边界：contracts/generated/ts/ui/go/php 分层明确，不使用万能 packages/shared。
  7. 多规模轨道：mvp、growth、scale、enterprise 的升级信号、容量、观测和回滚规则。
  8. 多项目 Overlay：公共框架保持通用，项目差异进入 project.config.json 和 docs/project/**。
  9. 多环境：local、dev、staging、production 的测试环境登记。
  10. 多层验收：任务级、模块级、项目级、发布级。
  11. 多风险等级：资金、权限、审核、账号、部署、数据迁移必须升级门禁。

6. 实践反哺规则

每次项目实践结束后，必须判断：

这个问题是否会在下一个项目再次出现？

如果答案是“会”，继续判断：

出现次数 动作
第 1 次 写入 Agent 日志风险与待办
第 2 次 写入公共规则或模板
第 3 次 升级为脚本/CI 门禁

例如：

  1. 假功能被用户指出一次：记录日志。
  2. 多个页面出现假功能：写入完成等级规则。
  3. 多个项目出现假功能：增加 validate-completion-claim 或等价门禁。

7. Go Gin + Laravel 的框架价值

团队当前默认技术线是 Go Gin + Laravel。它产生公共价值的前提不是“某个项目用了它”，而是：

  1. 新项目能复用同一套服务边界。
  2. Agent 能知道哪个接口归 Go Gin，哪个接口归 Laravel。
  3. OpenAPI 能标注 owner service。
  4. CI 能分别跑 Go 和 Laravel 检查。
  5. ECC 能覆盖跨服务链路。
  6. 高风险逻辑不因技术栈不同而绕过审计、幂等和测试。

8. Web 与 Scale Profile 的框架价值

Web 能力产生公共价值的前提是：

  1. 新项目能明确选择 apps/web、apps/admin 或 apps/mobile，而不是混在一个目录里。
  2. 移动 App 项目默认考虑官网、下载页、隐私条款、服务条款和应用商店资料。
  3. PC/H5/Web 项目有响应式、SEO异常验证、路由、权限态、API 接入和截图验收。
  4. Agent 能通过 framework.config.json 知道哪些 Web surface 存在、需要哪些视口验收。
  5. Nuxt 4 + Tailwind CSS v4 的目录、CSS-first token、@tailwindcss/vite 集成和 packages/ui 共享边界清楚。

公共包边界产生公共价值的前提是：

  1. packages/contracts 是跨平台契约源头。
  2. packages/generated/ts|go|php 是生成物，不能手写业务逻辑。
  3. packages/ts、packages/go、packages/php 分别服务各自平台。
  4. packages/ui/tokens|web|mobile 分清 token、Web UI 和 Mobile UI。
  5. AI Agent 不能把跨平台代码塞进 packages/shared 这种万能目录。

Scale Profile 产生公共价值的前提是：

  1. MVP 阶段不乱拆服务，但保留 owner、契约和数据边界。
  2. Growth 阶段强制补缓存、队列、慢查询、监控和 Web CDN 策略。
  3. Scale 阶段强制补服务拆分、数据扩展、容量评估、SLO、压测和回滚。
  4. Enterprise 阶段强制补多环境、权限、灾备、审计和成本治理。

项目 Overlay 产生公共价值的前提是：

  1. 公共框架只定义通用底线，不写死某个产品的选择。
  2. 当前项目的 app、service、技术栈、第三方、设计验收和例外全部进入 project.config.json。
  3. 项目专属约束进入 docs/project/**，而不是污染 AGENTS.md 或公共规则。
  4. 公共硬规则，如 Agent 日志、红蓝对抗、Contract First、项目级验收和 mock 不能冒充完成，不能被项目关闭。
  5. scripts/validate-project-overlay.py 能在开发前发现配置缺失、启用模块不匹配或例外未登记。

9. 合入要求

任何声称“优化 AI 框架”的改动，必须在 Agent 日志中回答：

  1. 本次沉淀的是规则、模板、脚本、技术栈适配器，还是项目经验？
  2. 哪些内容可复制到下一个项目？
  3. 哪些内容仍然只属于当前项目？
  4. 是否增加了自动校验？
  5. 是否降低了 Agent 偷懒空间？
  6. 是否支持 Go Gin + Laravel 或配置化技术栈？
  7. 是否支持 Web surface、Nuxt 4 + Tailwind CSS v4、公共包边界和 Scale Profile？
  8. 是否支持项目 Overlay，而不是把项目约束写死进公共框架？
  9. 是否通过 npm run check？

没有回答这些问题，不允许把改动称为框架优化。
