8.1 部署形态

8.1.1 环境

环境 用途 配置规模
local 开发者本地（Docker Compose） 单容器 mini
dev 开发集成测试（共享） K8s 1 node
staging 准生产，全链路联调，UAT K8s 3 node，资源 = 生产 50%
production 正式生产 K8s ≥ 6 node

8.1.3 容器化

镜像 Base 大小
go-* 服务 gcr.io/distroless/static-debian12 < 30 MB
nginx nginx:1.25-alpine < 50 MB
SRS ossrs/srs:5 或自构 < 200 MB
mysql-exporter / redis-exporter 官方 < 50 MB

构建：多阶段 Dockerfile，CGO_ENABLED=0 静态编译，-trimpath -ldflags="-s -w"。

8.1.4 K8s 资源声明

每个 Deployment 必带：

spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0  # 资金类服务严禁可用度下降
  template:
    spec:
      containers:
      - name: go-api
        image: registry.kickoff.tv/go-api:v1.2.3
        resources:

          limits:   { cpu: 2, memory: 4Gi }
        livenessProbe:
          httpGet: { path: /healthz, port: 8080 }
          periodSeconds: 10
        readinessProbe:
          httpGet: { path: /readyz, port: 8080 }
          periodSeconds: 5
        env:
        - name: TRACE_ID_HEADER
          value: X-Trace-Id
        envFrom:
        - configMapRef:  { name: app-config }

---

8.1.5 灰度发布

阶段 流量 时长 触发回滚
Canary 5% 10 min 错误率 > 1% / P99 > 1.5x baseline
25% 25% 15 min 同上
50% 50% 15 min 同上
100% 100% — —

实现：Nginx Ingress weight 灰度 或 K8s + Argo Rollouts。

资金类服务严禁热更新 push key 等 Secret，必须重启 Pod。

8.1.6 回滚

  • 保留前 3 版本镜像
  • 一键回滚：kubectl rollout undo deployment/<name>
  • DB migration 回滚：仅当 down.sql 已验证；生产 migration 不可逆需求必须申请评审
  • 配置回滚：ConfigMap 走 Git 版本化，kubectl apply 回退

8.2 配置与密钥管理

8.2.1 分类

类别 存储 注入 变更
普通配置 ConfigMap 环境变量 kubectl apply
密钥（DB pwd / Redis pwd / JWT secret / 支付商户私钥） K8s Secret 环境变量或文件挂载 走 secret rotation 流程
业务运营配置（抽水率 / 等级门槛 / 风控阈值） DB system_config level_config risk_rules 启动加载 + 5min 刷新 后台修改即生效

8.2.2 密钥轮换

  • JWT secret：每 6 个月轮换（保留旧 secret 7 天作过渡）
  • 数据库密码：每 90 天
  • 支付商户密钥：跟随通道商要求
  • 推流 / 播放 secret：每月轮换

8.2.3 v2 升级

引入 HashiCorp Vault，K8s ServiceAccount + Vault Agent Injector，所有密钥从 Vault 拉。

8.3 数据库部署

8.3.1 MySQL

  • 1 主 + 2 从（异地从 1，本地从 1）
  • StatefulSet + PVC NVMe SSD
  • 主从复制：row-based binlog，async（v2 可上 semi-sync）
  • 主从延迟告警：> 5s
  • 备份：xtrabackup 每日全量 + binlog 持续，30 天保留
  • 异地灾备：备份每日同步到异地 OSS
  • 自动 failover：Orchestrator 或 MHA（v2，v1 可人工切）

8.3.2 Redis

  • 1 主 + 2 从 + 3 sentinel
  • StatefulSet + PVC
  • AOF everysec + RDB 6h
  • 内存上限 8GB，maxmemory-policy allkeys-lru
  • 主从切换：sentinel 自动
  • 监控：QPS / 命中率 / 内存 / 大 key

8.3.3 Kafka（如启用）

  • 3 broker KRaft 模式（无 ZK）
  • StatefulSet + PVC SSD 100GB / broker
  • 副本因子 RF=3，min.insync.replicas=2
  • 保留：默认 7 天，audit 类 365 天
  • 监控：堆积 / 延迟 / 副本同步

8.4 监控架构

8.4.1 拓扑

Prometheus (scrape, 15s 间隔)
├── /metrics  ← go-api × 4
├── /metrics  ← go-admin × 2
├── /metrics  ← go-ws × 3
├── /metrics  ← worker-* × 多
├── mysqld_exporter × 3（主+从）
├── redis_exporter × 3
├── kafka_exporter（如启用）
├── srs_exporter（自研，从 SRS HTTP API 拉 stats）
├── node_exporter × 全部 K8s node
├── blackbox_exporter（接口存活探针）
└── nginx_exporter

Grafana
├── 业务大盘（GMV / 在线 / 主播 / 押注）
├── 资金健康（账本平衡 / 对账差异 / 派彩成功率）
├── 直播质量（首帧 / 卡顿 / 回源率 / 推流稳定性）
├── 服务性能（API P99 / 错误率 / QPS）
├── 基础设施（MySQL / Redis / Kafka / Node）
└── 风控运营（告警数 / 处置时长 / 规则触发率）

Loki + Promtail：日志聚合
  - 资金类日志独立 retention 365 天
  - 一般日志 retention 30 天
  - 关键日志关键字告警（"PAID_BUT_FAIL_LEDGER" / "ledger_imbalance" / "panic"）

Jaeger：链路追踪
  - 关键资金链路 100% 采样
  - 一般业务 1% 采样

Sentry：客户端 + 服务端异常上报

Alertmanager → Telegram bot + 邮件（按严重度路由）

8.4.2 标签规范（Prometheus）

标签 值
env dev / staging / production
service go-api / go-ws / worker-settle / ...
region cn-east / cn-south
instance Pod 名
version 镜像 tag

业务指标命名：kickoff_<domain>_<metric>_<unit>，如 kickoff_predict_bets_total、kickoff_wallet_recharge_amount_rmb_sum。

8.5 必须告警的 24 项

# 类别 指标 阈值 严重度
1 API P99 延迟 > 1s 持续 5min HIGH
2 API 5xx 错误率 > 1% 持续 1min HIGH
3 API QPS 异常 同比 ± 50% MED
4 DB 慢查询数 > 100 / min MED
5 DB 主从延迟 > 5s HIGH
6 DB 连接数使用率 > 80% MED
7 DB CPU > 70% 持续 5min MED
8 Redis 命中率 < 90% MED
9 Redis 内存使用率 > 80% HIGH
10 Redis 大 key（> 1MB） 出现即告警 LOW
11 队列 Streams 堆积 > 10w 条 MED
12 队列 死信队列长度 增长 > 100/h MED
13 支付 充值成功率 < 95% HIGH
14 支付 回调失败率 > 0.5% HIGH
15 资金 押注失败率 > 1% HIGH
16 资金 派彩失败 出现即告警 HIGH
17 资金 对账差异金额 > ¥1000 / 日 HIGH
18 直播 推流断开次数 同主播 1h ≥ 3 MED
19 直播 源站 CPU > 70% 持续 5min MED
20 直播 CDN 回源率 > 30% MED
21 直播 首帧时间 P99 > 3s MED
22 直播 卡顿率 > 5% MED
23 业务 房间在线人数突降 > 30% / 30s LOW
24 风控 高优告警未处理 ≥ 3 HIGH

8.5.1 告警路由

# alertmanager.yml
route:
  group_by: ['alertname', 'service']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  receiver: feishu-default
  routes:
  - match: { severity: critical }
    receiver: feishu-oncall-urgent
    continue: true
  - match: { severity: high }
    receiver: feishu-oncall
  - match: { team: finance }
    receiver: feishu-finance
  - match: { team: ops }
    receiver: feishu-ops

8.5.2 On-Call 轮值

  • 主 oncall + 备 oncall，每周轮换
  • Telegram bot + 邮件推送 + 电话 fallback（v2，海外语音网关如 Twilio）
  • 响应 SLA：HIGH ≤ 5min，MED ≤ 30min，LOW ≤ 2h
  • 每次告警必走"响应 → 排障 → 修复 → 复盘"四步骤
  • 重大故障写 post-mortem 入 docs/agents/logs/incidents/

8.6 日志规范

8.6.1 格式

zap structured logger，JSON 输出：

{
  "ts": "2026-07-15T03:45:23.123+08:00",
  "level": "info",
  "service": "go-api",
  "trace_id": "abc123def456",
  "user_id": 1234,
  "action": "predict.bet",
  "bet_id": 5678,
  "amount": 1000,
  "duration_ms": 45,
  "msg": "bet placed successfully"
}

8.6.2 必带字段

  • ts、level、service、trace_id、msg
  • 业务字段按上下文（user_id、order_id、room_id、action 等）

8.6.3 级别

  • DEBUG：开发用，生产关闭
  • INFO：业务正常流转、资金动作、登录登出
  • WARN：可恢复异常、降级触发
  • ERROR：未捕获异常、业务失败
  • FATAL：进程级故障（罕用）

8.6.4 资金类强制 INFO+

所有资金动作、风控决策、后台敏感操作必须 INFO 落日志，且字段含完整业务 ID。

8.6.5 敏感字段脱敏

日志输出前过滤：手机号、邮箱、支付宝账号、身份证、密码、token。中间件统一处理。

8.7 链路追踪

8.7.1 OpenTelemetry

  • 入口（Gin / WS）注入 trace_id
  • 透传到 Redis / MySQL / Kafka / HTTP 出站
  • 资金类接口 100% 采样
  • 其他 1% 采样

8.7.2 关键 span

  • HTTP request
  • DB transaction
  • Redis pipeline
  • Kafka send / consume
  • 三方调用（支付 / 短信 / OSS）

8.9 CI / CD

8.9.1 GitLab CI Pipeline

stages: [lint, test, build, security-scan, deploy-dev, e2e, deploy-staging, deploy-prod]

lint:
  - golangci-lint run
  - sqlc verify
  - openapi-cli validate
  - shellcheck deploy/scripts/*.sh

test:
  - go test ./... -race -coverprofile=cover.out
  - 覆盖率 ≥ 80%（资金类 100%）

build:
  - 多阶段 Docker build
  - 镜像签名 cosign
  - 推送私有 Registry

security-scan:
  - trivy scan image
  - gosec
  - secrets scan（gitleaks）

deploy-dev: kubectl apply（自动）
e2e: Playwright + go-e2e（自动）
deploy-staging: 手动批准
deploy-prod: 手动批准 + 灰度

8.9.2 PR 门禁

每个 MR 必须：

  • [ ] PRD 需求 ID 关联
  • [ ] OpenAPI 契约同步更新
  • [ ] 单测覆盖率 ≥ 80%（资金类 100%）
  • [ ] 慢查询 review 通过
  • [ ] 代码 review 通过（含 owner 跨域审核）
  • [ ] Agent 日志 / Task brief 填写完整
  • [ ] CI 全绿

资金类、风控类 MR 强制 2 人 review。

8.10 应急工具箱

工具 用途
kubectl rollout undo 服务回滚
kubectl exec ... -- /app/admin-cli 运维 CLI（限超管 + 审计）
手动对账补单脚本 scripts/recon-fix.go 处理通道差异
派彩重跑脚本 scripts/predict-resettle.go 异常派彩重跑（幂等）
强制下播 API 后台 / CLI
全局开关 feature.* 应急降级
MySQL 单事务回滚 DBA 介入

所有应急工具调用必须 INSERT admin_audit_log 并实时推 Telegram + 邮件告警。
