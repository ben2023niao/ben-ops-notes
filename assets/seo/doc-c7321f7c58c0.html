  • 分类：安全事件（对外暴露的运维工具 + 凭据硬编码 + 被外部利用）
  • 用户要求：关闭该 S3 文件管理器容器，避免被黑客恶意利用

一、现象

群内持续收到 S3 上传/删除通知，其中包含明显异常的条目：

📤 /app/public/localprobe.txt（11B）        📤 x（0B，MD5 d41d8cd9…=空文件）
📤 ${AWS}x.txt（1B）                        📤 probe/p.txt（8B）
🗑 ace/ace-021122.ipa（454.14 MB）          🗑 x、${AWS}x.txt、probe/p.txt

二、核查结果

2.1 容器暴露面（高危三件套）

· 公网监听：0.0.0.0:8111（无任何访问控制）
· 容器环境变量内含 AWS 凭据：AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY（对该下载桶有读写删权限）
· 启动策略 --restart=always：杀掉进程也会自动拉起（本次已改为 no）

2.2 鉴权形同虚设

app.py 中所谓"密码"仅在前端 JS 里做了一次提示校验：

<script>if(localStorage.getItem('auth')!=='18game'){if(prompt('请输入访问密码')==='18game'){…}}</script>

服务端接口（/upload、/delete/<key>、/progress/…）没有任何鉴权——知道 URL 就能直接上传/删除对象。

2.3 授权安全测试者行为（全部来自同一外部 IP：103.107.199.30）

INFO: 103.107.199.30 - "POST /upload"                            200 OK      ← 上传 probe 文件
INFO: 103.107.199.30 - "GET /delete/%24%7BAWS%7Dx.txt"           200 OK      ← ${AWS} 模板注入探测
INFO: 103.107.199.30 - "GET /delete/probe/p.txt"                 200 OK
INFO: 103.107.199.30 - "GET /delete/x"                           200 OK
INFO: 103.107.199.30 - "GET /delete/../../../../../../../../etc/passwd"  500 ← 目录穿越尝试
INFO: 103.107.199.30 - "GET /delete/../../etc/passwd"            500
INFO: 103.107.199.30 - "GET /delete/no-such-xxxxxxxxxxxxxxxxxxxx" 500 ← 模糊测试
INFO: 103.107.199.30 - "GET /progress/1791557513_ace-021122.ipa" 200 OK

该 IP 同时是先前两起告警的来源（同一台外部机器）： 近 6 小时调用 /dns_check.php 85 次、/boce_check_api.php 多次 —— 即它是持续针对我们运维接口的授权安全测试源。

2.4 实际损失确认

用只读方式列出下载桶 18game-download-176528004422 的 ace/ 前缀：

ace/icon.png        0B        2026-01-30
ace/manifest.plist  1.3KB     2026-03-28
→ 454MB 的 ace/ace-021122.ipa 已不在桶里（对应删除通知），iOS 分发链路会因此失效

2.5 凭据硬编码（仓库侧）

devops/python/s3-manager-app-apk/ 下 9 个文件（3 套 deploy.sh / README.txt / s3信息/info.txt） 含明文 AWS 访问密钥、秘密密钥，以及控制台登录密码。

三、处置（已完成）

# 动作 结果
1 docker stop s3-manager-xcp-prod 已停止（Exited 0）
2 docker update --restart=no s3-manager-xcp-prod 重启主机后不会再自动拉起
3 校验无自启来源 root crontab / systemd / compose 均无引用
4 封禁授权安全测试源 iptables -I INPUT 1 -s 103.107.199.30 -j DROP，脚本 /usr/local/sbin/youdianse-block-attacker-20261009.sh + @reboot 持久化
5 复核其他主机 网关 / 后端 / 宝塔 / 测试 EC2 均无同类容器、无 8111 监听
6 仓库凭据脱敏 9 个文件中的访问密钥/秘密密钥/控制台密码替换为占位符（<…已脱敏_请用环境变量注入>）

四、验证

· docker ps -a → s3-manager-xcp-prod  Exited (0)   ；ss -ltn 无 8111
· 主机 iptables INPUT 首条为 103.107.199.30 DROP，且 @reboot 定时已写入
· 相关接口复核：/dns_check.php、/boce_check_api.php 仍为 disabled（上午两次停用保持生效）
· 仓库复检：rg "AKIA[0-9A-Z]{16}" devops → 无匹配（明文密钥已清零）

五、遗留事项（必须跟进）

  1. 轮换凭据（最高优先）：该下载桶对应的 IAM 用户（18game-devops，账号 176528004422） 的访问密钥与控制台密码必须轮换——原因：① 曾以环境变量形式放在公网可达容器里； ② 已明文提交进仓库（git 历史仍存在，脱敏只清理当前文件）； ③ 授权安全测试者做过 ${AWS} 环境变量注入探测。 轮换后同步更新使用方（若有自动化上传脚本依赖同一密钥，需要一并改）。
  2. 补回被删对象：ace/ace-021122.ipa（454MB）需业务方重新上传或从备份恢复。
  3. 若仍需 S3 管理能力：重做时要求 - 服务端鉴权（登录/Token），不要前端 JS 写死密码； - 仅内网或 IP 白名单访问（安全组 + 反向代理），不要直接暴露 8111； - 最小权限（按桶/前缀授予，禁止整账号密钥进容器环境变量，优先临时凭证/SSM）； - 操作审计（谁在何时删了什么，落日志）。
  4. 同类风险排查：s3-manager-18gane-prod、s3-manager-18gane-test 两套代码同源， 本次未发现部署实例；如后续要启用，请按第 3 条整改后再上。

六、回滚 / 恢复

# 如需临时恢复容器（不建议，除非已轮换密钥并加访问控制）
sudo docker update --restart=no s3-manager-xcp-prod   # 保持不自启
sudo docker start s3-manager-xcp-prod
# 解除 IP 封禁（若确认 103.107.199.30 为我方机器）
sudo iptables -D INPUT -s 103.107.199.30 -j DROP
sudo crontab -l | grep -v block-attacker-20261009 | sudo crontab -
