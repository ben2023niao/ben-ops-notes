一、分析目的与方法

目的：把「刷量攻击来源」和「真实用户」区分开，避免误封真实用户，同时不放过脚本。

数据源：
  · 网关日志（203.0.113.1，2026-09-26 已补 X-Forwarded-For，可看到真实客户端 IP、UA、路径）；
  · 后端业务日志（runtime/app-logs/api_request-2026-09-2x.log，含 ip / deviceId / userId / action / version）。

三条判据：
  1) 是否带设备号 deviceId：正常 App/H5 每个请求都带；脚本通常为空；
  2) 访问接口数量：真人会跨首页/详情/列表/充值等；脚本常固定打 1 个接口；
  3) 频率形态：真人随浏览波动；脚本 24 小时恒定。

辅助手段：对来源 IP 做反查（PTR）。
  · 含 hstgr.cloud / compute.amazonaws.com → 机房、云服务器；
  · 含 adsl / broad / dynamic / 省份+运营商 → 家宽或移动网络（真实用户）。

同段其它 IP：…:5274::1（525 次）、…:d5f7::1（358）、…:4376::1（78）、…:5158::1（49）

规模：09-24 302,114 次；09-25 371,421 次；09-26 00:00-10:35 160,702 次；合计约 83.4 万次

2.3 第三类｜CDN 边缘 IP（不是攻击来源）

52.46.x / 64.252.x / 3.172.x / 18.68.x / 143.x / 13.x 等是 CloudFront 边缘节点：
网关看到的「来源」其实是 CDN，真实用户 IP 在 X-Forwarded-For 中（本次新增该字段后才看清）。
因此：这些段绝不能封（封了等于封自己的用户），现有 CC 守卫也已配置跳过 CDN 段。

2.4 真实用户长什么样（举例）

· 203.0.113.1 → PTR …203.0.113.1.broad.zz.fj.dynamic.163data.com.cn（福建漳州电信宽带）
· 203.0.113.1   → PTR …adsl-pool.jlccptt.net.cn（吉林联通 ADSL 拨号池）
· 大量 2408:xxxx / 2409:xxxx 开头的 IPv6 = 国内手机流量用户
共同特征：带 deviceId、访问多个接口、频率随浏览起伏、UA 为手机浏览器或 App

三、区分真实用户 vs 刷量脚本（判定口径）

| 特征 | 真实用户 | 刷量脚本 |

| --- | --- | --- |

| IP 归属 | 家宽/移动网络（PTR 含 adsl / broad / dynamic） | 机房/云厂商（hstgr.cloud、compute.amazonaws.com） |

| deviceId | 有 | 空 |

| userId | 登录后有 | 空 |

| 访问接口 | 多个（首页/详情/列表/充值…） | 常固定 1 个 |

| 访问频率 | 随浏览波动 | 24 小时恒定（如 4.4 次/秒） |

| UA | 手机浏览器/App（HeyTap / Chrome / Safari…） | 非浏览器或固定值（Dart / python-requests…） |

封禁口径（防误伤）：

1. 只封「机房段 + 单接口 + 无 deviceId + 恒定高频」四项同时命中的来源；
2. 家宽/移动段（含 adsl/broad/dynamic）一律不按段封，仅做频率限制；
3. CDN 边缘段永不封。

四、当前防护与待确认

已生效：
  · Hostinger 段 2a02:4780：网关 444 + ip6tables 直连封禁（后端 0 命中）；
  · CC 守卫：每分钟按真实客户端 IP 统计 /api，单客户端 ≥4 次/秒（6 万行窗口）自动写入网关拦截清单；
  · 网关日志带 XFF；磁盘 75% 看门狗；日志每 6 小时归档 S3（本地 1-2 天）。

待业务确认后再处理：
  · 203.0.113.1（checkTokenV2，16.6k/天，无 deviceId）
  · 203.0.113.1（LoginNew/account + UserProduct/getProductList，65k/天，带 deviceId）
  · 上述一批 AWS 小量 IP（合计约 1.2 万次/天，无 deviceId）
