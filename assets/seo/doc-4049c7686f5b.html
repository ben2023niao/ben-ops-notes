本文记录跨团队问题「现在国内的那几个域名，挂的客户端资源是哪里的」的只读核验过程与结论。核验对象为用户列出的 pg-static.hkcloudplay01-05.com 与 pg-games.hkcloudplay01-05.com，并顺带核对了同架构下其余厂商静态/动态域名的解析归属。

本轮为只读核验：未改 DNS、未改 CloudFront、未改 S3、未改 Nginx、未同步任何资源，不产生生产写操作。

一、结论（一句话）

国内面向的 pg-static.hkcloudplay01-05.com 与 pg-games.hkcloudplay01-05.com 不在国内节点、
也不在巴西 GCS，全部托管在香港 AWS（ap-east-1）：
  静态：Cloudflare DNS-only CNAME -> CloudFront（d1wnhpyrlnptrk.cloudfront.net）
        -> 香港私有 S3 bizops-h5-hk-517506432530 的 pg-static 前缀
  动态：Cloudflare DNS-only CNAME -> CloudFront（d1n4qfcp941cy6.cloudfront.net）
        -> 香港入口 Nginx 192.0.2.14 -> 外部双后端 192.0.2.18 / 192.0.2.19

补充口径（容易被误问成两个答案的地方）：

1. 客户端实际拉的静态地址自 2026-08-28 起由 platform-api 下发的 static_hosts 决定，
   当前仓库配置为 S3 公开地址 https://bizops-h5-hk-517506432530.s3.ap-east-1.amazonaws.com/pg-static；
   pg-static.hkcloudplay0X.com 为同桶同对象的兜底域名（保留可用）。
   两条口径最终都落在同一个香港 S3 桶，只是入口不同。
2. 香港 S3 的 pg-static 内容不是本地独有源，来源是 client 代码仓库 -> 巴西 GCS -> 同步到香港 S3；
   pg6/pg7 例外，直接以 client 仓库 pg6static/pg7static 为源。
3. cn 没有 Cloudflare Worker（记录全是「仅 DNS」，不过 CF 代理）；静态也不经过服务器
   Nginx，nginx-bizops.conf 的静态规则只是历史兜底，且已失效（详见第十节）。

十、追加核验：cn 没有 Worker，静态也没走服务器 Nginx 的静态规则

追加提问（2026-09-24）：「cn 是没有 worker 的，静态用上服务器里面的 nginx 的静态规则了吗？」结论如下。

10.1 结论

1. cn 没有 Cloudflare Worker —— 正确。
   hkcloudplay0[1-5].com 的所有记录都是「仅 DNS」（灰云，不过 Cloudflare 代理），
   Worker 只能挂在被代理的流量上；master/巴西那套 Worker Cache 在 cn 不生效、也不使用。
   cn 静态链路上唯一的边缘计算是 CloudFront Function（pp-static 的 customizations.info），
   与 Cloudflare Worker 无关。
2. 静态没有走服务器 Nginx 的静态规则 —— 当前玩家链路完全不经过 192.0.2.14。
   主链路：platform-api 下发 static_hosts = S3 公开地址直出；
   兜底链路：<前缀>.hkcloudplay0[1-5].com -> CloudFront -> 香港私有 S3。
   实测静态响应头为 server: AmazonS3 + x-amz-version-id，没有任何 nginx 参与。
3. nginx-bizops.conf 里的静态规则仍在，但属于历史兜底，且已经与现状脱节
   （见 10.3）。只有在把静态域名解析切回入口机时才会被用到。

10.2 实测证据

探测 结果 含义
dig 静态/动态域名（5 zone × 22 记录） 全部直接返回 CloudFront A 记录，无 Cloudflare 代理 IP 记录为灰云，Worker 不可能生效
GET https://pg-static.hkcloudplay01.com/85/c445ebb91e.cadb1.json 200，server: AmazonS3，x-amz-version-id: STmRJLx… 静态走 CloudFront → S3，不经 nginx
GET https://pp-static.hkcloudplay01.com/customizations.info 200，0 字节，server: CloudFront，x-cache: FunctionGeneratedResponse from cloudfront PP 特殊文件由 CloudFront Function 生成，不依赖 nginx 规则
curl --resolve pg-static.hkcloudplay01.com:443:192.0.2.14 /85/… 404，server: nginx/1.18.0 (Ubuntu)，body 为 GCS NoSuchBucket 强制打入口机会命中 nginx 静态兜底，但兜底已失效
同上强制打入口机 pg6-static / g759-static 404，content-type: text/plain + 动态 CORS 头（x-token 等） 这两个前缀没有对应 server 块，落进了 platform-api 默认站
curl --resolve pp-static.hkcloudplay01.com:443:192.0.2.14 /customizations.info 200，0 字节，server: nginx/1.18.0 nginx 侧同名规则确实存在，但只在强制打入口机时才会走到

10.3 Nginx 静态兜底的现状与风险

docker/deploy/hongkong/nginx-bizops.conf 的静态兜底把请求改写成 storage.googleapis.com/<GCS 桶><uri>，map $host $bizops_gcs_bucket 只覆盖 11 个前缀：

pg-static / pg3-static / pg4-static / pg5-static / vendor_b-static / vendor_b-static1 /
vendor_b-static2 / pp-static / ppk-static / vendor_d-static / vendor_c-static

两处已经不一致：

1. 兜底目标桶名过期：map 用的是旧桶 bizops-gcs-<前缀>，公网探测返回
   NoSuchBucket（bucket 不存在）；现役桶名是 newgg2-bizops-gcs-<前缀>
   （2026-09-24 实测根路径 200 可列目录）。即 nginx 静态兜底现在取不到内容。
2. 覆盖范围过期：pg6-static / pg7-static / g759-static 既不在 map 里，
   也没有对应 server_name；这两组内容本来就不在 GCS（git 直供），
   若静态域名回切入口机，会落进 platform-api 默认站而不是静态资源。

影响面：当前静态链路纯走 S3/CloudFront，风险不暴露；但如果因为故障要把静态域名 临时切回入口机（历史上 2026-07-16 的架构就是这样），兜底会直接 404。

10.4 建议待办

1. 择机把 nginx 静态兜底目标改为香港 S3（或现役 newgg2-bizops-gcs-* 桶），
   并补 pg6-static / pg7-static / g759-static 的 map 与 server_name；
   改前必须先确认是否还要保留「兜底回 GCS」这条历史语义。
2. 若保留 GCS 语义，需要明确 pg6/pg7/g759 三组走 S3（不回落 GCS），
   避免回切时这三组静默失败。
3. 在 DNS 回滚剧本里显式写明：静态域名切回入口机前，必须验证兜底可用。
