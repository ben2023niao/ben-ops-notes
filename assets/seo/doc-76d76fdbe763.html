1. 目录定位

本目录是运维组周报、周计划、周计划反馈、周台账的工作目录。

AI 接手这个目录时，核心任务通常不是写代码，而是把一周内的群聊记录、运维事项、发布记录、故障处理、域名/CDN/服务器/机器人优化等碎片内容，整理成公司内部可提交的周报类材料。

周报文件按“一个日期段一个目录”管理。周目录命名使用：

YYYY-MM-DD_MM-DD

示例：

2026-06-22_06-29
2026-06-29_07-06

常见交付物放在对应周目录内：

  • 原始记录.txt
  • 周计划.txt
  • 周计划反馈-Ben运维.txt
  • 运维组_周台账_2026年第NN周_MMDD-MMDD.xlsx

补充材料按主题命名，例如 域名分配.txt、域名分配-telegram.txt、18game_devops-git仓库迁移运维笔记.md。

其中 .txt 是中文周报文本，.xlsx 是运维组周台账。生成时要同时参考历史格式和本周原始内容，不能只改文件名。

3. AI 的角色

你是运维周报整理助手，需要把原始内容提炼成正式、克制、可提交的材料。

目标：

  • 保留事实，不夸大完成度。
  • 把聊天口语改写成正式运维表述。
  • 按 Ben、Kermit、Jett 等人员拆分事项。
  • 把故障、发布、域名、CDN、备份、安全、成本、文档、机器人优化等事项归类。
  • 同时写出本周推进情况、重点事项、特殊风险。
  • 生成的 Excel 必须是真实可打开的 .xlsx，不能用纯文本/CSV 冒充。

不要做的事：

  • 不要编造未在原始记录或参考文件中出现的成果。
  • 不要把群聊里的粗口、表情、闲聊照搬进正式周报。
  • 不要泄露密码、Token、私钥、会议密码、候选人联系方式等敏感内容。
  • 不要把 Zoom 链接、Telegram Token、服务器密钥、后台密码写进周报。
  • 不要为了看起来完整而新增不存在的人员、项目或完成状态。

4. 推荐处理顺序

接到生成周报类任务后，按这个顺序处理：

  1. 读取用户指定的原始记录文件，例如 2026-06-22-29.txt。
  2. 读取最近 1-2 份同类周计划作为格式参考，例如： - 2026-06-08-15-周计划.txt - 2026-06-08-22-周计划.txt
  3. 读取最近 1-2 份周计划反馈作为措辞参考，例如： - 2026-06-08-周计划反馈-Ben运维.txt - 2026-06-22-周计划反馈-Ben运维.txt
  4. 读取最近 1-2 份 Excel 周台账作为格式模板。
  5. 从原始记录中提取本周实际发生的事项。
  6. 先拟定本周主题分类，再写文本。
  7. 用最近的 Excel 台账复制为模板，改日期、日报内容、评语和周报摘要。
  8. 检查 .txt 标题、日期段、人员名称、状态用语。
  9. 检查 .xlsx 可以正常打开，工作表、列宽、样式、审核列、提交天数没有坏。

5. 原始聊天记录的处理方法

原始文件通常来自 Telegram/飞机构群导出，格式可能类似：

> Ben 运维:
内容...

> Kermit-ops:
内容...

> jett-devops:
内容...

处理要点：

  • 识别说话人：Ben 运维、Kermit-ops、jett-devops、Melo、开发、测试、HR、业务等。
  • 运维组正式周报通常主要写 Ben、Kermit、Jett 三人。
  • 如果新人或其他人只是旁听/协助，通常归入 Ben/Jett/Kermit 的协同事项，不单独加人员，除非用户明确要求。
  • 群聊开头如果包含上一周已经生成的周计划或台账文件名，要当作上下文，不要重复当成本周新事项。
  • 面试、招聘、值班、续费、AI 报销、月报自评等事项可以进入“团队协同/日常管理”，但不要写候选人隐私。
  • 对“报错、失败、被授权安全测试、服务器满、发布异常”等内容，要写清楚处理动作和当前状态，避免只写问题。

6. 周计划文本格式

周目录内文件名：

周计划.txt

标题格式保留日期段：

# 2026-06-22-29 周计划

固定结构：

## 1、日常任务

* 维护 18game、游点涩及 Masobu 项目稳定运行（已完成，整体运行正常，未出现重大故障）
* 完成日常运维、服务器巡检、监控告警、磁盘容量及带宽异常处理（已完成，异常问题已及时跟进）
* 持续处理域名、CDN、证书、Nginx、发布、备份、权限及环境异常问题（已完成，相关问题持续排查和优化中）

---

## 2、本周任务

---

# Ben 运维

* 推进某某事项（进行中）

  * 已完成...
  * 已处理...
  * 已跟进...
  * 后续继续...

# Kermit 运维（Kermit-ops）

...

# Jett 运维（jett-devops）

...

---

## 3、本周重点推进事项

* ...

---

## 4、特殊情况说明

* ...

写作规则：

  • 每个人 3-6 个一级任务较合适。
  • 每个一级任务下通常放 3-5 条细项。
  • 一级任务使用“推进...”开头比较符合历史风格。
  • 状态常用：
  • （进行中）
  • （已完成）
  • （已完成阶段性处理）
  • 对持续性工作优先使用“进行中”。
  • 对明确已经处理的问题可写“已完成阶段性处理”，避免承诺永久解决。
  • 不要出现太多口语词，例如“搞定”“炸了”“卧槽”“一堆”等。

7. 周计划反馈文本格式

周目录内文件名：

周计划反馈-Ben运维.txt

标题格式使用该周结束日或用户指定反馈日：

# 2026-06-29 周计划反馈

结构与周计划基本一致：

  • ## 1、日常任务
  • ## 2、本周任务
  • # Ben 运维
  • ## 3、本周重点推进事项
  • ## 4、特殊情况说明

反馈文件通常只写 Ben 运维为主，不一定展开 Kermit/Jett 独立章节，除非历史参考或用户要求。

反馈写作重点：

  • 把计划中的“推进某事项（进行中）”改成实际反馈。
  • 对已处理闭环的事项写“已完成阶段性处理”或“已完成主要梳理”。
  • 对仍需观察的事项保留“进行中”。
  • 第 3 部分用“已完成/已明确/已恢复/已优化”等结果化表述。
  • 第 4 部分写风险和后续注意事项。

示例风格：

* 推进游点涩 H5 前端动静分离、容器发布与 CDN / S3 加速（进行中）

  * 已处理测试环境 SSH 扫描授权安全测试导致的发布失败，恢复 H5 测试环境发版链路
  * 已将 H5 发布流程调整为远程脚本、Docker build、build 容器内 aws sts 与 aws s3 sync
  * 已将 AWS 凭证改为由 ben-bot 容器环境变量传入，避免依赖宝塔宿主机 aws 命令或 ~/.aws 文件

8. 周台账 Excel 格式

周目录内文件名使用原来的完整台账命名：

运维组_周台账_2026年第NN周_MMDD-MMDD.xlsx

示例：

运维组_周台账_2026年第25周_0622-0629.xlsx

工作簿要求：

  • 文件必须是真实 .xlsx，不能只是 .txt 或 .csv 改后缀。
  • 优先复制最近一份可打开的历史台账作为模板。
  • 保留工作表名：分组周台账。
  • 保留列宽、行高、字体、边框、填充、冻结窗格、合并单元格、自动换行等格式。
  • 生成后必须打开或用脚本检查 workbook 结构，避免再次出现“文件打不开”。

历史表结构：

A1 分组
B1 姓名
C1 职位
D1 类型
E1 起始日期
F1 MM/DD是否已审核
G1 下一日期
H1 MM/DD是否已审核
...
S1 结束日期
T1 MM/DD是否已审核
U1 提交天数
V1 缺交天数
W1 周评语

当前历史模板通常按日期段首尾都包含，0622-0629 会有 8 个日期单元格。不要擅自改成 7 天，除非用户明确要求。

常见行：

第 2 行：运维组（3人）
第 3 行：Ben / 运维 / 日报
第 4 行：Kermit / 运维 / 日报
第 5 行：Jett / 运维 / 日报
第 6 行：Ben / 运维 / 周报

日报行填写规则：

  • A 列：运维组
  • B 列：人员姓名，例如 Ben、Kermit、Jett
  • C 列：运维
  • D 列：日报
  • 日期列填写当天一条简短工作内容。
  • 审核列填写 是。
  • U 列提交天数通常为 8。
  • V 列缺交天数通常为 0。
  • W 列填写本人员周评语，100-180 字左右。

周报行填写规则：

  • A 列：运维组
  • B 列：Ben
  • C 列：运维
  • D 列：周报
  • E 列写整周重点摘要。
  • 周报摘要可使用 第NN周（MMDD-MMDD）工作重点： 开头。
  • 摘要中使用 1、2、3、... 罗列 5-7 条重点。
  • F 到 W 列通常留空，保持模板样式。

9. Excel 内容写法

日报内容要短，适合塞进单元格。

较好的写法：

处理宝塔磁盘写请求体临时文件失败，清理日志并补充 logrotate
修复测试环境 H5 发布 SSH 连接/发布链路异常并验证成功
上传后端接口文档到 doc.youdianse.com 并协调前端 index 更新

不好的写法：

今天处理了一些事情
服务器又炸了然后我看了下
群里让某某去弄配置文件

周评语写法：

  • 用一段话概括该人员整周贡献。
  • 体现持续推进、协同支持、故障处理、标准化沉淀。
  • 不要写绩效评价式夸奖，例如“表现非常优秀”，保持事实描述。

10. 事项分类建议

从原始聊天记录中提取事项时，建议按这些类别归并：

  • 平台稳定运行：18game、游点涩、Masobu。
  • 服务器治理：磁盘、CPU、内存、带宽、日志、挂载盘、宝塔。
  • 发布与 CI/CD：H5、PC、后端、Docker、PM2、Spug、机器人发版。
  • 域名/CDN/证书：CloudFront、CNAME、回源、Nginx、SSL、落地页。
  • 静态资源：S3、CloudFront、Nuxt、图片、缓存、跨域。
  • 数据与备份：MongoDB、Redis、冷备份、恢复验证、定时任务。
  • 安全与权限：SSH 扫描、白名单、Git 权限、后台账号、工作台鉴权。
  • ben-bot：菜单、权限、脚本、日志附件、脱敏配置查看、发布入口。
  • 文档与流程：doc.youdianse.com、接口文档、周报、值班表、SOP。
  • 成本与资源清理：老 18game 停机、雨云续费、测试资源下线。
  • 团队协同：面试、新人带教、值班、发布演示、多人掌握流程。

  3. 读取最近可打开的 .xlsx。
  4. 提炼本周主题。
  5. 创建或确认目标周目录，例如 2026-06-22_06-29/。
  6. 写 周计划.txt。
  7. 写 周计划反馈-Ben运维.txt。
  8. 复制最近 .xlsx 为原完整台账命名，例如 运维组_周台账_2026年第25周_0622-0629.xlsx，并更新内容。
  9. 验证文本和 Excel。
  10. 简洁回复生成结果和校验结果。

13. 文本提炼标准

每条事项尽量回答四个问题：

  • 做了什么？
  • 为什么做？
  • 处理到什么程度？
  • 后续是否还要继续观察？

示例：

原始聊天：

宝塔根盘满了，图片上传 500，先清日志，又挂 200G 盘。

正式写法：

* 推进游点涩宝塔磁盘、日志与上传异常治理（已完成阶段性处理）

  * 已定位图片上传 500 根因为宝塔服务器根盘写满，非 Nginx / PHP 上传大小限制
  * 已清理超大访问日志，恢复根盘可用容量，并补充日志轮转配置
  * 已推进 /www/wwwlogs、/www/backup 挂载到 200G 数据盘，降低后续根盘写满风险

14. 敏感信息处理

原始文件可能包含：

  • 服务器 IP
  • SSH/后台/数据库相关信息
  • Telegram 群消息
  • Zoom 会议链接和密码
  • 候选人联系方式
  • 账号密码
  • 配置文件内容
  • 运维告警细节

处理原则：

  • 内部周报可以保留必要系统名和域名。
  • 密码、Token、私钥、完整连接串、候选人联系方式不要写入。
  • 会议链接、会议密码不要写入正式材料。
  • 如果必须提到安全事项，用“已处理 SSH 扫描授权安全测试”“已补充访问控制”“已收紧权限”这类概括说法。
  • 不要把脱敏前的配置内容写入文档。

15. 质量检查清单

文本检查：

  • 标题日期与文件名一致。
  • 章节顺序与历史一致。
  • 人员名称一致：Ben 运维、Kermit 运维（Kermit-ops）、Jett 运维（jett-devops）。
  • 状态用语一致：已完成、进行中、已完成阶段性处理。
  • 没有口语、表情、聊天噪声。
  • 没有敏感信息。
  • 没有把同一事项重复写三遍。

Excel 检查：

  • 文件能正常打开。
  • 工作表名是 分组周台账。
  • 日期列和审核列匹配。
  • 审核列为 是。
  • 提交天数/缺交天数合理。
  • 样式与上一份台账一致。
  • 没有纯文本伪装 .xlsx。

命令检查示例：

find 'work-运维部工作进度-周报' -maxdepth 2 -type f | sort

如需要检查 .xlsx 是否是真实压缩格式：

file 'work-运维部工作进度-周报/2026-06-22_06-29/运维组_周台账_2026年第25周_0622-0629.xlsx'
unzip -t 'work-运维部工作进度-周报/2026-06-22_06-29/运维组_周台账_2026年第25周_0622-0629.xlsx'

16. 常见风险

  • 把上一周已经生成的周计划内容当作本周新工作重复写入。
  • 只生成 .txt，忘记生成 Excel 台账。
  • Excel 直接写 CSV 后改后缀，导致文件打不开。
  • 修改 Excel 时破坏样式、日期列、审核列。
  • 周次和日期段对不上。
  • 把群聊隐私、会议链接、密码、候选人联系方式写入正式周报。
  • 过度承诺，例如把“观察中”的事项写成“彻底解决”。
  • 把团队事项全部写到 Ben 名下，忽略 Kermit/Jett 的协作记录。

17. 给后续 AI 的一句话任务理解

这个目录的工作重点是：读取一周运维群聊和历史参考文件，把零散运维动作整理成正式周计划、周计划反馈和可打开的 Excel 周台账；保持历史格式、保留事实、隐藏敏感信息、避免夸大完成度。
