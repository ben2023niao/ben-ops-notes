  • 时间：2026-10-17 02:20 ~ 02:35（北京时间）
  • 现象：开发已把只读查询改成随机走 01/02 两个从库，但实测流量仍 100% 落在从库01（203.0.113.1），从库02（203.0.113.1）连接数 0、query 2.9/s，基本闲置
  • 结论：不是代码没改，而是配置层面两个从库槽位指向了同一台机器，驱动永远只连一台

一、根因（三层叠加）

1. .env 里两个从库槽位是同一个主机名

[database.mongodb.slave1] host = server.db2.com
[database.mongodb.slave2] host = server.db2.com     ← 与 slave1 完全相同
[database.mongodb.default] host = server.db1.com

2. 容器 /etc/hosts 把同一个域名指向两个 IP

203.0.113.1   server.db2.com      ← 先出现，glibc 优先返回
203.0.113.1  server.db2.com
203.0.113.1  server.db1.com

3. 连接串没有 replicaSet 参数，驱动按"单机直连"处理

app/Core/Mongodb/MongoDbConnection.php:37-47 拼出来的 URI 形如：

mongodb://<user>:<pass>@server.db2.com:27017        ← 没有 ?replicaSet=...

.env 里 replica 这一行是被注释掉的（#replica = ...），因此驱动不会做副本集发现，只会用解析到的第一个地址 —— 永远是 203.0.113.1。

实测证据

web 容器到各 Mongo 节点的 TCP 连接数：
  203.0.113.1:27017   23 条
  203.0.113.1:27017  23 条（主库，写路径）
  203.0.113.1:27017   0 条   ← 从库02 从来没有被连上

驱动视角（12 次从库选择）：
  当前配置      → server.db2.com:27017 ×12（即始终 44.11）
  加 replicaSet → 44.11 ×8 | 39.177 ×4
  两个地址都写 + replicaSet → 44.11 ×6 | 39.177 ×6

二、修复方案（两选一，推荐 B）

方案 A（最小改动，不动代码）

把两个从库槽位写成不同地址，让代码里的"随机 01/02"真正落到两台机器：

[database.mongodb.slave1]
host = 203.0.113.1      ; 或给 01 配独立域名，如 server.db2a.com
port = 27017
dbname = 18game

[database.mongodb.slave2]
host = 203.0.113.1     ; 或给 02 配独立域名，如 server.db2b.com
port = 27017
dbname = 18game
  • 优点：零代码改动，立即生效
  • 代价：单机直连模式没有自动故障转移；某台从库挂掉时，走该连接串的查询会直接报错

方案 B（推荐：副本集发现 + 从库负载均衡）

  1. .env 恢复副本集配置（代码已支持该字段，见 MongoDbConnection.php:44-46）：
[database.mongodb.default]
replica = youdianse        ; 副本集名称实测为 youdianse

[database.mongodb.slave1]
replica = youdianse

[database.mongodb.slave2]
replica = youdianse
  1. 连接串再补 readPreference=secondaryPreferred（当前代码未拼这个参数，需要在 MongoDbConnection::getClient() 里按连接名追加）：
mongodb://server.db2.com:27017/?replicaSet=youdianse&readPreference=secondaryPreferred

⚠️ 关键提醒：只加 replicaSet 而不加 readPreference，驱动默认读偏好仍是 primary，读请求会被导到主库 —— 实测"只加 replicaSet"时 8/12 次选中从库、但经 executeCommand 仍走主库。所以两个参数要一起加。

  1. 副本集成员与角色（实测，供配置参考）：
副本集名称：youdianse
  203.0.113.1:27017   PRIMARY
  203.0.113.1:27017   SECONDARY
  203.0.113.1:27017    SECONDARY   （同时跑着 Redis）

三、顺手回答群里的两个问题

1）"从日志大小看，用户流量当时是不是有突增？"

不是。实测近 1 小时逐分钟：

指标 数值 判断
网关出（=用户流量） 15.8 ~ 19.0 MB/s，长时间平稳 没有突增
后端入（=从 Mongo 拉数据） 61 ~ 72 MB/s 是网关出流量的 3~4 倍
从库01 出 59 ~ 80 MB/s 全部是这条内部读链
主库出 1.6 ~ 3.0 MB/s 读已搬走，但扫描仍在（放大 1,047 倍）

日志体积大 ≠ 流量突增：api_request + api_response 每天写 9 GB，是全量请求/响应落盘造成的（见指南 B6）。

2）"游戏那边有外挂"

从 API 层看不出单账号刷量特征：今日 api_request 采样窗口内，最高频账号只有 116 次、TOP10 账号都在 50~120 次区间，没有单账号霸榜。游戏外挂发生在游戏服（不在本系统日志里），建议由游戏侧提供异常账号/设备清单，我们再和网关/接口侧数据做交叉比对。

四、下一步建议

  1. 【立即可做】按方案 A 或 B 修从库配置，让 02 真正承接读流量（当前 02 完全空闲，白放着）
  2. 【波特提到】"01 是 redis + 数据库，是谁的量不好分，最好独立出来" —— 建议纳入中期计划：把 Redis 从 01 拆出，或把主要读库挪到 02
  3. 剩余大头仍是读放大（主库 1,047 倍）：按指南 B1/B2/B3 做配置类缓存与投影，否则均分只是把同样压力摊到两台
