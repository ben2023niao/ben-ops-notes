一、现象与线索

开发（C++）反馈：「jili 这个游戏还是报错」，给了两条线索：
  1) 游戏页：https://jili-static1.k8x2v9.shop/lj500/index.html?...&gameID=664&name=lj500&lang=cn...
  2) 一条 curl：GET https://jili-games.m4q7z1.shop/lj500/ 带 key/token/lang/name/referer/origin
     （origin/referer = https://jili-static1.k8x2v9.shop，sec-fetch-site: cross-site）
token 里的 iat=1791176375 / exp=1791176985 → 会话时间 2026-10-05 12:59:35 ~ 13:09:45（北京）。

二、定位过程（先排除误判）

1) 页面与映射本身没问题：
     jili-static1.k8x2v9.shop/lj500/index.html = 200 / 97,383B（JILI 自己的大阪桶）
     /lj500/ = 302 -> /lj500/index.html；主 JS /commom_v3_1.0.9.js = 200 / 45,119B（MIME 正确）
     jili-games.<域>/health = 200
2) POST /lj500/req 用空 body 测出的 500「Invalid IP.」是**我自己的测试假象**：
     · 直接打后端（源码 203.0.113.1 → 私网）时 share.utils.get_real_ip 返回 None → 抛 Invalid IP
     · 用 tcpdump 抓真实链路：后端收到的是 X-Real-IP: 43.168.x（EdgeOne 公网）、
       X-Forwarded-For: 112.207.x, 43.168.x，都是公网；用同组合打 platform-api
       /what-is-my-ip 能正确回显公网 IP → 链路 IP 传递没问题
     · 再用空 body 打 /lj500/req 时后端报的是 protobuf 解码失败（serverProto.Request），
       即空 body 本来就该失败 —— 不是游戏的问题
     · 容器 mmdb、share.so（md5 e5589555…）、start.sh 与巴西源端一致，均无差异
3) 真正在报错的是**静态资源 403**。按开发会话窗口（04:55–05:12 UTC）过滤 standby nginx：
     41 × 403  /astarte/3.6/web-mobile/assets/jili/native/**（4 个文件反复重试）
      5 × 403  /csh/htt/smallicon/setting.json
      4 × 403  /lj500/favicon0.ico
      7 × 404  /lj500/src/{polyfills,system}.bundle.*.js、/lj500/TaDa_Logo_APNG_s.png、
               /lj500/JILI_NEW.png、/lj500/Intro_ProgressBar*(_Bottom)_JILI.png
     16 × 405  /cdn-cgi/rum（Cloudflare RUM 探针，无害）
      3 × 500  /lj2/req
4) 这些资源去哪儿了？实测各个源：
     · JILI 大阪桶 dbqp-s3-jili-static1：只有 lj500/index.html 和 astarte/…/jili/index.8c409.js 等，
       **没有** /lj500/src/*.js、logos、intro 图片 → 403
     · 老 HK 主桶 dbqp-h5-hk-517506432530 的 tada-statics1 / tada-statics2 前缀：
       `tada-statics1/lj500/src/polyfills.bundle.5adbf.js` = 200 / 14,750B
       `tada-statics1/lj500/src/system.bundle.692e9.js` = 200 / 12,028B
       `tada-statics1/lj500/Intro_ProgressBar_JILI.png` = 200 / 1,003B
       `tada-statics2/lj500/TaDa_Logo_APNG_s.png` = 200 / 41,805B
       `tada-statics2/lj500/JILI_NEW.png` = 200 / 242,584B
     → 即：**游戏页从 JILI 新桶加载，但同目录的其余资源还留在老的 TADA 前缀里**
       （老映射本来就是 jili-static -> tada-statics、jili-static1 -> tada-statics1）。

三、修复（standby nginx，JILI 静态域名）

思路：JILI 自己的桶优先（内容正确），**缺的对象再回退老 TADA 前缀**（补资源缺口），
      不改变「JILI 优先」的口径，也不影响其它厂家。

改动 1：nginx-standby.conf 新增 map（按 server_name 捕获的前缀选老前缀）
  map $dbqp_static_prefix $dbqp_jili_tada_prefix {
      default          "___noprefix___";   # 其它前缀兜底链最终 403（等于查不到）
      jili-static      tada-statics;
      jili-static1     tada-statics1;
  }

改动 2：snippets/dbqp-hk-standby-jili-static.conf
  · location /、/static/images/intro/、= /astarte/.../versions.json 都加
        proxy_intercept_errors on; error_page 403 404 = @jili_tada_fallback;
  · 自己再定义一个 location ~* \.js$（放在通用 static-extra 片段之后，正则先匹配先赢）：
    与通用片段同口径（OPTIONS 204 / 强制 application/javascript; charset=utf-8 / CORS *），
    但回源失败时也走 @jili_tada_fallback —— 否则 /lj500/src/*.bundle.js 会被通用 .js 规则抢先处理，回退不生效
  · 新增 @jili_tada_fallback：rewrite 成 /<tada 前缀><原 URI>，回源 HK 主桶（ap-east-1）

备份：/etc/nginx/sites-available/dbqp-hk-standby.conf.bak-20261005-1311-jilitada +
      /etc/nginx/snippets/dbqp-hk-standby-jili-static.conf.bak-20261005-1311；nginx -t 通过后 reload。

五、仍然缺的资源（需要开发补，nginx 无法兜）

这几个路径在**所有源**里都不存在（JILI 大阪桶 / HK 主桶 tada-statics1-5 / GCS 全试过）：
  /astarte/3.6/web-mobile/assets/jili/native/1a/1a23e78f3.d3fbc.webp      ← 41 次 403
  /astarte/3.6/web-mobile/assets/jili/native/1c/1c8b28224.eabe3.webp
  /astarte/3.6/web-mobile/assets/jili/native/29/299d2d3a-…-70d88dda59fd.23b03.png
  /astarte/3.6/web-mobile/assets/jili/native/fd/fd30e95d-…-fc4fdd3051b8.bb552.webp
  /csh/htt/smallicon/setting.json                                        ← 5 次 403
  /lj500/favicon0.ico                                                    ← 4 次 403（TADA 前缀也没有，影响小）
两个注意点：
  · 06/07 的静态域名走 Cloudflare Worker（不经过本机 nginx），本轮的 nginx 兜底对它们无效，
    要么让开发把这些资源也传到 JILI 大阪桶，要么改 Worker；
  · 若同一路径 JILI 桶与 TADA 前缀都存在，**永远是 JILI 桶优先**（本轮设计如此）。
