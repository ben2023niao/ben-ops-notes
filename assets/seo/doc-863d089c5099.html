一、结论

某业务平台原先只有 2026-05 的历史全量数据。本次以原始全量备份为基线，从 sample-node-22-new 的 relay/binlog 提取 2026-05-10 至 2026-11-07 的完整行级变更，并将 21 张用户相关表恢复到 2026-11-07 00:04:53，截止点 固定为 2026-11-07 00:05:00。

恢复结果位于隔离库 bizdb_pitr0005_test_20261108，没有覆盖生产 主节点。首批 8 张核心用户表增加的数据量与 binlog 中的 INSERT 数一致；补充回放覆盖 13 张关联表，其中 daily_user_accounts 和 user_ext2 有新数据。21 张表 CHECK TABLE 全部返回 OK，已恢复表的主键无重复，核心时间字段在截止点 之后的记录数为 0。

某地区 PG 下注转圈问题另有独立根因。实测确认某地区 PG65 结果集与巴西同名文件 一致，目录权限正确，结果数据库可写且 quick_check=ok；但重启后的 PG 容器 无法建立到 MySQL 192.0.2.48:3306 的新连接。香港侧已按现场要求暂停 全部操作，等待数据库与基础设施方处理，不再继续启停容器。

二、历史问题核对

仓库中与本次现象相关的历史记录有三份：

  • 2026-08-26-1345-【故障处理】巴西G759旋转报错结果库权限修复记录.md 记录的典型报错是结果集目录属主错误，SQLite 出现只读连接失败，最终表现为 “没有可用结果”。
  • 2026-09-04-0200-【问题排查】真实用户游戏开始转圈日志分析记录.md 记录的结果是钱包结算、游戏开放名单及存储过程参数问题，不能只凭“转圈” 判断为 CORS。
  • 2026-09-09-1633-【发布+问题修复】V20260909三后端发布与结果集权限修复记录.md 要求结果集目录和文件统一由 uid=1000 运行账号可写。

本次某地区 PG65 已排除上述结果集文件和权限问题。下注请求由后端选出结果并写入 余额变化，随后在投注流水记录阶段阻塞约 15 秒；Nginx 记录为 499，浏览器 因此显示 CORS 和持续转圈。重启后又确认新 MySQL 连接被 192.0.2.48:3306 超时阻断。

三、某业务平台 恢复方法

1. 基线

基线包：

/root/vendor_a-zips/bizdb-full-users_db-20261107.sql.gz
SHA256 43bc7feeae62942f117fa9c8538516d5c3ae66e21c23bac95f70b2008f85d682

该包使用 MySQL 5.7 导出，包含原始 InnoDB 表结构与 2026-05 数据。本次未复用 此前被旧版 BINLOG 客户端并发修改过的临时库。

2. 增量

源端 relay 文件范围为 000003 至 000602，使用 my2sql 解码为带表名和主键 条件的标准 DML，截止时间为 2026-11-07 00:05:00。

核心用户表使用 205 个 SQL 文件、2,119,170 条语句：

UPDATE：2,113,253
INSERT：5,917
DELETE：0
DDL/DROP DATABASE：0
最后业务事件：2026-11-07 00:04:53

补充关联表使用 204 个 SQL 文件、638,793 条语句：

UPDATE：637,390
INSERT：1,403
DELETE：0
DDL/DROP DATABASE：0
输入分片条件异常：0

核心与补充任务各生成 8 个压缩包，共 16 个；源端与恢复机的 SHA256 逐包一致， gzip 校验全部通过。

3. 隔离回放

回放前从原始全量包重建目标库，并关闭时间戳字段的隐式自动更新；回放完成后 恢复表结构。由于 user_account.last_update_time 等字段带有 ON UPDATE CURRENT_TIMESTAMP，禁止隐式更新可避免回放时间被写成执行当天。

核心任务 2,119,170 条 DML 耗时约 123 秒。补充任务 638,793 条 DML 耗时 44.4 秒。两轮均按 UID 哈希分到 8 个 MySQL 连接并行执行。每个 UID 始终落到 同一连接，并严格保持 relay 时间顺序，因此同 UID 的 UPDATE 覆盖顺序不变。 补充回放前另外保存了 13 张表的数据和表定义，便于回退。

七、完整性与安全边界

  • 恢复目标为临时库，生产 主节点 未写入。
  • 核心与补充共 16 个增量包均通过 gzip 与 SHA256 校验。
  • 409 个 SQL 文件通过 DDL/DROP 黑名单与分片条件检查。
  • 21 张用户相关表 CHECK TABLE 全部返回 OK。
  • 所有已恢复主键 UID 无重复，核心时间字段没有越过截止点。
  • 补充回放前的数据备份 SHA256 为 5990d7651e5e454ec7e17907ea00480f62a2b0d367fcbaa406947894b821640b。
  • 资源文件、SQL 包和密码未写入仓库。

3. 当前阻断项

某地区 PG01 重启后进入自动重启循环，日志明确报：

Can't connect to MySQL server on '192.0.2.48' (timed out)

香港 01、02 和入口 Nginx 对该地址的 TCP 3306 均超时。PG01 在停止前已自动 重启 55 次，现保持停止；PG02 和其他香港容器未再操作。现场已明确暂停香港侧 操作，等待运维完成网络与白名单处理。

香港 Nginx 主入口：192.0.2.52 / 192.0.2.50
香港 Nginx 备用入口：192.0.2.53 / 192.0.2.50

需放通 MySQL TCP 3306 和 Redis TCP 6379。若数据库支持 VPC 内网访问，优先 使用上述内网 IP；否则使用对应公网/32。

九、剩余工作

  1. 某业务平台 将隔离库结果提交 DBA 与开发验收；由责任人决定何时迁移到生产实例。
  2. 如需补齐恢复点后的数据，继续评估 relay/binlog 与业务双写差异，不在未确认 的情况下直接覆盖生产。
  3. 香港侧等待现场恢复；白名单与网络确认后再校验 PG01，并按 01、02 顺序逐台 滚动重启，不同时中断两套后端。
  4. 香港服务恢复后重新执行一次 PG 下注，确认 15 秒阻塞和 CORS 表象消失。
