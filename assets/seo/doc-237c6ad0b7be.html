结论先行

Web 直播间已完成去 mock：弹幕、进场、连击、观看人数改走 GET /danmaku 历史 + WS 推送，主推竞猜走 /activities，打赏接真实 POST /tip。前端严格按契约 §16 的 type 码与字段实现，未做任何字段适配（按团队约定，前端不写转换器迁就后端错误返回）。

但实测当前 dev 后端的 WS 推送协议与契约脱节，导致对接当前后端时 WS 弹幕 / 进场 / 连击 / 观看人数不生效；弹幕历史接口直接 500。后端按契约修齐后，前端无需改动即可恢复。

下列各项均经实测核实（WS 握手抓帧 + curl）。

W1【阻断】WS envelope 结构与契约 §16.3 不符

影响：所有 WS 推送均无法被前端正确识别 / 去重。

契约定义（§16.3 双向通用 envelope）：

{ "type": "live.danmaku.received", "msg_id": "01H9XYZ-...-ABC", "ts": 1719404400123, "trace_id": "abc123", "data": { } }
字段 契约 说明
type string 类型码（§16.6）
msg_id string 消息唯一 ID，客户端按此去重（§16.8 强制）
ts int64 服务端 Unix ms
trace_id string 链路追踪
data object 类型相关 payload

后端实际推送（握手后立即抓到的帧）：

{ "type": "viewer_count", "data": { "count": 1 }, "ts_ms": 1779788188037 }
契约字段 后端实际 状态
ts ts_ms 字段名不符
msg_id （缺） 缺字段，且 §16.8 要求按 msg_id 去重，无此字段则无法去重
trace_id （缺） 缺字段

建议：envelope 补齐 msg_id / trace_id，ts_ms 改 ts。

W2【阻断】WS type 码 / data 字段与契约 §16.6 不符（观看人数）

影响：观看人数实时刷新不生效（前端监听 live.viewer.count.updated，收不到）。

契约定义（§16.6 直播间通道 S→C）：

type 码 data 关键字段
live.viewer.count.updated viewer_count, peak_count

后端实际：

契约 后端实际 状态
type live.viewer.count.updated viewer_count 类型码不符（契约规则 <channel>.<entity>.<action> 点分小写，后端用扁平下划线码）
data.viewer_count data.count 字段名不符
data.peak_count （缺） 缺字段

其余 type 码大概率同样脱节，但未抓到样本：测试房间 match: null、无进行中竞猜，仅推 viewer_count，未能观察到以下契约事件的实际形态，请后端自查全表对齐 §16.6，或提供一个有进行中赛事 / 可发弹幕的房间以便前端复核：

  • live.danmaku.received（user_id, nickname, level, color, content, sent_ts）
  • live.enter.normal / highlight / banner / fullscreen / global（user_id, nickname, level[, source_room_id]）
  • live.tip.combo（user_id, nickname, combo_count, diamond_amount）
  • live.system.notice / live.danmaku.deleted 等

建议：WS type 码全表 + data 字段按 §16.6 对齐。

W3【严重】GET /api/v1/live/room/{room_id}/danmaku 弹幕历史 500

影响：进房拉不到历史弹幕。前端已对该兜底接口静默降级（不弹 toast），但历史始终为空。

契约定义：返回 LiveDanmaku[]（msg_id, room_id, user, content, color, sent_at, sent_ts），支持 query since_ts / limit。

后端实际返回：

{ "code": 10001, "message": "服务器异常", "data": null }

建议：修复该接口 500。

附：处理原则

  • 上述脱节前端未做适配映射，按契约 type 码 / 字段实现 + 仅加防御性降级（弹幕历史失败静默不阻塞实时链路）。
  • 修复方向应为「后端对齐契约 §16」或「先改契约 packages/contracts/openapi/v1.yaml 再 make openapi 同步、前端按新契约调整」，两者择一，避免前后端各自为政。
  • WS 心跳（client.ping / server.pong，§16.4）、重连（§16.5）、close code（§16.7）前端已按契约实现；若后端实现有出入，请一并在本清单补充。

验证：单测 9/9 通过；typecheck 无新增报错；浏览器实测 desktop + 移动 theater 渲染正常、聊天为空（无 mock）、竞猜卡按 activities 隐藏、后端 danmaku 500 时无 toast 刷屏。
