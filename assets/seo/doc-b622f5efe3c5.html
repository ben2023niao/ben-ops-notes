  • 文档日期：2026-09-30 19:50（北京）/ 11:50（UTC）

  • 分类：安全事件（E4 · 生产环境外部暴露 + 持续暴力破解）
  • 发现方式：本轮「清理垃圾日志」时发现 /var/log/syslog 被 MSSQL 登录失败刷到 2.5G，顺线追出

一、发现经过

起因：清理该机垃圾日志时，/var/log/syslog 已达 2498M，且最后 2 万行里 99% 是同一条：
  sqlservr[864]: Logon Error: 18456, Severity: 14, State: 8.
  sqlservr[864]: Login failed for user 'sa'. Reason: Password did not match ... [CLIENT: x.x.x.x]

二、事实（VERIFIED）

  • sqlservr 监听 0.0.0.0:1433 与 [::]:1433（对公网全开）
  • syslog 中 Login failed for user 'sa' 累计 7,957,782 条（统计窗口：Sep 27 07:07 起， 约 2.6M 次/天、平均约 30 次/秒）
  • 授权安全测试源 TOP（按失败次数）：
来源 IP 失败次数
167.104.164.116（HostHatch） 7,933,721（99.7%）
38.60.251.87 13,336
171.100.164.7 4,031
95.111.234.173 3,856
84.241.19.200 / 152.52.118.97 / 122.176.216.183 / 106.51.2.65 数百
  • 处置前 ss -tn 显示 167.104.164.116 对本机 1433 保持 59 条 ESTABLISHED 连接（高频重试）
  • 注：167.104.164.116 与本机 nginx 授权安全测试源黑名单里的那个 IP 是同一个 （见 10-youdianse-prod-maps.conf 的 ~*167.104.164.116 1）， 即该来源同时打 80/443（已被 nginx 444）和 1433（此前无任何防护）
  • 附带影响：MSSQL 常驻 3.4G 内存（该机最大内存占用进程）、 /var/opt/mssql/log/errorlog 被刷到 1.7G

三、处置（2026-09-30 11:38~11:45 UTC）

  1. 本机防火墙止血（仅放行 VPC/内网，其余 DROP）：
iptables -I INPUT 1 -p tcp --dport 1433 -s 203.0.113.1/16 -j ACCEPT
iptables -I INPUT 2 -p tcp --dport 1433 -j DROP
  1. 断开存量连接：ss -K dst 167.104.164.116 连续执行 3 轮 → 外部连接归零
  2. 持久化：新增 /usr/local/sbin/youdianse-mssql-1433-guard.sh（幂等，重复执行不会加重复规则）， root crontab 增加 @reboot /usr/local/sbin/youdianse-mssql-1433-guard.sh （本机没有 netfilter-persistent，重启后靠这条恢复）

四、验证

· 外部连接：ss -tn | grep :1433 | grep -v 203.0.113.1 → 0 条
· 授权安全测试是否停止：连续 10 秒 syslog 新增 "Login failed" = 0 条（处置前约 30 条/秒）
· 规则生效：iptables -S INPUT 可见 ACCEPT(203.0.113.1/16) + DROP 两条
· 业务无影响：nginx active、H5(3003)/PC(3004)/healthz 全部 200、公网首页 200

五、遗留风险与建议（待决策）

  1. AWS 安全组大概率仍对 0.0.0.0/0 放行 1433 —— 本次只是本机 iptables 兜底。 建议在安全组直接把 1433 收口到 VPC 网段（或删除该入站规则），否则任何一次 系统重装/规则丢失都会重新暴露。
  2. MSSQL 疑似无人使用：处置期间本机无任何正常客户端连接（只有暴力破解与 203.0.113.1 少量）。 若确认业务不需要，建议停用/卸载 —— 可同时回收 3.4G 内存与 1.7G errorlog （该机此前「内存使用率偏高」的主要占用之一就是它）。
  3. sa 账号若曾使用弱口令，建议改密/禁用；MSSQL 未用时直接停服务最彻底。
  4. /var/opt/mssql/log/errorlog 1.7G 未处理：MSSQL 持有文件句柄，安全做法是 EXEC sp_cycle_errorlog（需有效凭据）或随服务停用一并处理，不建议直接 truncate。

六、回滚

· 删除 iptables 两条规则：iptables -D INPUT -p tcp --dport 1433 -s 203.0.113.1/16 -j ACCEPT
                          iptables -D INPUT -p tcp --dport 1433 -j DROP
· 移除 root crontab 中 `@reboot /usr/local/sbin/youdianse-mssql-1433-guard.sh` 一行
· 删除 /usr/local/sbin/youdianse-mssql-1433-guard.sh（如需彻底撤销）

七、安全与敏感内容

本记录不含 token、密钥、私钥正文；授权安全测试源 IP 与统计口径属安全事件证据，可记录。

八、追查：这个 MSSQL 是干什么的？（2026-09-30 12:10 UTC 补充）

8.1 结论：是标准的"装完没人用"组件，不是业务依赖

  • 安装时间：2026-06-10 21:49 UTC（/var/log/dpkg.log：install mssql-server:16.0.4255.1-8）， 与 /opt/mssql、/var/opt/mssql 目录创建时间完全一致 —— 即服务器初始装机时就一并装上了
  • 版本：SQL Server 2022（16.0.4255.1），mssql-tools18 同装；mssql.conf 为默认（仅 EULA + sqlagent）
  • 没有任何用户数据库：/var/opt/mssql/data 只有 master/model/msdb/tempdb 系列系统库 （master.mdf 的修改时间只是被暴力破解的登录尝试刷出来的），从未建过业务库
  • 没有任何调用方：四台机器上没有服务、cron、容器、应用配置引用 1433/mssql （唯一命中是新加的加固脚本本身）；容器只有 H5/PC 前端与 beszel-agent
  • 连接来源只有两类：203.0.113.1（SQL Server 自身/Agent 的内部连接）+ 外部暴力破解
  • bash_history 无安装痕迹（装机脚本或他人会话执行，已无从追溯）

8.3 四台统一加固与验证

  • 统一脚本 /usr/local/sbin/youdianse-mssql-1433-guard.sh（幂等：按规则序号清理历史/重复规则后再插入）， 四台 root crontab 均加 @reboot 恢复
  • 现状：每台 INPUT 仅两条 1433 规则（ACCEPT 203.0.113.1/16 + DROP），外部连接 0
  • 验证方式与假象排除：
  • 网关 DROP 计数器 8 秒内 6595 → 7030（+435），说明外部 SYN 正在被丢弃
  • 从 ben-bot 机（AWS 新加坡，VPC 外）测三台 1433 全部不可达； 发 MSSQL 预登录包无任何响应（超时）
  • 注意：从办公网/本机 Python connect() 测会误报"可连" —— 实测本机连 1434 / 9999 / 14330 这些确定关闭的端口也报成功，是本机出口网络中间盒造成的假象， 不能作为"端口还开着"的依据
  • AWS 安全组层面仍需收口（本机规则只是兜底，见第五节第 1 条）

8.4 业务影响确认（重点）

加固只涉及 1433（且保留 VPC 内访问），业务链路实测无影响：

九、处置升级：四台统一停用 MSSQL（观察期）+ 垃圾日志清理（2026-09-30 12:20~12:35 UTC）

9.1 用户决策

用户确认：先停服务观察一段时间（不卸载），并把垃圾日志清理掉；需确认宝塔不依赖它。

9.2 「宝塔是否需要 MSSQL」的核查结论：不需要

  • 宝塔面板自己的库 /www/server/panel/data/default.db 中 databases 表 0 条（没有任何 SQL Server 库登记）
  • 面板/站点配置里对 mssql|1433|sqlsrv 的命中全部是面板自带的字典/模板： config/weak_pass.txt、config/pass1000.txt（弱口令字典）、overview_template.json（UI 模板）、 plugin_list.json（插件目录）、data/warning/*.json（漏洞告警库）、safeCloud 规则（webshell 检测）
  • 站点 PHP 目录命中仅为 PHP 源码自带的 mssql_* 函数名与 Zend 头文件
  • 停服务后实测：bt 面板服务 active、面板端口响应、本机 www/h5 站点 200 —— 面板与站点完全不受影响
  • 结论：宝塔、四个站点、后端 PHP、H5/PC 前端都不使用 MSSQL，可以停

9.5 观察期与回滚

  • 观察期：至确认无影响为止（建议跨一个完整业务日 + 节后首个工作日），期间关注 后端 API/发布、宝塔面板、CICD、H5/PC 页面与支付回调；当前（停用后即刻）全部 200
  • 回滚（1 条命令，数据未动）：systemctl enable --now mssql-server
  • 卸载（如观察期确认无问题后再决定）：apt purge mssql-server mssql-tools18 + 删除 /var/opt/mssql、/opt/mssql（未执行，等用户决定）
