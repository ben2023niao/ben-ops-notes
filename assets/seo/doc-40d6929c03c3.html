整理日期：2026-10-19 20:20｜日期依据：文件名日期

时间：2026-10-19 20:20（北京）｜2026-10-19 09:20（巴西圣保罗） 范围：巴西线上 01 203.0.113.1、02 203.0.113.1、入口机 34.151.249.53 执行方式：本地 + 宝塔跳板 + 后端 SSH，全程未发群通知

一、结论

  1. 日志目录 /data/server-runtime/logs/<厂家>/<日期>.log 一直按天增长，但 logrotate 配置仍指向旧目录 /opt/pgserver/logs/*/*.log，导致 9/19 之后没有轮转，01/02 根盘持续上涨。
  2. 已把 logrotate 配置和归档脚本的日志根目录改到现目录，后续按小时 + 单文件 1G 上限轮转，保留 7 天。
  3. 存量日志用 pigz 就地压缩（只压缩、不删除原日志），先把磁盘降下来，压缩产物保留待归档。
  4. 入口监控、PG6/PG7 启动链监控完成中文告警改造，并修正两类长期误报（旧 GCS 桶 404、SOCKET 接口 405）。

二、磁盘与根因

机器 处置前 处置后
01 203.0.113.1 475G / 484G，99% 239G / 484G，50%
02 203.0.113.1 447G / 484G，93% 242G / 484G，50%
03 203.0.113.1 222G / 484G，46% 未处置（打包机）

根因链路：

  • 运行目录已从 /opt/pgserver/logs 迁到 /data/server-runtime/logs/<厂家>/<日期>.log。
  • /etc/dbqp-logrotate/pgserver-hourly 仍写的是旧路径，logrotate 每小时执行但匹配不到文件。
  • dbqp-game-log-archive.service 的 --log-root 也还是旧路径，S3 归档候选一直是 0。
  • 结果是 9/19–10/19 近一个月的日志全部堆在本地，单文件最大约 11G。

三、处置内容

3.1 存量日志压缩（只压缩不删除）

脚本：/root/compress-old-logs.sh（两台一致，仓库版本 docker/scripts/compress_old_logs.sh）

find "$ROOT" -mindepth 2 -maxdepth 2 -type f -name "*.log" -mtime +"$DAYS" -print0 |
  xargs -0 -r -n1 -P "$PARALLEL" nice -n 10 ionice -c2 -n7 pigz -"$LEVEL" -p "$THREADS"

默认 DAYS=2 PARALLEL=2 LEVEL=1 THREADS=4。最初用 -6 单并发，单文件 11G 压缩过慢， 实测后改为 -1 + 2 并发，压缩率仍有约 1/5~1/7。

执行方式：systemd-run --unit=compress-old-logs，日志 /root/compress-old-logs.log。 只处理 2 天前的 .log，压缩完成后由 pigz 自行删除被压缩的源文件；当天正在写的日志不碰。

注意：压缩期间临时停了 dbqp-game-log-archive.timer，避免 logrotate 在整点对正在压缩的大文件做 copytruncate 导致压缩包损坏；压缩结束后已重新 systemctl start dbqp-game-log-archive.timer。 02 上额外挂了一个一次性等待任务 resume-archive-after-compress，压缩结束后自动恢复定时器， 已确认 13:30 UTC 恢复并触发轮转。

3.2 logrotate 配置修正

文件：/etc/dbqp-logrotate/pgserver-hourly

/data/server-runtime/logs/*/*.log {
    su root root
    hourly
    rotate 200
    maxsize 1G
    maxage 7
    missingok
    notifempty
    compress
    copytruncate
    dateext
    dateformat -%Y%m%d-%H%M%S
}

说明：

  • copytruncate 保证业务继续写同名文件，不需要重启容器。
  • maxsize 1G 让大日志不必等满一小时；maxage 7 控制本地保留期。
  • 已用 logrotate -d 做语法与匹配检查，0 错误。
  • 备份：01 /root/pgserver-hourly.bak-20261019-121043，02 /root/pgserver-hourly.bak-20261019-121050。

3.3 归档脚本日志根目录修正

文件：/etc/systemd/system/dbqp-game-log-archive.service.d/override.conf

[Service]
ExecStart=
ExecStart=/usr/sbin/logrotate -s /var/lib/logrotate/dbqp-pgserver-hourly.status /etc/dbqp-logrotate/pgserver-hourly
ExecStart=/usr/bin/python3 /usr/local/sbin/dbqp-game-log-archive.py upload-old --log-root /data/server-runtime/logs

已 systemctl daemon-reload。归档逻辑是「先同步到 S3，再用 head-object 校验字节数一致，最后删本地」，超过 7 天的轮转包才会被清理。

四、监控告警汉化与误报修正

4.1 入口监控 entry_health_monitor.py

  • 标题统一为 【DBQP 巴西项目｜入口监控｜故障报警/恢复】@运维 @Ben_Bird @benb6879。
  • 时间行统一为「北京时间 + 巴西圣保罗时间」。
  • 修正 6 个游戏页探测地址：旧 dbqp-gcs-<厂家>-static-sa.storage.googleapis.com 桶已删除（实测 404），改为 <厂家>-static.xqv9m8.icu，入口机实测 6 项全部 200。
  • 修正 SOCKET 误报：接口只接受 POST，用 GET 探测返回 405，原白名单没有 405，导致 25 项里 12 项长期 alerted=True；现已把 405 计入正常。
  • 增加历史状态键清理：不在当前清单里的旧键会自动移除。
  • 新增 --dry-run：只探测、不改状态、不发群。

  • 同样改为中文标题、双时区时间、@ 提及。

五、阈值建议（Beszel Hub）

现状是 Beszel Hub 的英文告警直接发群，阈值偏低且没有分级，容易长期刷屏。建议按下表调整（需 Hub 后台权限）：

指标 现状 建议 依据
CPU 1 分钟 75%~80% 触发 85% 持续 5 分钟 01/02 平时 2%~3%，发版/巡检有短时尖峰
内存 80% 85% 持续 10 分钟 32G 机器常态可用 13G 以上
磁盘 70% 85% 警告 / 92% 严重 日志型机器 70% 属常态，70% 会长期常亮
负载 1 分钟 5（8 核） 12（≈1.5×核数）持续 5 分钟 8 核机器 load 1~2 属正常
网络丢包 默认 10% 持续 5 分钟 降低偶发抖动误报

另建议增加「磁盘 24 小时增长 > 5%」的增速告警，比静态百分比更早发现问题。

六、待办与风险

  1. 压缩产物为 <日期>.log.gz，不匹配归档脚本的 *.log-YYYYMMDD-HHMMSS.gz 规则，暂不会自动上传 S3；确认后可统一归档或按保留期清理。
  2. 归档脚本按「目录名=厂家」识别，当前目录结构已变化，后续需补一次适配（本次未改代码，避免影响正在压缩的任务）。
  3. Beszel Hub 在东京 34.146.121.225:8090，22 端口拒绝、2222 端口要求公钥，本次没有可用密钥，中文告警镜像与阈值暂未在 Hub 落地。 中文告警镜像的补丁、Dockerfile 和部署/回滚步骤已放在 docker/scripts/beszel-zh/，拿到 Hub 权限后可直接构建替换。
  4. 处理原则：只压缩、不删除原始日志；未重启任何业务容器。

七、复核命令

# 磁盘
df -h /

# 压缩任务
systemctl is-active compress-old-logs
tail -n 20 /root/compress-old-logs.log

# 归档定时器（压缩期间临时停过，必须确认已恢复）
systemctl is-active dbqp-game-log-archive.timer

# 轮转配置
logrotate -d /etc/dbqp-logrotate/pgserver-hourly

# 归档服务最近一次结果
journalctl -u dbqp-game-log-archive.service -n 30 --no-pager

# 入口监控（不改状态、不发群）
python3 /opt/pgserver/docker/scripts/entry_health_monitor.py --dry-run
python3 /opt/pgserver/docker/scripts/pg67_games_watch.py --dry-run

八、实测结果

压缩在 13:30 UTC 全部结束：

机器 压缩前 压缩后 日志目录
01 475G，99% 239G，50% 53G
02 447G，93% 242G，50% 约 60G

轮转实测（01，13:08 UTC 那一轮）：

  • 2026-10-16/17/18.log 各 8~9G，已转出为 *.log-20261019-130845.gz，源文件归零；
  • 当天 2026-10-19.log 从 4.6G 归零后继续正常写入，说明业务用的是追加写，copytruncate 没有产生空洞；
  • 整轮完成后 01 磁盘从 57% 进一步降到 50%。
