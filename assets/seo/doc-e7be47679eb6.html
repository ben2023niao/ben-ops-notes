一、需求

Ben(C++)：香港这边配置一下 wss://vendor_b-games.hkcloudplay06.com/lifeservice/ws2
确认口径：
  · 「和 vendor_a 一样就行」——参考巴西 vendor_a 的 ws 站点写法
  · 端口 8765（与巴西 vendor_a 一致）
  · 「域名映射就行了，启动的都是 vendor_a」——vendor_b 复用 vendor_a 的 ws 服务，不另起后端
本侧按要求只做 nginx 域名映射（不改造 start.sh/stop.sh、不新增后端端口）。

二、巴西参考（master 配置）

upstream vendor_a_ws2_backend {   # 192.0.2.1 / 0.4 / 0.11 : 8765
    server ... keepalive 32 ...
}
location ^~ /lifeservice/ws2  -> proxy_pass http://vendor_a_ws2_backend;   # 仅 vendor_a-games.* 可用
location ^~ /ws2              -> proxy_pass http://vendor_a_ws2_backend;
两者都带全套 WebSocket 头：Upgrade/Connection/Host/X-Original-Host/X-Real-IP/
  X-Real-Port/X-Forwarded-*/REMOTE-HOST/X-Vendor-Host，
  proxy_connect_timeout 5s、proxy_read_timeout 3600s、proxy_send_timeout 3600s，
  proxy_next_upstream error timeout http_502/503/504 + tries 2。
线上实测对照：wss://vendor_a-games.xqv9m8.icu/lifeservice/ws2 -> 101 Switching Protocols

三、香港实现

落在 standby 入口（bizops-hongkong-nginx-standby-01，新域名 06/07 的入口），老入口机未改动。

docker/deploy/hongkong/nginx-standby.conf 新增：

upstream bizops_hk_standby_vendor_a_ws2 {           # vendor_b 复用 vendor_a 的 ws 服务
    least_conn;
    server 192.0.2.1:8765 max_fails=3 fail_timeout=10s;
    server 192.0.2.1:8765 max_fails=3 fail_timeout=10s;
}

server {
    server_name ~^vendor_b-games\.hkcloudplay0[67]\.com$;
    location ^~ /lifeservice/ws2 { include snippets/bizops-hk-standby-ws.conf; proxy_pass http://bizops_hk_standby_vendor_a_ws2; }
    location ^~ /ws2             { include snippets/bizops-hk-standby-ws.conf; proxy_pass http://bizops_hk_standby_vendor_a_ws2; }
    location /                   { include snippets/bizops-hk-standby-proxy.conf; proxy_pass http://bizops_hk_standby_vendor_b; }
}

新增公共片段 docker/deploy/hongkong/nginx-standby-ws.conf（WebSocket 头 + 长超时）， 照抄巴西写法，仅把上游换成香港自建后端内网 IP。

部署：两个文件写入 standby（旧站点配置已备份 bizops-hk-standby.conf.bak-YYYYMMDD-HHMM）→ nginx -t 通过 → systemctl reload nginx。

四、验证（真正的 WebSocket 握手，不用 curl 拼头）

用 Python 标准库 socket/ssl 手工发 Upgrade 请求：

探测 结果
直连 192.0.2.1:8765 的 /lifeservice/ws2 HTTP/1.1 101 Switching Protocols
直连 192.0.2.1:8765 的 /ws2 101
经 standby nginx（SNI=Host=vendor_b-games.hkcloudplay06.com） 101
公网 wss://vendor_b-games.hkcloudplay06.com/lifeservice/ws2 101
公网 wss://vendor_b-games.hkcloudplay06.com/ws2 101
公网 wss://vendor_b-games.hkcloudplay07.com/lifeservice/ws2 与 /ws2 均 101
巴西对照 wss://vendor_a-games.xqv9m8.icu/lifeservice/ws2 101（口径一致）

排查过程备注：

一开始用 curl 加 Upgrade 头测试，得到 200 application/json（11 字节）与偶尔 000 超时，
一度误判为「后端不是 ws 端点」。改用标准 WebSocket 握手脚本后全部 101，
说明是 curl 的握手头不完整（缺标准 Sec-WebSocket-Key 规范/未走 ws 流程）导致的误判。
=> 以后验证 ws 一律用握手脚本或 wscat，不用 curl。

五、待办与风险

1. 单点风险：8765 的 ws 容器目前只在 prod-02（192.0.2.1）监听，prod-01（192.0.2.1）不可达；
   upstream 已按双后端写，等 prod-01 也起 vendor_a_ws 容器后自动双活。
2. 老域名 vendor_b-games.hkcloudplay01-05.com（老入口机）本轮未配 ws —— 用户本次只要求 06/07；
   如需老域名同样支持，需在老入口机 nginx 加同样的 location（并在确认后端就绪后灰度）。
3. vendor_a-games.* 域名在 cn 仍不启用（cn 只保留 vendor_b 复用 vendor_a 前端/WS 资源，不开放 vendor_a 对外域名）。
