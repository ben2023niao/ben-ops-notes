一、工单与背景

来源：游戏平台-运维-melo / 番子-远程后端 / Ben 运维（群内）
现象：测试环境发布新配置后，宿主机配置已更新，但容器内仍是老配置
      例：alb_white.txt 宿主机已含“星姬调教工坊 / ntrapi.1uhg.com”，web/cron 容器内仍是 8/27 旧文件
追加要求（用户）：
  1) 其他 txt 配置也要按同样机制同步（不能只写死 alb_white*.txt）
  2) 配置发布必须校验三方 md5 完全一致才允许判定“发布成功”：
     代码配置仓库文件 md5 = 宿主机配置文件 md5 = 各容器内配置文件 md5
  3) 线上环境-游点涩-配置-发版 参考 测试环境-游点涩-配置-发版 同步优化
  4) 全部操作留下详细文档；每步通知 18game运维 + 18GAME_ 上线群（正式環境）

二、现象与证据（修复前）

测试环境 15.152.247.196（/opt/docker-youdianse-php，分支 dev）
  alb_white.txt：宿主机 md5=7c83cfed…（新） vs 容器 md5=2f12c2e4…（旧，mtime 08-27 15:57）
  alb_white_secret.txt：宿主机 c77ac424…（新） vs 容器 68c67118…（旧）
  env/.env.dev：宿主机与容器一致（e630b41b…）→ env 已随容器重建生效

结论：env 正常、白名单类文件不生效，即“宿主机更新、容器内仍旧”只在非 bind mount 的本地配置文件上出现。

三、根因

1. 白名单等 app-local-files 文件不是 bind mount，而是发布时通过 docker cp 写进容器；
2. 配置发版/自动同步走的是 sync_runtime_config_no_build()（仅 docker compose up -d
   --force-recreate --no-build web nginx cron），未调用
   sync_protected_app_local_files_to_containers()；
   只有完整发布 deploy() 才会执行 docker cp → 因此“配置发版”后宿主机生效、容器内不生效；
3. 校验函数 collect_runtime_config_sync_status() 只比对 env/nginx/php/fpm 四类挂载文件，
   不比对白名单，所以同步报告显示“复查已一致”，形成假阴性；
4. 写死 PROTECTED_APP_LOCAL_FILES（alb_white.txt、alb_white_secret.txt），
   配置仓库新增其它 txt 配置不会自动同步；
5. （线上）即便手工 docker cp 过白名单，下一次“配置发版”仍不会重新下发，
   历史版本会长期滞留在容器内。

    sync_protected_app_local_files_to_containers()（branch=当前运维分支），重新 docker cp 进 web/cron

  · collect_runtime_config_sync_status()：env 增加配置仓库 config-repo/env/<env> 比对源；
    新增 app_local_file_runtime_checks() 覆盖本地配置文件（web/cron）
  · 只有三方完全一致（needs_sync=False）才算发布成功
