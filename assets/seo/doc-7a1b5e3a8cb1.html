整理日期：2026-10-14 11:00｜日期依据：文件名日期

时间：2026-10-14 11:00（北京）/ 03:00（UTC） 现象（用户报告）：

https://pg4-static.tada-cdn-2026.icu/100/assets/resources/import/03/03bba7f7d.87cd6.json
「为什么访问不了」，并补充「香港那边可正常访问」

本轮不通知飞机群。

一、结论

根因：这个 JSON 是**今天 05:51:31 UTC 才上传到 GCS 的**；
      而它上传前后有请求打过来，拿到 GCS 的 404（NoSuchKey），
      这个 404 被 Cloudflare **连响应一起缓存了 7 天**（cacheEverything + cacheTtl 604800），
      于是文件补上之后，巴西侧用户仍然一直吃到缓存里的 404。
      香港那台没被这个 404 污染（首次请求就是 MISS → 回源拿到 200），所以「香港能访问」。

修复：对所有服务 pg4-static.* 的 22 个 zone 做 purge_everything；
      复测该 URL 在巴西侧已恢复 200（application/json，696B）。

二、排查证据（逐条实测）

① 马尼拉（PH）出口：403 + Worker 的 "Access Denied" 页
   → 这是 Worker 国家白名单（BR/SG/HK/AE）拦截，属预期行为，不是本次问题的原因。

② 巴西出口（宝塔 35.247.205.6）：404，content-type: application/xml，
   cf-cache-status: HIT，age=2280s，cache-control: public, max-age=604800
   响应体：<Error><Code>NoSuchKey</Code>…No such object:
           newgg2-dbqp-gcs-pg4-static/100/assets/resources/import/03/03bba7f7d.87cd6.json</Error>
   → 404 是 GCS 给的，而且被缓存在边缘（HIT + age=2280 + 7 天有效期）

③ 香港出口（HK-01）：200，application/json，696B，cf-cache-status: MISS，
   x-goog-stored-content-length: 696 → 没被污染，实时回源拿到正确内容

④ GCS 侧：对象确实存在，696 字节，创建时间 2026-10-14T05:51:31Z（今天）
   → 是"上传后被缓存 404 挡住"，不是对象缺失

时间线还原：

~05:51  某请求命中 pg4-static.<zone>/100/assets/.../03bba7f7d.87cd6.json → GCS 404（对象还没上传/刚上传）
~05:51  该 404 被 CF 缓存，TTL 604800s（7 天）
之后    巴西侧再访问 → 直接吃缓存的 404（HIT），即使文件已在 GCS
香港侧  本地边缘没有这条缓存 → MISS 回源 → 200

三、修复动作与复测

在宝塔执行：
  bash /opt/dbqp-scripts/cf_purge_zones.sh --vendor pg4
  → PURGE_DONE ok=22 fail=0

复测（巴西出口，同一个 URL）：
  tada-cdn-2026.icu  200  application/json  696B  MISS  x-goog-stored-content-length: 696
  xqv9m8.icu         200  …   696B  MISS
  q7m9v8.icu         200  …   696B  MISS
  t6qv8m.icu         200  …   696B  MISS
  响应体是正常的 Cocos 图集 JSON（[1,[…sprite frame uuid…],["_textureSetter",…]]）
→ 访问已恢复；首次 MISS 之后会按正常逻辑重新缓存 200。

四、为什么会这样（Worker 的缓存行为）+ 建议

当前 Worker（summer-wave-c94f）对静态资源是：
  fetch(gcsRequest, { cf: { cacheKey: 内部键, cacheEverything: true, cacheTtl: 604800 } })
它只对 200 的响应补写 Cache-Control: public, max-age=604800，
但 cacheEverything: true 会把上游返回的任何状态码（含 404）都写进边缘缓存并保留 7 天，
于是"上传前的 404"会把"上传后的正确文件"挡 7 天。

建议（二选一或都做）：
  A. Worker 侧：不要缓存非 200 —— 把 fetch(cf:{cacheEverything}) 换成显式 Cache API
     （caches.default.match/put），只对 status===200 的响应 put，非 200 透传并加 no-store。
  B. 运维侧（当下可做）：每次往 GCS 上传/替换静态资源后，刷一次对应厂家的 zone
     （bash /opt/dbqp-scripts/cf_purge_zones.sh --vendor <厂家>），把可能被缓存住的旧 404/旧内容清掉。

五、运维手册（同类问题怎么快速定位/处置）

# 1) 看是不是"被缓存的错误响应"：重点看 cf-cache-status / age / content-type
curl -s -o /dev/null -D - "https://<静态域名>/<路径>" | grep -iE "^HTTP/|cf-cache-status|age|cache-control|content-type"
#    404 + application/xml + HIT + age 大 → 本文这种（缓存住的 GCS NoSuchKey）
#    403 + text/html + Access Denied 页 → 国家白名单拦截（换允许的国家出口再试）

# 2) 确认对象在不在 GCS
export CLOUDSDK_CONFIG=/root/.config/gcloud
gcloud storage ls -l "gs://newgg2-dbqp-gcs-<厂家>-static/<路径>"

# 3) 刷缓存（整 zone；--vendor 会自动探测哪些 zone 在服务该厂家）
bash /opt/dbqp-scripts/cf_purge_zones.sh --vendor <厂家>

# 4) 复测时换一个"这次没请求过"的对象，避免被自己刚建立的缓存干扰
