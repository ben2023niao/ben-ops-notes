注意：不要在群里、文档里、提交里粘贴完整 launcher URL、JWT、ot、cookie、会员 token。本文只记录脱敏后的链路、域名和状态码。

问题摘要

环境：

环境/厂牌：巴西试玩 PG
会员 ID：151
问题等级：P2

涉及游戏：

阿努比斯 / Anubis Wrath：1623475
玻尔修斯传奇 / Legend of Perseus：128

测试侧现象：

点击游戏后，加载页卡在 50% 左右，无法进入游戏。
部分情况下页面提示登录失败并自动重试。
后端日志看不到 verify 请求，表现为“网络没到服务器”。

核心结论

这次不是 PG 静态资源没同步，也不是两个游戏目录缺资源。

两款游戏的 pg-static 静态资源目录存在，GCS / CDN 抽样访问 200。真正问题集中在部分 pg-games 入口域名生成 verify/API host 的逻辑：

正常入口：
https://pg-games.xqv9m8.icu/128/index.html

正常 verify：
https://pg-games.xqv9m8.icu/web-api/auth/session/v2/verifyOperatorPlayerSession

异常入口：
https://pg-games.t6qv8m.icu/128/index.html

异常 verify：
https://pg-games.t6qv8api.icu/web-api/auth/session/v2/verifyOperatorPlayerSession

pg-games.t6qv8api.icu 不是当前合法域名，没有 DNS 记录，浏览器直接报：

net::ERR_NAME_NOT_RESOLVED

因此请求根本到不了 Cloudflare / 宝塔 Nginx / 后端服务，后端日志自然没有 verify 记录。

全游戏扫描补充

2026-07-06 全游戏扫描期间继续观察 PG 线上日志，确认类似问题不是单个游戏资源包问题，而是 pg-games.t6qv8m.icu 入口域名的通病。

今天日志里这些游戏在 t6qv8m 入口下都有页面活动，但没有成功 verify：

67       少林足球(Shaolin Soccer)                  refs=1   verify=0 spin=0
106      麒麟送宝(Ways of the Qilin)               refs=9   verify=0 spin=0
115      超市大血拼(Supermarket Spree)             refs=1   verify=0 spin=0
128      玻尔修斯传奇(Legend of Perseus)           refs=13  verify=0 spin=0
135      赏金大对决(Wild Bounty Showdown)          refs=5   verify=0 spin=0
1623475  阿努比斯(Anubis Wrath)                    refs=8   verify=0 spin=0

判定口径：

  • refs 是今天线上日志里该游戏从 pg-games.t6qv8m.icu/<gid>/index.html 产生的后续页面活动次数。
  • verify=0 表示同一入口没有任何成功 verifyOperatorPlayerSession。
  • spin=0 表示同一入口没有任何成功 Spin。
  • 106 / 128 / 135 / 1623475 样本相对充分，可作为确认同类问题。
  • 67 / 115 只有 1 条样本，不能证明该游戏独有问题，但因为入口同为 pg-games.t6qv8m.icu，仍属于同一域名派生规则的风险覆盖范围。

对 106 和 1623475 进行浏览器复测，均复现同类错误：

入口：https://pg-games.t6qv8m.icu/<gid>/index.html?...
实际 verify：https://pg-games.t6qv8api.icu/web-api/auth/session/v2/verifyOperatorPlayerSession?traceId=...
浏览器错误：net::ERR_NAME_NOT_RESOLVED
页面表现：登录失败，系统正在重试

其他入口域名如：

pg-games.xqv9m8.icu
pg-games.m7v8k3.cyou
pg-games.p8m7xv.cyou
pg-games.q7m9v8.icu

在同一轮扫描中能看到 verify 200 或 Spin 200，说明后端服务和游戏 API 本身可用。问题集中在 t6qv8m 入口派生 API host 的规则。

当前运维侧处理方式

运维目前做的是定位、排除和临时规避，没有把误拼域名正式化作为长期方案。

2026-07-06 已完成最终线上处理：

1. 提交并发布 e127daa ops: remove risky pg m icu game hosts。
2. 两台 platform-api 均运行 pgserver:master-e127daa。
3. default / pg3 / pg4 / pg5 的 game_hosts 均为 20 个，risky=[]。
4. 之前扫出的 67 / 106 / 115 / 128 / 135 / 1623475 运行态分发池均无 pg-games.t6qv8m.icu / pg-games.6qv8m.icu。
5. 已通过 ben-bot 发飞机群通知，message_id=2642。

最终上线复测记录见：

docker/doc/2026-07-06-【修复Bug】PG卡50百分比问题修复上线复测记录.md

已经完成的排除项：

1. 排除静态资源缺失：
   /www/wwwroot/pg-static/<gid> 目录存在；
   pg-static / GCS / CDN 抽样资源返回 200。

2. 排除 PG API 反代/CORS 主链路问题：
   宝塔 Nginx 当前已接入 pg-games.* 和 api.*；
   正常入口下 verifyOperatorPlayerSession / GameInfo / Spin 能返回 200。

3. 排除单游戏包问题：
   同一个游戏换 xqv9m8 / m7v8k3 / p8m7xv 等入口可正常 verify 或 Spin；
   问题集中在 pg-games.t6qv8m.icu 入口。

当前处置结果：

1. 已从 platform-api/conf/domains/pg.json 的 PG game_hosts 下线 pg-games.t6qv8m.icu。
2. pg-games.6qv8m.icu 虽然本轮样本少，但同属 m.icu 结尾，按现有误拼规则也已一并下线。
3. 覆盖 default / pg3 / pg4 / pg5 game_hosts，static_hosts 不变。
4. 优先使用已验证正常的入口：
   pg-games.xqv9m8.icu
   pg-games.m7v8k3.cyou
   pg-games.p8m7xv.cyou
   pg-games.q7m9v8.icu
5. docker/deploy/update_pgserver.py 已增加 platform-api / all 发布预检，后续 PG game_hosts 再出现 m.icu 结尾动态入口会中断发布。

运维不建议作为长期方案的兜底：

给 pg-games.t6qv8api.icu / pg-games.6qv8api.icu 补 DNS 和 Nginx。

原因：

1. 这会掩盖 API host 派生 bug。
2. 会把错误域名变成正式维护对象。
3. 如果后续还有其他字符串替换变体，仍会继续漏。

如果业务必须马上恢复且后端来不及发版，运维可以短期兜底二选一：

方案 A：从 PG game_hosts / 分发池移除 pg-games.t6qv8m.icu 和 pg-games.6qv8m.icu。
方案 B：临时给误拼域名补 DNS + 宝塔 Nginx server_name，让它们也走 pg_game_backend。

推荐顺序：

先用方案 A 避开风险入口；2026-07-06 已按方案 A 执行。
后端修 API host 生成逻辑后，再恢复完整域名池。

为什么会拼出 t6qv8api.icu

从现象看，客户端或后端返回给客户端的域名派生逻辑很可能做了类似：

把 hostname 里的 "m." 替换成 "api."

pg-games.t6qv8m.icu 末尾正好包含：

m.icu

如果做字符串替换，就会变成：

pg-games.t6qv8api.icu

这不是预期的 API 域名。预期应是以下二选一：

https://pg-games.t6qv8m.icu/web-api/...

或者：

https://api.t6qv8m.icu/web-api/...

当前宝塔运维侧已经支持 pg-games.* 和 api.* 两类 host 反代 PG API；但是不支持这种误拼出来的 pg-games.t6qv8api.icu。

同类风险域名：

pg-games.t6qv8m.icu -> 可能被误拼成 pg-games.t6qv8api.icu
pg-games.6qv8m.icu -> 可能被误拼成 pg-games.6qv8api.icu

只要根域名最后是 m.icu，都要重点检查。

静态资源排除项

这两款不是 PG3 / PG4 / PG5 拆包特殊资源组，platform-api/conf/domains/pg.json 里它们走 default：

128：default pg-static.*
1623475：default pg-static.*

宝塔静态目录存在：

/www/wwwroot/pg-static/128
/www/wwwroot/pg-static/1623475

GCS / CDN 抽样资源访问 200：

https://pg-static.xqv9m8.icu/128/713dc0937e.26c4c.js -> 200
https://pg-static.xqv9m8.icu/1623475/f33bdb7aaf.f3bd1.js -> 200

pg-static/<gid>/index.html 404 不是问题，因为 PG 的入口页来自：

https://pg-games.<root>/<gid>/index.html

静态域名只负责加载 JS / JSON / 图片 / 音频等资源。

后端开发建议修复

优先修业务侧 API host 派生逻辑，不建议长期靠新增奇怪域名兜底。

建议规则：

  1. 如果当前入口是 pg-games.<root>，verify / game-proxy / game-api 可以直接走同源：
apiBase = window.location.origin

最终请求：

https://pg-games.<root>/web-api/auth/session/v2/verifyOperatorPlayerSession
https://pg-games.<root>/web-api/game-proxy/v2/GameName/Get
https://pg-games.<root>/game-api/pg/v2/GameInfo/Get
  1. 如果必须分离到 api.<root>，只能做明确前缀替换：
pg-games.t6qv8m.icu -> api.t6qv8m.icu

不要对 hostname 做泛化字符串替换，例如不要替换任意位置的 m.。

伪代码：

def pg_api_host(game_host: str) -> str:
    if game_host.startswith("pg-games."):
        return "api." + game_host[len("pg-games."):]
    return game_host

需要加单测的 host：

pg-games.xqv9m8.icu      -> api.xqv9m8.icu 或 pg-games.xqv9m8.icu
pg-games.t6qv8m.icu      -> api.t6qv8m.icu 或 pg-games.t6qv8m.icu
pg-games.6qv8m.icu       -> api.6qv8m.icu 或 pg-games.6qv8m.icu
pg-games.p8m7xv.cyou     -> api.p8m7xv.cyou 或 pg-games.p8m7xv.cyou
pg-games.m7v8k3.cyou     -> api.m7v8k3.cyou 或 pg-games.m7v8k3.cyou

验证标准：

入口页 200
verifyOperatorPlayerSession 200
GameName/Get 200
GameInfo/Get 200
Resources/GetByResourcesTypeIds 200
页面到达“开始”
Spin 能返回 200

运维临时兜底方案

如果后端来不及改，运维侧可以做两类临时兜底。

方案 A：先摘掉高风险入口

临时不要给 PG launcher 分配：

pg-games.t6qv8m.icu
pg-games.6qv8m.icu

优先使用已经验证可用的入口：

pg-games.xqv9m8.icu
pg-games.m7v8k3.cyou
pg-games.p8m7xv.cyou

这个方案影响范围小，但需要确认域名池/随机分配逻辑在哪里控制。

方案 B：补误拼域名

给误拼域名补 DNS 和宝塔 Nginx 映射：

pg-games.t6qv8api.icu
pg-games.6qv8api.icu

映射到当前 PG 反代站点，和 pg-games.* / api.* 一样走 pg_game_backend。

缺点：

  • 这是兜底，不是根因修复。
  • 会把错误域名正式化，后续维护成本更高。
  • 如果还有其他类似字符串替换变体，需要继续补洞。

额外发现：Service Worker scope 警告

两款游戏的 Console 都有同一个警告：

The path of the provided scope ('/') is not under the max scope allowed ('/shared/service-worker/').
Adjust the scope, move the Service Worker script, or use the Service-Worker-Allowed HTTP header to allow the scope.

这不是本次 verify 不到服务器的主因，因为 xqv9m8 入口在出现该警告的同时仍能成功进入游戏。

但它会影响 service worker 缓存注册，可能造成缓存策略不生效或某些浏览器表现不一致。后续可在 Nginx 对：

/shared/service-worker/sw.js

补：

add_header Service-Worker-Allowed "/" always;

这个属于优化项，不应替代 API host 根因修复。

可发给后端的短版

PG 这次不是单游戏静态资源缺失，pg-static / GCS / CDN 抽样资源 200。

本轮全游戏扫描在 pg-games.t6qv8m.icu 入口下扫到以下游戏有同类问题：
67 少林足球(Shaolin Soccer) refs=1 verify=0 spin=0
106 麒麟送宝(Ways of the Qilin) refs=9 verify=0 spin=0
115 超市大血拼(Supermarket Spree) refs=1 verify=0 spin=0

1623475 阿努比斯(Anubis Wrath) refs=8 verify=0 spin=0

失败发生在部分 pg-games 入口域名派生 verify/API host 时：
pg-games.t6qv8m.icu 会把 verify 拼成 pg-games.t6qv8api.icu。
这个域名没有 DNS，浏览器报 net::ERR_NAME_NOT_RESOLVED，请求没有到 Cloudflare/宝塔/后端，所以后端看不到 verify 日志。

同一游戏换 pg-games.xqv9m8.icu / pg-games.m7v8k3.cyou / pg-games.p8m7xv.cyou 等入口，verify、GameName、GameInfo、Resources 或 Spin 能 200。

运维当前处理：
1. 已排除静态资源缺失、GCS/CDN 同步、宝塔 Nginx CORS/API 反代主链路问题；
2. 已从分发池 game_hosts 下线 pg-games.t6qv8m.icu，pg-games.6qv8m.icu 同属 m.icu 结尾也已一并下线；
3. 不建议长期补 pg-games.t6qv8api.icu / pg-games.6qv8api.icu 这种误拼域名，容易掩盖代码 bug。

建议后端修 API host 生成逻辑：
1. 最好直接使用当前 pg-games 同源请求 /web-api 和 /game-api；
2. 如果必须转 api 域名，只允许 pg-games.<root> -> api.<root> 的前缀替换；
3. 不要替换 hostname 任意位置的 "m."，否则 t6qv8m.icu / 6qv8m.icu 会被误拼成 t6qv8api.icu / 6qv8api.icu。
