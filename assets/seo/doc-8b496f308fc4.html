时间：2026-09-24 14:45（北京时间）/ 06:45（UTC） 对象机器：后台 01 203.0.113.1、后台 02 203.0.113.1、打包机 03 203.0.113.1、入口机 34.151.249.53 需求：03 改成打包机后不需要监控；把容器监控的误报收敛掉。本轮不发飞机群通知。 结果：① 03 已从容器监控移除；② 新增「发版窗口自动静默」，发版期间停容器不再报警； 　　　③ 汇总行不再含糊；④ 顺带查出 02 的 TADA 主服务（9096）现在真的没在跑（见第五节）。

一、03 为什么退出监控

需求原话：「03 服务器做打包用不需要监控」。实测确认 03 的性质确实变了：

03（203.0.113.1）docker ps -a 全量（2026-09-24 06:40 UTC）：
  beszel-agent / registry / jms_celery / jms_chen / jms_core / jms_koko /
  jms_lion / jms_postgresql / jms_redis / jms_web / dbqp-resource-sync(Exited)
  hopeful_feistel|Up 3 seconds          ← docker run 不带 --name 的匿名打包容器

监听端口只剩：22 / 80 / 2222 / 5000
厂家容器 game-service-*-prod：**一个都没有**（上一轮 9/18 起的 8 个也都已下线）

也就是说：03 上已经没有厂家容器，而它是发版的打包 / 资源源机—— 02 的 shell 历史显示发版时是从 03 拉 /data/server-runtime（见第二节）。 继续按厂家名监控 03，只会每 2 分钟误报一次（用户收到的 17:06 那条就是这么来的）。

改动：BACKENDS 从三台减成两台。

BACKENDS = [("203.0.113.1", "01"), ("203.0.113.1", "02")]
# 2026-09-24：03（203.0.113.1）已改成打包机，厂家容器全部下线，不再纳入监控。

期望容器数从 29 个变成 20 个（01 十个 + 02 十个）。

二、发版窗口自动静默（这次误报的真正原因）

1. 证据：02 上的发版流程

02 的 root shell 历史（原样摘录）：

sh stop.sh tada
sh stop.sh pp
sh stop.sh api
docker ps
rsync -avz --delete --exclude 'logs' --exclude '*.db-shm' --exclude '*.db-wal' \
      root@203.0.113.1:/data/server-runtime /data/
rsync -avP --delete -e "ssh -o ServerAliveInterval=15 -o ServerAliveCountMax=3" ...（同上）
sh start.sh pp 20260923-ben
sh start.sh tada 20260923-ben
sh start.sh api 20260923-ben

发版顺序是：停容器 → 从打包机 03 同步 /data/server-runtime → 再启动容器。 这个窗口实测能超过 50 分钟（大 DB 传输慢），远超原来 6 分钟的宽限， 所以 9/23 那三条 02 的报警（16:48 / 16:50）其实是发版窗口，不是故障。

2. 机制

在该后端上检测有没有发版/同步进程：rsync / start.sh / stop.sh / build.sh。 检测方式和 docker 列表走同一次 SSH，不增加采集开销：

echo "META|$(pgrep -cf '[r]sync|[s]tart.sh|[s]top.sh|[b]uild.sh' 2>/dev/null || true)"; \
docker inspect --format '{{.Name}}|{{.State.Status}}|{{.RestartCount}}|{{.Config.Image}}' $(docker ps -aq)

（[r]sync 这种方括号写法是为了让 pgrep 不匹配到 pgrep 自己那条命令行）
META>0 → 判定为发版窗口：
   · 容器缺失只记日志，不报警，也不累计缺失次数（misses 归零，窗口结束重新数）
   · 状态里标记 window=true
META=0 → 恢复原来的「连续 3 次（约 6 分钟）才报警」逻辑

设计要点：静默能力会随着发版进程结束自动失效——开发万一同步完忘了启容器， 6 分钟内照样会报出来，不会因为“静默”把真故障吞掉。

防卡死上限：发版进程就算一直不退出，最多静默 RELEASE_WINDOW_MAX_SAMPLES 次采样 （默认 30 次 ≈ 60 分钟），超限后按正常缺失逻辑报警（再约 6 分钟发警）。

开关：DBQP_CONTAINER_RELEASE_WINDOW=0 可整体关闭该特性； DBQP_CONTAINER_RELEASE_WINDOW_MAX=N 改上限。

三、另外两处顺手修掉的问题

① 汇总行不再含糊
   老版本：容器在宽限期、甚至已经报过警了，也照样打印 “OK … 全部正常”，
           看起来像“一切正常”，容易误解（本次排查时就被这条误导过）。
   新版本：[dry-run] 期望容器 20 个 | alerts=0 recovers=0 | 发布窗口暂缺=0 | 缺失中=1
           OK 2026-09-24 14:41:33 期望容器 20 个 ｜ 缺失中 1 个（宽限或已报警）

② 状态文件清理补齐
   上一版的清理只在「遍历到的后端」里做，03 退出监控后它的键永远不会被清。
   现在额外做一次全局清理：非 backend: 前缀且不属于在监控 IP 的键、
   以及已退出监控机器的 backend:<ip> 键，全部删掉。

四、验证（本次实测）

① 语法：python3 -m py_compile 通过。
② 部署一致性：本地与入口机 md5 相同 a70fcc36fd3b031ffd79e91008bc5b1d。
③ dry-run（入口机，真实数据）：
   [dry-run] 期望容器 20 个 | alerts=0 recovers=0 | 发布窗口暂缺=0 | 缺失中=1
④ 真实跑一次（入口机）：
   OK 2026-09-24 14:41:33 期望容器 20 个 ｜ 缺失中 1 个（宽限或已报警）
   （随后 14:42:01 的定时任务也已经是新版：同上格式，确认 cron 生效）
⑤ 远端命令在真机（01）验证过输出格式：先打 META 行，再打 docker inspect 行。
⑥ 逻辑回归（本地假数据，不动线上）：
   · 基线 20 个期望容器；
   · 无发版进程时容器缺失 → 第 1、2 次静默（打「缺失中」），第 3 次报警；
   · 有 rsync 进程时同样的缺失 → 4 次采样全程「发布窗口中暂缺 N 个（不报警）」；
   · 发版进程结束后容器仍缺 → 重新计数，第 3 次报警；
   · 发版进程卡死且超过上限 → 按正常逻辑报警；
   · 预置 03 的旧状态键 + dbqp-*-release-* 旧键 → 跑一次后全部被清理，状态键 22 个（2 后端 + 20 容器）。

五、⚠️ 顺带查出的真问题：02 的 TADA 主服务（9096）现在没在跑

这一条不是误报，是本次排查时确认的真实缺口。

1. 事实

02（203.0.113.1）docker ps -a 全量里只有 game-service-tada-ws-prod（8765），
没有任何名字的 TADA 主服务容器（不是「换名字了」——全量列过了，就是没有）；
02 上 9096 端口没有任何进程监听（ss -ltnp 只有 22/8765/9018/9019/9020/9090/9091/9098/9099）。
02 本地 start.sh 的 ALL_VENDORS 是有 tada 的：
  ALL_VENDORS="api pg tada tada_ws ppk pp playson panda g759"
02 上 tada/api/pp 三个容器是同一次发版（20260923-ben）起的，
  但 api-prod、pp-prod 现在是 Up（21 小时），tada-prod 却不在 —— 属于「同步完漏启 / 启了又没了」。

2. 用户影响（有日志证据）

入口机 nginx error log（2026-09-24 06:40~06:41 UTC，真实客户端 IP）：

connect() failed (111: Connection refused) while connecting to upstream,
  request: "GET /lt/ HTTP/2.0", upstream: "http://203.0.113.1:9096/lt/",
  host: "tada-games.xqv9m8.icu"
（每 12 秒一条，反复出现）

线上表现：nginx 的 proxy_next_upstream 会把失败的请求重试到 01，
          所以用户大多还能打开（实测 tada-games 域名 health 连续 10 次 200），
          但每次命中 02 都会多一次失败重试（增加延迟），并偶发 500（access log 里有 13 条 500）。
TADA 冗余：02 上等于没有 TADA 后端，01 单点扛 TADA。

3. 建议处理（未执行，等确认）

在 02 上执行（版本号照 01 上 tada 容器正在用的 tag，当前 01/02 都是 20260923-ben）：
    cd /data/server-runtime
    sh start.sh tada 20260923-ben
    # 起来后确认：docker ps | grep tada、ss -ltnp | grep 9096、curl 本机 9096
再盯一会儿 nginx error log，确认 203.0.113.1:9096 的 refused 不再出现。

4. 后续（2026-09-24 17:15 更新）

· 用户已手动执行 sh start.sh tada 20260923-ben，02 的 TADA（9096）已恢复。
· 消失原因已查明：不是故障也不是自动任务，是有人在 02 上一个从 9/18 起就一直挂着的
  常驻 SSH 会话（工作目录 /data/server-runtime）里手动执行了 sh stop.sh tada，
  而 stop.sh 是 stop + rm，之后没执行对应的 start.sh。
  完整证据链（含 journald 逐秒日志、常驻会话 PID/对端 IP）见：
  docker/doc/2026-09-24-1715-【问题排查】02的TADA容器消失原因定位-常驻会话手动stop记录.md

六、回滚方法

监控脚本（入口机 34.151.249.53）：
  # 回到「还在监控 03、没有发版窗口静默」的版本
  cp -a /opt/pgserver/docker/scripts/container_health_monitor.py.bak-20260924-144110-before-03-out-and-release-window \
        /opt/pgserver/docker/scripts/container_health_monitor.py

监控状态文件（入口机）：
  /var/tmp/dbqp-container-health.json.bak-20260924-144110
  （另可用 /var/tmp/dbqp-container-health.json.bak-20260919-092950 回到更早状态）

只想临时关掉「发版窗口静默」而不动脚本：
  在入口机 crontab 那一行前面加 DBQP_CONTAINER_RELEASE_WINDOW=0（或用环境变量文件）。

七、明确没做的事

· 没有启停任何业务容器（包括没有替开发去启 02 的 tada）。
· 没有改 nginx（01+02 双活、03 down 的现状保持）。
· 没有动 03 上的打包相关东西（jumpserver / registry / 临时容器都没碰）。
· 没有停 03 的 beszel-agent：那是宿主机监控（CPU/内存/磁盘），与本次容器报警无关；
  如果希望 03 连宿主机监控也一起摘掉，需要单独确认（本次未做）。
· 没有发飞机群通知。

九、2026-09-24 后续迭代：告警样式统一（项目标识 + @提及 + 双时区 + 测试通道）

用户要求：容器缺失/恢复这类通知也要 @ 到人，并且巴西要带项目标签，样式对齐「结果集权限告警」。

改造后的样式：
  【DBQP 巴西项目｜容器监控｜报警】@运维 @Ben_Bird @benb6879
  时间：北京 2026-09-24 17:05:12 ｜ 巴西圣保罗 2026-09-24 06:05:12

  【DBQP 巴西项目｜容器监控｜恢复】@运维 @Ben_Bird @benb6879
  时间：北京 … ｜ 巴西圣保罗 …
  - 容器恢复：game-service-tada-prod（203.0.113.1 / 02）image=…

改动内容：
1) MENTIONS = @运维 @Ben_Bird @benb6879（可用环境变量 DBQP_MONITOR_MENTIONS 覆盖）
   —— @Ben_Bird / @benb6879 是真实 Telegram 用户名会被提醒；@运维 非法用户名只作称呼。
2) PROJECT_NAME（默认「巴西项目」，可用环境变量覆盖）拼进标题，
   与结果集权限告警的【DBQP <项目>｜…】保持同一套写法。
3) 时间改成「北京 + 巴西圣保罗」双时区（用 zoneinfo，取不到时回退 +8/-3 固定偏移），
   日志里仍沿用原来的本地时间戳，避免影响按日志排查的习惯。
4) 新增 `--test-notify`：只往群里发一条【报警·测试】+一条【恢复·测试】用于验证
   提及/时间/标题样式，**不采集容器状态、不读写状态文件**，不用再为了验证去弄坏线上。
5) send() 现在会把 Telegram 返回的 {"ok":true,…} 打一行到日志，方便事后确认送达情况
   （之前只有异常才可见）。

  · 入口机部署后 md5 一致 1283ccd349113d24d3e149f94d918adc；
  · --dry-run 仍为「期望容器 20 个 | alerts=0」；
  · --test-notify 两条都返回 ok:true（message_id 7433 报警·测试 / 7434 恢复·测试，
    chat = 监控报警群 -5203304347）；
