三、根因（两条）

3.1 根因 A：攻击绕过网关直连宝塔源站，源站没有任何限流

两个入口最终都汇聚到宝塔 /api（proxy_pass http://203.0.113.1:8088 → 线上后端）：

| 链路 | 路径 | 限流情况 |

| --- | --- | --- |

| A | 公网 → 网关 203.0.113.1 → 宝塔 → 后端 | 网关已有 limit_req zone=api_perip rate=50r/s，实测有效（该 IP 被压到 ≈55 次/秒） |

| B | 公网 → 宝塔 203.0.113.1（www.youdianse.com 源站）→ 后端 | 无限流、无拦截 ← 被打穿 |

证据：宝塔 new.youdianse.com.log 采样 100,000 条中，203.0.113.1 直连源站 37,149 条， 路径 POST /api/v1/Login/account 占 63,738 条（64%）。

3.2 根因 B：CC 守卫看不到 /api 刷量，也覆盖不到宝塔

守卫日志（ben-bot cc_guard/state/guard.log）长期 api_flood=0/0，攻击期间完全没触发封禁。两个代码缺陷：

  1. 多跳 XFF 被丢弃：网关日志的 X-Forwarded-For 是多跳字符串 （如 203.0.113.1, 203.0.113.1），api_flood_suspects() 把整串交给 is_ip_like() 判定 → 返回 False → 整行被丢掉，等于永远看不到刷量源。
  2. 只守网关：youdianse_cc_guard.py 只采网关日志、只封网关 iptables 与网关 nginx 清单， 对「直连宝塔源站」的链路完全没有感知（因此也不会封）。

七、补充处置（2026-09-30 05:00 北京时间｜守卫误封自有 IP）

7.1 事件：守卫把自己的网关 IP 当成攻击源

拦截生效后守卫发出告警：XFF 封禁样本：203.0.113.1(1735)。

203.0.113.1 是 18game H5/PC 统一网关本身（前端容器所在服务器），被自己的守卫封了。

原因：H5/PC 容器的 SSR 服务端渲染会通过公网域名回打接口，出口就是网关自己的公网 IP， 因此网关日志里 XFF 第一跳即 203.0.113.1；单页渲染会连打多个 /api， 采样窗口（6 万行）内累计 1735 次，超过 900 次阈值 → 被判定为刷量源。

影响：我们自己的 SSR/接口请求会被打成 444。

7.2 修复：自有 IP 全量清点 + 永不封禁

清点来源：devops/ai_context/servers.yml、ops/production/servers.json、workbench/MACHINE_ACCESS_MATRIX.md。 共 14 个自有 IP（另含监控出口段 2a02:4780::/32）：

| 类别 | IP |

| --- | --- |

| 线上环境 | 203.0.113.1（网关）、203.0.113.1（宝塔源站）、203.0.113.1（后端）、203.0.113.1（H5） |

| 线上前置 | 203.0.113.1 / 203.0.113.1 / 203.0.113.1、203.0.113.1 |

| 测试环境 | 203.0.113.1、203.0.113.1、203.0.113.1 |

| 运维工具机 | 203.0.113.1、203.0.113.1、203.0.113.1 |

代码改动：

  • 新增 SELF_IPS 常量 + SELF_IP_PREFIXES + is_self_ip()
  • 在「识别（suspect 过滤）、告警、封禁（iptables/网关清单/宝塔清单）、清单生成」四个环节全部排除自有 IP
  • load_state() 载入时自动剔除自有 IP（历史误封项自动清理）
  • 新增可维护文件 state/self_ips.txt（一行一个 IP，支持 # 注释；按 mtime 热加载） → 后续新增自有 IP 只需追加该文件，无需改代码，守卫每分钟生效

清理结果：状态文件剔除 203.0.113.1，重写网关与宝塔两侧清单，核验自有 IP 零残留。

7.3 连带发现：第二个误封风险（已改为不按 IP 封）

修复自身 IP 后，守卫继续识别出 8 个刷登录来源： 203.0.113.1、203.0.113.1、203.0.113.1、203.0.113.1、203.0.113.1、203.0.113.1、203.0.113.1。

取证：这些 IP 只打 /api/v1/Login/account 一个接口（采样窗口内累计 6289 次，无其它接口）， UA 固定 Mozilla/5.0，单 IP 峰值 861 次/分钟（≈14r/s）→ 属刷量/凭证填充脚本。

但它们属菲律宾移动运营商网段（大量使用 CGNAT，一个公网 IP 背后是很多真实用户）， 按 IP 封会误伤真实用户。处置：

  • 立即解封这 7 个 IP
  • 宝塔源站侧改为 只告警不自动封 IP：新增开关 CC_BAOTA_AUTO_BLOCK（默认 0）， 告警文案标注 baota_api_flood=N(仅告警)
  • 改用不误伤用户的压制手段：登录接口严格限流（见 7.4）

7.4 登录接口严格限流（替代按 IP 封）

| 位置 | 配置 | 说明 |

| --- | --- | --- |

| 宝塔源站 | location ~* ^/api/v1/login/account → limit_req zone=yds_login_perip rate=2r/s burst=6 nodelay | 新增 zone 见 00-abuse-guard-http.conf；location 必须声明在通用 /api 正则之前 |

| 线上后端 | login_perip 30r/s → 5r/s（burst 60 → 15） | 兜底 |

依据：刷量脚本单 IP ≈14r/s，真实用户登录仅个位数请求/分钟。

实测验证：单次登录 HTTP 200 / 0.23s；连发 20 次出现 429（限流生效）； H5 页面 200、PC 页面 200、网关 API 200，真实路径未被误拦。

8.2 登录接口限流放宽（弱网重试）

用户反馈：部分用户网络较差，登录会多次重试。原 2r/s + burst 6 偏紧，放宽为：

| 位置 | 原值 | 现值 |

| --- | --- | --- |

| 宝塔源站 yds_login_perip | 2r/s + burst 6 | 5r/s + burst 20 |

| 线上后端 login_perip | 5r/s + burst 15 | 10r/s + burst 30 |

依据与实测：

  • 弱网重试：串行连发 25 次全部 200（正常重试完全够用）
  • 防刷量：100 并发时 23 个 200 / 77 个 429（刷量脚本实测 ≈14r/s，仍被有效压制）
  • 真实用户：登录 200 / H5 页面 200 / 网关 API 200

安全边界：解析结果中属于共享 CDN 边缘网段的 IP 被主动跳过（Cloudflare 104.16-27./172.64-71. 等）。 原因：这类 IP 是全互联网共用的边缘节点，加白等于给任意人开后门绕过限流。 走 Cloudflare 的游戏（Mili Ai / TGAI Ai）其真实来源在 X-Forwarded-For 第一跳，同样能被日志记录与识别。

ELB IP 会变化 → 在 ben-bot 上配置 */30 定时任务自动重新解析并下发（生成器见下）。

9.2 三方游戏登录调用专用日志

宝塔源站登录 location 增加独立 access_log：

access_log /www/wwwlogs/youdianse-3rd-login.log youdianse_3rd;

日志格式（youdianse_3rd）含游戏归属列：

时间 client=<真实客户端IP> xff="<XFF>" third=<是否三方白名单> game="<游戏名>" "请求" 状态 字节 ua="..." ref="..." rt=...

记录全部登录接口调用（不只三方）：因为走 CDN 的三方其来源 IP 不在白名单里，只记白名单会漏。 分析脚本：/usr/local/bin/youdianse-3rd-login-report.py（按游戏/按 IP/按分钟/状态码/UA 聚合）。

首次实测（2026-09-30 04:51~04:55，样本 21,403 条）：

· 三方游戏登录调用：0 条（全部 game='-'）→ 当时打登录接口的不是三方游戏
· 登录压力来源：UA 全部为 Mozilla/5.0 的脚本刷量（203.0.113.1 2094 次、203.0.113.1 2011 次 …）
· 限流效果：200 → 13,251 条 / 429 → 8,107 条（约 38% 被限流拦下）
· 峰值：6,145 次/分钟

9.3 日志轮转 + S3 归档（防占盘）

| 项 | 配置 |

| --- | --- |

| 轮转 | 宝塔 /etc/logrotate.d/youdianse-baota-wwwlogs：size 200M / rotate 7 / compress / copytruncate（systemd logrotate.timer 每日触发） |

| 归档 | ben-bot devops/scripts/youdianse-baota-log-s3-archive.sh：把 /www/wwwlogs 超过 24 小时的 .gz 上传 s3://youdianse-prod-gateway-logs/baota/ 后删除本地 |

| 定时 | ubuntu crontab 17 */6 * * *（每 6 小时） |

首次执行结果：13 个归档文件全部上传 S3（http=200）并删除本地，S3 已核对存在 （baota/h5.youdianse-main.xyz.log-20260701-*.gz … baota/new.youdianse.com.log-20260929-*.gz）。

说明：宝塔日志目录 /www/wwwlogs 实际挂载在 196G 数据盘 /data（非根盘）， 本次归档 + 轮转策略可防止长期堆积；新增的 youdianse-3rd-login.log 同样被上述轮转与归档覆盖。

9.4 本次踩到的坑（重要）

nginx 不允许 reload 时修改 limit_req_zone 的 key：

[emerg] limit_req "yds_api_perip" uses the "$yds_tp_api_key" key
        while previously it used the "$yds_client_ip" key

后果：reload 静默失败（nginx -t 通过、-s reload 也返回成功，但 master 拒绝加载）， 线上继续跑旧配置 → 表现为「配置改了但日志/白名单没生效」。

处置：改 key 时必须换 zone 名（本次改为 yds_api_perip_v2 / yds_login_perip_v2 / login_perip_v2）， 避免重启 nginx 造成入口中断。后续如需回收旧 zone，可在计划内重启一次。

10.2 为什么不能按 IP 封

  • 来源是 2,118 个 PH 住宅 IP，且 PH 是平台主要用户地区（Converge/PLDT/Globe 大量 CGNAT） → 按 IP 封必然误伤真实玩家，且攻击者换 IP 即可绕过
  • 因此维持「源站刷量仅告警不自动封 IP」；本次 11 个 IP 仅作观察记录

10.3 处置：机器人 UA 指纹拦截

规则：/api/v1/Login/account 且 UA 精确等于 Mozilla/5.0 且非三方白名单 → 444

map $http_user_agent $yds_login_bot_ua { default 0; "~^Mozilla/5\.0$" 1; }
location ~* ^/api/v1/login/account {
  set $yds_login_block 0;
  if ($yds_login_bot_ua) { set $yds_login_block 1; }
  if ($yds_is_3rd_party)  { set $yds_login_block 0; }   # 三方游戏回调豁免
  if ($yds_login_block)   { return 444; }
  ...
}

影响面测算（基于 33,734 条真实样本）：非该 UA 仅 ~68 条（Dart/完整浏览器串/python-requests），零误伤真实端。

十一、被刷接口改为「UA 真实性」判断（2026-09-30 09:00 北京时间）

11.1 思路

不针对某个具体 UA 打补丁，而是判断请求的 UA 是否像完整的真实客户端： 像 → 放行；不像 → 444。攻击者换 UA 字符串也没用（凑不出真实客户端该有的形态）。

11.2 判定规则（$yds_ua_real：1=可信，0=可疑）

1) 完整浏览器 UA：必须同时具备「(平台/系统信息括号)」+「引擎/浏览器标识」
   ~*^Mozilla/5\.0[ ]+\([^)]+\)[ ].*(AppleWebKit|Gecko|Presto|Trident)
   ~*^Mozilla/5\.0[ ]+\([^)]+\)[ ].*(Chrome|Chromium|CriOS|Firefox|FxiOS|Safari|Edg|OPR|YaBrowser|MiuiBrowser|HuaweiBrowser|Quark|UCBrowser)
2) 原生 App / SDK 固定前缀：Dart（Flutter）、okhttp、Dalvik、UnityPlayer、BestHTTP、UnityWebRequest、libwww-perl
3) 明确判为可疑：curl、Wget、python-requests、Go-http-client、Java、Scrapy、极简串 Mozilla/5.0
4) 例外：三方游戏白名单命中不做 UA 拦截

11.3 操作步骤（可回滚）

| 序 | 位置 | 动作 |

| --- | --- | --- |

| 1 | 宝塔 00-abuse-guard-http.conf（http 级） | 新增 map $http_user_agent $yds_ua_real |

| 2 | 宝塔 .../extension/new.youdianse.com/00-youdianse-fixed-reverse-proxy.conf（server 级） | 登录 location 内加三段 if（UA 不可信→444，三方白名单豁免）；文件带 immutable，需 chattr -i → 写入 → chattr +i 复原（已备份 .bak.uacheck-*） |

| 3 | 宝塔 | nginx -t → nginx -s reload |

| 4 | 后端 nginx/main.conf | 加同一份 $yds_ua_real map |

| 5 | 后端 nginx/default.conf | 登录 location 加同样三段 if |

| 6 | 后端 | 临时容器校验 → 重启 nginx 容器生效 |

11.4 环境坑：单文件 bind mount 被 inode 替换后失联

后端 nginx 的 main.conf / default.conf 是单文件 bind mount。 用 install / mv 覆盖会生成新 inode，容器仍指向「已删除的旧 inode」：

现象：宿主机文件是新内容，容器内 grep 仍是旧配置；nginx -t 还通过（因为它测的是容器内旧文件）
处置：容器内生效必须原地写入，或重启容器重新绑定挂载（本次用重启）

→ 后续所有涉及后端 nginx 配置的变更都必须注意这一点。

| 状态分布 | 444（拦）= 9,096 / 200（成功）= 9 / 404 = 22 |

| 被拦 UA 构成 | Mozilla/5.0 9,047 条、python-requests 69 条 |

| 流量 | 04:58~04:59 峰值 7,000~8,000 次/分钟 → 05:03 降至 9 次/分钟 |

  1. UA 判断只是提高门槛，攻击者复制真实浏览器 UA 仍可绕过（日志已见 3 条伪造的老 iOS UA） → 建议第 2 道闸：登录接口全局 QPS 上限（如全局 200 次/秒）兜底
  2. 根治：登录加图形验证码 / 短信二次校验（产品侧）
