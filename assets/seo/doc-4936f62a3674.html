一、结论

本次完成巴西和香港全量发布，并把结果集安全同步规则固化进发布台：

  • 巴西四台全部升级到 20261105-ben，各 9 个容器运行；
  • 香港两台全部升级到 20261105-ben，各 10 个容器运行；
  • 每次向业务节点同步结果集前，必须先停止该节点全部业务容器并确认 game-service* 运行数为 0；

  • 巴西/香港一键发布成功后，由服务端自动发送指定测试通知；

五、香港发布与门禁故障

5.1 第一次失败

用户首次发起香港任务 39134113409d4ca5（15:36:22）。stop.sh all 停止 9 个容器后，game-service-vendor_a-prod 仍在运行；新门禁在 15:42:36 判定 running=1 并中止，结果集未同步。

5.2 第二次失败

03 上香港模板补入 vendor_a 后，第二次任务 c7fcaf047a7b4fa4 在 15:46:17 发起。

该任务停止 9 个旧列表容器后，准备同步结果集前的新门禁发现：

业务容器未全部停止（running=1）
game-service-vendor_a-prod Up 43 hours
❌ 禁止同步结果集

任务在 15:46:33–15:47:58 以 exit=1 中止，结果集仍未同步。

根因：

03 配置模板已补 vendor_a，但香港 01/02 本机 runtime 的 start.sh / stop.sh
仍是旧文件，ALL_VENDORS 漏了 vendor_a；
发布页 VENDORS.hk 也漏了 vendor_a。
vendor_a HTTP 9096 自 2026-11-03 已在线启用。

5.3 修复

香港 03 配置源、香港 01、香港 02 三处 start.sh / stop.sh 均加入 vendor_a；
发布页 VENDORS.hk 加入 vendor_a；
香港业务容器总数由 9 修正为 10。

HK01 恢复后 10/10 running，重启数 0，然后重跑。

六、发布台新增规则

6.1 一键准备同步 03 结果集

一键准备顺序改为：

拉 ben 分支
→ 校验 share.so / version-bx / version-zh MD5
→ sh sync_results.sh all
→ 校验 7 个结果集目录非空
→ 4 路动态补位打包
→ 域名和 runtime 合并

结果集同步输出：

RESULT_SET_VENDOR_OK=<vendor> files=<count>
RESULT_SET_SYNC_OK files=<total>

6.2 全停硬门禁

每个业务节点在 rsync 前执行：

stop.sh all
统计 game-service* 运行数
存在任一运行容器则 exit 1
运行数为 0 才输出 BUSINESS_CONTAINERS_STOPPED=0

该门禁首次运行就阻止了香港热覆盖，证明有效。

6.3 成功通知改为服务端

巴西/香港发布成功后，由 FastAPI 任务结束逻辑发群，不再依赖浏览器保持打开。 前端不再重复发送成功通知。

状态：running / healthy

七、后续优化建议

  1. 将 rsync --info=progress2 改为结构化输出，只展示 xfr#、实际传输字节、 当前文件和剩余变化文件，避免把目录总大小误读为本次要传的大小。
  2. 镜像拉取仍是单节点发布的主要耗时来源；后续可评估香港本地 registry mirror 或镜像预热，但不得影响结果集安全门禁。
  3. 香港 vendor_a 首启偶发 Sanic worker 30 秒确认超时，可评估为该服务单独设置 SANIC_WORKER_ACK_TIMEOUT=120，避免首启无意义重启。
  4. 对“本次变化文件清单 + 总字节”增加自动摘要，便于 DBA/开发确认是否只更新 预期文件。
  5. 一键准备的结果集拉取耗时和 sync_results.sh all 输出较长，后续可保存单独 日志文件并从页面提供摘要/完整日志入口。
