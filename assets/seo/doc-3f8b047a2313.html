原理与可行性调研

原理与可行性调研。本文属于工具与脚本 / 打孔业务，这份文档记录"为什么最后是现在这个方案"。所有结论都是在目标机器上实测出来的， 不是查资料抄的。环境： 个人 LINE 账号 没有任何官方读取 / 发送接口 。想自动化只有两条路： 解密本地数据库 —— 一次性成本极高，见第 4 节

这份文档记录"为什么最后是现在这个方案"。所有结论都是在目标机器上实测出来的， 不是查资料抄的。环境：

macOS            26.6.2 (25G83)
LINE for Mac     26.5.0 (Qt/QML)
Python           3.11.15 (Homebrew)
机器时区         Asia/Manila

1. 先说结论

个人 LINE 账号没有任何官方读取 / 发送接口。想自动化只有两条路：

  1. 驱动桌面客户端 —— 本方案采用
  2. 解密本地数据库 —— 一次性成本极高，见第 4 节

而"驱动桌面客户端"里，读取部分必须靠截图 + OCR，因为 LINE 是 Qt/QML， 辅助功能树里没有文字。

2. 逐个排除的通道

2.1 LINE Messaging API

Bot API 的模型是：你创建一个 Official Account（官方账号），用户加你为好友或把你 拉进群。它不能以你的个人身份登录，也不能读你个人账号的聊天记录。 想让它往你那个「打卡」群里发消息，前提是那个群本身挂了官方账号 —— 不成立。

2.2 LINE Notify

实测 curl https://notify-bot.line.me/ 返回 HTTP 200，但页面正文是停服公告：

…with regret, we will end this service on March 31, 2025.

已死。

2.3 LINE Login / LIFF

是给第三方网站做"用 LINE 登录"和"在 LINE 里打开网页"的，只能拿到用户 ID、 头像、昵称（还要用户授权），拿不到聊天内容。

2.4 AppleScript / Apple Events

$ /usr/libexec/PlistBuddy -c "Print :NSAppleScriptEnabled" \
    /Applications/LINE.app/Contents/Info.plist
Print: Entry, ":NSAppleScriptEnabled", Does Not Exist

$ /usr/libexec/PlistBuddy -c "Print :OSAScriptingDefinition" \
    /Applications/LINE.app/Contents/Info.plist
Print: Entry, ":OSAScriptingDefinition", Does Not Exist

没有脚本字典，tell application "LINE" 除了 activate 什么都做不了。

2.5 URL scheme

Info.plist 里注册了 line 和 lineb 两个 scheme。它能做的是"打开某个页面 / 拉起分享面板"，不能读内容，也不能指定群发消息。

2.6 本地 API / IPC

~/Library/Group Containers/VUTU7AKEUR.jp.naver.line.mac/LINEPB_IPC 看着像接口目录， 实际是个 ASCII 文本文件（里面是几个 base64 token），不是目录。

lsof -p <LINE pid> 显示 LINE 只开了几个 UNIX socket（Qt 单实例锁、distnoted 连接）， 没有监听任何 TCP 端口。没有可以蹭的本地 API。

2.7 通知中心数据库

LINE 的消息通知会落到 ~/Library/Group Containers/group.com.apple.usernoted/db2/db。 实测该库里 LINE（app_id=95）的 record 表是空的 —— 这台机器上没留下通知记录， 而且就算有，也只覆盖"最近收到过通知的会话"，不是全量列表。

3. 辅助功能 API：能拿结构，拿不到文字

这是最反直觉的一点，值得单独说。

AXWindows 属性返回空数组（LINE 的主窗口不在里面），但 AXMainWindow 有值。 遍历之后能拿到完整的控件结构：

[AXWindow] LINE
  [AXSplitGroup]
    [AXSplitGroup]
      [AXTextArea]        ← 消息输入框
      [AXList]            ← 左侧聊天列表（rows=2）
    [AXList]              ← 右侧消息列表（rows=11）
    [AXTextField]         ← 搜索框

每一行的矩形是精确的：

AXList frame=(431.0, 352.0, 302.0, 377.0) rows=2
    row 0 (431.0, 352.0, 302.0, 71.0)
    row 1 (431.0, 423.0, 302.0, 71.0)

但把某一行的所有属性打出来，文字字段全是空：

AXRow         AXTitle = ""   AXDescription = ""   AXValue = (不存在)
AXStaticText  AXTitle = ""   AXDescription = ""   AXValue = (不存在)

原因是 LINE 用 Qt Quick/QML 渲染，这些列表项是自定义 QML 组件， 没有设置 Accessible.name，所以 Qt 只生成了"占位"的辅助功能节点。

结论：AX 用来拿位置，不用来拿文字。

4. 本地数据库

~/Library/Containers/jp.naver.line.mac/Data/Library/Containers/
    jp.naver.line/Data/db/
├── qw7fdffd1e7f4d5a5869cbb3b8dda2e3.edb        主库（聊天、消息）
├── qw7fdffd1e7f4d5a5869cbb3b8dda2e3.edb-wal    3MB 的 WAL
├── album_*.edb / keep_*.edb / chatStats_*.edb  相册 / Keep / 统计
└── f59c00309acd23908b1254ee081d8258            ← 这个**是**明文 SQLite

那唯一的明文 SQLite 里只有贴纸元数据：

CREATE TABLE _meta_info(m_n varchar(50) PRIMARY KEY, ...);
CREATE TABLE _sticker_metadata(_packageId INTEGER, _metadata TEXT, ...);

其余 .edb 的头部是 76 32 f3 7a 6d 4a a4 9a（"v2" + 4 字节）， 每个文件的第 5–8 字节都不同，说明是逐文件的密钥 / IV。 WAL 里的 strings 输出全是随机字节。

这是 LINE 自己改造过的加密 SQLite（二进制里有 PRAGMA %Q.page_size 之类的定制串）。 要读它得逆向它的密钥派生与页加密算法。

评估： 收益是"100% 精确、结构化、含全部历史"，成本是一次性的逆向工作， 而且 LINE 每次大版本更新都可能改算法。作为长期方案值得考虑，但不适合作为第一步。

5. 读取：ScreenCaptureKit 是关键

screencapture -l <windowID> 也能抓单个窗口，但有个致命问题： 窗口被遮挡、或应用不在前台时，经常抓到空白图（拿不到 GPU 表面）。

ScreenCaptureKit（macOS 12.3+）的 SCContentFilter(desktopIndependentWindow:) 配合 SCScreenshotManager.captureImage，可以稳定拿到被遮挡窗口的真实内容， 而且不需要激活它。

实测对比（前台应用是 Telegram，LINE 窗口被完全盖住）：

方式 结果 前台是否变化
screencapture -l 有时是空白图 不变
ScreenCaptureKit ✅ 拿到完整内容（能 OCR 出「打卡（5）」「Bob 上班打卡 上午8:30」） 不变

PyObjC 里两个坑：

  • 必须先 NSApplication.sharedApplication()，否则直接断言失败： Assertion failed: (did_initialize), function CGS_REQUIRE_INIT
  • 完成回调要走 RunLoop 才会被调度，不能直接 Event.wait() 干等

本项目里对应 linepunch/macos_shot.py。

6. 文字识别：Vision

VNRecognizeTextRequest，recognitionLevel = accurate， 语言设成 ["zh-Hans", "en-US"]，关掉 usesLanguageCorrection（会让中文乱猜）。

两个提高准确率的做法：

  1. 先裁剪再识别。 用 AX 拿到的行矩形把图裁成一条，再放大 3 倍送进 OCR。 一张图里只有一行字，错误率显著下降。
  2. 按视觉行聚类排序。 直接按 y 排序，在"一行里混着消息预览和时间戳"的布局上会错位， 要先按 y 聚类成行、行内再按 x 排。

实测（对「打卡」群）：

会话标题   打卡（5） 4心 QC目： 5 @Aken @maggie        → 包含"打卡" ✅
最近消息   Bob | 上班打卡 | 上午 8:30
           @Aken @maggie | 上班 下 | 上午 8:04
           cw-阿果（资金往来当面） | 泰铢换 人民币 5.08 泰铢换 | U 33.5 | 下午 1:06

7. 写入：CGEvent 必须投给进程，不能投给事件流

7.0 最重要的一条（踩了很久才发现）

把事件投到 kCGHIDEventTap / kCGSessionEventTap，LINE 收不到：

kCGHIDEventTap   + HID 事件源      → 输入框 AXValue 仍是 ''   ❌
kCGSessionEventTap + 合并会话源     → 输入框 AXValue 仍是 ''   ❌
CGEventPostToPid(pid, event)       → 输入框 AXValue 变成 '下班打卡' ✅

早期的实现是"先把 LINE 切到前台，再往 tap 投事件"，那时候能work，所以一直没暴露。 直到 LINE 重启过一次之后彻底不生效，才定位到根因。

改用 CGEventPostToPid 之后，键盘输入不再需要焦点： LINE 全程在后台，你正在用的程序一直是最前台，鼠标也不会被挪走。

7.0.1 但鼠标不能照搬 —— Qt 列表行有它自己的脾气

同一条路用在鼠标上就失效了。实测三种"点开某个聊天"的方式：

方式 结果
CGEventPostToPid 投鼠标事件 ❌ 标题不变
AXPress 按在行 / 单元格 / 静态文本上 ❌ 标题不变
标准事件流点击（CGEventPost 到 kCGHIDEventTap） ✅ 标题变成目标会话

所以最终的分工是：

动作 方式 抢焦点 动鼠标
读窗口 / 列表 / 标题 / 消息 ScreenCaptureKit + Vision OCR ❌ ❌
输入文字、按回车 CGEventPostToPid ❌ ❌
点列表行打开会话 标准事件流点击 ❌ ✅（用完放回）

7.0.2 顺带发现：macOS 会拒绝后台应用抢焦点

为了点列表行，代码里调用了 NSRunningApplication.activate()。虽然它返回 True， 但 20ms 频率采样 1.3 秒的结果是：

调用 activate(LINE) -> True
之后前台: Code        ← 没有变
20ms 采样到的前台序列: Code (1280 ms)

系统实际拒绝了这次激活（现代 macOS 对抢焦点有拦截）。点击之所以还能送达 LINE 窗口，是靠"穿透点击" —— 事件带绝对坐标，直接落到那个坐标上的窗口。

结论：连"点列表行"这一步，你的前台窗口也不会被切走，只是鼠标会跳一下。

实测（从"目标群未打开"开始跑完整流程）：

运行前  前台=Code  光标=(1091.83, 452.06)
运行后  前台=Code  光标=(1091.83, 452.06)

7.1 中文输入

不需要切输入法。用 CGEventKeyboardSetUnicodeString 把 UTF-16 直接塞进键盘事件：

event = Quartz.CGEventCreateKeyboardEvent(source, 0, True)
Quartz.CGEventKeyboardSetUnicodeString(event, len(ch), ch)
Quartz.CGEventPost(Quartz.kCGHIDEventTap, event)

注意 PyObjC 里这个函数只接受 Python 字符串， 传 ctypes 缓冲区会报 buffer not compatible。

7.2 聚焦输入框

两种手段要组合用，缺一不可：

AXUIElementSetAttributeValue(input_el, kAXFocusedAttribute, True)  # 辅助功能置焦点
CGEventPost(...)                                                    # 再补一次鼠标点击

只做前者时有些 Qt 版本不认；只做后者时，窗口被遮挡会点到别的窗口上。

7.3 一个真实的坑

早期用 Swift 版本测试时出现过"点击生效了但按键没打进去"。 事后定位到原因：点击确实发生了（LINE 的搜索框拿到了焦点，AX 里 AXFocused=1）， 但随后 LINE 又被别的窗口盖住了，键盘事件就发到别的应用去了。

教训：激活之后不要假设焦点还在。所以现在每次输入完都会回读输入框的 AXValue 做二次确认，不一致就判定失败，而不是盲目按回车。

8. 窗口识别

LINE 一个进程里有十来个窗口（LINE.AudioService、各种 VideoPreviewService、 多个 1440x30 的辅助条、一个在 -10000,10899 的离屏窗口）。 它们的标题都是空的，靠 kCGWindowName 根本分不出来。

可靠的办法是用几何位置匹配：AX 给出主窗口的矩形（点）， 在 CGWindowListCopyWindowInfo 的结果里找 layer=0、位置尺寸在 4 点容差内完全吻合的那个。

d = abs(x - ax.x) + abs(y - ax.y) + abs(w - ax.w) + abs(h - ax.h)

本项目里对应 macos_shot.window_id_for()。

9. 为什么没有用"完全不起窗口"的方案

理论上还有一条路：把脚本跑在独立的 macOS 用户会话里， 这样它抢焦点也影响不到你。这是生产环境最干净的形态，但需要：

  • 新建一个 macOS 用户，在里面单独登录 LINE
  • 或者用一台专门的机器 / 虚拟机

本项目没有强制这么做，而是把"抢焦点"压缩到发送前后的约 2 秒， 并且支持把执行时间安排在你不使用电脑的时段。 需要更强隔离时，直接把这套代码搬到独立用户会话即可，代码本身不用改。
