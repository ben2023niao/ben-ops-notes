任务边界

用户要求：

巴西项目目前是 3 台后端服务器 + 1 台前置宝塔 Nginx。
当前有 1 台后端没有跑业务容器，需要利用起来。
发布、更新文件等操作后续都要同步到 3 台后端服务器。

用户决策：

03 直接卸载 Docker 重新安装（不再修复 docker0 bridge）。

宝塔：192.0.2.8 / 192.0.2.1 / bizops-saopaulo-game-results-data-bt

后台 03：192.0.2.20 / 192.0.2.1 / bizops-saopaulo-sanic-prod-03

03 容器崩溃根因排查

只读核验结论（均实时执行）：

docker0 bridge 本身正常：容器能拿到 192.0.2.1/16，ping 网关 192.0.2.1 通。
真正原因：
1. systemd 服务 bizops-docker-internal-only.service 在 DOCKER-USER 注入
   `-i ens4 ! -s 192.0.2.1/20 -j DROP`，容器无法访问内网/公网以外的地址；
2. /etc/docker/daemon.json 强制 DNS=192.0.2.2，容器内不可达，DNS 全部超时。
结果：业务容器启动时 DNS/依赖连接超时（对应 Sanic worker ack 超时）导致崩溃/重启。

对比 01/02：DOCKER-USER 为空、daemon.json 无 DNS 覆盖、ufw 未启用，容器网络正常。

Docker 卸载重装（03）

1. 备份既有镜像：/root/docker-images-backup-20260807/docker-images-full.tar（926M）。
2. systemctl disable --now bizops-docker-internal-only.service，并删除该 unit。
3. apt purge docker.io containerd docker-compose-v2 + autoremove。
4. 清理 /var/lib/docker、/var/lib/containerd、/etc/docker。
5. apt 重装 docker.io 29.1.3 + containerd + docker-compose-v2。
6. daemon.json 对齐 01/02（json-file 日志 100m x 7，无 DNS 覆盖）。
7. 验证：docker pull 正常；容器 DNS 解析正常；出网 TCP 正常；端口发布正常；DOCKER-USER 为空。

网络核验（谷歌云 API）

通过 gcloud 复核 VPC 防火墙：4 台实例同一 VPC/子网
（bizops-saopaulo-slotsapi-network-v2 / 192.0.2.1/20），
open-all、game9000-10000 等规则已放行，无需新增防火墙规则。
宝塔 -> 03 的 9090/9091/9096/8765/9101/9102/9103/9104 全部可达
（未监听时为 Connection refused = 可达；部署后返回与 01 一致）。
说明：本次未新增/修改任何 GCP 防火墙规则。
