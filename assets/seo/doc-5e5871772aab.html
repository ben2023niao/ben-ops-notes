规模化架构轨道

本文件定义公共 AI 框架从快速 MVP 演进到大流量系统的规则。目标不是一开始过度设计，而是让团队知道什么时候保持简单、什么时候必须升级架构。

1. Scale Profile

framework.config.json 必须声明当前项目规模轨道：

{
  "scale": {
    "defaultProfile": "mvp",
    "allowedProfiles": ["mvp", "growth", "scale", "enterprise"]
  }
}
Profile 适用阶段 默认策略
mvp 快速验证、早期交付 单服务优先、单库优先、契约和 owner 先行。
growth 有真实流量和运营压力 缓存、队列、读写分离、慢查询、基础监控必须补齐。
scale 大流量、多团队、多服务 服务拆分、数据 owner、SLO、压测、容量评估、回滚策略必须补齐。
enterprise 多区域、多业务线、多合规要求 多环境治理、权限审计、灾备、成本治理和组织权限必须补齐。

2. MVP 阶段原则

MVP 默认不鼓励为了“看起来经典”拆很多服务：

services/go-app
  internal/http/handlers/public
  internal/http/handlers/admin

此阶段更重要的是：

  1. PRD、OpenAPI、数据 owner 清楚。
  2. 高风险模块有测试。
  3. Web、App、后台和 API 能形成闭环。
  4. 目录边界不要误导，例如不要把完整 Laravel app 叫成 admin-api。

3. Growth 阶段升级信号

出现以下信号，应从 mvp 升级到 growth 评审：

  1. 单接口 P95 延迟持续超出目标。
  2. 数据库慢查询、锁等待或连接数成为常态问题。
  3. 首页、Feed、搜索、消息、订单等模块互相拖慢。
  4. 管理后台任务影响用户端 API。
  5. 部署频率提高，但单服务发布风险过大。
  6. 静态资源、图片、Web 首屏加载影响转化。

Growth 必须补：

Redis 缓存策略
队列削峰策略
慢查询治理
基础指标和告警
Web CDN / 静态资源缓存
任务重试和幂等

4. Scale 阶段拆分规则

服务拆分按压力点、数据 owner 和部署边界进行，而不是按“前台/后台”机械拆。

常见演进：

services/
  gateway/          # 网关、鉴权、限流、路由
  user-go-app/         # 用户、资料、关系
  feed-go-app/         # 首页、动态、推荐
  wallet-go-app/       # 订单、钱包、账本、扣费
  call-go-app/         # 呼叫状态、通话会话
  realtime/         # WebSocket、IM、在线状态、世界频道
  media-callback/   # 第三方音视频、支付、CDN 回调
  admin-bff/        # 后台聚合 API，或继续使用 Laravel
  worker/           # 异步任务

拆分前必须回答：

  1. 新服务的数据 owner 是什么？
  2. 是否需要独立部署和扩容？
  3. 是否降低现有服务风险？
  4. OpenAPI / Event 契约如何变化？
  5. ECC 如何证明跨服务链路仍然可用？
  6. 回滚如何处理数据库 migration 和事件兼容？

5. 数据扩展

数据库演进建议：

mvp:
  MySQL 单库 + Redis

growth:
  读写分离
  热点缓存
  队列削峰
  慢查询和索引治理

scale:
  按领域拆库
  大表分区/分表
  账本独立库
  消息/Feed 独立存储
  搜索走 OpenSearch/Elasticsearch
  事件总线 Kafka/NATS/RabbitMQ

资金、订单、账本、扣费、权限、审核处罚等高风险数据，不允许因为拆服务而丢失强事务、幂等和审计。

6. Web 扩展

Web 流量增长时必须考虑：

  1. CDN 和静态资源版本化。
  2. 图片压缩、响应式图片、懒加载。
  3. 官网和产品 Web 分离部署。
  4. SSR/SSG/CSR 选择与 SEO异常验证、性能目标一致。
  5. API 缓存和边缘缓存不得破坏权限态。
  6. App 下载落地页必须能独立发布，避免被主业务部署阻塞。

7. Scale Review

从 growth 开始，以下变更必须写 scale review 或 ADR：

  1. 拆服务。
  2. 拆库、分表、读写分离。
  3. 引入消息队列、搜索引擎、对象存储、CDN。
  4. Web SSR/SSG 架构切换。
  5. 高风险模块的缓存、异步化、最终一致性改造。

没有容量评估、监控指标、回滚方案和 ECC 验证，不允许把 scale 级变更标记为完成。

压测、SLO 和观测结果必须结构化写入：

docs/qa/performance-evidence.json

并通过：

npm run check:performance-validator
npm run check:performance

Scale review 使用模板：

docs/templates/scale-review-template.md
