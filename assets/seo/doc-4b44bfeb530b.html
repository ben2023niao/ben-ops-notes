本规范定义团队公共代码底线。它不替代具体项目的 lint、formatter、语言版本和框架配置；具体项目可以在 docs/project/constraints.md 中加严，但不能低于本文的工程底线。

1. 通用代码规范

  1. 代码必须围绕 PRD 需求 ID、OpenAPI/Event 契约和验收证据实现，不能把聊天里的临时理解写成隐性业务逻辑。
  2. 业务规则放在 application/domain/service 层，不放在 handler、controller、page、component 里堆判断。
  3. 公共代码先判断平台和消费者，遵守 docs/architecture/package-boundaries.md，不能恢复万能 packages/shared。
  4. 错误必须可定位：返回统一 error code、message、trace id 或 request id；日志里不能泄露密码、token、验证码、密钥。
  5. 配置必须来自环境变量或配置文件，不把密钥、第三方 key、线上地址硬编码进代码。
  6. 时间使用 UTC 存储，展示层再按用户时区格式化。
  7. 金额、金币、积分、库存、计数等数值禁止使用 float。金额使用最小货币单位整数，汇率或比例使用 DECIMAL 或明确精度整数。
  8. TODO、mock、fallback、temporary 必须写明原因、owner 和移除条件；运行时代码不能把 mock 冒充真实完成。
  9. 新增依赖必须说明用途、替代方案和风险；不能为一个小函数引入大依赖。
  10. 删除字段、接口、表、配置或行为前必须确认兼容策略和回滚方案。

2. TypeScript / Nuxt / Web / Mobile

  1. TypeScript 代码必须通过 typecheck，禁止用 any 绕过契约；确需使用时必须解释边界。
  2. API 类型优先来自 packages/generated/ts，不手写重复 DTO。
  3. 页面组件只负责展示、交互和状态组合，业务流程放到 composable、hook、service 或 store。
  4. 表单必须有 loading、disabled、success、error 状态。
  5. 鉴权态必须由真实 token/session 驱动；不能用本地假登录状态冒充。
  6. Web 页面必须验证根节点挂载、静态资源、console、移动和桌面视口。
  7. apps/admin 必须有登录、权限、审计和敏感操作反馈；不能做无鉴权数据面板。
  8. apps/web 默认使用 Nuxt 4 + Tailwind CSS v4；公共 UI 资产按 packages/ui/tokens、packages/ui/web、packages/ui/mobile 分层。

3. Go Gin

  1. Go 代码必须通过 gofmt，项目启用后必须跑 go test ./...；高风险服务建议跑 go test -race ./... 和 go vet ./...。
  2. Gin handler 只做参数绑定、鉴权上下文、调用 use case、响应映射。
  3. 业务用例放在 internal/application，领域规则放在 internal/domain。
  4. Repository interface 放在 domain/application 需要的位置，MySQL/Redis/第三方实现放在 internal/infrastructure。
  5. 所有请求必须接收 context.Context，外部调用必须设置 timeout。
  6. 事务边界必须明确；账本、订单、扣费、库存等强一致写操作必须在服务端事务中完成。
  7. 高风险写接口必须支持幂等键或天然唯一业务键。
  8. 错误返回使用统一 envelope，不把 Go 内部错误原文直接暴露给客户端。

4. Laravel / PHP

  1. Laravel 代码必须遵守项目 formatter，默认建议 Laravel Pint；启用后必须跑 Feature/Unit tests。
  2. Controller 只接 HTTP，不写复杂业务；请求校验放 FormRequest。
  3. 权限放 Policy/Gate/Middleware，不在 Blade、Vue 或 Controller 中散写。
  4. 输出放 Resource/DTO，并对齐 OpenAPI schema。
  5. 复杂业务动作放 Action/Service；Queue Job 必须幂等、可重试、可观测。
  6. Filament 资源必须声明权限、字段可见性、敏感操作确认和审计日志。
  7. Migration 必须可重复部署，禁止手改线上表后再补迁移。
  8. Model 不承担跨聚合复杂业务流程，避免 fat model。

5. 测试

  1. 单元测试覆盖纯业务规则、状态机、金额/金币计算、权限判断。
  2. API/Feature 测试覆盖鉴权、成功、失败、幂等、参数校验。
  3. 数据库测试必须覆盖唯一约束、事务回滚和高风险并发路径。
  4. 前端测试或浏览器验收必须覆盖真实用户路径和失败路径。
  5. 任何未运行测试的任务，Agent 日志必须写明原因、风险和补测计划。

6. Review 门禁

Review 必须回答：

  1. 代码是否追踪到 PRD 需求 ID。
  2. 实现是否对齐 OpenAPI/Event/DTO。
  3. 业务规则是否放在正确层级。
  4. 是否引入未登记 mock、fallback 或假状态。
  5. 是否有测试或明确测试豁免。
  6. 是否影响数据表、索引、迁移、事务或审计。
  7. 是否影响性能、容量、日志、指标或告警。
  8. 是否更新 Agent 日志和验收证据。
