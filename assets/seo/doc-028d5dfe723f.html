1. 验证目标

验证用户侧是否已经实现：

后端 uploads 图片
-> test-img.hbabaxb.cn 和 test-img.hbazuua.cn 谁快用谁
-> 两个腾讯备案图片域名都失败后
-> 最后回退 AWS CloudFront 老地址

期望候选链路：

1. https://test-img.hbabaxb.cn/uploads/...
2. https://test-img.hbazuua.cn/uploads/...
3. https://d1rct3ku9n07y3.cloudfront.net/uploads/...

2. 浏览器验证方法

本机没有可用 in-app browser 实例，改用本机 Chrome DevTools Protocol 抓 Network，效果等价于打开浏览器 F12 Network。

验证页面：

https://test-pc.hbabaxb.cn/
https://test-pc.hbazuua.cn/

Chrome 启动参数：

--headless=new
--remote-debugging-port=9223
--ignore-certificate-errors

说明：

  • --ignore-certificate-errors 只用于验证 hbazuua.cn 当前回源链路，因为 EdgeOne 免费证书仍在腾讯侧签发/校验过程中。
  • 真实浏览器正式访问仍需等证书部署完成。

4. 当前结论

真实页面当前没有实现“谁快用谁 + AWS 最后兜底”。

依据：

  • 页面实际请求中没有看到自动请求 test-img.hbazuua.cn。
  • 页面实际请求中没有看到图片失败后自动回退 d1rct3ku9n07y3.cloudfront.net。
  • 后端当前主要仍返回 test-img.hbabaxb.cn。
  • DNS/CDN 只能让一个域名可访问，不能让浏览器自动在多个域名之间赛跑。

所以当前状态是：

后端返回哪个图片 URL
浏览器就请求哪个图片 URL
不会自动择优
不会自动切另一个备案图片域名
不会自动切 AWS CloudFront

5. 手动模拟多候选加载结果

在浏览器页面里注入测试脚本，对同一张图片构造三条候选 URL：

test-img.hbabaxb.cn
test-img.hbazuua.cn
d1rct3ku9n07y3.cloudfront.net

验证结论：

  • 三条候选链路可以分别被浏览器加载。
  • test-img.hbazuua.cn 已具备作为候选图片域名的能力。
  • AWS CloudFront 可以作为最后兜底链路。
  • 但这是手动注入脚本模拟，不是当前页面已有功能。

示例冷请求结果：

图片路径 hbabaxb hbazuua AWS CloudFront 最快
/uploads/2025-10-24/b80f9ee..._large.webp 588ms 884ms 17ms AWS
/uploads/2026-01-30/842b59..._large.webp 965ms 488ms 12ms AWS

注意：

  • 冷请求测试里加了随机 racecb 参数避免浏览器缓存作弊。
  • AWS 返回的是老 CloudFront 图片链路，不走腾讯备案域名防盗刷。
  • AWS 很快，但只能作为兜底，不建议作为优先链路，否则会绕过当前防盗刷设计。

6. 推荐实现方式

不建议每张图片都同时打三个请求，因为会把图片请求量放大。

推荐前端做统一图片加载器：

  1. 页面启动时，用一张小图或轻量 URL 测速两个腾讯图片域名。
  2. 本页默认选择更快的腾讯图片域名。
  3. 单张图片加载失败时，先切到另一个腾讯图片域名。
  4. 两个腾讯图片域名都失败，再切 AWS CloudFront。
  5. 图片路径、token/t 保留；只替换 host。

伪流程：

原始后端图片 URL:
https://test-img.hbabaxb.cn/uploads/a.webp?敏感凭据：[已脱敏]

候选 1:
https://test-img.hbabaxb.cn/uploads/a.webp?敏感凭据：[已脱敏]

候选 2:
https://test-img.hbazuua.cn/uploads/a.webp?敏感凭据：[已脱敏]

兜底:
https://d1rct3ku9n07y3.cloudfront.net/uploads/a.webp

说明：

  • 当前签名只按 path 和时间计算，同一张图替换 host 后可以复用 token/t。
  • AWS 兜底不需要 token。
  • 前端要统一处理 img.onerror 或封装图片组件，不能分散在页面里硬写。

7. 给不同角色看的大白话

给运营：

现在两个备案图片域名都已经准备好，但页面还没有自动谁快用谁。
要做到用户无感切换，需要前端加一个图片加载兜底逻辑。

给前端：

后端现在主要返回 test-img.hbabaxb.cn。
前端可以基于返回 URL 派生 hbazuua 和 AWS 候选。
优先用更快的腾讯备案域名，失败再 fallback。

给运维：

CDN、DNS、Nginx、后端签名能力已经具备。
剩余不是解析问题，而是用户侧图片加载策略问题。
