三、现状分析（香港 PP 静态资源的三条链路，均为 2026-10-14 实测）

链路 域名 缓存层 实测（连发两次请求） 结论
老域名 pp-static.hkcloudplay01-05.com CloudFront 分配 E2B947FD8LP93P，缓存策略 4135ea2d-6df8-44a3-9df3-4b5a84be39ad（Managed-CachingDisabled） 两次都 x-cache: Miss from cloudfront 本就没有边缘缓存（逐请求回源），无需清
新域名 pp-static.hkcloudplay06/07.com 橙云 + Worker bizops-hk-static-proxy（routes 28 条）+ Cache Rules statics（cache=true，edge_ttl=604800） 第 2 次 cf-cache-status: HIT 有缓存，需清
EdgeOne pp-static.m4q7z1.shop / pp-static.k8x2v9.shop 腾讯 EdgeOne 边缘缓存 第 2 次 eo-cache-status: HIT 有缓存，需清

源站：老域名走香港主桶 bizops-h5-hk-517506432530（CloudFront OAC）；06/07 与 EdgeOne 回源 AWS 大阪独立桶 bizops-s3-pp-static（对象直接放桶根）。

关键机制（决定清缓存只能整 zone 刷）：

06/07 上并存两套缓存键：
  1) 按请求 URL 的键 —— zone 级 Cache Rules `statics` 允许缓存 Worker 响应（edge TTL 7 天）；
     请求可能直接命中它，**换 Worker 缓存键清不掉**（实测：换盐后同一 URL 仍 HIT 且 age 连续增长，
     只有带新 query 的请求才 MISS）。
  2) Worker 内 fetch(cf.cacheKey + cacheEverything) 的自定义键 —— 按 URL purge files 对它无效。
=> 唯一可靠手段 = 对服务这些静态子域名的 zone 做 purge_everything（与巴西口径一致）。

四、执行过程

执行通道：本机 → 巴西宝塔 192.0.2.8（本机有私钥）→ 香港入口机 192.0.2.14 （宝塔持有香港机 bizops_hk_bootstrap_sync_ed25519 免密私钥）；EdgeOne 走 巴西宝塔 → gcloud compute ssh → 香港 standby 192.0.2.37（腾讯云凭据在本机 /root/.config/tencentcloud/edgeone.credentials）。

4.1 EdgeOne（两个站点，按 host 精准刷新）

动作：CreatePurgeTask（Type=purge_host, Method=invalidate）
      —— 注意国际站不支持 PurgeCaches（返回 InvalidAction），动作名必须是 CreatePurgeTask。
m4q7z1.shop（zone-3vm5evyb78ic）Targets=[pp-static.m4q7z1.shop] -> JobId 3w63iv44ohzr
k8x2v9.shop（zone-3vm7ccg417yf）Targets=[pp-static.k8x2v9.shop] -> JobId 3w63j7rg57u6
两次 FailedList 均为空。
（p3w9n5.shop / r2v8k4.shop 未绑套餐、pp-static 无 A 记录，不在服务范围，未动。）

4.2 Cloudflare 06/07（整 zone purge_everything）

① 先按巴西思路用香港入口机 token 调 purge_cache：
   /root/.config/cloudflare/{api-token,workers-token} 均返回 10000 Authentication error
   （token 有效但**缺 Zone.Cache Purge**）→ API 刷新走不通。
② 备用手段（香港手册 C 节：改缓存盐重部署 = 全量失效）：
   拉取线上 Worker 实况存档 -> 缓存键加盐 CACHE_SALT=v2-20261014 -> 重部署。
   实测发现：加盐后新 query 请求 MISS/重建正常，但**原 URL 仍 HIT 旧条目**（见第三节机制），
   说明 URL 键那层清不掉。为避免在开发侧维护的线上脚本上留下非必要分叉，已**回滚**为线上原版。
③ 改用巴西宝塔 `/root/bizops-cf-workers.env`（账户级 token，与香港同一 Cloudflare 账号，
   带 Zone.Cache Purge）执行 purge_everything：
   hkcloudplay06.com（fd8476ddbd25b40f4c870d8066329aca）success=true
   hkcloudplay07.com（ad235f3123a5c6259f5b2e699bdd7b93）success=true
   时间 2026-10-14T02:51:12Z。

4.3 CloudFront 01-05

分配 E2B947FD8LP93P 的 DefaultCacheBehavior.CachePolicyId =
4135ea2d-6df8-44a3-9df3-4b5a84be39ad（Managed-CachingDisabled），实测连续两次均 Miss。
=> 该层无边缘缓存，创建 invalidation 属无效动作，本轮**不做**，只记录事实。
（如需后续恢复缓存，是另一件事：TASK-20260902-HK-CF-CACHE-RESTORE。）

六、发现与风险（需留档）

1. 线上 Worker ≠ 仓库 hk_static_worker.js
   线上 6732 字节（开发侧 2026-09-14 版，CF modified 2026-09-25T06:41:37Z，无 CACHE_SALT）；
   仓库 12899 字节（本侧自研版，含 CACHE_SALT / echo-platform CORS，从未部署）。
   => 今后部署 Worker 不要用仓库版覆盖线上版，否则会连带回退开发侧改动（2026-09-25 有过同类事故）。
      实况存档见 docker/deploy/hongkong/worker-live/。
2. 06/07 的缓存分两层（URL 键 + Worker 自定义键），只清一层等于没清干净。
3. 凭据缺口：香港入口机 token 缺 Zone.Cache Purge，清缓存目前要借巴西宝塔账户级 token。
   建议为香港机 token 补 Zone.Cache Purge（或单独建一个"缓存刷新"专用 token），减少跨机依赖。
4. vendor_b-static 桶仍为空（health.json 403），与 2026-09-25 记录一致，属开发侧上传待办，非本次引入。
5. 老域名 01-05 的 CloudFront 层无缓存，玩家侧"资源没更新"若仍出现，应查浏览器缓存/启发式缓存
   （S3 对象无 Cache-Control），而不是 CDN 缓存。

七、回滚路径

Cloudflare：无需回滚（purge 只清缓存，不改配置）。Worker 已在 02:51Z 回到线上原版。
EdgeOne：purge 只清缓存，不改规则；如需再次刷新，重跑同一 CreatePurgeTask。
若误刷到不该刷的 zone：缓存会在回源后自然重建（首访变慢），无数据风险。
