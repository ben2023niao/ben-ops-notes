1. 目标

{{PROJECT_NAME}} 采用 Monorepo + AI 工程团队模式。技术栈选择优先服务于：

  1. 稳定扩展优先。
  2. 让前端、后端、测试和 AI Agent 围绕契约并行开发。
  3. 让团队常用技术栈可以复用同一套目录、Git、日志、QA 和发布门禁。
  4. Demo 阶段可快速部署，后续可平滑拆分服务。
  5. 技术栈选择必须显式写入 framework.config.json 和 ADR，不能靠口头约定。

2. 公共技术栈适配原则

公共 AI 框架不强制所有项目使用同一套语言或框架。它约束的是：

  1. 技术栈必须被声明。
  2. 技术栈必须有对应目录、脚本、测试和部署适配器。
  3. 技术栈变化必须写 ADR。
  4. 业务契约优先于具体框架实现。

团队当前优先沉淀一条组合后端技术线：

Go Gin + Laravel

细则见：

docs/architecture/backend-stack-go-gin-laravel.md

同时保留两条语言能力：

技术线 优先级 适用场景
Go Gin P0 高并发 API、实时服务、worker、网关、长连接、强性能服务。
PHP / Laravel P0 完整 Laravel 应用服务、传统业务 CRUD、运营配置、内容审核、快速 MVP。
Nuxt 4 + Tailwind CSS v4 P0 官网落地页、PC 站、H5、公开 Web 产品站。
其他语言/框架 P2 需要先补适配文档、脚本和 QA 门禁后再使用。

团队默认 Web 技术线：

Nuxt 4 + Tailwind CSS v4

细则见：

docs/architecture/web-stack-nuxt-tailwind.md

3. Go 适配器

Go 是团队优先技术线之一。团队默认优先 Go Gin，其他框架作为可选适配：

框架 优点 风险
net/http + ServeMux 标准库、依赖少、升级稳定、适合早期清晰薄切片 中间件和工程组织需要自己约定。
Gin 团队默认优先；生态成熟、资料多、团队容易上手 风格较轻，需要自己组织工程边界。
Fiber 性能好、API 简洁 基于 fasthttp，部分标准库兼容习惯不同。
Echo 简洁、稳定、中间件清晰 国内团队熟悉度略低于 Gin。

选择规则：

  1. 团队标准项目优先 Gin。
  2. 快速薄切片或低依赖服务可选 net/http。
  3. 中间件结构清晰优先 Echo。
  4. 明确需要 fasthttp 性能模型时再选 Fiber。

实践说明：某次早期项目实践曾使用 Go 标准库 net/http + http.NewServeMux()，而不是 Gin。因此框架必须区分“团队默认推荐”和“具体项目事实”。

4. PHP / Laravel 适配器

PHP 是团队优先技术线之一，Laravel 作为 P0 默认候选。

框架 优点 风险
Laravel 生态成熟、后台和 CRUD 效率高、队列/任务/权限/ORM 体系完整 需要严格服务层、DTO、契约和测试边界，避免控制器肥大。
Symfony 组件化强、企业级结构清晰 上手和团队统一成本略高。
Slim 轻量 API 大型业务需要补齐工程约束。

Laravel 项目必须遵守：

  1. API 字段以 packages/contracts 为准，不能在 Controller 内私自发明字段。
  2. 请求校验使用 FormRequest 或等价机制。
  3. 业务逻辑进入 Service/Action，不堆在 Controller。
  4. 金额、订单、权限、审核等高风险逻辑必须有 Feature Test 和审计日志。
  5. 数据库变更必须有 migration，禁止手改线上表结构。
  6. 队列任务必须幂等，回调必须可重放。
  7. OpenAPI 更新必须早于 Controller 实现。

5. Go + PHP 混合服务边界

当一个项目同时使用 Go 和 PHP 时，默认边界如下：

服务类型 推荐技术 说明
高频 API、实时、网关、worker Go 优先稳定、并发和资源控制。
Web/API、Filament 后台、CRUD、配置、审核、采集任务 Laravel 优先开发效率和 Laravel 生态。
共享契约 OpenAPI / events 不归属 Go 或 PHP，统一放 packages/contracts。
共享业务规则 docs/prd、docs/architecture 不写进某个服务私有 README。

如果 Go 服务和 Laravel 服务都暴露 API，必须：

  1. 在 packages/contracts/openapi/ 标注 owner service。
  2. 在 docs/api/ 说明路由归属。
  3. 在部署策略中说明网关或 Nginx 路由。
  4. 在 ECC 测试中覆盖跨服务链路。

6. 数据库设计原则

数据库类型由项目选择，团队默认优先 MySQL。MySQL 作为核心事实来源时，必须优先保证一致性和可追踪。

关键原则：

  1. 金币账本强事务。
  2. 订单必须幂等。
  3. 支付回调必须幂等。
  4. 礼物、通话扣费、任务奖励都必须有账本记录。
  5. 用户余额不得以客户端为准。
  6. 预留分库分表扩展空间。

预留策略：

  1. 所有核心表使用全局唯一 ID。
  2. 大表预留 user_id、created_at 等分片和归档字段。
  3. 金币账本、消息、通话记录、订单等高增长表提前设计索引。
  4. 避免跨库强事务作为长期依赖。

7. Redis 使用范围

Redis 用于提升性能和支撑实时能力，但不是核心资金事实来源。

适用：

  1. 在线状态。
  2. WebSocket 连接路由。
  3. 世界频道 Pub/Sub。
  4. 限流。
  5. 短期验证码/登录态辅助。
  6. 分布式锁。
  7. 轻量异步队列。

不适用：

  1. 金币最终余额事实来源。
  2. 订单最终状态事实来源。
  3. 审核最终状态事实来源。

8. 高风险业务原则

不论选择 Go、Laravel 还是其他框架，高风险业务规则一致：

  1. 账本强事务。
  2. 订单幂等。
  3. 支付回调幂等。
  4. 权限服务端校验。
  5. 审核、处罚、删除必须有审计日志。
  6. 客户端状态不能作为资金、权限和审核事实来源。

账本建议：

CoinLedger
  id
  user_id
  direction        IN / OUT
  amount
  balance_after
  type             RECHARGE / CALL_CHARGE / GIFT_SEND / TASK_REWARD / ADMIN_ADJUST
  biz_id
  idempotency_key
  created_at

订单建议：

Order
  id
  user_id
  provider
  provider_order_id
  product_id
  amount_usd
  coins
  bonus_coins
  status
  idempotency_key
  created_at
  paid_at

10. 后台运营复杂度

后续可能存在复杂运营后台，因此后台端需要预留：

  1. RBAC 权限。
  2. 审计日志。
  3. 用户管理。
  4. 主播审核。
  5. 内容审核。
  6. 订单和账本查询。
  7. 运营配置。
  8. 数据看板。

11. 新项目必须确认

以下问题不阻塞 PRD 初稿，但进入实现前必须确认：

  1. API 服务使用 Go、Laravel，还是 Go + Laravel 混合。
  2. Go 框架选择 net/http、Gin、Echo 或 Fiber。
  3. PHP 框架选择 Laravel、Symfony 或 Slim。
  4. 前端/客户端框架。
  5. 数据库、缓存、队列。
  6. 部署方式和环境边界。
  7. 高风险模块的测试和审计策略。

技术栈最终选择必须同步到：

framework.config.json
docs/architecture/technology-stack.md
docs/decisions/ADR-0002-technology-stack.md
