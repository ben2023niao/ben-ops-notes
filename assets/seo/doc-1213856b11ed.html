一、用户优化后的命令（复核对象）

# 香港同步
rsync -avP --delete \
  -e "ssh -o ServerAliveInterval=15 -o ServerAliveCountMax=3" \
  --exclude 'logs' \
  --exclude 'game_result_datas' \
  --exclude 'conf' \
  --exclude '*.db-shm' \
  --exclude '*.db-wal' \
  root@192.0.2.20:/data/server-runtime-hk/ /data/server-runtime/

# 香港结果集同步
rsync -rtvP --delete \
  -e "ssh -o ServerAliveInterval=15 -o ServerAliveCountMax=3" \
  --exclude '*.db-shm' \
  --exclude '*.db-wal' \
  root@192.0.2.20:/data/server-runtime/game_result_datas /data/server-runtime/

结论：核心修复正确 ✅

把 --exclude 'conf/domains' 改成 --exclude 'conf' 是这两次故障的根因修复：

10-03、10-05 两次 vendor_b/vendor_d 崩溃循环，都是因为**同步源** /data/server-runtime-hk/conf/ 里放的是旧版
configs-vendor_b.py(95行) / configs-vendor_d.py(42行)（缺 is_top_new_configs），
而 start.sh 会把宿主机的 conf/configs-<厂家>.py 挂载成容器内的 configs.py →
旧文件覆盖镜像里正确的那份 → 容器 import 失败、启动即崩 → vendor_b 502、游戏进不去。

改成 --exclude 'conf' 后，整个 conf/ 既不传输也不删除（--exclude 同时受 --delete 保护），
香港自己的 domains + configs + 以后任何本地改动都不会再被覆盖。
⚠️ 千万不要加 --delete-excluded —— 那会把被排除的 conf/ 从香港删掉。

二、可选补强（建议但不强制）

1. 结果集同步加 --chown=1000:1000
   现在用的 -rtvP 不带 -p/-o/-g，但 rsync 由 root 执行，落盘属主仍是 root:root；
   容器内业务进程是 appuser(uid 1000)，结果集目录不可写就会出现「所有厂家不能下注」
   （10-02 那次事故的根因）。加上 --chown=1000:1000 从源头规避；
   现有「结果集权限自愈」定时任务仍然保留作为兜底。
2. 加 --delete-delay 与 --timeout=180/300
   先传完再删，减少窗口期不一致；网络卡住时 rsync 不至于一直挂着。
3. 用 sshpass -f /root/.rsync-pass 代替手工输密码（两台已有该 600 文件，内容即该密码）。
4. 同步后自检 conf：确认 configs-vendor_b.py / configs-vendor_d.py 仍是 101 / 47 行且带
   is_top_new_configs（本侧脚本已内置这一步）。

推荐终版（可以直接替换）

# 香港同步
rsync -avP --delete --delete-delay --partial-dir=.rsync-partial --timeout=180 --stats \
  -e "sshpass -f /root/.rsync-pass ssh -o ServerAliveInterval=15 -o ServerAliveCountMax=3 -o StrictHostKeyChecking=no" \
  --exclude 'logs' --exclude 'game_result_datas' --exclude 'conf' \
  --exclude '*.db-shm' --exclude '*.db-wal' \
  root@192.0.2.20:/data/server-runtime-hk/ /data/server-runtime/

# 香港结果集同步
rsync -rtvP --delete --delete-delay --timeout=300 --chown=1000:1000 \
  -e "sshpass -f /root/.rsync-pass ssh -o ServerAliveInterval=15 -o ServerAliveCountMax=3 -o StrictHostKeyChecking=no" \
  --exclude 'logs' --exclude '*.db-shm' --exclude '*.db-wal' \
  root@192.0.2.20:/data/server-runtime/game_result_datas /data/server-runtime/

脚本版已入仓：docker/deploy/hongkong/hk_sync.py（支持 runtime|results|all，可 --dry-run 预演， 自带日志与 conf 自检），两台已放到 /opt/bizops-hk-ops/。

更新（2026-10-05 13:35）：原 hk-sync.sh 被仓库自检拦下（docker/ 下不允许 Shell 脚本， 见 docker/ci/check.py 的 reject_shell_scripts），已改写为 Python hk_sync.py，行为与参数完全一致。 详见 docker/doc/2026-10-05-1335-【运维】hk-sync脚本改写为Python并修复CI自检.md。

三、本次 vendor_b 故障的处理（已修复）

现象：vendor_b-games.{m4q7z1,k8x2v9}.shop/health = 502，浏览器「vendor_b 进不去」；
      vendor_b 容器 restarting（restarts 12~16），日志：
      ImportError: cannot import name 'is_top_new_configs' from 'configs' (/app/vendor_a/configs.py)
根因：conf 被同步覆盖（同上），vendor_b 启动即崩 → 宿主机 9093 无监听 → nginx 502。
修复：
  1. 两台从镜像提取正确 configs 覆盖回宿主机（备份 /root/conf-configs-healed-20261005/）
     -> vendor_b/vendor_d 恢复 running（vendor_b 01 restarts 停在 16、02 停在 12）
  2. 顺带把**同步源** 192.0.2.20:/data/server-runtime-hk/conf/ 的 configs-vendor_b.py /
     configs-vendor_d.py 也换成正确版本（源端备份 /root/conf-configs-backup-20261005/），
     这样即使某次忘了加 --exclude conf 也不会再崩。
验证：
  http://vendor_b-games.m4q7z1.shop/health  -> 200
  http://vendor_b-games.k8x2v9.shop/health  -> 200
  WS 握手（经 EdgeOne，curl --http1.1 + Upgrade 头）：
    wss://vendor_b-games.m4q7z1.shop/lifeservice/ws2 -> 101
    wss://vendor_b-games.m4q7z1.shop/ws2            -> 101
    wss://vendor_b-games.k8x2v9.shop/lifeservice/ws2 -> 101
    wss://vendor_b-games.k8x2v9.shop/ws2            -> 101
  源站直连 nginx 同路径 -> 101（两域名一致）
  => 香港的 ws 没有缺：之前 426 是 vendor_b 进程崩溃期间的表现，链路本身是通的。
