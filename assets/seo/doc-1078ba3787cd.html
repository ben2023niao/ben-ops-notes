关键结论：

  • 巴西 01/02 的内存基线就有 57%~58%，用 80% 阈值只剩约 7G 余量，发版高峰容易误报。
  • 香港 01/02 磁盘本来就 69%~70%，正好压在原来的 70% 阈值上，会长期常亮。
  • 所有机器负载都很低，5 这个阈值对 8 核机器偏敏感，发版/压缩时会短时冲高。

三、建议阈值（Beszel）

| 指标 | 建议值 | 依据 |

| --- | --- | --- |

| CPU 1 分钟 | 85% 持续 5 分钟 | 平时 2%~3%，发版/巡检会有短时尖峰 |

| 内存 | 88% 持续 10 分钟 | 基线 57%~58%，88% 才代表真的吃紧 |

| 磁盘 | 85% 警告，92% 严重 | 香港两台基线已 69%~70%，70% 会长期误报 |

| 磁盘增速 | 24 小时增长 ≥ 5% | 比静态百分比更早发现异常写入 |

| 负载 | 8 核 12、4 核 6，持续 5 分钟 | 约 1.5 倍核数，避免发版误报 |

| 网络丢包 | 10% 持续 5 分钟 | 过滤偶发抖动 |

| 容器异常 | 连续 3 次采样（约 6 分钟） | 与现有容器监控一致，避开滚动发版 |

降噪原则：

  1. 磁盘用「警告/严重」两级，不要用单一低阈值常亮。
  2. CPU 和负载按核数区分，不要所有机器一个值。
  3. 容器类告警保留 3 次采样确认，避免 stop/rm/run 的滚动发版误报。

四、本轮巡检修复的监控项

4.1 静态域名巡检（cf_static_cname_monitor.py）

现象：日志里累计 1818 次 HTTP Error 404，每次执行都在 first_object() 处整轮退出， 监控实际上已经停摆；原因是 CNAME 仍指向已删除的旧桶 dbqp-gcs-*-static-sa。

修复：

  • 桶不存在时不再抛异常中断，改为记录该条异常并继续检查其余记录；
  • 桶名按当前架构推导：<前缀>.xqv9m8.icu -> newgg2-dbqp-gcs-<前缀>；
  • 只巡检在用 zone（默认 xqv9m8.icu,tada-cdn-2026.icu），迁移前的 15+ 个旧 zone 不再纳入；
  • 新增 --dry-run（不发群、不写状态）和 --no-notify（不发群、写状态）。

结果：静态 26 个、动态 165 个，全部正常；旧 zone 的 256 条历史记录不再参与巡检。

五、进东京监控机（当前阻塞点）

三条可行路径，任选一条：

  1. 串口控制台（本次使用，已验证）：
   gcloud compute connect-to-serial-port dbqp-tokyo-gitlab-cicd-01 \
     --zone=asia-northeast1-a --port=1
   # 登录用户 root，密码见运维密码库
  1. 如果以后要在宿主机上开 sshd：装 openssh-server，把端口改到 22 以外并在防火墙放行， 再把运维公钥加到 /root/.ssh/authorized_keys。
  2. 开启 OS Login 并给运维账号授权，之后用 gcloud compute ssh。

拿到权限后，Beszel 的落地步骤就是：

# 1) 备份数据与 compose
cp -a /opt/beszel/beszel_data /opt/beszel/beszel_data.bak-$(date +%Y%m%d-%H%M)
cp -a /opt/beszel/docker-compose.yml /opt/beszel/docker-compose.yml.bak-$(date +%Y%m%d-%H%M)

# 2) 用仓库里的 docker/scripts/beszel-zh/ 构建中文镜像并替换
# 3) 在 Hub 后台按第三节的阈值表逐项调整
