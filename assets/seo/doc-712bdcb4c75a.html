四、香港 vendor_a 接入与 Nginx 修复

排查发现香港 Nginx 的动态 upstream 仍指向旧公网地址：

192.0.2.18
192.0.2.19

当时香港后端实际内网地址为：

192.0.2.1
192.0.2.1

这会让 PP/vendor_a/G759 动态请求返回 502。已把全部香港动态 upstream 切换为当前内网地址，并增加 vendor_a HTTP 9096 upstream。

香港 01、02 已按顺序启动 game-service-vendor_a-prod，9096 正常监听。 nginx -t 通过后完成 reload。

操作前备份：

/etc/nginx/sites-available/bizops-hongkong.conf.bak-20261103-123139-vendor_a-enable
/etc/nginx/sites-available/bizops-hongkong.conf.bak-20261103-123247-private-upstreams

从巴西 03 复测：

PP/vendor_a/G759 五个香港动态域名 /health：HTTP 200
25 款新游戏静态入口：HTTP 200

五、巴西游戏无法进入的排查

5.1 已排除

巴西 Nginx：active，配置测试通过，80/443 正常监听
巴西 upstream：均为当前内网 192.0.2.1/.4/.5/.14/.15
近期 Access Log：未发现集中性 502/503/504 上游连接错误
四台后端：停止维护前主机、容器和端口均正常

因此，本次不是 JSON 未开放、静态资源缺失或 Nginx upstream 错配导致的 全厂家故障。

5.2 后端原始错误归类

以下内容已脱敏，仅保留故障类别：

API：
接口执行超时 | 异步函数: p_login | 耗时约 29.99s
p_register 超时
余额/钱包请求超时

Redis exception: Timeout connecting to server
user_type_conditions not exist
user_level_configs not exist
common_req 超时

PP：
html5Game / gameService / reloadBalance / saveSettings 超时

G759 的异常同时影响旧游戏和新游戏，证明问题位于共享缓存、数据库或钱包 依赖，而不是某一批游戏配置。开发随后确认数据库卡住。

vendor_a 日志还记录了个别智利来源 IP 被地区白名单拦截，但该问题不解释 全厂家、全用户范围的超时，属于并列的局部现象。

六、停服操作与恢复边界

开发最初要求依次重启巴西服务器；随后明确更正为“服务器不需要重启， 只重启上面的容器”。BR01、BR02 在更正前已经发生系统重启，BR04、BR05 没有重启；更正后未再重启任何服务器。

随后用户发布数据库维护通知，并要求关闭四台巴西后端的全部业务容器。 最终状态：

节点 主机 game-service* 运行数 主机状态
BR01 192.0.2.10 0 在线
BR02 192.0.2.11 0 在线
BR04 192.0.2.49 0 在线
BR05 192.0.2.50 0 在线

监控代理保持运行。业务容器不会自动启动。

恢复门禁

必须同时满足：

  1. DBA 明确数据库维护完成；
  2. 用户明确通知可以恢复巴西业务容器；
  3. BR01 启动并通过容器、端口、镜像 ID、日志和业务调用检查；
  4. BR01 稳定后，才允许开始 BR02，再依次 BR04、BR05。

任一台失败立即停止后续节点，保留已正常节点，不扩大故障范围。

  • 香港 Nginx 可使用上述两份备份恢复；
