一、优化效果复测（全部优化后 vs 竞品）

当前生效优化：Argo 3 套 + CF CDN 静态域 + CacheRule（静态 HTML 全缓存）+ Brotli + Early Hints + Polish/WebP + nginx 源站缓存 + launcher preconnect。

点继续→加载出：我方 7.5/7.3/7.7（均值 7.5s）vs 竞品 7.1/8.5/7.1（均值 7.5s）→ 持平
点击图标→完整加载：我方 11.7/11.9/11.9（均值 11.8s）vs 竞品 13.7/16.6/12.1（均值 14.1s）→ 快 2.3s
画布出现：我方 1.2-1.6s vs 竞品 2.1-5.1s → 我方明显快

优化前后（我方）：点继续→加载出 7.7 → 7.5s（-0.2s）；点击图标→完整加载 12.3 → 11.8s（-0.5s）。 6 条带水印视频已发群。

二、前端静态代码深挖（扒来资源）

资源构成（pg/pp/vendor_a 三库，仓库内）

PNG   12093 张 / 357.5MB（最大头，另有 webp 7566 张/52MB）
HTML  169 个 / 31.8MB（单页最大 1.5MB）
JS    730 个 / 55.3MB（单文件最大 1.3MB min.js）
JSON  489 个 / 16.5MB
CSS   196 个
字体  1 个 ttf 237KB

具体发现

  1. PNG 357.5MB：CF Polish 已自动转 WebP（省 43-45%，已验证）；主动 PNG→WebP 批量替换可再省（免每次动态转换，且对非 CF 场景也生效）——P1；
  2. 个别老游戏 HTML 1.5MB（如 pg/static_res/1997301/index.html）：内嵌大量 JS， 非 base64；vendor 文件改动风险高，Brotli 已压（实测 40KB 页面→13KB）；
  3. 大 JS：pp game-history-client main.*.min.js 1.3MB/1.1MB、vendor_a _nuxt 636KB—— 已 min；可做分包/按需加载（vendor 代码，风险中，P2）；
  4. 字体：1 个 ttf 237KB，可转 woff2（省 50-70%）——P2（影响小，仅 1 个）；
  5. 重复/冗余文件：JSON 489 个 16.5MB，可清理未引用资源——P3（需资产审计脚本）。

建议

P1 PNG→WebP 批量转换（脚本 + 同步 GCS；与 Polish 互补，源站体积也降）
P2 大 JS 分包/懒加载（vendor 风险，需灰度）
P2 字体 woff2
P3 冗余资源清理（static_resource_integrity_audit.py 扩展）

三、服务器 / 后端 / CDN / 域名可操作项（更新）

服务器

已做：nginx keepalive/源站缓存/gzip（宝塔修正+备用机补齐）/shared 边缘缓存
建议（P3）：sysctl tcp_max_syn_backlog 512→2048、netdev_max_backlog 提升

后端

已做：launcher P0-1、动态接口 gzip
建议：P1 launcher P0-2（模板静态化 + ticket 小接口，省 0.3-0.6s）
     P2 GET 配置类接口短 TTL 缓存（game.list 等）
     P2 DB/Redis 慢查询专项

CDN

已做：HTTP3/0-RTT、Argo 3套、CacheRule 静态全缓存、Brotli、EarlyHints、Polish、源站缓存、GCS 缓存头
建议：P2 更多 GET 接口边缘缓存；Tiered Cache 需 Enterprise（不采用）

域名

已做：3 套 Argo（xqv9m8/vendor_a-cdn-2026/cdn-tokyo-bizops）、game_hosts 精简、HSTS
待办：t6qv8m/q7m9v8 Argo 订阅重试；香港静态切 CF + 东京桶（cn 分支）

四、结论

  1. 优化后我方点击图标→完整加载 11.8s vs 竞品 14.1s（快 2.3s），点继续→加载出持平；
  2. 前端静态最大空间在 PNG（357MB）与个别大 JS/HTML，Polish 已先见效， 主动 WebP 转换是下一步大头；
  3. 其余可操作项按 P1→P3 排期（launcher P0-2、接口缓存、sysctl、字体 woff2）。
