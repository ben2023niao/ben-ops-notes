数据表设计规范

数据表设计规范。本文属于业务系统运维 / 小蓝直播，本规范定义团队默认 MySQL 表设计底线。项目可以选择 PostgreSQL、MongoDB 或其他存储，但必须在 ADR 和 docs/project/constraints.md 中说明替代规范；没有替代说明时，默认按本文执行。

本规范定义团队默认 MySQL 表设计底线。项目可以选择 PostgreSQL、MongoDB 或其他存储，但必须在 ADR 和 docs/project/constraints.md 中说明替代规范；没有替代说明时，默认按本文执行。

1. 命名

  1. 表名使用小写 snake_case，默认使用复数名词，例如 users、audit_logs。
  2. 字段名使用小写 snake_case。
  3. 主键统一命名为 id。
  4. 外键字段使用 <singular>_id，例如 user_id、order_id。
  5. 布尔字段使用 is_、has_、can_ 前缀。
  6. 时间字段使用 _at 后缀，例如 created_at、paid_at。
  7. 状态字段使用 _status 后缀，例如 order_status、review_status。
  8. 索引名称必须表达用途：idx_<table>_<columns>、uniq_<table>_<columns>。

2. 主键

  1. 默认使用 BIGINT UNSIGNED AUTO_INCREMENT 或框架等价类型。
  2. 需要跨库、跨区域、离线生成或外部暴露 ID 时，可以使用 UUID/ULID，但必须写 ADR。
  3. 外部展示 ID、订单号、流水号不等同于主键，应单独建唯一业务键。
  4. 多租户表必须显式包含 tenant_id 或等价隔离字段，并在唯一索引中考虑租户边界。

3. 字段

  1. 所有字段必须有明确类型、是否可空、默认值和说明。
  2. 非业务必需字段默认 NOT NULL。
  3. 字符串长度按业务上限设计，不用无意义超大 varchar。
  4. 金额使用最小货币单位整数，例如 amount_minor BIGINT，并配套 currency_code CHAR(3)。
  5. 金币、积分、次数、库存等使用整数，不使用 float。
  6. 比率、折扣、汇率使用 DECIMAL 或带精度整数，并说明精度。
  7. JSON 字段只能用于扩展属性、外部回调原文或低频配置；高频查询字段必须拆成显式列。
  8. PII 字段必须标记敏感性，必要时加密、脱敏或独立权限控制。

4. 索引

  1. 每个外键或逻辑关联字段必须评估索引。
  2. 查询路径必须从 PRD/API/后台列表反推索引，不为猜测场景建索引。
  3. 唯一业务约束必须建唯一索引，不能只靠代码判断。
  4. 组合索引按过滤条件、排序条件和基数设计，并记录主要查询场景。
  5. 高写入表谨慎增加索引，必须说明写放大成本。
  6. 分页默认使用稳定排序字段，避免大 offset；大数据列表优先 cursor/keyset pagination。

5. 约束

  1. 单服务拥有的数据表，优先使用数据库唯一约束和必要外键。
  2. 跨服务或大流量场景可以使用逻辑外键，但必须保留索引、数据 owner 和一致性校验方案。
  3. 状态字段不建议使用 MySQL ENUM 作为默认方案，优先使用字符串/小整数加应用层 enum，避免状态扩展困难。
  4. 删除策略必须明确：硬删除、软删除、冷静期、归档或匿名化。
  5. deleted_at 只在业务需要软删除时添加，不作为所有表默认字段。

6. 迁移

  1. 所有表结构变更必须通过 migration，不允许手改数据库后再补文档。
  2. 迁移文件名必须包含时间和动作，例如 202605170001_create_users_table。
  3. 线上变更遵守 expand -> backfill -> contract：先加兼容字段，再回填，再切读写，最后删除旧字段。
  4. 大表变更必须评估锁表、回滚、耗时和灰度方案。
  5. 删除字段、改类型、改唯一约束属于高风险变更，必须有 ADR 或 migration plan。
  6. Migration 必须和 docs/architecture/data-model.md、模块 PRD、OpenAPI/DTO 保持一致。

7. 账本

涉及余额、金币、订单、扣费、收益、积分、库存等强一致数据时：

  1. 必须有流水表或账本表，不能只更新余额快照。
  2. 账本写入必须在服务端事务中完成。
  3. 必须有幂等键，例如 idempotency_key 或唯一业务单号。
  4. 必须记录变动前后值或可重放的 delta。
  5. 必须记录业务来源，例如 source_type、source_id。
  6. 必须记录操作方和 trace id。
  7. 对账、补偿和审计查询必须有索引。

8. 审计

后台、权限、资金、审核、处罚、数据删除、配置变更等敏感操作必须有审计日志：

  1. 操作人：actor_id、actor_type。
  2. 操作对象：target_type、target_id。
  3. 操作动作：action。
  4. 操作前后摘要：before_snapshot、after_snapshot 或 delta。
  5. 请求来源：ip、user_agent、trace_id。
  6. 结果：result、error_code。
  7. 时间：created_at。

审计日志默认只追加，不更新、不删除；如因合规必须清理，需要独立 retention 策略。

9. 表设计模板

新增核心表前，必须在 docs/architecture/data-model.md 或模块 PRD 中登记表设计，推荐使用：

docs/templates/database-table-template.md

表设计必须说明：

  1. 表归属服务和数据 owner。
  2. 需求 ID。
  3. 字段、类型、可空、默认值、说明。
  4. 索引和唯一约束。
  5. 事务、幂等、审计、删除策略。
  6. 主要查询路径和容量预估。
