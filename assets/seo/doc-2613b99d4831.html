一、处置结论

旧 JumpServer 1.4.8 被用于长期投放恶意载荷。授权安全测试者在 2026-11-07 分四个波次删除 某支付平台、某业务平台、另一业务平台和 某业务公司 巴西环境的业务数据库。现有证据已经确认勒索提示、恶意持久化、删除语句和各环境恢复截止点。

巴西 128、DMG、DS 的网站最小开服核心 6 库已经全部恢复，日志库也已补齐。某支付平台 主库已通过日备加 binlog 恢复到删除前，57 张 _bak 历史表也已全部导入。

另一业务平台已从 DB1、DB2 的原始数据页中找到 users_db.account 的真实页；当前 DB1 2 路、DB2 4 路扫描继续补齐其余缺失库。另一业务平台的 DB1 和 DB2 已同时开展只读页扫描，两台各 8 路。

某业务平台已从 binlog 精确确认删除窗口，恢复截止点固定为 2026-11-07 00:27:11。两个超大日志库均已解包完成并进入 12 路导入，与其他已完成基线合计 24 路 MySQL 并发；导入完成后自动写基线标记并启动受保护的 PITR 回放。

根据最新处置安排，我方自动恢复任务已全部暂停，交由 DBA 使用服务器快照还原。暂停时未删除已恢复数据，未覆盖原始数据库目录，未重放 DROP DATABASE，也未停止生产 MySQL 服务。

二、确认的破坏时间

时间均为数据库服务器原始时区 UTC+8。某支付平台、某业务平台、另一业务平台 和 BJ 的时间来自二进制日志中的实际 DROP DATABASE 语句；128、DMG、DS 的历史主库 binlog 已被授权安全测试或清理，现存证据只能确认最后有效业务写入时间和恢复点，不能伪造精确到秒的删除时刻。

七、安全复核

范围 总数 完成 不可达 结论

全量内存哈希抽查 57 49 8 已扫描项未命中已知恶意 ELF 哈希
历史授权安全测试专项资产 16 16 0 两处新后门已取证并阻断

已修复的系统项包括勒索 motd、恶意 hosts、隐藏 systemd unit、删除态内存进程、恶意 ELF、公开数据端口和 SSH 密码/root 登录。当前可登录核心业务服务器未发现复发 IOC。

尚未消除的系统风险包括 sudo NOPASSWD、SELinux Disabled、CentOS 7 EOL、部分 RPM 基线漂移、历史日志清空和少数资产网络/认证不可达。对于曾以 root 失陷的主机，最终仍应以可信镜像重装为安全边界。

八、未完成项与处置建议

  • BJ users_db 的原始页已从 DB2 找到，仍需完成页合并、字段解析、依赖视图和账号首末时间校验；其余缺失库继续扫描。
  • 另一业务平台 需完成 DB1/DB2 共 16 路页扫描，再合并账号、充值、游戏配置和日志表；当前不把找到的原始页视为业务恢复完成。
  • 某业务平台的两个日志库完成 24 路导入后，自动校验失败队列、建立基线标记，再执行 PITR；geoip 未包含在现有备份源，必须继续查找，不能伪造空库。
  • paydb2、paydb_20220101 按指示排到后续任务。
  • 百利 / bail 任务已暂停，未对主从库做覆盖、停止或配置修改。
  • 统一轮换 SSH key、数据库、Redis/MQ、JumpServer 和云 API 凭据，并清理临时恢复密钥与临时数据库账号。

九、证据与复现

  • 某支付平台 删除来源：DB2 binlog，时间 2026-11-07 00:08:40，位置 693350583/693350648。
  • 某业务平台 删除来源：sample-node-03 的 mysql-bin.002742 与 relay-bin.001739，两份日志删除顺序一致。
  • 另一业务平台 删除窗口：2026-11-07 00:29:12 至 00:30:11；恢复截止点为 00:29:11。
  • BJ 删除来源：sample-node-04 的 mysql-bin.000711 与 relay-bin.002151。
  • 恢复并发：另一业务平台 使用 DB1 与 DB2 各 8 路并配置磁盘阈值；某业务平台 两个日志库各 12 路导入；BJ 使用 DB1 2 路和 DB2 4 路并配置磁盘阈值。
  • 进度口径：某业务平台 使用 MySQL 进程实际读取偏移和已完成文件字节数；另一业务平台/BJ 使用各分片最新进度日志和页文件产出量。
  • 常驻监控：从 2026-11-07 22:50 起连续监控 3 小时，每 5 分钟发送一次真实进度；监控进程异常退出后自动重启。
  • 恢复脚本、审计采集脚本、原始 JSON 和本报告纳入本地 Git；临时密码、私钥、Job 文件和恢复中间包不提交。
