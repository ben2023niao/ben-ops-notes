对齐 PRD：product-prd.md §6.4 数据一致性等级

决策原则：按业务量级演进，不为未来扩展提前付出 v1 复杂度成本。Redis Streams 起步，到达硬触发阈值时迁 Kafka。

5.1 总体原则

  1. 资金链路同步落账（不进队列），队列仅用于异步通知 / 解耦扇出
  2. 统一抽象层 internal/infra/stream/，业务代码不感知底层实现
  3. Topic / Stream 命名规则统一，迁移时不改业务代码
  4. 关键事件双写（事务内写 DB + 异步推队列），队列丢失不影响主流程
  5. 消费方幂等，任何消息可能被消费 ≥ 2 次

5.2 v1 起步：Redis Streams

5.2.1 为什么不直接上 Kafka

维度 Redis Streams Kafka
部署复杂度 0（复用 Redis Sentinel） 3 broker + KRaft 协调
持久化 AOF 默认强
单实例吞吐 ~10w msg/s 100w+/s
跨团队消费 弱（消费组数受限） 强（无上限）
历史回放 < 1 天（内存限制） 任意时间窗
学习成本 低（同 Redis） 高
运维成本 低 高（独立集群）
故障域 与缓存共享（不推荐资金强依赖） 独立

5.2.2 Kickoff 32 天赛季实际事件量级

事件 日均 峰值 QPS Streams 是否够
押注事件 bet.placed ~50w 800 ✓
派彩事件 bet.settled ~30w（批量） 5000（瞬时） ✓
打赏事件 tip.committed ~10w 500 ✓
充值回调 payment.recharge ~1w 50 ✓
提现状态 payment.withdraw ~5000 5 ✓
进场广播 room.enter ~5w 100 ✓
风控信号 risk.signal ~1k 10 ✓
审计写入 audit.write ~30w 200 ✓
弹幕 5000w 5w/s ★ ✗ 不进队列！直接 Pub/Sub

结论：除弹幕走 Redis Pub/Sub 外，所有业务事件 Redis Streams 单实例完全够用。

5.4 统一抽象层 internal/infra/stream/

package stream

type Producer interface {
    Send(ctx context.Context, topic string, key string, payload []byte) error
    SendWithTx(ctx context.Context, tx *sql.Tx, topic string, key string, payload []byte) error // 事务后异步发
}

type Consumer interface {
    Subscribe(ctx context.Context, topic, group string, handler MessageHandler) error
}

type MessageHandler func(ctx context.Context, msg *Message) error

type Message struct {
    Topic   string
    Key     string
    Payload []byte
    Offset  string // Streams: messageID; Kafka: offset
}

两份实现：

internal/infra/stream/
├── stream.go          # 接口定义
├── redis/
│   ├── producer.go    # XADD 写入
│   └── consumer.go    # XREADGROUP 消费 + ACK
└── kafka/
    ├── producer.go    # kafka-go 实现
    └── consumer.go    # consumer group 实现

切换时只改 DI 注入：

// cmd/api/main.go
if cfg.Stream.Driver == "kafka" {
    streamProducer = stream.NewKafkaProducer(cfg.Kafka)
} else {
    streamProducer = stream.NewRedisProducer(cfg.Redis)
}

5.5 消费者模式

5.5.1 消费组划分

消费组 处理 Topic Worker 名
settle-cg match.ended, bet.placed（统计） worker-settle
realtime-cg tip.committed, live.session.*, room.enter, level.upgraded worker-realtime
risk-cg bet.placed, tip.committed, payment.*, live.disconnected, risk.signal worker-risk
audit-cg audit.write worker-cron（落 ES/数据湖，可选）
notify-cg bet.settled, payment.recharge.paid, payment.withdraw.approved worker-realtime（推站内信/短信）

5.5.2 幂等消费

每条消息必须可被重复消费而不出错。常见做法：

func HandleBetSettled(ctx context.Context, msg *Message) error {
    var ev BetSettledEvent
    json.Unmarshal(msg.Payload, &ev)

    // 幂等键 = 业务唯一标识
    key := fmt.Sprintf("consumed:notify:bet.settled:%d", ev.BetID)
    if ok, _ := redis.SetNX(ctx, key, "1", 7*24*time.Hour); !ok {
        return nil // 已处理过，幂等返回
    }

    // 真实业务逻辑（发站内信 / 推 WS）
    return notifyService.Send(ctx, ev)
}

5.5.3 重试与死信

错误类型 行为
临时错误（DB 抖动） 指数退避重试 3 次（1s / 5s / 30s）
业务错误（数据不存在） 重试 1 次后丢死信队列 <topic>.dlq
解析错误 直接丢死信队列 + 告警
死信队列 每日扫描 + 告警，人工处置

5.6 Kafka 升级硬触发条件（任一即升级）

触发条件 检测点
日订单（押注 + 充值 + 打赏 + 提现）> 50 万条 Prometheus 每日聚合
跨业务消费方 ≥ 3 个（如 v2 引入推荐 / 数据分析 / 财务 BI） 评审时识别
需要事件回放 > 24h 业务需求
Redis 集群成为消息瓶颈（队列堆积 > 10w 持续 5min） 告警
团队拆分（消费方在不同团队 owner） 组织变化

5.7 Kafka 升级路径

Step 1: 部署 Kafka 集群（3 broker KRaft + 16c/32GB/SSD），保留 30 天
Step 2: 创建对应 Topic（按 §5.3 规划）
Step 3: 双写阶段（2 周）：业务侧同时写 Streams + Kafka，消费方仍读 Streams
Step 4: 验证 Kafka 数据完整性（offset 全覆盖，无丢失）
Step 5: 消费方切到 Kafka（按 worker 一个个切，灰度）
Step 6: 验证 7 天稳定后停 Streams 生产
Step 7: 保留 Streams 30 天作为应急回滚
Step 8: 清理 Streams

5.8 消息丢失的容忍度

事件类型 容忍度 设计
资金类（押注、派彩、充值、提现） 零丢失 DB 事务内已落账，队列仅通知
通知类（站内信、短信） 可容忍延迟 / 偶发丢失 重试 + 死信 + 人工补
统计类（GMV、排行榜） 可容忍延迟 周期性重算
实时类（弹幕、进场） 可容忍丢失 UDP-like 行为，过即过
审计类 零丢失（合规） 同步写 DB audit_log + 异步落数据湖

关键不变式：所有强一致资金状态变更必须先在 DB 事务内完成，队列消息仅作通知，不能依赖队列的"至少一次"语义保证业务正确性。

5.9 监控指标

指标 阈值
Streams 队列长度（XLEN） > 10w 告警
Streams 消费 lag > 5 min 告警
Kafka topic lag > 10w / > 5 min 告警
死信队列长度 增长率 > 100/h 告警
消费失败率 > 1% 告警
Producer 发送失败率 > 0.1% 告警

5.10 ADR-0005 决策记录

  • 决策：v1 上 Redis Streams 起步，按 §5.6 触发条件升级 Kafka
  • 理由：32 天赛季 + 团队 < 6 人 + 业务事件量未达 50w/日 → 复杂度收益不成正比
  • 风险：若赛季中突破 50w/日 → 触发紧急升级（已有预案 §5.7）
  • 抽象层 internal/infra/stream/ 提前预留，迁移成本可控
