一、背景

用户反馈：全量预热后“东京访问仍慢”。
排查结论：09-02 的全量预热从巴西 GRU 单区执行；CF Worker Cache API
按 zone + PoP 隔离，东京 NRT 边缘仍是冷缓存。

二、东京现状实测（预热前）

东京 NRT 边缘（临时 e2-micro/e2-standard-2，已删）：
  pg6-static…1834850/index.html：首访 DYNAMIC TTFB 1.72s -> 二次 HIT 0.08s
  pg-static…85/c445ebb91e.cadb1.json：首访 DYNAMIC 1.75s -> HIT 0.07s
  其它 zone（p8m7xv 等）同样首访 DYNAMIC
动态链路（结构性，与静态无关）：
  api.xqv9m8.icu/health 东京约 0.33s（恒定回巴西源站）

三、东京边缘全量预热执行

节点：GCP 临时 e2-standard-2 asia-northeast1-a（先试 e2-micro 太慢已删除）
脚本：docker/scripts/cdn_warm_static.py --assets --health --threads 32
结果：
  入口 + 同源 JS/CSS 全量跑完；瞬时 ERR 1560（大入口超时，同 GRU 模式）
  -> cdn_warm_urls.py 低并发重试 1560/1560 全恢复；
  health.json：280/280；
日志留档：/tmp/tokyo_warm.log（本地副本）。

四、复测（东京预热后）

14 前缀 health.json × 2 zone + 真实入口样例（c445/1834850/1897678）
= 31/31 cf-cache-status=HIT；
TTFB：pg6 index 由首访 DYNAMIC 1.72s -> HIT 30-42ms（约 40-55 倍提升）。

五、结论与后续

1) 静态“首次点击慢”在东京已解决（全部厂家 20 zone 已暖 NRT 边缘）；
2) 若用户仍慢，剩余为动态链路：游戏页 HTML/API 回巴西源站（东京 api/health
   约 0.33s 恒定；游戏启动 API 若干次往返），需 Asia 边缘缓存/实例方案
   （见 2026-09-02-2114 F12 文档 P0 项与 2026-08-29-0005 方案 B/C 评估）；
3) 后续每次发布需“分地区预热”：GRU（巴西）+ NRT（东京）+ 其它用户区，
   建议把该步骤并入发布按钮/CI（当前 bot 按钮为单区 GRU，需扩展多区）。
