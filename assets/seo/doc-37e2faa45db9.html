本文记录 2026-07-04 PG 特殊资源包拆分静态域名的维护变更，供后续 AI / Codex / 运维助手接手时快速理解现场。

背景

测试反馈 PG 部分游戏进入后出现认证登录类报错。排查平台 API 日志时，服务端 p_login 链路本身能正常完成并生成 launcher，但日志里能看到特殊游戏只带了单个静态域名，例如 PG65 只返回：

['pg4-static.xqv9m8.icu']

这会让 PG3 / PG4 / PG5 三组特殊资源包没有完整的静态域名池，前端资源选择和容灾能力不足。

本次目标：

  • PG3 / PG4 / PG5 的 static_hosts 从单域名扩成完整 22 个域名。
  • 宝塔 Nginx 同步把 22 个域名映射到对应静态目录。
  • 发布 platform-api，让游戏登录生成的 launcher 使用完整域名池。
  • 每次类似大维护变更后，在 docker/doc 新增日期格式维护 prompt 文档。

涉及游戏分组

PG 特殊资源包目前在 platform-api/conf/domains/pg.json 的 special_games 内维护：

pg3: 1799745, 2100928, 1849515, 1940257, 1981965, 67
pg4: 65, 74
pg5: 91

目录映射：

/www/wwwroot/pg3-static -> pg3-static.*
/www/wwwroot/pg4-static -> pg4-static.*
/www/wwwroot/pg5-static -> pg5-static.*

每组各 22 个静态域名，共 66 个新静态域名入口。

代码变更

已修改：

platform-api/conf/domains/pg.json

关键提交：

132b99a ops: route pg split static domains
1d61a87 ops: fill pg3 game hosts
442378e ops: expand pg split static hosts

注意：

  • 132b99a 创建 PG3 / PG4 / PG5 特殊静态域名分流，并在 game_domains_manager.py 增加空数组兜底能力。
  • 1d61a87 显式补上 PG3 的 game_hosts，避免配置层看起来为空。
  • 442378e 把 PG3 / PG4 / PG5 的 static_hosts 全部扩成 22 个。

当前期望：

PG 67  -> static_hosts=22, game_hosts=22, static prefix=pg3-static
PG 65  -> static_hosts=22, game_hosts=22, static prefix=pg4-static
PG 74  -> static_hosts=22, game_hosts=22, static prefix=pg4-static
PG 91  -> static_hosts=22, game_hosts=22, static prefix=pg5-static
PG 135 -> static_hosts=22, game_hosts=22, static prefix=pg-static

宝塔 Nginx 变更

宝塔服务器：

192.0.2.8

Nginx 配置文件：

/www/server/panel/vhost/nginx/pg3-static.xqv9m8.icu.conf
/www/server/panel/vhost/nginx/pg4-static.xqv9m8.icu.conf
/www/server/panel/vhost/nginx/pg5-static.xqv9m8.icu.conf

每个配置文件只保留一个站点文件，但 server_name 扩成该组 22 个域名，分别指向：

root /www/wwwroot/pg3-static;
root /www/wwwroot/pg4-static;
root /www/wwwroot/pg5-static;

已执行：

/www/server/nginx/sbin/nginx -t
/www/server/nginx/sbin/nginx -s reload

结果：

3. 登录日志观察

变更前查看平台 API 近期日志：

  • p_register、p_login、on_user_login 能正常完成。
  • launcher 能正常生成。
  • 日志中 PG65 当时只输出 ['pg4-static.xqv9m8.icu']，说明问题重点不是平台 API 登录主链路失败，而是特殊资源包静态域名池过窄。

后续测试时，如仍看到“认证失败”，优先再查：

/opt/pgserver/logs/bizops-platform-api-release-01/platform-api.log
/opt/pgserver/logs/bizops-platform-api-release-02/platform-api.log
