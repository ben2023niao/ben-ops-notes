访问域名过程 客户端-pc-h5-apk-app --> 业务域名

业务域名 --> DNS服务器返回 A CNAME 等记录 --> 客户端-pc-h5-apk-app

                                                                                             --> A 记录                          -->  直接请求源服务器 web服务(nginx apache) -->  服务器判断是否有证书 ssl --> 根据(nginx apache)配置路由到后台
                                                                                             --> A 记录+txt等证书记录 -->  直接请求源服务器 web服务(nginx apache)                                                   --> 根据(nginx apache)配置路由到后台

客户端-pc-h5-apk-app --> 根据缓存策略缓存DNS解析信息 --> CNAME记录 --> 直接请求cdn --> HYU TFSs 自建CDN --> CDN验证判断证书ssl --> 根据压缩和缓存等规则返回 html css js 以及图片静态资源 --> 客户端-pc-h5-apk-app 域名 | 异常 | 切入 V --> CLF --> CDN验证判断证书ssl --> 根据压缩和缓存等规则返回 html css js 以及图片静态资源 --> 客户端-pc-h5-apk-app

获取到前台代码 浏览器工作流程：构建DOM -> 构建CSSOM -> 构建渲染树 -> 布局 -> 绘制 客户端-pc-h5-apk-app --> 解析HTML --> 生成DOM树 --> 解析CSS --> 生成cssom树 --> DOM树和CSSOM树结合生成渲染树(Render Tree) --> Painting(重绘):根据渲染树以及回流得到的几何信息，得到节点的绝对像素 --> Display: 将像素发送给GPU调用操作系统Native GUI的API绘制页面上。 A | | V Layout(回流):根据生成的渲染树，进行回流(Layout)，得到节点的几何信息（位置，大小）

  • CSSOM会阻塞渲染，只有当CSSOM构建完毕后才会进入下一个阶段构建渲染树。(页面白屏环节原因)
  • 通常情况下DOM和CSSOM是并行构建的，但是当浏览器遇到一个不带defer或async属性的script标签时，DOM构建将暂停，如果此时又恰巧浏览器尚未完成CSSOM的下载和构建，由于JavaScript可以修改CSSOM，所以需要等CSSOM构建完毕后再执行JS，最后才重新DOM构建。

(页面白屏原理)

动态链路 用户登录(token+redis) 客户端-pc-h5-apk-app(生成一个唯一标识ID) --> 业务域名 --> api域名 --> CDN --> netscaler防火墙 --> 后端服务器nginx(检查ssl/请求方法/跨域/token/ip/地区/url资源地址/伪静态等) --> 根据负载算法proxy到upstream配置的vip --> mysql数据库查询用户是否存在

用户存在 --> 携带传递ID和token --> 中间件redis集群是否命中用户uuid --> 还在有效期内就正常登录/失效就掉线重新登录

var uuid = "user-token:" + UUID.randomUUID();
 redisTemplate.opsForValue().set(uuid, byUsernameAndPassword.getId().toString(), 30, TimeUnit.MINUTES);
 return new Result<>(true, uuid);

用户不存在 --> mysql返回json --> 前台js代码提示用户不存在并引导注册 前端在请求头中放入Token,之后从请求头中获取Token,从Redis中获取token是否存在,存在返回为true并且重新设置有效期,不存在就返回false设置响应状态为401 参考代码

前端框架漏洞 redis DB库没区分导致冲突 目录遍历 redis安全没做导致被黑 防火墙/CDN限制到真实用户ip 3方短信/验证码异常 密码弱加密被破解 前后端拦截检查不到位被sql注入/空字符绕过等 xss漏洞注入导致Cookie、SessionID等泄漏

CSRFnginx配置 * 被伪造跨站 携带上用户Cookie登录/json劫持等 XML格式数据的XEE攻击 SSLStrip 攻击 OpenSSL Heartbleed 安全漏洞 CCS 注入漏洞 证书有效性验证漏洞 文件换后缀/类型上传 业务漏洞是跟具体的应用程序相关，比如参数篡改（连续编号 ID / 订单、1 元支付）、重放攻击（伪装支付）、权限控制（越权操作）等。

HTTP/1.1（RFC2616）规范定义了 HTTP TRACE 方法，主要是用于客户端通过向 Web 服务器提交 TRACE 请求来进行测试或获得诊断信息。当 Web 服务器启用 TRACE 时，提交的请求头会在服务器响应的内容（Body）中完整的返回， 其中 HTTP 头很可能包括 Session Token、Cookies 或其它认证信息。攻击者可以利用此漏洞来欺骗合法用户并得到他们的私人信息。

解决方案

禁用 HTTP TRACE 方法。 强制 HTTP/2.0 协议
