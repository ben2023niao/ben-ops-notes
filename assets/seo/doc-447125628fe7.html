一、根因：两层缓存都在“帮倒忙”，其中一层根本不在 Worker 里

1. pp 这次改的是不带 hash 的稳定文件名

最近改动对象（gs://newgg2-bizops-gcs-pp-static，2026-10-14）：
  gs2c/common/v5/games-html5/games/vs/vs20frankie/mobile/build.js
  …/packages/pt_GUI_mobile.json、id_GUI_mobile.json、zh_GUI_mobile.json …
  …/game/main_resources001.json、…012.json、…015.json
拓展名分布：json 56 / png 7 / js 3 / css 1 / jpg 1
→ 文件名**没有内容哈希**，URL 不变；只要缓存没到期，用户就一直用旧文件。

2. 真正覆盖策略的是 zone 级规则（xqv9m8.icu），不是 Worker

两条规则（表达式都匹配 *-static.xqv9m8.icu 与 vendor_a-statics.xqv9m8.icu）：
  A) http_response_headers_transform / statics-cache-response
     → 对所有响应 **强制 set Cache-Control: public, max-age=604800**
       （所以 Worker 里按资源类型设置的头完全没用；连 GCS 的 404 也会被浏览器/边缘拿住 7 天）
  B) http_request_cache_settings / statics
     → cache=true，**edge_ttl=604800 + override_origin**
       （边缘忽略源站头，一律缓存 7 天；这也是 2026-10-14「404 被缓存 7 天」的真正原因）

排查过程的关键点：
  · 新版 Worker 已 100% 部署、拉回来的线上源码与本地 md5 完全一致，但响应头仍是 604800
    → 说明不是 Worker 没生效，而是**别的层在覆盖**；
  · 顺手发现：10-14 那个 404 也带 max-age=604800，而 Worker 只对 200 设置 Cache-Control，
    → 该头必然来自 zone 规则，顺这条线找到了上面两条规则。
  · 另外 3 个抽查 zone（q7m9v8.icu / t6qv8m.icu / vendor_a-cdn-2026.icu）**没有这两条规则**，
    所以本次只需修 xqv9m8.icu 一个 zone。

3. Worker 自身也有问题（即使没有 zone 规则）

旧逻辑：fetch(cf:{cacheEverything:true, cacheTtl:604800}) + 对所有 200 设
        Cache-Control: public, max-age=604800
  · 浏览器缓存 7 天（含 HTML / build.js / *.json）→ 更新后用户看不到
  · 边缘缓存 7 天且缓存键不带版本 → 只能整 zone 刷新才能失效，影响其它厂家
  · cacheEverything 连 404 也缓存 → 文件补上后被旧 404 挡 7 天

二、修复内容（已部署并实测）

1. Worker（summer-wave-c94f，版本 58→59；源码已备份）

① 按厂家缓存版本（CACHE_VERSION）：
     CACHE_VERSION = { "pp-static": "v2" }
   只有列出的厂家在缓存键里带版本 → **只让 pp 的边缘缓存整体失效**，
   其它厂家缓存键保持不变（避免全站同时冷缓存）。
   以后要让某厂家缓存立刻失效：把它的版本号 +1 再部署即可，不用整 zone 刷新。

② 按资源类型的缓存策略 cachePolicy()：
      HTML                        → 浏览器 no-cache, must-revalidate；边缘 60s
      带 hash 的文件               → 浏览器 public, max-age=31536000, immutable；边缘 7d
        （识别规则：文件名含 8 位以上 hex，或 name.<4位hex>.<ext>，如 0.28720e9b.min.js）
      其它（build.js/*.json 等）   → 浏览器 public, max-age=300, must-revalidate；边缘 300s
      health.json                 → 60s

③ 边缘 TTL 用 cacheTtlByStatus：200-299 按上面的值、301-302 60s、**404 和 5xx = 0（不缓存）**；
   并加 try/catch 兜底：若运行时拒绝该参数就退回普通 fetch，保证最差情况也能正常回源。

④ 只有 pp 的缓存键变了（加了 /v2），因此 deploy 后 pp 的边缘缓存等于整体失效一次。

2. zone 规则（仅 xqv9m8.icu）

· http_response_headers_transform「statics-cache-response」→ 规则清空（不再强制 Cache-Control）
· http_request_cache_settings「statics」→ edge_ttl 改成 **respect_origin**
  （先备份到 /root/bizops-cf-backups/rulesets-20261017/xqv9m8.{headers,cache}.json）
· 注意：respect_origin 模式下不能同时带 default 值（API 报 20107），已去掉。

三、实测验证（巴西出口）

资源 修复前 修复后 判定
build.js（稳定文件名） public, max-age=604800 public, max-age=300, must-revalidate ✅ 5 分钟内生效
index.html public, max-age=604800 no-cache, must-revalidate ✅ 每次协商（GCS 有 ETag）
0.28720e9b.min.js（带 hash） public, max-age=604800 public, max-age=31536000, immutable ✅ 长缓存照样省带宽
health.json public, max-age=604800 public, max-age=60 ✅
不存在的路径（404） max-age=604800，第二次 HIT private, max-age=14400，连续两次都是 MISS ✅ 不再被缓存 
另外抽查 vendor_d-static（同 zone 的另一厂家）→ 同样拿到新策略（max-age=300），
说明规则改动对整个 zone 生效、且不同厂家互不影响缓存键。

四、⚠️ 需要知道的一个前提（给测试/开发）

本次修复管的是"今后的缓存策略"。
对于**已经用旧策略把文件缓存在自己浏览器里**的用户（最多 7 天），
服务端无法远程清掉他们的本地缓存 —— 这部分用户需要：
  · 强制刷新一次（手机浏览器清缓存/无痕窗口打开），或
  · 等他们本地缓存自然过期（旧 TTL 最长 7 天）。
一次性处理完以后，就按新的 5 分钟策略走了，不会再出现"更新了但很久不生效"。

六、运维手册

# 某厂家资源更新后，让它的边缘缓存立刻失效（不用整 zone 刷新）
#   1) 打开 docker/scripts/worker-js-cdn-代码备份/【线上在用】worker.js
#   2) CACHE_VERSION 里把该厂家版本号 +1（如 "pp-static": "v2" → "v3"）
#   3) 部署
python3 /root/cf_worker_deploy.py --script summer-wave-c94f \
  --file '【线上在用】worker.js' --backup-dir /root/bizops-cf-backups/$(date +%Y%m%d-%H%M%S) \
  --token-file /root/bizops-cf-workers.env

# 验证缓存策略（用 ?t= 绕开已有缓存，看真实响应头）
curl -s -o /dev/null -D - "https://pp-static.xqv9m8.icu/gs2c/..../build.js?t=$(date +%s)" \
  | grep -iE "^HTTP/|cf-cache-status|cache-control"

# 如果发现响应头又被“固定值”覆盖，先查 zone 规则（不在 Worker 里）：
#   GET /zones/<zone>/rulesets  → 看 http_response_headers_transform /
#   http_request_cache_settings 两个 phase
