一、vendor_a 的两个服务是什么

vendor_a HTTP   ：游戏接口（登录/旋转/事件上报），端口 9096，入口 /app/vendor_a/vendor_a.py
vendor_a WS2    ：实时推送 WebSocket，端口 8765，入口 /app/vendor_a/lifeservice/vendor_a_ws2.py
              对外路径 https://vendor_a-games.<域名>/lifeservice/ws2，握手成功返回 101
两者原本在同一个容器里跑（01 就是这样）；02 现在是拆成两个容器跑。

二、01 上「原始」的启动方式（单容器跑两个服务）

01 的容器 bizops-vendor_a-release-01 用的镜像 pgserver:master-1516f8dd，启动命令是 python /app/docker/scripts/start_service_group.py，靠一个环境变量声明要跑哪几个服务：

docker run -d \
  --name bizops-vendor_a-release-01 \
  --restart unless-stopped \
  -p 9096:9096 \
  -p 8765:8765 \
  -e SANIC_WORKER_ACK_TIMEOUT=120 \
  -e 'SERVICE_GROUP_CONFIG=[{"title": "vendor_a HTTP", "log_file": "vendor_a.log", "command": "python -u vendor_a/vendor_a.py"}, {"title": "vendor_a WS2", "log_file": "vendor_a-ws2.log", "command": "python -u vendor_a/lifeservice/vendor_a_ws2.py"}]' \
  -v /opt/pgserver/version.json:/app/version.json \
  -v /opt/pgserver/server_configs:/app/server_configs \
  -v /opt/pgserver/logs/bizops-vendor_a-release-01:/app/logs \
  -v /opt/game_results_datas/vendor_a:/app/game_result_datas/vendor_a \
  pgserver:master-1516f8dd \
  python /app/docker/scripts/start_service_group.py

要点：

· 一个容器里同时跑 HTTP 与 WS2，两个端口都发布（9096 + 8765）
· WS2 有没有起来，取决于 SERVICE_GROUP_CONFIG 里有没有那一条
· 镜像自带 PATH/PYTHONPATH=/app/VERSION_FILE_PATH/GAME_DOMAINS_PATH 等 env，
  容器只额外传了 SANIC_WORKER_ACK_TIMEOUT 和 SERVICE_GROUP_CONFIG

三、02 现在的启动方式（脚本化，每个厂家一个容器）

02 的容器不是手工一条条 docker run，而是脚本批量起：

/data/server-runtime/start.sh    用法: sh start.sh <厂商|all> <镜像tag>
/data/server-runtime/stop.sh     用法: sh stop.sh  <厂商|all>

镜像来自 03 上的私有 registry：192.0.2.1:5000/game-service-<厂商>:<tag>
当前 tag（本次）：20260916-ben-cb8f2c55
厂商列表：api pg vendor_a ppk pp vendor_c vendor_d g759 （端口 9090/9091/9096/9098/9099/9020/9018/9019）

start.sh 里给每个厂家拼的 docker 参数（原文摘录）：

docker_args="-d --name $container_name -p ${port}:${port} --restart=always \
  -v /data/server-runtime/share.so:/usr/local/lib/python3.11/site-packages/share.so \
  -v /data/server-runtime/server_configs:/app/server_configs \
  -v /data/server-runtime/version.json:/app/config/version.json \
  -v /data/server-runtime/xxxxxx.mmdb:/app/config/xxxxxx.mmdb \
  -v /data/server-runtime/conf/domains:/app/config/domains \
  -v /data/server-runtime/game_result_datas/${v}:/app/data/game_result_datas/${v} \
  -v /data/server-runtime/logs:/app/${appdir}/logs"
docker run $docker_args "$image"                     # 普通厂家：用镜像默认 CMD
docker run $docker_args "$image" python /app/vendor_a/vendor_b.py   # 只有 vendor_b 有特例入口

镜像是 game-service-vendor_a:20260916-ben-cb8f2c55，它的：

默认 CMD = /bin/sh -c python /app/${CURRENT_VENDOR}/${MAIN_ENTRY}
           （CURRENT_VENDOR=vendor_a、MAIN_ENTRY=vendor_a.py → 即只跑 HTTP，不跑 WS2）
内置 env = PYTHONPATH=/app、VERSION_FILE_PATH=/app/config/version.json、
           GAME_RESULT_DATAS_PATH=/app/data/game_result_datas/vendor_a、
           GAME_DOMAINS_PATH=/app/config/domains、SERVER_CONFIGS_PATH=/app/config/server_configs
镜像内已有 /app/vendor_a/lifeservice/vendor_a_ws2.py（WS2 入口就在镜像里）

所以 sh start.sh all 只会起 8 个厂家容器，vendor_a 只有 HTTP，没有 WS2 —— 这就是 02 缺 WS 的原因。 （docker 事件也印证：game-service-vendor_a-ws-prod 是后来单独 create/start 的。）

四、02 上手动启动 vendor_a WS2 的命令（可直接复制）

与 start.sh 的参数保持完全一致，只是容器名/端口换成 WS 的，并把入口换成 vendor_a_ws2.py：

docker run -d \
  --name game-service-vendor_a-ws-prod \
  -p 8765:8765 \
  --restart=always \
  -v /data/server-runtime/share.so:/usr/local/lib/python3.11/site-packages/share.so \
  -v /data/server-runtime/server_configs:/app/server_configs \
  -v /data/server-runtime/version.json:/app/config/version.json \
  -v /data/server-runtime/xxxxxx.mmdb:/app/config/xxxxxx.mmdb \
  -v /data/server-runtime/conf/domains:/app/config/domains \
  -v /data/server-runtime/game_result_datas/vendor_a:/app/data/game_result_datas/vendor_a \
  -v /data/server-runtime/logs:/app/vendor_a/logs \
  192.0.2.1:5000/game-service-vendor_a:20260916-ben-cb8f2c55 \
  python /app/vendor_a/lifeservice/vendor_a_ws2.py

重启（先删后起，幂等）：

docker rm -f game-service-vendor_a-ws-prod 2>/dev/null
# 然后重新执行上面那条 docker run

停止：

docker stop game-service-vendor_a-ws-prod && docker rm game-service-vendor_a-ws-prod

一键脚本（已放在 02 上）：/data/server-runtime/run_vendor_a_ws.sh

cd /data/server-runtime
sh run_vendor_a_ws.sh                      # 自动用与 vendor_a HTTP 容器相同的镜像 tag
sh run_vendor_a_ws.sh 20260916-ben-cb8f2c55  # 或指定 tag

本命令已在 02 上用临时端口 8766 实测通过（不碰线上 8765）： 容器正常启动、日志出现 🚀 WebSocket 服务已启动 ws://192.0.2.1:8765/ws2、握手返回 101 Switching Protocols。

五、验证（三层）

# 1) 本机端口：426 = WS 服务在听（正常的"需要升级协议"响应）
curl -s -o /dev/null -w '%{http_code}\n' http://192.0.2.1:8765/

# 2) 本机 WS 握手：期望 101 Switching Protocols
curl -s -D - -o /dev/null --http1.1 --max-time 8 \
  -H 'Connection: Upgrade' -H 'Upgrade: websocket' -H 'Sec-WebSocket-Version: 13' \
  -H 'Sec-WebSocket-Key: x3JJHMbDL1EzLkh9GBhXDw==' \
  http://192.0.2.1:8765/ | head -2

# 3) 公网（经 Cloudflare → 入口机 nginx → 后端）：期望 101
curl -s -D - -o /dev/null --http1.1 --max-time 8 \
  -H 'Connection: Upgrade' -H 'Upgrade: websocket' -H 'Sec-WebSocket-Version: 13' \
  -H 'Sec-WebSocket-Key: x3JJHMbDL1EzLkh9GBhXDw==' \
  https://vendor_a-games.xqv9m8.icu/lifeservice/ws2 | head -2

对应 nginx 开关（入口机 /etc/nginx/conf.d/00.vendor-upstreams.conf）：

upstream vendor_a_ws2_backend 里，「不带 down」的那台机器就是 WS2 当前的后端。
2026-09-18 晚已完成切换：vendor_a_ws2_backend -> 02 (192.0.2.1:8765)，
                          其余 8 个后端也全部在 02（01、03 全部 down 备用）。
要改回 01：把 01 那行去掉 down、02 那行加 down，nginx -t && systemctl reload nginx。

五·补、本次在 02 上的实际操作（已验证）

1) 脚本放到 02：/data/server-runtime/run_vendor_a_ws.sh（仓库来源 docker/scripts/run_vendor_a_ws_on_02.sh）
2) 在 02 上执行：sh /data/server-runtime/run_vendor_a_ws.sh
   → 自动用与 game-service-vendor_a-prod 相同的镜像 tag
   → 先删旧容器再起新的 game-service-vendor_a-ws-prod（8765，--restart=always，带 /data 挂载）
3) 验证：
   · 容器日志：🚀 WebSocket 服务已启动 ws://192.0.2.1:8765/ws2
   · 02 本机 http://192.0.2.1:8765/ → 426（在听）
   · 02 本机 / 入口机直连 192.0.2.1:8765 / 公网 wss://vendor_a-games.xqv9m8.icu/lifeservice/ws2
     → 全部 101 Switching Protocols
4) 随后把入口机 nginx 的 vendor_a_ws2_backend 从 01 切到 02（两台机器同步改 + reload）

六、建议：把 WS2 固化进 start.sh（避免每次手工补）

start.sh 目前只有 vendor_b 特例。建议按同样方式加一个 vendor_a WS 分支，例如在 for v in $ALL_VENDORS 循环之后追加：

# vendor_a WS2（与 vendor_a HTTP 同镜像，单独容器、单独端口）
if [ "$VENDOR" = "all" ] || [ "$VENDOR" = "vendor_a" ]; then
    WS_NAME="game-service-vendor_a-ws-prod"
    WS_IMAGE="${REGISTRY}/game-service-vendor_a:${VERSION_TAG}"
    [ "$(docker ps -a -q -f name=^/${WS_NAME}$)" ] && { docker stop "$WS_NAME" >/dev/null 2>&1; docker rm "$WS_NAME" >/dev/null 2>&1; }
    docker run -d --name "$WS_NAME" -p 8765:8765 --restart=always \
      -v /data/server-runtime/share.so:/usr/local/lib/python3.11/site-packages/share.so \
      -v /data/server-runtime/server_configs:/app/server_configs \
      -v /data/server-runtime/version.json:/app/config/version.json \
      -v /data/server-runtime/xxxxxx.mmdb:/app/config/xxxxxx.mmdb \
      -v /data/server-runtime/conf/domains:/app/config/domains \
      -v /data/server-runtime/game_result_datas/vendor_a:/app/data/game_result_datas/vendor_a \
      -v /data/server-runtime/logs:/app/vendor_a/logs \
      "$WS_IMAGE" python /app/vendor_a/lifeservice/vendor_a_ws2.py
fi

对应地，stop.sh 的 ALL_VENDORS 停止逻辑里也要能停掉它（docker stop game-service-vendor_a-ws-prod）， 否则 sh stop.sh all 之后 WS 容器还在跑。

七、注意事项

  1. 镜像来源：02 用的是 03 上的私有 registry 192.0.2.1:5000/game-service-vendor_a:<tag>； 02 上必须能拉到该 tag（本地已有就不需要拉）。01 用的是 pgserver:master-<commit>，两套镜像不同。
  2. 配置来源：02 的容器把宿主机 /data/server-runtime/... 挂进容器的 /app/config/...； 配置（version.json / conf/domains / server_configs）是从 03 rsync 过来的，更新配置后要重启容器生效。 之前那个手工起的 WS 容器没有挂载（用的是镜像内配置），建议按本文的命令带上挂载，与 vendor_a HTTP 保持一致。
  3. 端口不要写错：WS 是 -p 8765:8765；02 上 vendor_a HTTP 是 9096，PP/PPK/PlaySon/vendor_d 分别是 9099/9098/9020/9018（与 01 的 910x 不同）。
  4. WS 与 HTTP 可以切到不同机器：现在就是 HTTP 在 02、WS 在 01；切完一定要分别验证（HTTP 看 /health，WS 看 101）。
