一、按优先级排序的待办

# 问题 证据 建议改法 验收指标
1 主库仍有 ~244 query/s 的重查询没走从库 主库出流量只有 1.1 MB/s，却每秒扫描约 100 万索引键，返回文档仅 ~1,000/s（放大 1,047 倍） 低峰开 profiling level 1 / slowms 200 采样 1~2 小时，用 db.system.profile 聚合出查询形状；逐条确认只读查询是否走 MongoModel::on('slave1'/'slave2')；写路径伴生查询只能靠索引/投影降低扫描 主库 query 降到 100/s 以下、放大倍数 < 50
2 配置类集合被亿级重复查询（收益最大） game_category 14.41 亿次、adv 2.19 亿、user_task_list 1.42 亿、app_version 1.39 亿、user_sign_config（只有 1 个文档）1.33 亿 缓存层已具备（cache() + CacheKey，Redis db3），把这些集合接进缓存；UserSignConfigModel 有 27 处直接调用、AppVersionModel 24 处，需收敛到 Service 层统一走缓存（指南 B1/B2） 主库 query 从 ~300/s 降到 <100/s；top 里这些集合增速趋零
3 MongoModel.php:238 写失败 今日 17 条 insert 报错（job、user_game_follow），error 字段为空（" in .../MongoModel.php line 238"） 在 catch 里补充上下文：集合名、文档 id、原始 BulkWriteException message/写关注结果，便于复现 再出现时日志能看到具体原因
4 支付接口慢 10-16 slow_api 1,792 条，其中 recharge/create 1,532；slow.log 里 curl_exec 2,054 次（CommonUtil.php:278 → PaymentService.php:954/:1021） 第三方支付 HTTP 调用加 CONNECTTIMEOUT=2s、TIMEOUT=5s + 快速失败；下单先落库再异步补偿通道调用 slow_api 降到 200 条/天以内
5 日志体积（每天 9 GB） api_request 6.1 GB + api_response 2.9 GB / 天；app-logs 24h 增 13.9 GB 写入点 BaseApiController.php:208/:259：只记「≥200ms 或非 2xx 或白名单接口」，其余按 1/20 采样；api_response 不写完整 body app-logs 24h 增量 < 4 GB
6 Redis KEYS 周期阻塞 + 连接不复用 SLOWLOG 128 条里 KEYS 126 条（0.3~0.67 秒/次，平均 129 秒一次）；20 秒新建 5,984 个连接（≈299/秒） UserService.php:1861（登录踢下线，102/126 次）等 8 处 redis()->keys() 改 SCAN 游标或 Set 索引；开启 pconnect/连接池 SLOWLOG 中 KEYS 趋零；单命令无 >10ms
7 前端请求与静态资源 tracking/record 4.2 万、recordPageVisit 4.0 万、exposureCollect/report 2.8 万（20 万请求窗口）；C8I3s652.js 823 KB/次、G.svg 623 KB/次；网关 perip_ssr 限流 6.3 万次 埋点批量上报（20 条/5 秒合并）；首屏配置包合并；静态资源走 CDN、_nuxt/images 不回源网关 三个埋点接口调用量 -80%；网关静态命中归零
