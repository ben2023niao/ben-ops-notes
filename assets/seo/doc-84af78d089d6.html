乌托邦 团队成员协作与 AI 使用规则

本文件定义团队成员如何使用 乌托邦、如何给 AI Agent 派活、如何限制写入边界、如何 Review、如何验收，以及如何把项目实践反哺公共框架。

乌托邦 不是只约束 AI 的规则集合。它同时约束团队成员，因为 AI Native 团队里，团队成员的任务描述、边界设定、验收判断和合并决策会直接决定 AI 输出质量。

1. 设计目标

  1. 让团队成员知道什么时候该补 PRD、什么时候该补 OpenAPI、什么时候可以进入实现。
  2. 让每次给 Agent 的任务都有明确需求 ID、执行角色、允许写入目录、只读参考目录、禁止修改目录和验收证据。
  3. 让团队在 Monorepo 中做到“读全局，写局部”，避免不同角色和 Agent 随意跨目录改动。
  4. 让团队成员 Review 不只看代码能不能跑，还要检查需求、契约、架构能力、测试、日志、验收和上线风险。
  5. 让框架摩擦能被团队成员识别并提交为公共框架改进，而不是继续留在聊天记录或个人经验里。

2. 基本原则

  1. 团队成员是最终责任人，AI Agent 是高效率执行者，不是完成定义的裁判。
  2. 团队成员发任务时必须先给边界，不能只说“继续完成”“修一下”“做得像设计图”。
  3. Agent 可以读取全局上下文，但默认只能写入任务授权的目录。
  4. 跨边界改动必须先声明原因、影响面和需要的 owner review。
  5. 没有需求 ID 的实现任务只能进入需求澄清或 PRD 阶段，不能直接写代码。
  6. mock、fixture、fallback、静态数据和假状态必须被团队成员识别为“未闭环”，不能在 Review 中默认放过。
  7. 团队成员可以选择项目技术栈和实现节奏，但不能降低 PRD、契约、日志、红蓝对抗和验收底线。

3. 角色责任边界

角色 主要负责 默认允许写入 必须协同
Product Owner 需求、范围、不做什么、验收标准 docs/prd/**、docs/project/** Tech Lead、QA、Design
Tech Lead 架构、目录边界、技术栈、质量门禁、合并判断 docs/architecture/**、docs/decisions/**、project.config.json 所有 owner
Contract Owner OpenAPI、事件、错误码、DTO、接口文档源头 packages/contracts/**、docs/api/** 前端、后端、QA
Frontend Owner Web、Admin、UI 状态、真实接口接入 apps/web/**、apps/admin/**、packages/ts/**、packages/ui/** Contract、Backend、QA
Mobile Owner App、移动端页面、真机视口、App 发布材料 apps/mobile/**、packages/ts/mobile/**、packages/ui/mobile/** Contract、Backend、QA
Backend Owner Go Gin、Laravel、Realtime、Worker、数据一致性 services/**、packages/go/**、packages/php/** Contract、DB、Ops、QA
QA Owner 测试计划、验收矩阵、E2E、回归证据 docs/qa/**、tests/** Product、Frontend、Backend
Ops Owner 环境、部署、回滚、密钥、备份、事故响应 infra/**、docs/operations/** Backend、Security、Tech Lead
Framework Owner 公共规则、模板、validator、preset、sync、升级策略 framework/**、scripts/**、docs/agents/rules/**、docs/templates/** Tech Lead、项目 owner

角色边界不是为了阻止协作，而是为了让跨边界协作有记录、有 Review、有责任人。

4. Solo 与团队模式

乌托邦 支持多种使用模式，但完成底线不变。

模式 适用场景 使用方式
solo-monorepo 个人开发、早期验证、小型项目 可以一个人负责多角色，但仍然要写需求 ID、契约、日志和验收证据。
team-monorepo 推荐团队模式 所有事实源在一个仓库，每个角色和 Agent 只管理授权目录。
hybrid-remote App、服务或构建链路变重 乌托邦 主仓保留 PRD、契约、QA、日志，业务代码可 remote，但必须回传验证证据。
federated-polyrepo 大团队、多业务线、多服务独立发布 乌托邦 作为中央事实源和治理中心，各业务仓库按需求 ID、契约版本和验收证据联动。

团队早期优先使用 team-monorepo。不要因为担心仓库大而过早拆 remote；先把角色边界、目录写入边界和 MR 门禁跑顺。

5. 任务发起规则

团队成员给 Agent 派活前，必须提供或确认以下信息：

  1. 需求 ID：来自 docs/prd/requirements.md。
  2. 背景和目标：说明为什么做、做到什么程度。
  3. 范围和不做什么：避免 Agent 自行扩大范围。
  4. 执行角色：product、contract、frontend、mobile、backend、qa、ops、framework 等。
  5. allowedWritePaths：本次允许写入的目录。
  6. readOnlyPaths：允许读取但默认不能写的参考目录。
  7. forbiddenPaths：本次明确禁止修改的目录。
  8. requiresReview：跨边界或高风险变更需要谁 Review。
  9. 验收标准：自动化测试、手工/E2E、截图、日志、红蓝对抗、上线证据。
  10. 是否涉及架构能力门禁、运维门禁、数据表规范、权限和审计。

推荐使用：

docs/templates/team-member-task-brief-template.md

如果团队成员无法一次性给全，Agent 应先补任务说明或标记待确认，而不是直接猜实现。

6. Agent 使用规则

团队成员使用 Agent 时应遵守：

  1. 先让 Agent 读 PRD、OpenAPI、设计、架构、QA 和现有日志，再让它实现。
  2. 明确告诉 Agent 当前任务是文档、契约、实现、测试、运维还是框架改进。
  3. 对实现任务要求 Agent 给出小步计划，尤其是前后端、后台、支付、权限、上线类任务。
  4. 对复杂任务要求 Agent 更新验收矩阵和工作日志，而不是只返回口头总结。
  5. 对 UI 任务要求真实视口、截图证据、接口状态和 console 检查。
  6. 对后端任务要求服务端测试、错误路径、鉴权、审计和数据一致性说明。
  7. 对框架任务要求说明是否可复用、是否项目污染、是否需要 validator。
  8. 当 Agent 输出“完成”时，团队成员必须核对 docs/qa/acceptance-evidence.md 和 docs/agents/logs/**，不能只看最终回答。

7. 目录写入边界

默认规则是：

读全局，写局部。

允许读取：

  1. README.md
  2. AGENTS.md
  3. docs/prd/**
  4. packages/contracts/**
  5. docs/architecture/**
  6. docs/qa/**
  7. docs/agents/logs/**
  8. 任务相关 app、service、package 目录

默认禁止跨角色写入：

  1. 前端 Agent 不应直接改后端服务实现，除非任务 brief 授权。
  2. 后端 Agent 不应直接改 UI 设计和页面布局，除非任务 brief 授权。
  3. QA Agent 不应直接改业务实现来让测试通过，除非任务 brief 授权。
  4. Framework Agent 不应把项目专属规则写进公共框架。
  5. 任意 Agent 不应删除用户资料、设计图、PRD 或历史日志。

跨边界必须记录：

requestedWritePaths:
  - packages/contracts/**
reason: "前端发现接口缺少错误码，需要更新契约"
requiresReview:
  - contract-owner
  - backend-owner

8. 团队成员 Review 规则

团队成员 Review 不只看代码差异，还要看交付闭环：

  1. 需求 ID 是否存在且状态正确。
  2. PRD 是否清楚说明范围和不做什么。
  3. OpenAPI、事件、DTO 是否已更新。
  4. 数据模型、迁移、索引、账本、审计是否符合规范。
  5. 是否越过 allowedWritePaths。
  6. 是否有自动化测试、手工/E2E 或截图证据。
  7. 是否有 Agent 日志和红蓝对抗。
  8. 是否涉及架构能力门禁，是否写明不适用原因。
  9. 是否涉及上线，是否有部署、回滚、密钥、备份和观测说明。
  10. 是否把项目专属经验误写成公共框架规则。

Review 结论只能是：

  1. 允许合入
  2. 有条件允许合入
  3. 不允许合入

不能用“看起来可以”“应该没问题”替代明确结论。

9. Git 与 MR 使用规则

Git 是协作边界，不只是提交代码。

  1. 每个 MR 必须说明需求 ID、执行角色、改动范围、测试和风险。
  2. 涉及跨目录改动时，MR 描述必须列出 requestedWritePaths 和 owner。
  3. CODEOWNERS 或人工 owner 必须覆盖契约、后端、前端、QA、运维和框架关键目录。
  4. 框架升级 MR 和业务功能 MR 尽量拆开。
  5. 大任务要拆小 MR，避免一次 MR 同时改 PRD、OpenAPI、前端、后端、运维和框架。
  6. 未通过 npm run check、npm run check:init 或项目约定门禁时，不允许合并。

10. 验收和上线规则

团队成员验收必须从整个项目闭环判断，不只验单端：

  1. 前端页面必须能走真实或明确受控的 API 状态。
  2. 后端接口必须符合 OpenAPI。
  3. 后台功能必须有登录、鉴权、权限和审计证据。
  4. QA 必须更新 docs/qa/acceptance-evidence.md。
  5. 项目级模块闭环必须更新 docs/qa/project-acceptance.md。
  6. 上线前必须检查 docs/operations/ops-readiness.md。
  7. 如果某项仍是 mock、placeholder、fixture 或配置待接入，状态只能是 进行中、阻塞 或 不适用，不能写 已完成。

11. 框架反哺规则

团队成员在项目实践中发现以下问题，应推动 乌托邦 改进：

  1. Agent 经常漏读某类文件。
  2. Review 经常发现同类假完成。
  3. 某类需求每次都要重复解释。
  4. 目录边界、owner、CODEOWNERS 或 MR 描述不清。
  5. 验收证据字段不够用。
  6. 运维、架构或数据表规则缺少可执行门禁。
  7. 新项目初始化仍需要大量人工补目录或补配置。

改进公共框架时必须判断：

  1. 是否可复用。
  2. 是否可配置。
  3. 是否可验证。
  4. 是否会污染其他项目。
  5. 是否需要更新 framework.sync.json、framework.config.json、CHANGELOG.md、PRD 和 Agent 日志。

12. 不允许的团队成员偷懒模式

  1. 只口头告诉 Agent 需求，不登记需求 ID。
  2. 让 Agent “边写边猜”，事后再用截图或浏览器报错纠正。
  3. 明知是 mock 或假数据，却让 Agent 写“完成”。
  4. 让一个 Agent 同时随意改前端、后端、契约、运维和框架。
  5. MR 只看页面，不看契约、鉴权、错误态、日志和验收矩阵。
  6. 项目踩坑后只在聊天里复盘，不沉淀到文档、模板或 validator。
  7. 因为是 MVP 就跳过 PRD、契约、日志、红蓝对抗和上线检查。

13. 常用清单

13.1 给 Agent 派活前

  1. 需求 ID 已存在。
  2. PRD 和验收标准已明确。
  3. allowedWritePaths 已明确。
  4. readOnlyPaths 已明确。
  5. forbiddenPaths 已明确。
  6. requiresReview 已明确。
  7. 涉及接口时 OpenAPI owner 已明确。
  8. 涉及上线时 Ops owner 已明确。

13.2 Review 前

  1. npm run check 已运行或说明失败原因。
  2. Agent 日志已写。
  3. 验收证据已更新。
  4. 红蓝对抗有明确结论。
  5. 跨边界改动有 owner。
  6. mock 和未完成项没有被包装成完成。

13.3 框架升级前

  1. 先运行 devtools/framework plan。
  2. 区分 Managed 和 Advisory。
  3. 不自动覆盖业务 PRD、业务代码和业务验收。
  4. 升级后运行 npm run check。
  5. 升级 MR 写清影响范围、风险和回滚方式。
