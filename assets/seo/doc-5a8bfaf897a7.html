处理结论

这次不是单个游戏资源包问题，也不是 PG 静态资源同步问题。

根因是 PG 客户端会把部分动态入口域名里的 m. 误替换为 api.：

pg-games.t6qv8m.icu -> pg-games.t6qv8api.icu
pg-games.6qv8m.icu  -> pg-games.6qv8api.icu

误拼出来的域名没有 DNS，请求不会到 Cloudflare / 宝塔 / 后端，页面表现为卡 50% 或登录失败重试，后端日志看不到 verify。

最终运维侧采用规避方案：

从 PG 全部动态入口 game_hosts 下线：
pg-games.t6qv8m.icu
pg-games.6qv8m.icu

覆盖范围是全 PG 分发池，不是只处理单个游戏：

default.game_hosts
special_games.pg3.game_hosts
special_games.pg4.game_hosts
special_games.pg5.game_hosts

每组 game_hosts 从 22 个变成 20 个。static_hosts 不变。

后续维护规则

PG game_hosts 后续禁止加入任何 m.icu 结尾动态入口域名。

发布脚本已加预检：

docker/deploy/update_pgserver.py
check_pg_domain_preflight()

触发条件：

发布 platform-api 或 all 时读取 platform-api/conf/domains/pg.json。
如果 default / pg3 / pg4 / pg5 的 game_hosts 出现 host.endswith("m.icu")，直接中断发布。

Python 维护约定

后续这类运维操作尽量使用 Python 实现，少写长 shell：

1. JSON 配置读取、域名池扫描、游戏列表比对，用 Python。
2. 远程核验可以用 Python subprocess 调 ssh，不要拼多层复杂 shell。
3. Telegram 通知用 Python urllib / requests 调 API。
4. shell 只作为启动器使用，例如 ssh 到宝塔、docker exec 启动 Python。
5. 如果某段 Python 核验逻辑会重复使用，沉淀到 docker/scripts 或 docker/deploy 里。

本次踩过的坑：

1. 多层 ssh + docker exec + here-doc 很容易引号错乱。
2. docker exec 传 stdin 时必须带 -i，否则 Python 代码不会进入容器。
3. 长时间发布命令建议写日志文件或由机器人执行，避免 SSH 断开后看不到输出。

后续如果测试仍反馈卡 50%

先收集：

1. 完整但脱敏后的入口域名和 game_id。
2. Console 里第一个失败的接口域名和错误码。
3. Network 里 verifyOperatorPlayerSession / GameInfo / Resources / Spin 的状态。
4. 当时落到的 pg-games host 和静态资源 host。

判断顺序：

1. 如果仍是 t6qv8api / 6qv8api，说明仍有旧 API 容器或旧配置在服务。
2. 如果是 verify 到了后端但返回错误，看后端 token / gid / IP 限制。
3. 如果是静态资源 404，再回到 pg-static / pg3-static / pg4-static / pg5-static 和 GCS/CDN 同步链路排查。
