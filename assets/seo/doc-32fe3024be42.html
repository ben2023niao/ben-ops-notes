一、用户反馈

vendor_b 还有跨域问题；动态域名有跨域。
（上一轮刚把 vendor_b 静态改成走 vendor_b 自己的大阪桶，并修好了 vendor_b 崩溃。）
本轮按要求不通知飞机群。

二、排查：动态域名现在的 CORS 实测（都正常）

1) 带 Origin 的 GET（Origin: https://vendor_b-static.k8x2v9.shop）
   vendor_b-games.k8x2v9.shop/health  -> 200 + access-control-allow-origin: <回显 Origin> + allow-credentials: true
   vendor_b-games.m4q7z1.shop/health  -> 同上
   vendor_b-games.hkcloudplay06.com   -> 同上（CF 链路）
   api.* / socket.p3w9n5.shop / pg-games.*  -> 同样回显 Origin
2) OPTIONS 预检（POST /sso-login.api、/webservice/...）
   -> 204 + allow-origin 回显 + allow-methods + allow-headers + max-age 86400
3) 4xx / 5xx（后端产生的）
   GET 不存在路径 -> 404 且带 ACAO ｜ POST 空 body -> 400 带 ACAO ｜ POST 无 key -> 500 带 ACAO
   => 后端（Sanic）的 CORS 中间件对错误响应同样生效，浏览器不会误报跨域。
4) 结论：**动态域名本身没找到缺 CORS 的接口**（三条链路口径一致）。

三、唯一的真实缺口：nginx 自己产生的网关错误没有 CORS 头

当后端容器不可用/超时时，是 **nginx** 直接返回 502/503/504（不是后端返回），
这类响应原来不带任何 CORS 头 -> 浏览器把「网关错误」显示成「跨域/CORS 报错」，
让人误以为是 CORS 配置问题。10-05 vendor_b 崩溃（进程 restarting、9093 没监听）期间
用户看到的「跨域」就是这个现象：真正的错误是 502。

修复（standby nginx 动态代理片段）

# /etc/nginx/snippets/bizops-hk-standby-proxy.conf（被 23 个动态 location include）
proxy_hide_header Access-Control-Allow-Origin;      # 先隐藏后端那一份
add_header Access-Control-Allow-Origin $http_origin always;   # 由 nginx 统一输出一份
add_header Vary "Origin" always;

要点：
  · 必须 hide + add 成对 —— 否则会出现两个 Access-Control-Allow-Origin，浏览器一样报错；
  · `always` 让 4xx/5xx（含 nginx 自产的 502/503/504）也带上 CORS 头；
  · 回显 Origin 与后端原本的行为一致（后端对任意 Origin 都回显），所以不改变现有语义；
  · Vary: Origin 避免任何中间层按 Origin 串缓存。
备份：/etc/nginx/snippets/bizops-hk-standby-proxy.conf.bak-20261005（服务器上）
同步入仓：docker/deploy/hongkong/nginx-standby-proxy.conf

四、验证

带 Origin 请求：
  /health（200）        -> ACAO 条数 1 ｜ vary: Origin ｜ allow-credentials: true
  /nope-xyz（404）      -> ACAO 条数 1 ｜ vary: Origin ｜ allow-credentials: true
不带 Origin 请求：
  /health（200）        -> ACAO 条数 0（nginx 不会输出空值头，干净）
nginx -t 通过 + reload 成功。

五、如果还看到跨域

目前所有动态接口（含 4xx/5xx）都带正确的 CORS 头，若仍有个别用户报跨域，请提供：
  1) 浏览器控制台里那条报错的完整原文（是 CORS 还是别的，例如 Mixed Content / 502）；
  2) 报错请求的完整 URL 与请求头里的 Origin；
  3) 是否只在某个域名/某个游戏出现。
便于按具体请求定位（例如：把 API 打到了静态域名、或旧版本客户端缓存了错误地址）。
