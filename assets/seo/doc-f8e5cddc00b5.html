一、结论

旧 JumpServer 的运行版本为 1.4.8，审计记录显示攻击者从 2026-08-29 起使用 operator_a 身份向数据库、Redis、基础组件和代理节点投放恶意 ELF，并在 2026-11-06 夜间执行勒索 motd 与数据库目录删除。

本次处置已完成旧堡垒机隔离、IOC 取证与隔离、复发持久化根因清除、可访问主机的数据端口和 SSH 入口收敛，并恢复巴西 128、BJ、DS、DMG 的主要业务库。旧 JumpServer 按要求保持运行，只限制来源 IP，没有清理其内部数据。

二、范围与时间线

  • 原始资产基线：56 台，完成深度采集 51 台。
  • 新增 base 资产：9 台，全部完成扫描。
  • gate / room / redis / mq / proxy 分类资产：95 台，其中新增 85 台、已有基线 10 台。
  • 合并去重后共 150 台；本轮专项 IOC 复查覆盖当前可登录的 123 台。

三、安全处置

1. IOC 根因与隔离

128-redis01 的内存脚本来自 /usr/libexec/systemd-integritysetup，由 systemd-integritysetup.service 启动。脚本每 300 秒从 https://api.dnslogs.org/s/xdg-user-dirs 下载 3,112,200 字节 ELF，写入 /usr/lib/locale/.locale.pack，并以 root 启动。

恶意 ELF SHA256：2814921df5ae84da24a58c948594d493a70ed98bddc73b93e165af5756e78ac2。同哈希文件也存在于 paydb-db1 的 systemd-binfmt-wait.service。

处置结果：

  • 终止投放脚本和恶意 ELF 进程。
  • 停止、禁用并 mask systemd-integritysetup.service 与 systemd-binfmt-wait.service。
  • 隔离 .locale.pack、.sync-host-beacon 和恶意 unit 文件。
  • 隔离后持续观察超过 10 分钟，IOC、进程和 3112200 字节实文件均未再出现。
  • 对 123 台当前可登录服务器做专项复查，未发现第二处可运行的 systemd-integritysetup 或 binfmt-wait 持久化。

2. 网络与认证加固

  • 数据端口 3306 / 6379 / 5672 / 15672：仅允许 loopback、10/8、172.16/12、192.168/16，公网默认 DROP。
  • SSH：仅允许新/旧堡垒机、打包机、运维固定 IP 和私网来源。
  • 7 台原先允许 root SSH 的节点已关闭 root 登录与密码登录。
  • 17 台腾讯 proxy 保留 root 公钥登录，关闭 SSH 密码认证。
  • 所有变更先保存 iptables 或 sshd 配置备份，并通过 sshd -t 与实际参数回读。

六、未完成项与风险

  • 27 台服务器当前不可达或认证失败，不能标记为安全已完成。
  • 另一业务平台 当前没有完整主数据源；某业务平台 仅有 2026-05 历史备份。
  • PAY_PLATFORM 在线源可读，源/目标之间公网 3306 不通，目标已恢复 normal 模式且没有半成品数据。
  • 旧 JumpServer 仍为 JumpServer 1.4.8，虽已限制来源 IP，但其保存的历史凭据仍应视为泄露。
  • 全量 SSH key、DB/Redis/MQ 密码、云 API 密钥和旧堡垒机凭据仍需统一轮换。
  • sudo NOPASSWD、SELinux Disabled、CentOS 7 EOL 和 RPM 基线漂移仍属于系统性风险。
  • 对已 root 失陷的主机，最终安全基线应通过重装系统或可信镜像重建实现；当前结果不能替代重装。
