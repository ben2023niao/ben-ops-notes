问题

访问 vendor_b-static.hkcloudplay05.com/fg/ 时，CloudFront 返回 HTTP 403，响应来自私有 S3，错误码为 AccessDenied。

只读检查确认：

  • bizops-gcs-vendor_a-statics/fg/ 存在并返回 HTTP 200。
  • fg/ 是一个带 HTML 内容的尾斜杠对象；常规 rclone 会把这类对象视为目录标记，因此同步工具需要单独识别和上传。
  • vendor_b CloudFront 当前读取独立的 /vendor_b-static* S3 前缀，其中没有最新的 /fg/ 页面。
  • vendor_a 对外域名在 CN 环境未启用，不能让 platform-api 直接返回 vendor_a-statics* 域名。

修复模型

vendor_b 保留自己的对外域名和动态端口：

类型 对外名称 实际目标
默认静态 vendor_b-static* S3 /vendor_a-statics；nginx 兜底到 bizops-gcs-vendor_a-statics
特殊组 1 vendor_b-static1* S3 /vendor_a-statics1；nginx 兜底到 bizops-gcs-vendor_a-statics1
特殊组 2 vendor_b-static2* S3 /vendor_a-statics2；nginx 兜底到 bizops-gcs-vendor_a-statics2
动态/API vendor_b-games* / vendor_b-api 两台后端 TCP 9093

这样 vendor_b 与 vendor_a 只有动态后端端口不同，前端对象只维护一份。

上线顺序

先备份三个 vendor_b CloudFront 分配配置，再依次执行：

python3 docker/deploy/hongkong/sync_gcs_to_s3.py vendor_a-statics
python3 docker/deploy/hongkong/sync_gcs_to_s3.py vendor_a-statics1
python3 docker/deploy/hongkong/sync_gcs_to_s3.py vendor_a-statics2

python3 docker/deploy/hongkong/create_cloudfront_static_distributions.py vendor_b-static
python3 docker/deploy/hongkong/create_cloudfront_static_distributions.py vendor_b-static1
python3 docker/deploy/hongkong/create_cloudfront_static_distributions.py vendor_b-static2

CloudFront 工具会先允许对应 vendor_b 分配读取共享 S3 前缀，再更新 OriginPath；仅在源路径发生变化时创建全路径失效请求。

同步工具会扫描 GCS 顶层目录标记，把其中非空的尾斜杠对象显式写入 S3，并只对发生变化的入口路径创建 CloudFront 失效请求，确保 /fg/ HTML 本身与其下级资源同时存在。

如需更新 nginx 兜底配置，安装仓库中的 nginx-bizops.conf 后先执行：

nginx -t

测试通过后再 reload，不能跳过语法检查。

验证

等待三个 CloudFront 分配均为 Deployed 后执行：

python3 docker/deploy/hongkong/validate_cloudfront_static.py
curl -fsS -o /dev/null -w '%{http_code} %{content_type}\n' https://vendor_b-static.hkcloudplay05.com/fg/

预期 /fg/ 返回 HTTP 200 和 HTML，不再出现 S3 AccessDenied。验证地址不需要携带登录 Token。

  • 当前 https://vendor_b-static.hkcloudplay04.com/pp/ 入口不再引用 astarte2、9330c、70ff4 或 vendor_bMain。
  • 当前 pp 入口实际引用的关键文件验证通过：
  • pp/：HTTP 200。
  • pp/src/import-map.a7842.json：HTTP 200。

  • fg/：HTTP 200。
  • fg/src/settings.00a8c.json：HTTP 200。

截图中的 9330c / 70ff4 请求判断为旧入口或浏览器站点缓存残留。已对 vendor_b-static、vendor_b-static1、vendor_b-static2 三个 CloudFront 分配提交并完成 /* 全量失效。测试复现时建议使用无痕窗口，或清理 vendor_b-static.hkcloudplay04.com 的站点缓存后重新进入。

同步工具已修正：GCS 顶层尾斜杠 HTML 对象会显式同步到 S3；校验时会扣除这类入口对象，避免 S3 比普通 rclone 源统计多出 marker 后误判失败。

2026-07-18 14:35 二次 403 复核

用户再次反馈 vendor_b-static.hkcloudplay04.com/pp/ 进入后 DevTools 中大量资源 403，截图中的典型 URL 为：

https://vendor_b-static.hkcloudplay04.com/astarte2/3.6/web-mobile/assets/vendor_bMain/config.9330c.json
https://vendor_b-static.hkcloudplay04.com/astarte2/3.6/web-mobile/assets/vendor_bMain/index.9330c.js
https://vendor_b-static.hkcloudplay04.com/astarte2/3.6/web-mobile/assets/vendor_bMain/config.70ff4.json
https://vendor_b-static.hkcloudplay04.com/astarte2/3.6/web-mobile/assets/vendor_bMain/index.70ff4.js

复核结果：

  • https://vendor_b-static.hkcloudplay04.com/pp/?apiId=10585 返回 HTTP 200。
  • 上述 4 个深层资源返回 HTTP 403，响应来自 Amazon S3。
  • AWS S3 私有桶 bizops-h5-hk-517506432530 中，vendor_a-statics、vendor_a-statics1、vendor_a-statics2 三个前缀均不存在上述 4 个对象。
  • GCS 源端 bizops-gcs-vendor_a-statics、bizops-gcs-vendor_a-statics1、bizops-gcs-vendor_a-statics2 均不存在上述 4 个对象。
  • 进一步检查当前香港配置内所有同步源桶：
  • bizops-gcs-pg-static
  • bizops-gcs-pg3-static
  • bizops-gcs-pg4-static
  • bizops-gcs-pg5-static
  • bizops-gcs-pp-static
  • bizops-gcs-ppk-static
  • bizops-gcs-vendor_d-static
  • bizops-gcs-vendor_a-statics
  • bizops-gcs-vendor_a-statics1
  • bizops-gcs-vendor_a-statics2

均不存在 astarte2/3.6/web-mobile/assets/vendor_bMain/*9330c* 或 *70ff4* 文件。

结论：

这批 403 不是 AWS 同步漏资源，也不是 CloudFront OriginPath 配错。vendor_b-static 当前 OriginPath 确认为 /vendor_a-statics，符合“vendor_b 复用 vendor_a 前端资源”的配置。403 的根因是当前测试链路或旧缓存引用了源端不存在的 vendor_b 线上版本资源。需要开发补齐对应资源，或调整入口/版本引用到源端真实存在的资源。

回滚

如果共享源路径导致异常，使用上线前保存的 CloudFront 配置和对应 ETag，将三个分配恢复到原 OriginPath：

vendor_b-static  -> /vendor_b-static
vendor_b-static1 -> /vendor_b-static1
vendor_b-static2 -> /vendor_b-static2

恢复后分别创建 /* 失效请求，并等待状态回到 Deployed。共享的 /vendor_a-statics* S3 对象是增量复制结果，不需要删除；Google 源桶也不得删除。
