方法

5 款同款游戏（Fortune Tiger 126/2196、麻将胡了 65/2223、寻宝黄金城 87/2218、 赏金大对决 135/2215、寻龙探宝 57/2201），每款两边各测： - 冷缓存：全新浏览器上下文 - 回访(warm)：同上下文再开一局（验证浏览器缓存 / 0-RTT / launcher host 记忆） 指标：出画(canvas) 与 网络稳定(idle 3s)。

结果（中位数，秒）

Fortune Tiger    6.6      5.4     1.0
麻将胡了         7.7      4.6     1.0
寻宝黄金城       6.1      4.3     1.0
赏金大对决       9.2      -       1.0

稳定    我方冷缓存  我方回访  竞品

寻龙探宝        11.2      8.2     4.0
汇总中位        10.7      7.9     4.0

（赏金大对决回访档超时未取到，样本 n=4。）

结论

  1. 回访档明显提升：出画 7.7s→4.9s（-36%）、稳定 10.7s→7.9s（-26%）；
  2. 冷缓存与上次基线基本持平（波动大）；report.js 边缘缓存生效，但冷启动大头仍是 游戏页回巴西的动态链路与游戏初始化；
  3. 竞品稳定 4.0s，我方回访 7.9s，差距从 2.4 倍收窄到约 2 倍。

证据：双方 Fortune Tiger 加载截图 + 对比柱状图已发群（有图有证据）。

复盘：剩余可优化点（按性价比）

P1 冷启动（7.7s canvas 大头）：游戏页 HTML/shared JS/内部 API 回巴西（动态不可缓存）
   -> 亚洲 platform-api 实例（B档，launcher/ticket/verify 就近）+ 最终游戏服务亚洲化（C档）
P2 CF Argo Smart Routing（付费）：优化 CF->巴西回源路径，省 100-200ms/请求
P3 launcher 彻底去掉客户端测速（服务端按 cf-ipcountry 直接定 host，ping 仅兜底）
P4 更多 GET 接口边缘缓存（game.list/配置类，短 TTL）
P5 前端：大厅封面图 WebP/懒加载（5.5MB->1MB）、APP 弹窗可跳过

补充：完整进游戏录屏测试与自动化脚本（2026-08-29 04:10）

应要求做"点击继续游戏 → 完整加载 → 录屏发群"： - 我方 5 款游戏（Fortune Tiger/麻将胡了/寻宝黄金城/赏金大对决/寻龙探宝）全部完成： 出画 11.0-14.2s、点击继续成功、稳定 25.8-28.8s；视频转 MP4（H.264+faststart）后 发群可自动播放，截图同步发送（有图有证据）； - 竞品当天连续登录触发对方 API 限流，视频待限流冷却后补； - 自动化脚本已固化：docker/scripts/game_load_video_compare.py + README （支持 --side our/comp/both、--games、自动录屏/截图/计时/MP4 转换）。

补充 2：新计时标准（点击继续→可玩）备用机复测（2026-08-29 05:00）

用户反馈：应把"设备检测/继续游戏"环节之后才视为游戏开始。改脚本计时标准为 continue_ready_ms（从点击"继续游戏"到网络稳定可玩）。在备用机 bizops-saopaulo-nginx-standby-01（巴西视角、新出口 IP）双方各 5 款：

游戏            我方    竞品
Fortune Tiger   7.6s   7.7s
麻将胡了        8.2s   7.4s
寻宝黄金城      8.9s   8.5s
赏金大对决      10.0s  7.9s
寻龙探宝        8.9s   8.4s

结论： 1. 竞品同样存在"设备检测/继续游戏"环节（双方 clicked=True，视频可见）； 此前竞品 4.0s 是从页面加载到空闲、未点继续的假象； 2. 新标准下双方几乎打平（差 0.3-2.1s）； 3. 我方全程走圣保罗桶（or=pg4-static-sa）。
