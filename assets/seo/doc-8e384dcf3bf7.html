二、vendor_b-static（06 zone）403 的定位

实测：https://vendor_b-static.hkcloudplay06.com/fg/index.html
  HTTP/2 403，cf-cache-status: HIT，age: 2019（约 33 分钟前写入的边缘缓存）
  body：<Error><Code>AccessDenied</Code> ... （S3 侧对象权限/存在性错误形态）
对照：
  - 直接打桶：https://bizops-s3-vendor_b-static.s3.ap-northeast-3.amazonaws.com/fg/index.html = 200 ✓
  - 同域名在 07 zone = 200 ✓
=> 属于「桶尚未公开期间（或错误版本期间）产生的 403 被边缘缓存」，
   换盐后该 zone 的请求仍命中了旧缓存条目，需要再做一次缓存失效才能自愈。

三、恢复手段（已执行 / 备选）

已执行：改 CACHE_SALT -> v4-20260925 并重新部署（作为兜底，已让大部分前缀恢复正常）。
若个别域名仍命中旧错误缓存，两种做法二选一：
  a) 再升一次缓存盐（改 CACHE_SALT）并重新部署；
  b) 对该 zone 做一次 Cloudflare 缓存清除（Cache Purge，需要相应权限）。
注意：Worker 用的是 `cf: { cacheEverything: true, cacheTtl: 604800 }`，
      错误响应（403/404）也可能被缓存，所以「源修好」不等于「立刻恢复」。

五、经验与建议

1) Worker 是账号级脚本，多人/多会话同时部署会互相覆盖——改动前先确认「当前线上是哪一版」
   （从 CF 拉源码比对，本侧工具：deploy_static_worker.py 部署时会自动备份被覆盖的版本）。
2) 切源（S3 桶 / GCS）必须先确认目标桶对匿名请求可读：
   本侧踩过两次——先是以「对象不存在」误判，后经 GCS 对照（同路径 S3 403 / GCS 200）
   才确认是桶策略未公开；桶策略没配好就切 Worker 会导致全站 403/404。
3) 错误响应会被边缘缓存，源修好后仍可能看到旧状态；必要时升缓存盐或 purge。
4) 若确认要改走 GCS 源，Worker 里的回源地址必须写成
   `https://storage.googleapis.com/<GCS桶>/<路径>`（或 GCS 的 bucket host 形式），
   不能把 GCS 桶名拼到 S3 域名上（本次 404 就是这个原因）。

   代码内对应位置另有 `[HK-差异 N]` 行内标记。
2) 部署：deploy http=200 success=True（旧版备份 /root/bizops-hk-worker-backup/20260925-v5）。
3) 复验：06/07 × 13 前缀 = 26 个域名，25 个 200；
   仅 vendor_b-static.hkcloudplay06.com 仍 403。

6.1 vendor_b-static（06）403 的最终根因

关键证据：403 响应的 x-amz-request-id = 4FNVS5TJHH29GMAH，与 04:14 诊断时完全相同；
         cf-cache-status: HIT、age: 2718（约 45 分钟前写入）。
=> 这条 403 是「桶还是私有」时期缓存的同一条响应，**至今没有被清掉**。

为什么升 Worker 的 CACHE_SALT 不起作用：
  Worker 内的缓存键（cf.cacheKey）只影响 Worker 自己发起的回源缓存；
  06 zone 上还有一条 zone 级 Cache Rules「statics」（按主机名结尾 -static. 匹配、
  边缘 TTL 604800），它按 URL 缓存 Worker 返回的响应 —— 包括这条 403，
  与 Worker 的缓存盐无关，所以升盐（v3/v4/v5）都无法让它失效。

为什么 07 正常：07 上这条 URL 是在桶公开之后才第一次被请求，缓存里存的是 200。

6.2 处理方式（需要权限）

本侧尝试用现有 token 直接 purge：POST /zones/<id>/purge_cache
  -> 401 Authentication error（该 token 没有 Cache Purge 权限）

可选做法（任一）：
  a) 面板手动清：Cloudflare -> hkcloudplay06.com -> 缓存 -> 清除缓存 ->
     自定义清除，填 https://vendor_b-static.hkcloudplay06.com/*  （首选，最直接）
  b) 给 workers-token 补 "Cache Purge" 权限后，本侧执行：
     cf-api POST /zones/fd8476ddbd25b40f4c870d8066329aca/purge_cache \
       --data '{"files":["https://vendor_b-static.hkcloudplay06.com/fg/index.html"]}'
  c) 临时把 vendor_b-static 从 zone 的 statics Cache Rules 排除（会失去该前缀的边缘缓存）
