二、start.sh 结构核对（香港可直接用）

用法：./start.sh <vendor> <VERSION_TAG>
镜像：${REGISTRY}/game-service-<vendor>:<TAG>
容器：game-service-<vendor>-prod，端口按内置映射（api 9090 / pg 9091 / jili 9093 /
      ppk 9098 / pp 9099 / panda 9018 / g759 9019 / playson 9020 / tada 9096 / tada_ws 8765）
挂载：share.so / server_configs / version.json / xxxxxx.mmdb / conf/domains /
      game_result_datas/<vendor> / logs
JILI：脚本内置 `docker run ... python /app/tada/jili.py`（与镜像自带
      CURRENT_VENDOR=tada + MAIN_ENTRY=jili.py 一致）
容器用户：脚本未写 --user，但镜像 Config.User=appuser，仍以 appuser 运行（与巴西一致）

各镜像自带 env 已核对（可省去手工传 env）：api=platform-api/main.py、pg=pg/server.py、 pp=pp/pp.py、ppk=ppk/ppk.py、panda=panda/panda.py、g759=g759/g759.py、 playson=playson/playson.py、jili=tada/jili.py。

四、步骤 1：静态资源同步（含工具修复）

发现问题：/usr/local/bin/dbqp-sync-gcs-to-s3 的桶映射仍是旧桶名 dbqp-gcs-*，实测报 directory not found（旧桶已在 2026-09-11 迁移中删除）， 现役桶是 newgg2-dbqp-gcs-*（公网抽查 200）。

处理：

1) 备份 /opt/dbqp-hk-ops/sync_gcs_to_s3.py -> *.bak-YYYYMMDD-HHMM
2) 映射统一改为 newgg2-dbqp-gcs-<前缀>（含 tada-statics/1/2）
3) 重新执行增量同步（后台）：/root/sync-statics.sh -> /root/sync-statics.log
   前缀：pg-static / pg3 / pg4 / pg5 / pp-static / ppk-static / panda-static /
        playson-static / jili-static / jili-static1 / jili-static2

待补：pg6-static / pg7-static / g759-static 的源是 gitlab client 仓库（非 GCS）， 需按 2026-09-02 的 git→S3 流程单独同步（不在本次脚本范围内）。

五、踩坑记录

1) GCS 桶名过期：同步工具写死旧桶 dbqp-gcs-*，实际已迁移到 newgg2-dbqp-gcs-*，
   不改会一直 directory not found。
2) pkill -f 自匹配（第二次踩）：命令行里包含同一模式串时会把自己所在 shell 杀掉，
   表现为命令无输出/后续步骤不执行；应使用 pgrep -x（精确进程名）或按 PID kill。
3) JILI 入口：必须 CURRENT_VENDOR=tada + MAIN_ENTRY=jili.py（镜像代码在 /app/tada），
   用 vendor=jili 会 can't open file '/app/jili/jili.py' 无限重启；start.sh 已内置正确写法。
4) /data/server-runtime/server_configs 是文件不是目录。
