支付通道选型：三方 vs 四方

决策决定文档。本期 Kickoff 上线前需要明确充值/提现的资金通道，本文给出三方/四方两种典型方案的对比、风险评估、合规要点与对我们抽象层的影响。

1. 名词解释

术语 含义
三方支付（持牌） 用户付款给持牌第三方支付机构（如微信支付、支付宝、银联），机构再结算到我方账户。直接接入官方文档。
四方支付（聚合/代付） 不直接接微信/支付宝，而是通过一个"聚合通道"中间商（俗称"码商""跑分平台"），他们汇总私人账号/小商户额度提供支付能力。

2. 对比

维度 三方支付 四方支付
资质 有央行支付牌照（如财付通/支付宝/银联） 无牌照，多为代收代付/POS 转售/个人账户聚合
接入门槛 需企业资质、ICP、行业准入；博彩/竞猜类被绝大多数三方拒签 几乎不审核，注册即用
费率 0.6% - 2%（标品） 4% - 12%+
到账速度 T+1 / T+0 通常 T+0，但延时不稳定
合规风险 受监管，被风控冻结风险低 极高：账户冻结、资金被冻、信息被监管追溯
回调可靠 文档完整、SLA 高、有沙箱 文档参差、回调可能丢、需轮询
退款 标准 API 经常需人工对接
可持续性 长期稳定 通道频繁挂掉（被关停 / 跑路 / 切换）
法律定性（国内） 合规 可能涉嫌帮信罪、洗钱、非法支付结算

3. 业务匹配分析

Kickoff 业务：世界杯竞猜 + 直播打赏 + 钻石充值/提现。

  • "竞猜"在国内法律语境下接近博彩（取决于"是否兑现金"、"是否带有运气成分赢得财物"）
  • 充值-竞猜-赢取-提现回 RMB 这条链路，几乎不可能通过三方机构的资质审核
  • 实际生态里，类似业务（直播+押注）绝大多数用四方，或者境外通道（加密货币/USDT/海外支付）

4. 三种现实可行的方向

A. 走三方（合规优先，业务受限）

做法：把"押注"包装成"积分游戏"，钻石只能在站内消费（打赏/兑换实物礼品），不开提现 RMB 链路。

优势 劣势
完全合规 业务模型变样，丧失"竞猜赢钱"的核心吸引力
资金安全 不能提现，用户留存差
公司可融资/上架应用商店 GMV 大幅下降

对当前代码影响：删除 /wallet/withdraw/* 接口、改成"实物兑换"流程。改动较小（提现 service 关掉，钱包账本不变）。

B. 走四方（业务优先，合规风险）

做法：接入聚合通道（具体厂商保密），充值/提现都走。

优势 劣势
业务完整 通道随时挂、运营商频繁换
到账快 法律风险（实际控制人可能受牵连）
接入简单 费率高、争议处理麻烦

对当前代码影响： - payment generic hook 已经能用（HMAC + 持久化 + 入账） - 提现走 admin 审核 + 人工/半自动转账（部分四方提供代付 API，部分要手动） - 需要"通道路由"：选择当前可用的子通道（同时挂 2-3 家防单点） - 需要"额度管理"：每家通道日限额单独控制

C. 走加密货币 / 境外（区域规避）

做法：USDT / 数字人民币 / 境外支付（Stripe / Crypto exchange）。

优势 劣势
链上透明、跨境无障碍 国内用户接受度低、需要钱包教育
不受国内监管 KYC/AML 反洗钱要求高（如果做合规 USDT 服务）
费率低 汇率波动、用户教育成本

5. 推荐策略（分阶段）

阶段 通道 业务模型
MVP 上线（32 天速通期间） 四方（接 1-2 家） 完整充值/竞猜/提现
稳定期 1（用户量起来） 四方 + 境外通道（USDT 可选） 多通道路由
长期 走境外公司主体 + 合规通道 合法化 + 跨境

本期实施建议：先按四方接入，代码层抽象到位，未来切通道只动 adapter。

6. 对当前代码架构的影响

当前已有的抽象（好消息：我们的设计是通道无关的）：

recharge_orders.channel     ←  通道标识（wechat/alipay/generic/...）
payment_callbacks.channel   ←  回调来源
service/hook/payment.go     ←  按通道路由到不同验签实现

接入新通道（如四方"X-Pay"）只需要：

  1. 在 pay.x_pay 配置加该通道签名密钥
  2. 在 service/hook/payment.go 加 HandleXPay() 方法
  3. 在 router/public.go 加路由 /hooks/payment/x_pay
  4. 在 wallet 充值发起接口的 channel 枚举加 x_pay
  5. 创建 channel adapter，封装"创建支付订单" + "查询状态" + "退款"

不需要改： - 复式记账 ledger - 充值 / 提现订单状态机 - payment_callbacks 持久化 - 幂等机制

这是面向通道扩展的开闭原则落地。

7. 待确认的信息（用户拍板）

决策点 选项 用户的选择
资金通道方向 A 三方 / B 四方 / C 境外 / 多选 待定
是否开提现 是 / 否 待定
通道厂商 微信/支付宝（A） / 具体四方名单（B） / Stripe/USDT（C） 待定
资金分账给主播 平台代付 / 主播自提 待定
大额风控阈值 单笔 / 日累计 / 月累计 当前 yaml：单笔 5w、日 20w（提现）
KYC 强制时机 注册 / 首充 / 首提 / 提现> N 当前 DDL：表已建，业务时机待定

8. 接入流程模板（无论哪种通道）

1. 通道厂商提供：
   - merchant_id / app_id / sign_key / pub_key（密钥放 env）
   - 沙箱环境地址 + 测试账号
   - 回调 URL 配置入口
   - 文档（签名/请求/回调/退款/对账）

2. 我方提供：
   - 公网回调入口（生产域名 + HTTPS）
   - 商户名 + 营业范围（可能被审核）
   - 财务账户（接收结算）

3. 代码工作（按抽象）：
   3.1 配置：cfg.Pay.<channel>.{merchant_id, app_id, sign_key, pub_key}
   3.2 service：service/hook/payment.go 加 Handle<Channel>()
   3.3 路由：router/public.go 加 hooks/payment/<channel>
   3.4 充值发起：service/wallet/InitRecharge 时构造该通道支付参数
   3.5 状态查询：service/wallet 增加"主动查通道状态"接口（部分通道回调不可靠时用）

4. 沙箱联调：
   - 充值-回调-入账 链路
   - 退款-回调 链路
   - 失败/重复/错签 边缘情况

5. 对账：
   - 日终拉通道流水
   - 比对 recharge_orders.third_party_no
   - 差异落 recon_diffs（admin 端处理）

9. 风险记录（必读）

风险 缓解
四方通道挂掉 → 充值无法到账 同时挂 2 家以上，前端按可用性切换
资金被冻结 钱包/订单/分录三表分离，能配合调查；公司主体与运营分离
回调被伪造 HMAC/RSA 验签必须严格；IP 白名单
退款链路被滥用 退款必须 admin 审核 + 二级复核 + 操作审计
提现"挤兑" 单用户日限额（已实现）+ 全平台日限额（待加）+ 强制 KYC
大额异常订单 单笔阈值告警 + 风控规则（待 P1 实现 risk_rules）
用户客诉资金问题 全量 ledger entries + payment_callbacks + admin_audit_logs，可追溯

10. 等用户回复后开始

请提供：

  1. 通道方向：A / B / C 或组合
  2. 具体厂商名（如 B：四方厂商名 + 联系人/沙箱地址）
  3. 是否开提现 + 提现方式（人工 / 半自动 / 全自动）
  4. 是否对接分账（主播是否在平台账户上还是单独结算）

收到上述信息后： - 我会按通道厂商文档加 service/hook/payment.go 的 Handle<Channel> 方法 - 在 service/wallet.go 加该通道的"创建支付订单"调用（部分通道是预创建，部分是发起即跳转） - 提供该通道的联调测试脚本
