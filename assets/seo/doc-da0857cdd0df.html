3. 服务器落盘太慢太卡 -> 改造：静态资源直接从 git 同步更新到 GCS（巴西 + 香港），
   不落盘服务器，两区桶内容一致（全部厂家前端客户端代码）；
4. 清理服务器上落盘的全部厂家静态资源；
5. 完善本次改造笔记；后续全部厂家静态同步 = git -> 巴西 GCS + 香港 GCS；
6. 参考 cn 分支最近改造（2026-09-02-1453 香港 PG 全量从代码仓库同步 S3）。

并发收敛说明

期间发现另有会话（非本对话）也在操作同一套宝塔/GCS/仓库（cn 侧已完成
PG 六前缀同步 S3 并提交 96ad0bd9）。经用户转达后，由本会话接管 master/GCS 侧：
- 已停止宝塔上全部 git_static_gcs_sync 审计/同步进程（含非本会话发起进程）；
- master 侧继续执行“git -> GCS（巴西 -sa + 香港/东京 asia + backup）”。

一、方案与工具

新工具：docker/scripts/git_static_gcs_sync.py
- 默认模式：以 last-synced commit 为基线，fetch client.git master 新提交，
  diff 变化文件后只把新增/修改文件上传到目标桶（增量、不删除）；
- --full-audit：只读报告（git tree vs LIVE 桶名称差异），绝不自动回灌；
  原因：GCS 与 git 存在历史差异（PNG->WebP 等运维转换、health.json 等运维
  补充对象、历史删除），整库“补缺失”会把已优化掉的旧资源大量回灌；
- 临时目录用完即清；不在服务器 wwwroot 落盘；仓库缓存仅保留 git 元数据
  （/root/.client-git-cache，blobless sparse，可增量 fetch）。

目录映射（14 组，与 gcs_static_sync 同源）：
  pgnew->pg-static / pg3->pg3-static / pg4static->pg4-static /
  pg5static->pg5-static / pg6static->pg6-static / pg7static->pg7-static /
  tadastatic->tada-statics / tadastatic1->tada-statics1 /
  tadastatic2->tada-statics2 / ppstatic->pp-static / popok->ppk-static /
  playsonstatic->playson-static / panda->panda-static / G759static->g759-static

目标桶：
  LIVE（巴西）  gs://dbqp-gcs-<prefix>-sa        （g759: dbqp-gcs-g759-static）
  ASIA（香港/东京） gs://dbqp-gcs-<prefix>         （g759: dbqp-gcs-g759-static-asia）
  BACKUP         gs://dbqp-game-statics-gcs/<prefix>

二、执行内容

1. health.json 补齐（完成）

给每个厂家桶根补统一模板 health.json
（{"rcode":0,"data":"k9#mP8$vX2!zL5qW","msg":"succ"}）：
- 巴西 LIVE(-sa) 14 家：已有（含 pg6/7 新增）；
- 香港/亚洲 asia 桶：补齐 12 家缺失（pg-static/pg3/4/5、tada-statics/1/2、
  pp/ppk/playson/panda、g759-static-asia）；
- backup 前缀：补齐 12 家缺失；
- 复核 TOTAL_MISS=0。

2. 现状核实（关键）

巴西 GCS 实际落后于代码仓库（用户反馈与实测一致）：
  https://pg-static.xqv9m8.icu/85/c445ebb91e.cadb1.json -> 404
  -sa 直连 404、asia 直连 404；
宝塔 wwwroot pg-static 34323 文件 vs 仓库 pgnew 39256 vs GCS -sa ~19610；
根因：服务器侧管道（历史 S3 包 -> 宝塔 wwwroot -> GCS）从未以 client.git
为源补齐，部分游戏资源（例 85/c445ebb91e.cadb1.json）仓库有但线上桶缺失。

3. PG 六前缀全量补齐（完成）

宝塔 cache sparse 物化 client master=1764a68b 六目录：
  pgnew 39256 / pg3 7304 / pg4static 21955 / pg5static 6394 /
  pg6static 684 / pg7static 1053 = 76646 文件，约 6.4GB，._ 残留 0；
gsutil -m rsync（增量不删除）上传至 -sa 桶：pgnew/pg3/pg4static/pg5static/
pg6static/pg7static 全部完成（76646 文件）；
-sa -> asia（香港/东京）6/6 云对云完成；-sa -> backup 6/6 完成。
样例恢复：pg-static/85/c445ebb91e.cadb1.json 在 -sa/asia/backup/公网 CF 均 200。

4. 其余厂家差异审计与补齐（完成）

仓库 vs LIVE 桶只读计数（python 精确计数，排除 gcloud 输出空行干扰）：
  tada-statics 17359 vs 17592（+233 运维对象）
  tada-statics1 2839 vs 2887（+48）
  tada-statics2 1062 vs 1087（+25）
  pp-static 25592 vs 25878（+286）
  ppk-static 8441 vs 8448（+7）
  playson-static 25818 vs 25921（+103）
结论：GCS >= 仓库，无缺失，无需回灌（历史差异为 PNG->WebP 等运维转换，
不回灌旧格式是预期行为）。
panda/G759static 大桶列举超时改为直接补齐：已从 git 物化
（panda 1.5G / G759 1.1G）rsync 至 -sa，并云对云 asia/backup 4/4 完成。

5. 服务器清理与 cron 替换（宝塔已完成）

权威源改为：client.git + GCS 双区桶（含 backup 归档）；
宝塔 wwwroot 版 gcs_static_sync（03:10 wwwroot->GCS）已替换为 git 直连：
  /www/server/cron/gcs_static_sync（原版备份 /root/gcs_static_sync.bak-20260902-git2gcs）
  + root crontab 每 30 分钟：python3 /root/git_static_gcs_sync.py
  （日志 /var/log/git_gcs_static_sync.log；凭据 /root/dbqp-git-client.env 600）
删除宝塔 /www/wwwroot 全部 14 组 *-static 落盘副本（约 30G，含 .user.ini
chattr 处理；回滚来源：GCS backup 桶 / git 仓库）；
nginx 静态站点配置保留（A 记录回退场景兜底，指向缺失目录时仅 404）；
清理公网复测：pg/pp/tada/panda/g759/pg6 等 health 与缺失样例全部 200。
备用机 34.151.249.53 落盘静态副本（约 29G）暂保留，待用户确认后清理。

三、验证计划

2. 已知缺失样例恢复 200：85/c445ebb91e.cadb1.json（-sa/asia/CF 域名）；
3. 抽样 ETag/SHA 与 git blob 一致；
4. -sa 与 asia 两区桶对象集一致（云对云后计数/抽样）；
5. 清理后公网静态 health/游戏页无回归。

服务器副本仅保留历史（待清理）；备用 nginx 不承载静态更新。
