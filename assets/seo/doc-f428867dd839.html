堡垒机处置（43.249.251.15）

现象

  • JumpServer koko 进程持续占用 380–400% CPU，4 核基本跑满。
  • core/mysql/redis/guacamole 正常，无 failed unit、无 OOM。
  • koko 日志与 auth.log 显示 root/nobody 等账号的高频爆破；来源包括 176.53.159.197/198、165.154.218.226 等。
  • 2222 端口仅 1 个活动会话，说明不是正常并发过高，而是组件卡在异常循环 + 爆破放大。

处置

  1. 只重启 koko 单组件，不重启 core/mysql/redis，不重启整台服务器。
  2. 封禁 12 个高频爆破 IP。
  3. 对 22 与 2222 增加按来源 IP 的连接限速： - 22：8 次新连接/分钟； - 2222：12 次新连接/分钟。
  4. 新增 uat-mgmt-guard.service，开机自动恢复限速与黑名单。

验证

  • CPU：98% user → 约 0%；Load 4.93/4.62/4.48 → 0.25/1.92/3.35 → 0.27/…。
  • Beszel：堡垒机 CPU 告警已自动清除，7 台当前 0 triggered。
  • 80、2222 仍可访问；SSH 22 仍可用。
  • uat-mgmt-guard.service 为 active/enabled。

中间件处置（43.249.251.11）

现象

  • 根分区 73G/98G，使用率 78.43%，接近 80% 告警线。
  • /var/lib/containerd 22G（镜像）、/var/lib/docker/volumes 19G（业务数据）、/data 12G（Harbor 4.4G + Jenkins 7.2G）、/home/backup 7.8G。
  • 旧镜像 prune 可回收 0B；数据卷均为业务数据，不适合删除。
  • LVM ubuntu-vg 还有 152.95G 未分配空间。

处置

  • 在线把根 LV 从 100G 扩到 150G：lvextend -r -L +50G /dev/ubuntu-vg/ubuntu-lv。
  • 未删除任何备份、镜像、数据卷或容器。

验证

  • 根分区：148G，已用 73G，剩余 68G，使用率 79% → 52%。
  • 中间件 CPU/内存/业务容器正常，无 unhealthy、无 failed unit。

代码与持久化

  • 新增 security/harden_jumpserver_ssh.sh：SSH/2222 限速、黑名单加载、systemd 开机恢复。
  • 更新 security/README.md。
  • 本地原始快照：/Users/ben/Downloads/UAT全量巡检_20261028_0427/health-snapshot.txt（不入库）。

最终状态

  • 7 台 Beszel 系统全部 up。
  • 当前 triggered 告警：0。
  • 24 个 Swarm 业务服务全部 2/2。
  • 无 unhealthy 容器、无 failed unit。
  • 当前关键指标：
  • 堡垒机：CPU 7.53%，内存 65.56%，磁盘 24.16%，Load1 0.27。
  • 中间件：CPU 21.78%，内存 43.26%，磁盘 51.94%，Load1 2.55。
  • manager：CPU 2.47%，内存 8.99%，磁盘 56.31%。
  • worker01/02：CPU 12.02%/9.54%，内存 54.83%/56.81%，磁盘 46.85%/43.26%。

后续建议

  1. 堡垒机 7.8G 内存仍偏紧（当前 65%，Swap 1.7G 历史占用）；持续观察，必要时升级内存或把 GitLab 从堡垒机拆走。
  2. SRS 韩国内存 69.5%，24 小时稳定；无 SSH 权限，仅通过 Beszel 观察。
  3. 中间件 /home/backup 仍有 7.8G 备份、Jenkins 7.2G；当前空间充足，不删除，后续可制定备份保留策略。
  4. 堡垒机 22 端口仍对外开放；长期应收敛为固定运维出口 IP，仅保留 80/2222 对外。
