## 一、03 为什么退出监控

需求原话：**「03 服务器做打包用不需要监控」**。实测确认 03 的性质确实变了：

```text
03（192.0.2.1）docker ps -a 全量（2026-09-24 06:40 UTC）：
  beszel-agent / registry / jms_celery / jms_chen / jms_core / jms_koko /
  jms_lion / jms_postgresql / jms_redis / jms_web / bizops-resource-sync(Exited)
  hopeful_feistel|Up 3 seconds          ← docker run 不带 --name 的匿名打包容器

监听端口只剩：22 / 80 / 2222 / 5000
厂家容器 game-service-*-prod：**一个都没有**（上一轮 9/18 起的 8 个也都已下线）
```

也就是说：03 上已经没有厂家容器，而它是发版的**打包 / 资源源机**——
02 的 shell 历史显示发版时是从 03 拉 `/data/server-runtime`（见第二节）。
继续按厂家名监控 03，只会每 2 分钟误报一次（用户收到的 17:06 那条就是这么来的）。

**改动**：`BACKENDS` 从三台减成两台。

```python
BACKENDS = [("192.0.2.1", "01"), ("192.0.2.1", "02")]
# 2026-09-24：03（192.0.2.1）已改成打包机，厂家容器全部下线，不再纳入监控。
```

期望容器数从 29 个变成 **20 个**（01 十个 + 02 十个）。

## 二、发版窗口自动静默（这次误报的真正原因）

### 1. 证据：02 上的发版流程

02 的 root shell 历史（原样摘录）：

```text
sh stop.sh vendor_a
sh stop.sh pp
sh stop.sh api
docker ps
rsync -avz --delete --exclude 'logs' --exclude '*.db-shm' --exclude '*.db-wal' \
      root@192.0.2.1:/data/server-runtime /data/
rsync -avP --delete -e "ssh -o ServerAliveInterval=15 -o ServerAliveCountMax=3" ...（同上）
sh start.sh pp 20260923-ben
sh start.sh vendor_a 20260923-ben
sh start.sh api 20260923-ben
```

发版顺序是：**停容器 → 从打包机 03 同步 /data/server-runtime → 再启动容器**。
这个窗口实测能超过 50 分钟（大 DB 传输慢），远超原来 6 分钟的宽限，
所以 9/23 那三条 02 的报警（16:48 / 16:50）其实是**发版窗口**，不是故障。

### 2. 机制

在该后端上检测有没有发版/同步进程：`rsync` / `start.sh` / `stop.sh` / `build.sh`。
检测方式和 docker 列表**走同一次 SSH**，不增加采集开销：

```bash
echo "META|$(pgrep -cf '[r]sync|[s]tart.sh|[s]top.sh|[b]uild.sh' 2>/dev/null || true)"; \
docker inspect --format '{{.Name}}|{{.State.Status}}|{{.RestartCount}}|{{.Config.Image}}' $(docker ps -aq)
```

```text
（[r]sync 这种方括号写法是为了让 pgrep 不匹配到 pgrep 自己那条命令行）
META>0 → 判定为发版窗口：
   · 容器缺失只记日志，不报警，也不累计缺失次数（misses 归零，窗口结束重新数）
   · 状态里标记 window=true
META=0 → 恢复原来的「连续 3 次（约 6 分钟）才报警」逻辑
```

设计要点：**静默能力会随着发版进程结束自动失效**——开发万一同步完忘了启容器，
6 分钟内照样会报出来，不会因为“静默”把真故障吞掉。

防卡死上限：发版进程就算一直不退出，最多静默 `RELEASE_WINDOW_MAX_SAMPLES` 次采样
（默认 30 次 ≈ 60 分钟），超限后按正常缺失逻辑报警（再约 6 分钟发警）。

开关：`某业务公司_CONTAINER_RELEASE_WINDOW=0` 可整体关闭该特性；
`某业务公司_CONTAINER_RELEASE_WINDOW_MAX=N` 改上限。

## 三、另外两处顺手修掉的问题

```text
① 汇总行不再含糊
   老版本：容器在宽限期、甚至已经报过警了，也照样打印 “OK … 全部正常”，
           看起来像“一切正常”，容易误解（本次排查时就被这条误导过）。
   新版本：[dry-run] 期望容器 20 个 | alerts=0 recovers=0 | 发布窗口暂缺=0 | 缺失中=1
           OK 2026-09-24 14:41:33 期望容器 20 个 ｜ 缺失中 1 个（宽限或已报警）

② 状态文件清理补齐
   上一版的清理只在「遍历到的后端」里做，03 退出监控后它的键永远不会被清。
   现在额外做一次全局清理：非 backend: 前缀且不属于在监控 IP 的键、
   以及已退出监控机器的 backend:<ip> 键，全部删掉。
```

```text
① 语法：python3 -m py_compile 通过。
② 部署一致性：本地与入口机 md5 相同 a70fcc36fd3b031ffd79e91008bc5b1d。

   [dry-run] 期望容器 20 个 | alerts=0 recovers=0 | 发布窗口暂缺=0 | 缺失中=1
④ 真实跑一次（入口机）：

⑤ 远端命令在真机（01）验证过输出格式：先打 META 行，再打 docker inspect 行。
⑥ 逻辑回归（本地假数据，不动线上）：
   · 基线 20 个期望容器；
   · 无发版进程时容器缺失 → 第 1、2 次静默（打「缺失中」），第 3 次报警；
   · 有 rsync 进程时同样的缺失 → 4 次采样全程「发布窗口中暂缺 N 个（不报警）」；

```

## 五、⚠️ 顺带查出的真问题：02 的 vendor_a 主服务（9096）现在没在跑

这一条**不是误报**，是本次排查时确认的真实缺口。

### 1. 事实

```text
02（192.0.2.1）docker ps -a 全量里只有 game-service-vendor_a-ws-prod（8765），
没有任何名字的 vendor_a 主服务容器（不是「换名字了」——全量列过了，就是没有）；
02 上 9096 端口没有任何进程监听（ss -ltnp 只有 22/8765/9018/9019/9020/9090/9091/9098/9099）。
02 本地 start.sh 的 ALL_VENDORS 是有 vendor_a 的：
  ALL_VENDORS="api pg vendor_a vendor_a_ws ppk pp vendor_c vendor_d g759"
02 上 vendor_a/api/pp 三个容器是同一次发版（20260923-ben）起的，
  但 api-prod、pp-prod 现在是 Up（21 小时），vendor_a-prod 却不在 —— 属于「同步完漏启 / 启了又没了」。
```

### 2. 用户影响（有日志证据）

入口机 nginx error log（2026-09-24 06:40~06:41 UTC，真实客户端 IP）：

```text
connect() failed (111: Connection refused) while connecting to upstream,
  request: "GET /lt/ HTTP/2.0", upstream: "http://192.0.2.1:9096/lt/",
  host: "vendor_a-games.xqv9m8.icu"
（每 12 秒一条，反复出现）
```

```text
线上表现：nginx 的 proxy_next_upstream 会把失败的请求重试到 01，
          所以用户大多还能打开（实测 vendor_a-games 域名 health 连续 10 次 200），
          但每次命中 02 都会多一次失败重试（增加延迟），并偶发 500（access log 里有 13 条 500）。
vendor_a 冗余：02 上等于没有 vendor_a 后端，01 单点扛 vendor_a。
```

### 3. 建议处理（未执行，等确认）

```text
在 02 上执行（版本号照 01 上 vendor_a 容器正在用的 tag，当前 01/02 都是 20260923-ben）：
    cd /data/server-runtime
    sh start.sh vendor_a 20260923-ben
    # 起来后确认：docker ps | grep vendor_a、ss -ltnp | grep 9096、curl 本机 9096
再盯一会儿 nginx error log，确认 192.0.2.1:9096 的 refused 不再出现。
```

### 4. 后续（2026-09-24 17:15 更新）

```text
· 用户已手动执行 sh start.sh vendor_a 20260923-ben，02 的 vendor_a（9096）已恢复。
· 消失原因已查明：不是故障也不是自动任务，是有人在 02 上一个从 9/18 起就一直挂着的
  常驻 SSH 会话（工作目录 /data/server-runtime）里手动执行了 sh stop.sh vendor_a，
  而 stop.sh 是 stop + rm，之后没执行对应的 start.sh。
```
