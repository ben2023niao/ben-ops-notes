## 二、问题现象

用户反馈：已经重新拉代码并打包，但通过运维发布页部署 G759 后仍运行旧镜像。

实测：

```text
BR01 Config.Image=203.0.113.1:5000/game-service-g759:20261028-ben
BR01 实际 Image ID=ddbf5ed4a577（旧镜像）
BR02/HK01/HK02 Config.Image=20261023-ben
03 registry 20261028-ben 实际 ID=803ec79ea262（修复镜像）
```

## 三、根因

发布页后端启动命令直接调用：

```bash
sh start.sh <vendor> <tag>
```

`start.sh` 使用本地已有的同名 tag，不执行 `docker pull`。因此：

```text
registry 已推送新 20261028-ben
→ 后端本地仍缓存旧 20261028-ben
→ docker run 按 tag 选中本地旧 Image ID
```

Docker tag 可移动到新 ID，但不会自动从 registry 同步；只看 tag 无法判断旧缓存。

## 四、发布页修复

后端步骤调整为：

```text
拉取目标镜像 → 停容器 → 同步文件 → 启动 → 校验 Image ID → 显示状态
```

### 4.1 按区域 registry 拉取

```text
巴西：203.0.113.1:5000
香港：34.39.180.82:5000
```

按实际镜像名拉取，`tada_ws` 和 `jili` 都映射到 `game-service-tada`。

### 4.2 启动后硬校验 Image ID

每个所选容器执行：

```bash
expected=$(docker image inspect <registry>/<image>:<tag> --format '{{.Id}}')
actual=$(docker inspect <container> --format '{{.Image}}')
if [ "$actual" != "$expected" ]; then
  echo "仍在运行旧镜像"
  exit 1
fi
```

任何厂家仍使用旧缓存，发布命令立即失败，不能把旧镜像误报为部署成功。

### 4.3 状态输出

容器状态表增加 Image 列，便于人工直接看到目标 tag。
