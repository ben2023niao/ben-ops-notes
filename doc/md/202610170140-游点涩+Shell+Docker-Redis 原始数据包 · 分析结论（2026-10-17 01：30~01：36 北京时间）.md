# Redis 原始数据包 · 分析结论（2026-10-17 01：30~01：36 北京时间）

> 来源文件：`~/Projects/work/game/youdianse-docker/main/docker-youdianse-php/docs/2026-10-17-0140-【排查】Redis原始数据结论（内存未满-命中率94%-KEYS阻塞与连接风暴）.md`

> 整理日期：2026-10-17 01:40｜日期依据：文件名日期

采集对象：`203.0.113.1:6379`（线上唯一的 Redis，db0=session 占位 / **db1=业务 `redis()`** / db2=队列 / **db3=缓存 `cache()`**）
采集方式：全部只读（INFO / SLOWLOG / CLIENT LIST / SCAN / 5 秒 MONITOR）；MONITOR 采样 5 秒，期间 Redis 吞吐会略降，已自动结束。

## 一、先回答「是不是 Redis 的问题」

**不是。** 三条硬证据：

| 对比项 | Redis | 数据库 |
| --- | --- | --- |
| 网络出流量 | **8.4 Mbps ≈ 1.05 MB/s** | 主库 2.3 MB/s + 从库 **61.1 MB/s** |
| 网络入流量 | 0.12~0.16 Mbps | 主库 1.1 MB/s / 从库 0.6 MB/s |
| 内存 | used **1.00 GB** 稳定，峰值 1.17 GB，`maxmemory=0`、`noeviction`、**淘汰键 0** | — |
| 命中率 | **94.29%**（命 999/s、未命中 60/s） | — |

也就是说：

1. **内存没满**：1.00 GB 稳定，没有触发淘汰（`evicted_keys=0`），也没有拒绝连接（`rejected_connections=0`）。
2. **Redis 不产生 Mongo 流量**：Redis 的网卡只有约 1 MB/s，与数据库从库 61 MB/s 差 60 倍；两者没有量级上的因果关系。
3. 反过来看，Redis 命中率 94% 说明**缓存是在工作的**，并不是"缓存失效导致全打到数据库"。

真正的原因仍是之前取证到的那条链：**数据库读放大 ~280~590 倍**。读分离只是把读请求从主库挪到了从库，扫描量没变，所以从库立刻被顶到 61 MB/s。

## 二、但 Redis 确实有两个真实问题（都要修）

### 问题 1：`KEYS` 周期性全阻塞（P0，依旧存在）

```
SLOWLOG 128 条：KEYS 126 条、DEL 2 条
单次耗时：0.50 ~ 0.67 秒        平均间隔：129 秒
类别：token_user（登录踢下线）102 次、tracking 12 次、tracking_guest_dl 9 次、product_click 5 次
样例：01:31:54  KEYS [敏感内容已脱敏]  513 ms
      01:31:47  KEYS [敏感内容已脱敏]  542 ms
```

- 来源：后端 `203.0.113.1`，代码位置 `app/Services/User/UserService.php:1861`（多点登录踢下线）等 8 处。
- 根因：`redis()` 用的 **db1 有 1,739,744 个键**，其中约 95% 是 `[敏感内容已脱敏] 是全库遍历，单线程 Redis 在这 0.5 秒内**所有请求排队**。
- 影响：每 2 分钟一次全局停顿，登录越密集越频繁 → 接口偶发抖动。

### 问题 2：连接风暴（P0/P1，新发现）

```
20 秒窗口：新建连接 +8,780 个 ≈ 439 个/秒
5 秒 MONITOR：出现过 2,037 个不同客户端连接
CLIENT LIST 快照：只有 17 个连接在线，其中 14 个 age<10 秒 → 连接寿命约 40 毫秒
MONITOR 命令分布：GET 4,236、**SELECT 2,031**、EXPIRE 444、SETEX 373、SADD 302、INCRBY 231…
```

每个连接平均只服务 3~4 条命令就被关闭，而且每个连接都要发一次 `SELECT`（5 秒 2,031 次 `SELECT`，占总命令 25%）。

结论：**应用侧每次调用 `redis()` 都在新建连接、没有复用**（未开启 pconnect / 无连接池）。代价是 TCP 握手 + Redis accept + `SELECT` 的开销全部由线上承担（累计连接数 19.7 亿），会拖慢接口并浪费 CPU。建议：

- 开启持久连接（phpredis `pconnect`）或引入连接池；
- 连接建立后只 SELECT 一次并复用；
- 这一项与数据库流量无关，但和"接口偶发变慢"高度相关。

### 附：其他观察

- `LATENCY` 监控未开启（返回 `[]` / "Latency monitoring is disabled"），所以拿不到延迟直方图；如需量化 P99，可临时开 `latency-monitor-threshold`（配置变更，需确认）。
- db2（`[queue] index = 2`）**0 个键** → 队列当前没有走 Redis；db0 只有 1 个键（`[session] adapter = Files`，session 落磁盘，符合配置）。
- db3（缓存）共 13,049 个键，热门键：`ph_system_config`、`ph_advbutton-popup`、`ph_jp_kf_config_list`、`ph_domain`、`ph_social_media`、`ph_config_dict`、`ph_lang_list`。
- **注意**：`game_category`、`user_sign_config`、`app_version`、`user_task_list` 这些在数据库侧被查了上亿次的配置集合，**在 Redis 里看不到对应缓存**（见指南 B1）——这才是数据库压力的正主。

## 三、同一时刻的数据库现状（对照用）

| 指标 | 主库 203.0.113.1 | 从库 server.db2.com |
| --- | ---: | ---: |
| query | 313~380 /s | 192 /s |
| getmore | 401~429 /s | 445 /s |
| insert / update | 83 /s、20 /s | 0 / 0 |
| 网络出 | **2.3~3.4 MB/s**（改造前约 107 MB/s） | **61.1 MB/s** |
| 复制延迟 | — | 主→从 1~2 秒 |

主库侧扫描仍然很高：**scanned 1,127,203 /s，但 returned 只有 1,920 /s → 放大 587 倍**（改造前 returned 5,752/s、放大 222~299 倍）。

解读：读分离生效了（主库输出从 107 MB/s 掉到 2.3 MB/s），但**读放大没有解决**，只是把压力搬到了从库。如果只做读分离不做缓存/投影，从库会重演主库之前的状况。

## 四、建议动作顺序

| 顺序 | 动作 | 责任 | 预期 |
| --- | --- | --- | --- |
| 1 | Redis：`KEYS` 改 `SCAN` / Set 索引（重点 `UserService.php:1861` 登录踢下线） | 后端 | 消除每 129 秒一次的 0.5 秒阻塞 |
| 2 | Redis：开启连接复用（pconnect/连接池），避免 439 连接/秒 | 后端 | 降低连接与 CPU 开销，接口抖动减少 |
| 3 | Mongo：配置类集合进缓存（`game_category`/`user_sign_config`/`app_version`/`user_task_list`/`adv`），并做投影与批量查询 | 后端 | 把 scanned 从 113 万/s 降到十万级 |
| 4 | Mongo：给从库也做容量与读偏好复核（读分离后从库成为主要读节点） | DBA | 从库 61 MB/s 回落 |

> 本包所有数据均为只读采集；唯一有性能影响的是 5 秒 MONITOR（已结束）。采样时间为凌晨低峰。
