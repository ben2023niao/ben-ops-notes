## 1. 背景

2026-09-01 静态域名 1027 事故后已升级 Workers Paid（$5/月，含 1000 万请求/月）。
但实测用量仍偏高（约 3.8-4.7 万请求/小时），月化超 2700 万，会超出含额产生按量费。
目标：业务稳定前提下把 Worker 请求量压到含额内（≤ 1000 万/月，理想 300 万以内）。

## 2. 为什么不能去掉 Worker（“直接转发存储桶”结论）

用户提议研究 Cloudflare 直接转发存储桶（免 Worker）。官方文档实测结论：

| 方案 | 可用性 | 结论 |
| --- | --- | --- |
| Origin Rules 改写 Host | **仅 Enterprise**（官方 availability 表：Free/Pro/Business 全部 No；只有“自定义回源端口”开放） | ❌ 现套餐不可用 |
| Page Rules Host Header Override | 全套餐有，但 Free 仅 3 条/zone（需每 zone 11-12 条前缀规则），Pro 20 条勉强够 | ⚠️ 仅 3 套 Pro zone 可行，且 API 被账户 token 拒绝需面板手动，工作量大、风险高 |
| Snippets 改写 Host | Free 不可用；Pro 可用但属轻量 header 规则，改写 Host 行为不确定 | ❌ 不可靠 |
| 保留 Worker（Paid） | 全 zone 统一、已稳定运行、缓存 7 天 | ✅ 唯一可靠方案 |

结论：**继续使用 Worker（Paid），把请求量降下来**是当前最优解。

## 3. 用量实测（Cloudflare GraphQL workersInvocationsAdaptive）

| 小时(UTC) | 请求数 | 小时(UTC) | 请求数 |
| --- | ---: | --- | ---: |
| 00 | 38,831 | 06 | 38,372 |
| 01 | 38,216 | 07 | 38,489 |
| 02 | 40,837 | 08 | 39,112 |
| 03 | 39,118 | 09 | 47,015 |

| 05 | 37,631 | | |

≈ 38-47 千/小时 ≈ **92 万/天 ≈ 2800 万/月**（超 Paid 含额 1000 万/月）。

### 消耗构成

1. **游戏可用性巡检（主因）**：备用机 7 厂家 × 每 2 分钟真实浏览器全量加载游戏
   （大厅→点卡→shell→试玩），每次几十~上百个静态请求走 Worker；
2. **入口健康监控**：每 2 分钟加载 7 个 H5 入口（大厅页会拉取静态资源）；
3. **静态 CNAME 监控**：每 10 分钟 × 242 域名（10 分钟改为 30 分钟后 ~35 千/天）；
4. 真实用户流量（7 天边缘缓存，重复访问命中 Worker Cache API，仍计请求数）。

## 4. 降耗改造（已完成）

### 4.1 游戏可用性巡检：2 分钟 → 每小时 1 次 + 随机抽样

- 备用机 cron 7 厂家错峰每小时 1 次：pg :0 / vendor_a :8 / pp :16 / popok :24 /
  vendor_c :32 / vendor_d :40 / g759 :48；
- `game_availability_monitor.py` 增加 `--random-cards`，每次随机抽 1 个游戏
  （113 张卡片中抽 1，实测 report.json `random_cards: true`），避免固定游戏漏检、
  避免同一游戏反复命中缓存掩盖其他游戏问题；
- 报警时效：连续失败 3 次 ≈ 3 小时（原 6 分钟）；入口监控仍 2 分钟兜底，
  可快速发现入口级故障。

### 4.2 静态 CNAME 监控：10 分钟 → 30 分钟 + 轻量探测直连桶

- 宝塔 cron `*/10` → `*/30`；
- 轻量探测从“CF 路径（走 Worker）”改为 **GCS 桶直连**（不产生 Worker 请求），
  每 30 分钟验证桶可用性与对象存在；
- 全量字节校验（CF 路径 vs 桶直连，带 `?cb=` 强制回源）仍每小时 1 次，
  用于确认 Worker/CF 链路字节一致。

### 4.3 保留项

- 入口健康监控（每 2 分钟）暂不动：入口级故障需快速发现；其大厅页静态请求
  为主要残留消耗，后续按需降为 5 分钟。
- Workers Paid $5/月保留：10M 请求/月含额 + 超出 $0.30/百万。

## 5. 预估效果

| 项目 | 改造前（/天） | 改造后（/天） |
| --- | ---: | ---: |
| 游戏可用性巡检 | ~50 万（7 厂家×每2分钟×~100 请求） | ~1.7 万（7 次/小时×~100 请求） |
| 静态 CNAME 监控 | ~3.5 万 | ~0.6 万（直连桶 + 每小时全量校验） |
| 入口监控/真实流量 | 不变 | 不变 |
| **合计（不含真实流量）** | **~54 万** | **~2.3 万** |

月化（不含真实流量）≈ 70 万/月，远低于 1000 万含额。

## 6. 验证结果

- pg 随机抽样巡检实测通过（24 秒，fails=0）；
- 宝塔 CNAME 监控新逻辑跑通：408 条全部 OK（含 165 动态），`last_full_verify` 正常；
- 静态域名抽检 200、health.json 内容校验通过；
- 两台机器 cron 已更新并持久化（备份：`/root/crontab.bak-20260901*`）。

## 7. 后续跟踪

- 24 小时后用 GraphQL 复测小时请求数，确认降到 ~1-2 万/小时；
- 若入口监控仍是消耗大头，再评估降为 5 分钟/次；
- 建议在 CF 面板关注 Workers 用量趋势，接近 800 万/月时预警。
