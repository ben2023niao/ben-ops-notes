# ADR-0017： 运营账号资金与打赏统计边界

> 来源文件：`~/Projects/work/game/xiaolan-watches/dev/docs/decisions/ADR-0017-operator-account-finance-boundary.md`

## 1. 背景

运营需要给测试/活动账号发放钻石，并在前台直播间送礼验证动效和氛围。如果这些账号的加钻和送礼进入真实充值、GMV、主播收益或排行榜，会污染财务和运营数据。

同时资金红线要求所有余额变动必须可追溯，不能因为“不计入真实财务口径”就绕过账本。

## 2. 决定

新增两个标记：

- `users.is_operator_account`：用户当前是否运营账号。
- `live_tips.is_operator_tip`：每笔送礼发生时是否运营账号送礼的历史快照。
- `live_tips.settlement_diamond_amount / settlement_rmb_equiv`：主播结算认可的礼物金额。
- `live_sessions.operator_tip_rmb / operator_tip_diamond`：本场运营礼物汇总，用于后台对账展示。

运营账号规则：

1. 后台调账仍走复式账本、`balance_adjustments` 和 `admin_audit_logs`。
2. 运营账号调账和运营账号送礼的对账账户使用 `platform:operations`，不使用 `platform:income`。
3. 运营账号调账不生成 `recharge_orders`，不增加累计充值。
4. 运营账号送礼仍扣钻并广播互动，`live_tips.rmb_equiv` 保留礼物展示/审计价值，但 `settlement_diamond_amount = 0`、`settlement_rmb_equiv = 0`、`is_operator_tip = true`。
5. `is_operator_tip = true` 会进入 C 端/主播端实时礼物榜、众筹解锁进度等互动展示口径，但排除真实 GMV、主播收益、主播结算、消费档位和奖励派发。
6. 后台场次对账同时展示 `settlement_tip_rmb`、`operator_tip_rmb`、`gross_tip_rmb`；主播结算只使用 `settlement_tip_rmb`。

## 3. 取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 完全不写账本 | 不会污染财务查询 | 资金不可追溯，违反项目资金红线 | 否 |
| 写账本但仍走 `platform:income` | 改动小 | 未来按分录汇总时仍可能污染真实收入 | 否 |
| 本方案：写账本 + `platform:operations` + 业务投影结算字段归零 | 可审计，真实经营口径干净，运营礼物可单独对账 | 报表查询要使用 settlement 字段或显式过滤 `is_operator_tip` | 是 |

## 4. 后果

- 运营账号历史送礼以 `live_tips.is_operator_tip` 为准，不随用户后续取消运营账号而回算。
- 财务如需核对运营发放，可按 `wallet_journals.meta.operator_account=true` 或 `platform:operations` 分录查询。
- 前端可通过后台用户列表的 `is_operator_account` 展示账号类型；C 端打赏响应和弹幕 tip meta 也会在运营送礼时附带 `is_operator_tip=true`。
- C 端和主播端互动展示、众筹进度不需要过滤运营礼物；财务/主播结算/奖励必须使用 `settlement_*` 或 `is_operator_tip=false` 口径。

## 5. 验收口径

- 后台用户管理可设置/取消运营账号并写审计。
- 运营账号加钻有账本和调账记录，但无充值订单。
- 运营账号送礼扣钻、广播礼物，`rmb_equiv` 保留展示价值，进入实时礼物榜和众筹解锁进度；但 `settlement_rmb_equiv=0`，不进入 GMV、主播收益和奖励。
- 后台房间场次历史可同时看到结算打赏、运营礼物和礼物总额。
