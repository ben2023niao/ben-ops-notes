# 上线测试门禁

> 来源文件：`~/Projects/work/game/xiaolan-watches/dev/docs/quality/release-testing-gates.md`

> 整理日期：2026-06-04 01:09｜日期依据：文件创建/修改时间

测试不是补充材料，而是项目是否具备上线资格的证据。乌托邦 允许项目按 MVP、growth、scale、enterprise 分阶段建设，但不允许用“先跑通”“冒烟通过”“页面看着差不多”替代测试闭环。

本门禁属于 乌托邦 Core，不依赖 Claude Code hook、Codex 或任何单一 Agent。Hook 是 Adapter 可选增强，但默认完成判断必须依赖可复查的命令、矩阵、截图、日志和红蓝对抗。

Agent 只有完成申请权，没有完成裁决权。Agent Claim 只能是 `implemented`、`verified`、`blocked`；Project Decision 才能是 `pending-review`、`accepted`、`rejected`、`released`。

## 1. 设计目标

1. 防止 AI Agent 没有真实测试就声明完成。
2. 防止单人项目里“执行者即 reviewer”导致自我放行。
3. 防止只验前端、只验后端、只验接口 200 或只跑冒烟测试就写 `已完成`。
4. 把上线判断从口头承诺升级成结构化证据和 CI/MR 门禁。
5. 保留不同项目的自由度，但不允许降低完成底线。

## 2. 不可降低的完成底线

任何需求、接口、页面、后台模块或运维变更要声明完成，必须同时满足：

1. 有需求 ID，且能追踪到 `docs/prd/**`。
2. 涉及接口时有 OpenAPI、事件或明确“不涉及”原因。
3. 涉及数据、权限、账本、审计时有数据模型和权限说明。
4. 有自动化测试，或明确不适用原因；业务功能不能用“不适用”逃避测试。
5. 有手工/E2E/场景验收证据。
6. 页面类需求有真实视口截图或录屏。
7. 后台类需求有权限、审计、异常路径验证。
8. 有测试环境记录，不能只在 Agent 心里“测过”。
9. 有 Agent 日志和红蓝对抗。
10. 有明确合入判断：`允许合入`、`不允许合入` 或 `阻塞`。

## 3. 测试层级

| 层级 | 必须回答的问题 | 最低证据 |
| --- | --- | --- |
| Unit | 核心逻辑和异常路径是否可靠 | 测试命令和结果 |
| Contract | 前后端是否围绕同一份 OpenAPI 或事件契约 | `npm run check:openapi`、`npm run check:contract` |
| Integration | 服务、数据库、缓存、队列、第三方是否真实协作 | 集成测试或沙箱验证 |
| E2E | 用户主流程是否真的走通 | Playwright/Appium/手工场景记录 |
| UI Runtime | 页面是否真实渲染、可点、无 console error、无横向溢出 | 截图、视口、`docs/qa/ui-visual-evidence.json` |
| Manual QA | 体验、文案、兼容性和异常状态是否符合验收 | 验收记录、截图或录屏 |
| Performance/SLO | 大流量或高风险服务是否满足容量和稳定性目标 | `docs/qa/performance-evidence.json` |
| Ops Readiness | 是否能部署、回滚、观测、恢复 | `docs/operations/**` 和 runbook |

## 4. 什么不能算完成

以下证据不能单独支撑 `已完成`：

1. “冒烟测试通过”。
2. “接口返回 200”。
3. “页面能打开”。
4. “本地看过了”。
5. “MVP 阶段先这样”。
6. “后续补测试”。
7. 只有 mock、fixture、placeholder 或 fallback。
8. 只有某一端完成，另一端没有契约或联调证据。
9. 没有截图、没有命令输出、没有日志、没有红蓝对抗。

冒烟测试可以作为补充证据，但不能作为完成结论的唯一依据。

## 5. 项目级闭环

乌托邦 的验收不是“前端验收”“后端验收”“后台验收”分开自嗨，而是模块闭环：

```text
PRD -> Contract -> Data/Permission -> Backend -> Frontend/Admin/Mobile -> Automated Test -> E2E/Manual -> Environment -> Red/Blue -> Agent Log
```

模块没有覆盖完整链路时，只能写 `进行中`、`阻塞` 或 `未开始`。确实不涉及某一层时，必须写明原因，例如纯文档规则、纯 CLI 工具或纯架构决策。

## 6. UI Runtime

涉及 `apps/mobile/**`、`apps/web/**`、`apps/admin/**` 的页面或交互变更，完成前必须运行真实页面验证。公共命令是：

```bash
UI_VISUAL_BASE_URL=http://localhost:3000 npm run verify:ui-runtime
```

该命令不依赖 hook。它用于 Agent 最终声明前、人工 review 前或 CI/MR 中执行。项目可选在 Claude Code Stop hook、Codex final checklist 或 GitLab CI 中调用它，但 Hook 不是 Core 默认要求。

最低验收：

1. 打开真实页面，不只看静态截图。
2. 覆盖项目要求的手机、平板、桌面视口。
3. 记录截图到 `docs/qa/screenshots/**`。
4. 结构化写入 `docs/qa/ui-visual-evidence.json`。
5. console error 为 0，或异常有明确解释。
6. 无横向溢出、关键按钮可点击、表单和导航流程可走通。

## 7. 上线前必跑命令

常规合入：

```bash
npm run check
```

新项目初始化：

```bash
npm run check:init
```

涉及 UI：

```bash
UI_VISUAL_BASE_URL=<local-or-staging-url> npm run verify:ui-runtime
```

涉及上线、环境、部署：

```bash
npm run check:ops
npm run check:test-env
```

涉及高并发或大流量：

```bash
npm run check:performance
```

## 8. Agent 完成声明

Agent 最终回复不能只说“完成了”，也不能自己宣布 `accepted`、`released`、`验收通过` 或 `可以上线`。必须引用：

1. Agent Claim：`implemented` / `verified` / `blocked`。
2. Project Decision：默认 `pending-review`，或引用 Reviewer / Owner / QA / CI 的明确裁决。
3. 需求 ID。
4. 修改范围。
5. 测试命令和结果。
6. UI 截图或不涉及原因。
7. E2E/手工场景。
8. `docs/qa/acceptance-evidence.md`。
9. `docs/qa/project-acceptance.md`。
10. Agent 日志。
11. 红蓝对抗结论。
12. 剩余风险。

没有证据时，只能写“未完成验证”或“不允许合入”，不能声明完成。

## 9. 团队责任

1. Agent 负责按证据写完成报告。
2. Reviewer 负责检查证据真实性。
3. QA 负责维护验收矩阵和关键场景。
4. Tech Lead 负责把项目特有测试要求沉淀回框架。
5. CI/MR 负责把可自动校验的规则变成红灯。

框架不是替代团队成员判断，而是让团队成员判断有证据可审。
