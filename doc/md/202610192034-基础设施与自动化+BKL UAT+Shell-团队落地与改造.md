# 团队落地与改造

## 1. 角色分工

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| 项目负责人 | 定目标、批准高风险操作、验收 | 不写全部文档 |
| 运维 | 机器矩阵、链路、发布、告警 | 不替开发改业务代码 |
| 开发 | 模块索引、接口、变更说明 | 不直接改生产 |
| AI | 读事实、写 plan、执行低风险步骤、写 result | 不批准自己的高风险操作 |

原则：AI 可以执行，但不能同时当申请人、审批人和验收人。

## 2. 三周落地

### 第 1 周：先能用

- 选一个真实项目，不要用玩具项目
- 安装 Workbench
- 填机器矩阵、运行链路、通知目标
- 选一个 1~2 小时能完成的任务试点
- 要求 AI 全程按 `AGENTS.md` 执行
- 完成后写一份 result

验收：

- 新会话能在 5 分钟内接手
- 通知能发到群
- 任务有文档、有提交

### 第 2 周：变成习惯

- 所有任务登记 `ACTIVE_TASKS.md`
- 每个任务写 context / plan / result
- 每次提交前跑检查
- 每步发通知
- 每天收工前更新 `CURRENT_STATE.md`

验收：

- 没有“口头任务”
- 没有“做完没文档”
- 没有“密码发群”

### 第 3 周：按团队改造

- 调整风险分级
- 调整通知标题和群
- 增加项目自己的模块索引
- 把常用命令写进 README
- 做一次复盘，删掉不用的字段

验收：

- 团队能不看聊天记录完成交接
- 新人能按文档独立完成一个小任务

## 3. 开发项目怎么改

### 3.1 模块索引

把 `PROJECT_INDEX.md` 改成真实模块：

| 模块 | 目录 | 说明 |
| --- | --- | --- |
| API | `src/api/` | REST 接口 |
| Web | `src/web/` | 前端 |
| Worker | `src/worker/` | 异步任务 |
| DB | `migrations/` | 数据库迁移 |

### 3.2 运行链路

写清：

- 本地怎么起
- 测试环境怎么起
- 依赖哪些中间件
- 端口、环境变量
- 发布顺序

### 3.3 验证

开发项目至少写：

```bash
make test
make lint
curl -f http://203.0.113.1:8080/health
```

没有测试的项目，先加 smoke test。

### 3.4 发布

把发布步骤写成 plan 模板：

1. 拉代码
2. 构建
3. 迁移数据库
4. 发布
5. 健康检查
6. 回滚命令

## 4. 运维项目怎么改

### 4.1 机器矩阵

必须写：

- 主机名
- 内网 / 公网 IP
- 角色
- 登录账号名
- 密码保存位置
- 是否走堡垒机

### 4.2 运行链路

必须写：

- 域名 → nginx → 后端
- 证书方式
- 端口监听范围
- 出网 / 专线限制

### 4.3 通知

必须写：

- 群名称
- chat_id
- 什么事件发这个群
- 什么事件不发

### 4.4 高风险清单

建议列出：

- 重启生产
- 改 DNS
- 改证书
- 改防火墙
- 改数据库
- 改权限
- 删除文件 / 容器 / 镜像

这些操作必须走 plan + 批准。

## 5. 要改什么，不要改什么

### 建议改

- 项目名称、负责人
- 机器矩阵
- 运行链路
- 通知目标
- 模块索引
- 风险分级的具体例子
- 验证命令

### 不要改

- 事实分级
- context / plan / result 三段式
- “验证后再提交”
- “秘密不进 Git”
- “高风险先批准”

这些是骨架，改了就容易退化成普通聊天。

## 6. 评审节奏

### 每日

- 更新 `ACTIVE_TASKS.md`
- 收工前更新 `CURRENT_STATE.md`
- 阻塞当天写清楚

### 每周

- 看本周完成了什么
- 有没有返工
- 有没有秘密泄露风险
- 文档是否跟得上
- 删掉过期任务

### 每月

- 复盘一次失败任务
- 更新风险分级
- 更新模板
- 轮换 token

## 7. 度量

| 指标 | 怎么算 |
| --- | --- |
| 接手时间 | 新会话从开始到能继续任务的时间 |
| 返工率 | 需要二次修复的任务 / 总任务 |
| 文档覆盖率 | 有 doc 的任务 / 总任务 |
| 验证覆盖率 | 有验证记录的任务 / 总任务 |
| 秘密事件 | 进仓库或发群的秘密次数，目标 0 |
| 阻塞时长 | 任务从阻塞到恢复的时间 |

不要追求漂亮数字，先看有没有真实改善。

## 8. 常见失败模式

| 失败模式 | 表现 | 修正 |
| --- | --- | --- |
| 只装模板不用 | 文件生成了，任务还是靠聊天 | 每周抽查一个任务是否按流程 |
| 文档变流水账 | 只写“已执行命令” | 必须写现象、证据、结论 |
| plan 太虚 | “检查一下、改一下” | 每一步可执行、可验证 |
| 通知刷屏 | 一条命令发一次 | 一个步骤发一次 |
| AI 权力太大 | 自动改生产 | 高风险必须人工批准 |
| 密码又进仓库 | 图省事写默认值 | 提交前跑 gitleaks / check |
| 模板太重 | 小任务也写一大堆 | 小任务用简化版 context |

## 9. 发到群里怎么发

1. 打包：

```bash
python3 workbench-kit-通用AI工作台/scripts/package_kit.py
```

2. 发 zip + 一段说明（见 `08-群公告模板.md`）

3. 让开发先做三件事：

```bash
python3 scripts/install.py /path/to/project --name "项目名" --with-vscode
python3 workbench/scripts/check.py .
python3 workbench/scripts/context_pack.py --project .
```

4. 收集反馈：

- 哪个文件看不懂
- 哪个步骤多余
- 哪个检查失败
- 需要什么行业的模板

5. 第二版按反馈收敛，不要一次加太多。

## 10. FAQ

**Q：小项目也需要吗？**

至少用 `AGENTS.md` + `ACTIVE_TASKS.md` + `doc/日期-事项`。三个文件就够。

**Q：和 Jira 冲突吗？**

不冲突。Jira 管工单，Workbench 管 AI 上下文和执行事实。

**Q：AI 会不会把 Workbench 写乱？**

会。所以要有 `check.py`、Git diff、人工评审。

**Q：一定要发通知吗？**

高风险和长任务建议发。小任务可以只在开始和完成各发一次。

**Q：一定要用 Telegram 吗？**

不。`notify.py` 只是示例，可以换成飞书、Slack、企业微信。

**Q：每个项目都要装一份吗？**

是。每个项目事实不同，独立 Workbench 最清晰。
