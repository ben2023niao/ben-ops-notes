# 故障响应规范

> 来源文件：`~/Projects/work/game/xiaolan-watches/dev/docs/operations/incident-response.md`

> 整理日期：2026-06-04 01:09｜日期依据：文件创建/修改时间

故障响应的目标是快速止损、恢复服务、保留证据、复盘改进。AI Agent 不能把“服务能启动”当成“具备运维能力”。

## 1. 严重级别

| 级别 | 定义 | 响应目标 |
| --- | --- | --- |
| P0 | 生产核心链路不可用、资金/账本错误、数据泄漏、无法登录、大面积 5xx | 立即响应，优先止损。 |
| P1 | 单模块严重异常、支付/通话/消息部分失败、后台审核不可用 | 快速定位并给出恢复方案。 |
| P2 | 局部功能异常、性能明显下降、有替代路径 | 安排修复和监控。 |
| P3 | 文案、非核心 UI、低风险运维问题 | 正常迭代处理。 |

## 2. 响应流程

```text
发现 -> 分级 -> 止损 -> 定位 -> 恢复 -> 验证 -> 复盘 -> 规则沉淀
```

每一步必须记录：

1. 时间。
2. 负责人。
3. 影响范围。
4. 采取动作。
5. 验证结果。

## 3. 必备信息

故障处理必须能拿到：

1. 服务名称和版本。
2. 最近一次部署 commit/tag。
3. 环境：dev/staging/production。
4. request id / trace id。
5. 错误日志。
6. 指标或告警。
7. 数据库/Redis/队列状态。
8. 第三方状态。
9. 回滚路径。

## 4. Runbook

高风险模块必须有 runbook。推荐模板：

```text
docs/templates/ops-runbook-template.md
```

最低覆盖：

1. API 5xx、502、504。
2. DB 连接、慢查询、锁等待。
3. Redis 故障。
4. Worker 积压、重试、死信。
5. 第三方回调失败。
6. 支付、账本、审核、权限异常。
7. 证书过期、域名错误、磁盘满。

## 5. 复盘

P0/P1 必须复盘：

1. 事故摘要。
2. 影响范围。
3. 根因。
4. 发现方式。
5. 为什么现有门禁没有提前发现。
6. 修复动作。
7. 防复发动作。
8. 是否需要更新 PRD、ADR、运维规范、监控或 Agent 规则。

## 6. Agent 规则

AI Agent 参与故障处理时：

1. 先止损和保留证据，不盲目重构。
2. 不删除日志、不清空数据、不重置数据库，除非用户明确批准并有备份。
3. 不把猜测写成根因。
4. 修复后必须补充验证命令和复盘记录。
5. 发现框架缺少门禁时，必须写入 Agent 日志风险与待办。
