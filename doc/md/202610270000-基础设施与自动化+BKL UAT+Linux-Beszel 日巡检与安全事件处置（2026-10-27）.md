## 事件摘要

14:04 起 manager 出现持续 Docker cgroup OOM，14:17 开始监控集中报告多个容器离线。初始现象像网络波动，实际是 manager 上出现伪装成 `nginx/php/postgres/apache2` 的高 CPU 异常进程，把 cadvisor、portainer-agent 和多个 1GiB 业务容器拖到资源上限。

## 根本原因

### 1. 直接原因：异常伪装进程耗尽 CPU 和内存

- `php-fpm` 父进程是 cadvisor，可执行文件为 `/.573HUqS3J04WXj82Uj6`
- `postgres` 父进程是 portainer-agent，可执行文件为 `/.urfc8ZJIRYocTowRDXknsfYip0QT`
- 两个异常进程各占约 2.4GiB，单进程 CPU 接近满核
- 两者持续派生僵尸进程，管理器上僵尸峰值达到 156
- 正常 cadvisor 只有约 80MiB，正常 portainer-agent 只有约 25MiB

cadvisor 和 portainer-agent 镜像本身不含这些程序，因此判定为容器内启动的伪装程序。

### 2. 安全入口：Docker API 无认证暴露公网

manager 的 `/etc/docker/daemon.json` 配置为：

```text
tcp://0.0.0.0:2375
```

从外网访问 `43.249.251.12:2375/version` 可直接取得 Docker 版本，说明未启用认证和 TLS。该接口允许调用 Docker API，可创建、停止、删除容器，并可利用高权限容器获得宿主控制能力。

Portainer agent 同时以**读写**方式挂载：

- 宿主 `/`
- `/var/run/docker.sock`
- `/var/lib/docker/volumes`

因此 portainer-agent 一旦被控制，影响范围等同于宿主 root。

### 3. 持久化：恶意 cron

发现 `/etc/cron.d/zzh` 每分钟以 root 执行 Base64 解码后的 `curl | bash`，属于典型的下载器持久化。该文件创建时间早于异常进程启动。已删除该文件和根目录下可疑空可执行文件 `/root/.1`。

### 4. 放大因素：单节点资源过度集中

- manager 同时运行 Swarm 业务副本和 Grafana/Prometheus/Alertmanager/cadvisor/Portainer
- 监控组件曾合计占用约 13GiB
- 业务服务统一限制 1GiB，多个常驻服务已使用 700~1000MiB
- manager 内存压力升高后，容器更容易触发 cgroup OOM

这不是本次事件的首要入口，但显著放大了故障影响。

## 处理过程

### 1. 监控与异常分析

- 读取 Beszel 7 台系统状态、24 小时趋势和告警
- 核对 manager/worker/middleware 的 CPU、内存、磁盘、Docker 服务和 OOM

- 确认 14:17 集中离线是 manager 异常导致，不是全部业务同时宕机

### 2. 业务恢复

先释放 manager 上传统监控组件占用，再将 8 个 OOM 或临界服务的内存上限从 1GiB 调整为 1.5GiB：

- `game-agent-open`
- `game-queue`
- `game-scheduler`
- `game-gateway`
- `pay-queue`
- `pay-scheduler`
- `pay-gateway`
- `middle-station-openapi`

批量 `start-first + rollback` 时部分服务因启动拥塞自动回滚，随后改为逐个 `stop-first + pause` 更新，全部收敛为 `2/2`。

### 3. 按最新要求精简监控

- 停用并移除传统监控容器：Grafana、Prometheus、Alertmanager
- 移除重复全局服务：cadvisor、node-exporter、portainer-agent
- 保留当前 Beszel Hub 与各节点 beszel-agent

- 删除 `/root/.1`
- 保留 `/etc/docker/daemon.json.bak-20261027` 作为变更前配置备份

未立即重启 Docker，以避免中断正在运行的业务。当前由防火墙实时阻断；daemon 配置已通过校验，后续重启会恢复为仅 Unix Socket。

## 附录：大白话讲清授权安全测试底层原因

### 一句话总结

这次不是“业务代码被黑”，而是**服务器管理接口像一扇没有锁的门直接开在公网上**，授权安全测试者进来后拿到了接近宿主机 root 的权限，并留下“每分钟自动重开”的定时任务。

### 1. Docker API 是什么

Docker 是管理容器的“总控台”，2375 就是总控台对外的遥控器接口。

- 2375：**没有密码、没有加密**。谁连上，谁就能创建/删除/停止容器、看日志、在容器里执行命令。
- 2376：给这个遥控器加了 TLS 证书校验，可以要求客户端也出示证书（双向 TLS）。
- SSH 隧道：不把遥控器开到公网，只在堡垒机上开一个加密小门，外部先登录堡垒机再用。

用生活里的比喻：2375 就像把家里的总电闸和门锁遥控器放在马路边，还没有密码。路人不仅能关灯，还能自己接一根线进来。

### 2. 授权安全测试是怎么一步步放大的

1. 公网扫描器发现 `43.249.251.12:2375` 能直接访问 Docker。
2. 授权安全测试者通过这个接口在 `cadvisor` / `portainer-agent` 容器里启动程序。
3. 这两个容器能读写宿主机 `/` 和 `docker.sock`，所以容器里的程序实际能碰宿主机文件和 Docker 控制权。
4. 恶意程序伪装成 `postgres`、`nginx`、`php`，一边吃 CPU，一边下载脚本。
5. 脚本写入 `/etc/crontab`，每分钟重新下载执行，同时重建 `/root/.1`。

所以只杀进程没用：定时任务会把它重新拉起来；只删 cron.d 也没用，因为这次藏在 `/etc/crontab`。

### 3. 为什么“换个端口”没用

换端口只是把没锁的门从 2375 换到 2380、3000 或别的门牌号。互联网上的扫描器会扫全端口，几分钟就能重新找到。

**没有认证和加密的 Docker API，只要放到公网，换哪个端口都不安全。**

### 4. 为什么“只监听内网 IP”也没挡住

机房把公网 IP 映射到了内网 IP。外面访问 `43.249.251.12` 时，流量会被送到 `203.0.113.1`，Docker 仍然收得到。

所以“只绑内网 IP”不等于“只有内网能访问”，还必须：

- 在主机/云防火墙按来源 IP 限制；
- 或者根本不在公网开放；
- 或者改成 SSH 隧道 / 双向 TLS。

### 5. Mark 问的“认证”是什么

不是简单的用户名密码。Docker API 的正式认证方式是**双向 TLS**：

- 服务端有证书；
- 客户端也要有证书；
- 双方互相验证，证书不对就连接不上。

最省事的方式是 SSH 隧道：公网只开 SSH，Docker 只监听本机，运维通过堡垒机进去管理。

### 6. 这次已经做了什么

- 2375/2376 只允许内网来源，公网已阻断；
- `portainer-agent` 已移除，不再让它读写宿主根目录和 Docker Socket；
- 恶意 cron、进程、隐藏可执行文件和 C2 地址已清理；
- 四台 UAT 已启用端口白名单和开机恢复；
- `daemon.json` 已改为仅 Unix Socket，等维护窗口重启 Docker 后 2375 会彻底消失。

### 7. 还必须记住的三句话

1. **Docker 2375 永远不要对公网开放。**
2. **换端口不是安全措施，认证和来源限制才是。**
3. **Portainer/cadvisor 这类监控容器不要读写挂载宿主 `/` 和 `docker.sock`。**

## 防复发清单

### 必须立即完成

- 禁止 Docker `2375` 暴露公网；远程管理只走 SSH 隧道或双向 TLS 2376
- 限制公网 SSH，只允许固定运维出口 IP；禁止 root 密码登录
- 轮换 manager 上的 SSH Key、GitLab Token、机器人 Token、监控账号、数据库/中间件凭据
- 轮换 Docker TLS CA/服务端/客户端证书，以及所有曾存放在 manager 的密钥
- 对 manager 做完整取证后重装系统，或在可信快照上重建；不要只依赖本次进程清理

### 长期基线

- 监控组件与 Swarm manager 分离部署，禁止在 manager 上跑高占用监控栈
- Portainer agent 不得挂载宿主根目录和 Docker Socket；非必要不部署
- Docker 节点只开放业务必需端口，默认拒绝其他入站
- 每周执行 `security/audit_docker_exposure.sh`
- 每日检查 `/etc/crontab`、`/etc/cron.d`、用户 crontab、systemd、异常可执行文件、OOM 和容器 restart loop
- 禁止重新部署 `portainer-agent`；监控统一使用 Beszel，cadvisor/node-exporter 仅保留只读挂载
- 对容器 CPU、内存、重启、僵尸进程增加告警
- 业务服务部署配置必须固化 1.5GiB 上限，不能只保留运行时 override
