# 2026-08-29 游戏启动链路 P0 优化方案（针对与竞品差距）

> 来源文件：`~/Projects/work/game/pgserver/master/docs/history/2026-08-29-0005-【优化方案】游戏启动链路P0优化方案.md`

> 整理日期：2026-08-29 00:05｜日期依据：文件名日期

时间：2026-08-29 00:05（Asia/Manila）
项目：DBQP / PGServer master
背景：同游戏对比竞品进游戏稳定 4.0s vs 我方 9.7s；静态已就近（东京桶 49ms），
差距主要在启动 API 链路与 launcher 测速流程。

## 现状量化（马尼拉实测）

```text
端点                    冷连接     回访(warm)
我方 Logintest          752ms      386ms
我方 pg-games           1154ms     970ms
我方 api                1154ms     440ms
竞品 api4               110ms      36ms
```

HTTP/3(QUIC)+0-RTT 已全量启用（42/42），回访连接建立省 0.2-0.7s；
剩余差距核心 = 我方 API 源站在圣保罗（warm ~400ms），竞品源站/边缘在马尼拉附近（36ms）。

## P0 方案（按收益排序）

### P0-1 服务器端就近选桶，去掉/缩短客户端测速（收益约 1-3s）

现状：launcher 页前端对 static_hosts/game_hosts 并发 ping（`var timeout = 3000`，
首批 5 个，等待首个响应），每局都跑，最坏 3s。

改法（platform-api + launcher.txt）：
1. `timeout` 3000 → 800ms，`b_size` 5 → 8；
2. 首测成功后把选中 host 写入 localStorage（按 host 记忆，7 天），下次直接使用，不再 ping；
3. launcher 页服务端读取 Cloudflare 请求头 `cf-ipcountry`/`cf-ray` 时区推断区域，
   直接按区域排好 host 顺序（BR→圣保罗桶，亚洲→东京桶），前端 ping 只作兜底降级。

### P0-2 launcher 模板边缘缓存（收益约 0.3-0.6s/次）

现状：launcher 页面整体由 platform-api 渲染（含 ticket，无法整页缓存），亚洲用户每次
都走圣保罗源站。

改法：
1. 把 `conf/launcher.txt` 模板抽成静态资源（launcher.js），Cloudflare 缓存（1h+）；
2. ticket 改由小接口返回，launcher.js 拉 ticket 后本地渲染；
3. 页面 HTML 只留 `<script src=...>`，可被边缘缓存/或前端框架直接加载。

### P0-3 动态 API 请求优化（收益约 0.3-0.8s）

1. 游戏页 `<link rel=preconnect>` 到 pg-games.<root>、东京桶、verify 域名；
2. ticket / verify / network-report 并行化或合并（当前串行）；
3. network-report 改为不阻塞（已 fire-and-forget，确认无 await）。

### P0-4 大厅体积（与竞品 1.4MB vs 5.5MB 差距）

image.prod-br.com 封面图 WebP/压缩 + 懒加载（前端项，独立排期）。

## 预期效果

```text
启动到稳定：9.7s -> 6.5-7.0s（P0-1 为主，P0-2/P0-3 叠加）
回访用户进一步受益：launcher 不再 ping（P0-1 记忆）+ 0-RTT
```

仍无法追平竞品 4.0s 的部分：我方 API 源站地理位置（圣保罗 vs 马尼拉），
需 Asia 侧 platform-api 实例或 Worker 边缘化（P1，成本更高，单独评估）。

## 风险与回滚

- P0-1 全部可参数化（环境变量开关），发布前先在备用机单测；
- launcher 改动影响所有厂商入口，先灰度 1 个厂商；
- 涉及 platform-api 发布（需用户确认 Push）。

## 实施记录（2026-08-29 01:00）

P0-1 已实施并发布（Git 226c814d，platform-api 3/3）：
- launcher 测速超时 3000 → 800ms（环境变量 LAUNCHER_PING_TIMEOUT_MS 可调）
- 并发批大小 5 → 8
- 选中 host 记忆 localStorage（dbqp_best_static / dbqp_best_game），回访免测速

复测（马尼拉，新浏览器上下文 × 2 轮）：canvas 6.4-11.5s、idle 9.4-14.5s，
样本波动大，顺风路径无肉眼可见提升（本地桶 50ms 响应，测速阶段本来就快）；
预期收益主要在：坏路径（无快速响应时 3s→0.8s 兜底）与回访（localStorage 免测速）。
严格验证需同上下文连续开两款游戏对比第二局。

## 多地区部署评估（platform-api）

现状：platform-api 在圣保罗 3 台后端，依赖 BR 内部 Redis（ticket/网络上报）与 MySQL；
游戏页（pg-games）也由 BR 后端出。巴西用户约 90%+，亚洲为少数。

方案分级：
```text
A 边缘缓存+Worker（轻量）：launcher 模板静态化缓存（P0-2），ticket 小接口；
   覆盖亚洲大部分可缓存收益，零架构改动，推荐先做。
B 亚洲 platform-api 实例（香港机/新 asia-east2 实例）：
   + 亚洲 Redis 副本；MySQL 仍回 BR（跨区），写路径 ~250ms；
   只省 用户->API 一段，DB 往返仍在 BR，收益有限，除非加 MySQL 只读副本。
C 完整亚洲副本（Redis+MySQL 副本 + 游戏页链路亚洲化）：
   收益最大，成本/一致性/监控复杂度最高；且游戏服务容器也在 BR，
   仅亚洲化 platform-api 无法让最终游戏页就近，需整体评估。
```

建议：先 A（P0-2/P0-3），亚洲流量达到阈值后再评估 B；竞品 36ms 是因为源站就在马尼拉，
我们为 10% 用户做全量复制性价比不高。

## 实施记录 2（2026-08-29 01:40，四项优化执行与调整）

### 瀑布诊断结论（马尼拉，游戏 126）

```text
游戏 HTML(pg-games) TTFB  1363ms   <- 回巴西源站，动态不可缓存
shared/report.js           968ms    <- 纯静态，但源站返回 cache-control:no-cache -> CF BYPASS
api/report/timing         1021ms    <- 后端上报接口
东京桶静态资源              ~23ms    <- 已就近，无瓶颈
```

### P0-2 调整（重要）

launcher 页面按 ticket 动态生成（每请求唯一 URL），把模板拆成静态 /launcher.js 也无法
减少"页面本身回巴西源站"的那一次往返（RTT 是成本，不是字节数），原方案预期收益约 0。
因此改为真正有效的替代：

1. **shared/report.js 等共享静态资源边缘缓存**（本次主要收益）：
   源站对该文件返回 `cache-control: no-cache`，导致 Cloudflare BYPASS 每次都回巴西。
   修复：在 Cloudflare 加 Cache Rule（Cache Everything + Edge TTL 1d），
   覆盖 `*-games.<root>/shared/*.js|json`（指令见下，需 Agent Lee 执行）。
2. preconnect/Early Hints：游戏页 HTML 为厂商页面、launcher 路由在镜像内，
   无法在 repo 侧注入 preconnect；Early Hints 需源站返回 Link 头，暂不可行，记为后续。
3. GCS 缓存头：对象无显式 cache-control（走默认 3600s），已批量设置
   图片/css/字体 → `public, max-age=31536000, immutable`；js → `max-age=86400`；
   html/json 保持默认（后台任务执行中）。

### Cloudflare Cache Rule 指令（shared 静态资源）

> 请对巴西 22 个根域 + 香港 6 个 zone（hkcloudplay01-05.com、hkplaycore.com），
> 每个 zone 创建一条 Cache Rule，名称 `DBQP shared static cache`：
> 表达式：
> (starts_with(http.host, "pg-games.") or starts_with(http.host, "tada-games.")
>  or starts_with(http.host, "pp-games.") or starts_with(http.host, "ppk-games.")
>  or starts_with(http.host, "playson-games.") or starts_with(http.host, "panda-games.")
>  or starts_with(http.host, "g759-games."))
> and starts_with(http.request.uri.path, "/shared/")
> 动作：缓存资格 = 可缓存；Edge TTL = 1 天；忽略源站 Cache-Control；Browser TTL = 1 天。
> 完成后报告成功/失败 zone 列表。

### nginx 方案实施（2026-08-29 02:00，替代 CF Cache Rule）

CF 免费版不缓存带 Set-Cookie 的响应；server_name_session cookie 由宝塔 WAF(btwaf)
Lua 钩子注入。用纯 nginx/宝塔实现，未建任何 CF 规则：

1. `/www/server/panel/vhost/nginx/00.vendor-upstreams.conf`：新增
   `map $host $dbqp_game_backend`（game host -> 厂商 upstream）与
   `map $uri $dbqp_shared_cc`；
2. `common/all-games-proxy.conf`：新增 `location ^~ /shared/`，按 host 直连厂商
   upstream，`proxy_hide_header Cache-Control/Set-Cookie` +
   `add_header Cache-Control "public, max-age=86400"` + CORS；
3. `/www/server/btwaf/header.lua`：仅对 `^/shared/` 路径跳过会话 cookie 注入
   （其余路径行为不变），已备份 `.bak-20260829`；
4. 持久化确认：同步脚本只重写受管 upstream/map 块，不影响新增 map 与 location；
   btwaf Lua 面板升级可能覆盖，需留意备份。

验证：
```text
report.js 响应：Cache-Control: public, max-age=86400，无 Set-Cookie
Cloudflare：cf-cache-status BYPASS -> MISS -> HIT（age 递增）
回归：pg-games/126/index.html/api 均 200；tada /shared 404（该厂商无此文件，正常）
```

预期效果：report.js 由每次回巴西源站 ~1s 变为边缘命中 ~50ms；浏览器侧同样缓存 1 天。

### nginx 连接复用优化（2026-08-29 02:30）

定位：宝塔 nginx `0.websocket.conf` 的 map 把非 WebSocket 请求的 Connection 头设为
`close`，导致**每次请求都向后端新建 TCP 连接**（upstream keepalive 形同虚设）。

修改：
```text
0.websocket.conf:  '' close;  ->  ''      "";
                   （非 WS 请求 Connection 头置空，启用 upstream keep-alive）
nginx.conf:        keepalive_timeout 60  -> 300；新增 keepalive_requests 10000
```

效果：宝塔→后端连接复用（内网 1ms 级）；CF→宝塔连接由 CF 按源站 keepalive 复用
（300s），减少跨洲 TLS 握手。gzip 原本已开启（api/js/css/json）。
备份：`0.websocket.conf.bak-20260829`、`nginx.conf.bak-20260829`。
