## 1. 背景

原型 `2026.05.23迭代版.html` 自 v3.60（2026-05-22）迭代到 v4.45（2026-05-23），35+ 个增量版本，与已落到 `docs/prd/modules/` 的 PRD v0.2（评审版）出现 5 大类系统性差异：

| 维度 | PRD v0.2 假设 | 原型 v4.45 实际 |
|---|---|---|
| 充值兑换 | `1 RMB = 10 💎` + 5 💎 赠送；正反向兑换 | `1 RMB = 1 💎` 一锤入账；兑换功能整体下线 |
| 平台费率 | 充值赠送、提现 2% | 充值扣 5%、提现扣 5%（统一 5%） |
| 账号管理 | 4-20 位 + 昵称 + 客服可重置密码 | 6-20 位 + 用户名（注册后改）+ 平台不可找回 + 字证图自存 |
| 直播间 | 1080p / 720p / 480p 清晰度切换；打赏 1 💎 连击；弹幕字数按等级阶梯 | 5 条线路 + 实时延迟 + 流畅度灯；打赏 modal 选金额；弹幕统一 100 字 |
| 客户端形态 | H5 5 pane（含设置）+ 沉浸式直播 | H5 4 pane（删设置 / 退出登录）+ 3 种直播模式（剧场式 / 横屏 / 沉浸式）+ 3 广告位 |

继续按 v0.2 PRD 实现，意味着实现完成后立即面临大面积返工。**v1 还未上线，是切换 PRD 基线最便宜的时点**。

## 2. 决定

**对齐 PRD 到 v0.3、并同步推动 5 个模块的代码改造**。具体决策点：

| # | 决策点 | 选择 | 关键理由 |
|---|---|---|---|
| 1 | 兑换功能 | **整体下线** | 业务上钱包已能直接覆盖（充值即得钻、提现即出钱），双向兑换属过度设计；保留只会增加心智+合规边界（钻石→RMB 反向 20% 手续费触博彩边界） |
| 2 | 充值比例 | **1 RMB = 1 💎** | 与 RMB 心智完全一致，普通用户无需算术；扣 5% 后向下取整入账 |
| 3 | 平台费率 | **充值 5% / 提现 5%**（统一） | 单一费率简化运营沟通；5% 在同类产品里属于中位偏低；不再为兑换通道单独定费率 |
| 4 | 账号格式 | **6-20 位** + 仅英数字_ | 4 位过短易撞库；20 位封顶避免滥用 |
| 5 | 密码强度 | **大写+小写+数字+特殊字符 + 8-20 位** | OWASP 推荐档；注册页 5 项 chip 实时校验、用户即时反馈 |
| 6 | 密码找回 | **平台不提供任何找回 / 重置路径** | 强制用户保管字证图 → 平台不持有客服恢复链路 → **彻底规避客服伪造身份骗密码的安全风险**；丢失即放弃账号 |
| 7 | 字证图 | **客户端 canvas 渲染 PNG，密码不上传** | 注册成功后 + me tab 主动触发；canvas API 一定渲染本地，密码不会出任何 RPC |
| 8 | 选端 modal | **二步式**（先选端 → 选 H5 再过字证图保存） | Web 用户可跳过保存（少打扰）；H5 用户强制保存（移动端最容易丢密码） |
| 9 | 退出登录 | **从 me tab 移除**（v4.26） | demo 阶段暂时简化；正式上线版若需退出建议放设置页（v2 交付） |
| 10 | nickname 字段 | **DB ALTER RENAME nickname → username** | 语义对齐 PRD；昵称（display name）与用户名（profile name）合并为一个字段 username，默认 = 注册账号 |
| 11 | 直播清晰度 | **改为"线路选择"** | 用户感知是"卡不卡"而非"分辨率"；5 条线路 + 实时延迟更直观 |
| 12 | 弹幕字数 | **去除等级阶梯，统一 100 字** | L1=20 / L6=200 实现复杂、产品价值低（L6 是钱多，不是字多） |
| 13 | 打赏 | **modal 选金额（10/100/.../10000）+ toast** | 取代连击 ×N，免去前端连击合并逻辑；6 档金额覆盖大部分场景 |
| 14 | H5 退出/设置 pane | **整体不交付** | v0.3 简化产品面；如需 v2 再补 |
| 15 | H5 直播间 | **剧场式默认 + 横屏 + 沉浸式 3 模式** | 剧场式接近 Twitch / 主流，沉浸式接近 TikTok 直播，覆盖不同用户偏好 |
| 16 | H5 广告位 | **3 个独立位（吸底 / 角标 / 气泡）** | 每个 tab 用不同形态，避免广告同质化干扰；RAF 弹墙气泡是产品差异化 |
| 17 | 支付通道清单 | **不在本 ADR 决策** | 原型 v4.03 演示了 5 种（微信/支付宝/银联/USDT/e-CNY），v1 启用哪几条留给 ADR-0010 单独定 |

## 3. 备选方案对比

### 3.A 充值比例

| 方案 | 优点 | 缺点 | 取舍 |
|---|---|---|---|
| 保持 1:10 + 5 💎 赠送 | 心智上"花 1 元得 15 钻"看起来赚 | 实际入账非整数（5% 手续费后），用户算不清；赠送规则运营要解释 | ❌ |
| **1:1 + 扣 5% 手续费** | 心智干净；钻石数字 = 净到账元数 | 失去"超值感"营销噱头 | ✅ |
| 1:100 玩家币模式 | 单位放大易看 | 又是新心智成本 | ❌ |

### 3.B 兑换功能去留

| 方案 | 优点 | 缺点 | 取舍 |
|---|---|---|---|
| 保留双向兑换 | 用户灵活；与原型评审版一致 | 反向 20% 手续费触博彩边界；ledger 多 4 个 op_type；前端多 1 个页面 | ❌ |
| **整体下线** | 钱包心智 = 一进一出；ledger 干净；合规边界清晰 | 用户钻石无法兑回 RMB（仅通过赢钱产生） | ✅ |
| 仅保留正向 RMB→💎 | 与现状接近 | 钱包卡需要保留"已兑换"字段，复杂度未降 | ❌ |

### 3.C 密码找回机制

| 方案 | 优点 | 缺点 | 取舍 |
|---|---|---|---|
| 客服后台重置（v0.2 方案） | 用户友好 | 客服需 KYC 用户身份 → 我们没有 KYC → 伪造身份骗密码风险高 | ❌ |
| 邮箱 / 手机找回 | 标准做法 | 我们 v0.3 已去手机/邮箱字段 | ❌ |
| **不提供找回 + 强制字证图** | 平台零密码恢复责任；用户自负 | 用户教育成本高；要在注册 + me tab 双重提醒 | ✅ |

### 3.D nickname 迁移

| 方案 | 优点 | 缺点 | 取舍 |
|---|---|---|---|
| **ALTER RENAME** | 代码语义统一；DB schema 干净 | 一次性 migration；要同步改 DTO/Admin | ✅ |
| 新增 username 列 + 保留 nickname | 向后兼容（如有外部消费方） | DB 冗余；触发器同步成本 | ❌（尚无外部消费方） |
| 仅 DTO 改名 | 零 migration | 前后端字段不一致，长期混乱 | ❌ |

## 4. 后果

### 4.1 正面后果

- **PRD 与原型完全对齐**：进入实现期不再有 PRD/原型分歧导致的返工
- **DB schema 更干净**：少 1 张表（exchange_orders）、少 4 个 ledger op_type、字段语义一致
- **客服面 / 合规面更轻**：不提供密码找回 = 不持有用户密码恢复责任；无反向兑换 = 不踩博彩边界
- **运营心智更简单**：单一费率 5%、单一比例 1:1，便于客服解释 + 营销文案

### 4.2 负面后果与缓解

| 风险 | 缓解 |
|---|---|
| 用户丢失账号无法找回 → 客诉 | 注册成功强制字证图保存（H5）；me tab 持续提醒；用户协议明确"不可恢复"免责 |
| 兑换功能下线后老用户已兑换的钻石如何处理 | v0.3 尚未上线，无老用户问题；exchange_orders 表 DROP（v0.3 增量 migration） |
| 取消"充值赠送"营销噱头 | 由运营在充值 modal 配活动 banner / 限时折扣替代（不进 PRD 默认逻辑） |
| 退出登录入口移除 → 共享设备用户无法切号 | 风险有限（夜场场景用户基本单设备）；v2 设置页补 |

                ├─ ALTER TABLE users CHANGE nickname username VARCHAR(64)
                ├─ DROP TABLE exchange_orders
                └─ ALTER ledger biz_type ENUM 去 exchange / exchange_fee
M3 Service     wallet/service.go
                ├─ 删 Exchange() / Quota()
                ├─ Recharge() 改：amount × 0.95 floor → diamond_balance
                └─ Withdraw() 改：amount × 0.95 → 到账，amount × 0.05 → FEE_OUT
                auth/service.go
                ├─ 注册去 nickname；账号正则 ^[a-zA-Z0-9_]{6,20}$
                └─ 密码正则强化

                ├─ 新增 UpdateAvatar / UpdateUsername

                http/public/wallet.go 删 Exchange 路由

## 7. 回滚预案

如果生产已上线且发现 v0.3 决策有重大问题：

1. **DB 回滚**：`make migrate-down` 退到 000009，exchange_orders 表恢复；username → nickname 反向 RENAME
2. **代码回滚**：`git revert <ADR-0011 实施 commits>`
3. **数据修复**：v0.3 上线后产生的"5% 手续费" ledger 记录需要回填（按用户充值流水按 v0.2 公式重算并发放差额）

回滚风险较低，因为 v0.3 上线前会先在 staging 跑 7 天稳定。
