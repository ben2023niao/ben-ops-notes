## 二、现场定位

### 2.1 后端 CPU（业务被打爆，不是机器故障）

实测：

- `load average: 58.92, 59.14, 56.27`，`%Cpu(s): 99.3 us`，内存/磁盘/网络/Mongo/Redis 全部正常
- `docker stats`：`youdianse-main-php-web` = **1590% CPU**，php-fpm 子进程批量满载
- 后端 nginx access.log 采样 40,000 条：**`POST /api/v1/Login/account` 占 65%（25,854 条）**
- 来源 TOP：`203.0.113.1` 占 ~50%（300k 采样 148,403 条）、`203.0.113.1` 占 13%
- 频率：`203.0.113.1` 稳定 **7,400~9,900 次/分钟（≈125~165 次/秒）**
- 指纹：UA 固定为极简 `Mozilla/5.0`、Referer 伪造成源站 IP、响应固定 200/128 字节 → 脚本刷登录，非真实用户

## 三、根因（两条）

### 3.1 根因 A：攻击绕过网关直连宝塔源站，源站没有任何限流

两个入口最终都汇聚到宝塔 `/api`（`proxy_pass http://203.0.113.1:8088` → 线上后端）：

| 链路 | 路径 | 限流情况 |

| --- | --- | --- |

| A | 公网 → 网关 203.0.113.1 → 宝塔 → 后端 | 网关已有 `limit_req zone=api_perip rate=50r/s`，**实测有效**（该 IP 被压到 ≈55 次/秒） |

| B | 公网 → **宝塔 203.0.113.1（www.youdianse.com 源站）→ 后端** | **无限流、无拦截** ← 被打穿 |

证据：宝塔 `new.youdianse.com.log` 采样 100,000 条中，`203.0.113.1` **直连源站 37,149 条**，
路径 `POST /api/v1/Login/account` 占 63,738 条（64%）。

### 3.2 根因 B：CC 守卫看不到 /api 刷量，也覆盖不到宝塔

守卫日志（ben-bot `cc_guard/state/guard.log`）长期 `api_flood=0/0`，攻击期间完全没触发封禁。两个代码缺陷：

1. **多跳 XFF 被丢弃**：网关日志的 X-Forwarded-For 是多跳字符串
   （如 `203.0.113.1, 203.0.113.1`），`api_flood_suspects()` 把整串交给
   `is_ip_like()` 判定 → 返回 False → 整行被丢掉，等于永远看不到刷量源。
2. **只守网关**：`youdianse_cc_guard.py` 只采网关日志、只封网关 iptables 与网关 nginx 清单，
   对「直连宝塔源站」的链路完全没有感知（因此也不会封）。

## 七、补充处置（2026-09-30 05:00 北京时间｜守卫误封自有 IP）

### 7.1 事件：守卫把自己的网关 IP 当成攻击源

拦截生效后守卫发出告警：`XFF 封禁样本：203.0.113.1(1735)`。

**203.0.113.1 是 18game H5/PC 统一网关本身**（前端容器所在服务器），被自己的守卫封了。

原因：H5/PC 容器的 SSR 服务端渲染会通过公网域名回打接口，出口就是网关自己的公网 IP，
因此网关日志里 XFF 第一跳即 `203.0.113.1`；单页渲染会连打多个 `/api`，
采样窗口（6 万行）内累计 1735 次，超过 900 次阈值 → 被判定为刷量源。

影响：我们自己的 SSR/接口请求会被打成 444。

### 7.2 修复：自有 IP 全量清点 + 永不封禁

清点来源：`devops/ai_context/servers.yml`、`ops/production/servers.json`、`workbench/MACHINE_ACCESS_MATRIX.md`。
共 14 个自有 IP（另含监控出口段 `2a02:4780::/32`）：

| 类别 | IP |

| --- | --- |

| 线上环境 | 203.0.113.1（网关）、203.0.113.1（宝塔源站）、203.0.113.1（后端）、203.0.113.1（H5） |

| 线上前置 | 203.0.113.1 / 203.0.113.1 / 203.0.113.1、203.0.113.1 |

| 测试环境 | 203.0.113.1、203.0.113.1、203.0.113.1 |

| 运维工具机 | 203.0.113.1、203.0.113.1、203.0.113.1 |

代码改动：

- 新增 `SELF_IPS` 常量 + `SELF_IP_PREFIXES` + `is_self_ip()`
- 在「识别（suspect 过滤）、告警、封禁（iptables/网关清单/宝塔清单）、清单生成」四个环节全部排除自有 IP
- `load_state()` 载入时自动剔除自有 IP（历史误封项自动清理）
- 新增可维护文件 `state/self_ips.txt`（一行一个 IP，支持 `#` 注释；按 mtime 热加载）
  → 后续新增自有 IP 只需追加该文件，无需改代码，守卫每分钟生效

清理结果：状态文件剔除 `203.0.113.1`，重写网关与宝塔两侧清单，核验自有 IP 零残留。

### 7.3 连带发现：第二个误封风险（已改为不按 IP 封）

修复自身 IP 后，守卫继续识别出 8 个刷登录来源：
`203.0.113.1`、`203.0.113.1`、`203.0.113.1`、`203.0.113.1`、`203.0.113.1`、`203.0.113.1`、`203.0.113.1`。

取证：这些 IP **只打 `/api/v1/Login/account` 一个接口**（采样窗口内累计 6289 次，无其它接口），
UA 固定 `Mozilla/5.0`，单 IP 峰值 **861 次/分钟**（≈14r/s）→ 属刷量/凭证填充脚本。

但它们属菲律宾移动运营商网段（**大量使用 CGNAT，一个公网 IP 背后是很多真实用户**），
按 IP 封会误伤真实用户。处置：

- 立即解封这 7 个 IP
- 宝塔源站侧改为 **只告警不自动封 IP**：新增开关 `CC_BAOTA_AUTO_BLOCK`（默认 `0`），
  告警文案标注 `baota_api_flood=N(仅告警)`
- 改用不误伤用户的压制手段：**登录接口严格限流**（见 7.4）

### 7.4 登录接口严格限流（替代按 IP 封）

| 位置 | 配置 | 说明 |

| --- | --- | --- |

| 宝塔源站 | `location ~* ^/api/v1/login/account` → `limit_req zone=yds_login_perip rate=2r/s burst=6 nodelay` | 新增 zone 见 `00-abuse-guard-http.conf`；location 必须声明在通用 `/api` 正则之前 |

| 线上后端 | `login_perip` 30r/s → **5r/s**（burst 60 → 15） | 兜底 |

依据：刷量脚本单 IP ≈14r/s，真实用户登录仅个位数请求/分钟。

实测验证：单次登录 HTTP 200 / 0.23s；连发 20 次出现 429（限流生效）；
H5 页面 200、PC 页面 200、网关 API 200，真实路径未被误拦。

### 7.5 新增交付文件

- `ops/production/scripts/baota-new-youdianse-fixed-reverse-proxy.conf`
  （宝塔 www vhost 反代配置，含登录接口严格限流 location；部署版本，带 immutable）
- `ops/production/scripts/baota-youdianse-api-proxy-snippet.conf`（/api 反代公共片段，备用）
- `18game_devops`: `devops/scripts/cc_guard/state/self_ips.txt`（运行机维护文件，不入库）

### 8.2 登录接口限流放宽（弱网重试）

用户反馈：部分用户网络较差，登录会多次重试。原 2r/s + burst 6 偏紧，放宽为：

| 位置 | 原值 | 现值 |

| --- | --- | --- |

| 宝塔源站 `yds_login_perip` | 2r/s + burst 6 | **5r/s + burst 20** |

| 线上后端 `login_perip` | 5r/s + burst 15 | **10r/s + burst 30** |

依据与实测：

### 9.4 本次踩到的坑（重要）

## 十一、被刷接口改为「UA 真实性」判断（2026-09-30 09:00 北京时间）

### 11.1 思路

不针对某个具体 UA 打补丁，而是判断请求的 UA **是否像完整的真实客户端**：
像 → 放行；不像 → 444。攻击者换 UA 字符串也没用（凑不出真实客户端该有的形态）。

### 11.2 判定规则（`$yds_ua_real`：1=可信，0=可疑）

```text
1) 完整浏览器 UA：必须同时具备「(平台/系统信息括号)」+「引擎/浏览器标识」
   ~*^Mozilla/5\.0[ ]+\([^)]+\)[ ].*(AppleWebKit|Gecko|Presto|Trident)
   ~*^Mozilla/5\.0[ ]+\([^)]+\)[ ].*(Chrome|Chromium|CriOS|Firefox|FxiOS|Safari|Edg|OPR|YaBrowser|MiuiBrowser|HuaweiBrowser|Quark|UCBrowser)
2) 原生 App / SDK 固定前缀：Dart（Flutter）、okhttp、Dalvik、UnityPlayer、BestHTTP、UnityWebRequest、libwww-perl
3) 明确判为可疑：curl、Wget、python-requests、Go-http-client、Java、Scrapy、极简串 Mozilla/5.0
4) 例外：三方游戏白名单命中不做 UA 拦截
```

### 11.3 操作步骤（可回滚）

| 序 | 位置 | 动作 |

| --- | --- | --- |

| 1 | 宝塔 `00-abuse-guard-http.conf`（http 级） | 新增 `map $http_user_agent $yds_ua_real` |

| 2 | 宝塔 `.../extension/new.youdianse.com/00-youdianse-fixed-reverse-proxy.conf`（server 级） | 登录 location 内加三段 `if`（UA 不可信→444，三方白名单豁免）；文件带 immutable，需 `chattr -i` → 写入 → `chattr +i` 复原（已备份 `.bak.uacheck-*`） |

| 3 | 宝塔 | `nginx -t` → `nginx -s reload` |

| 4 | 后端 `nginx/main.conf` | 加同一份 `$yds_ua_real` map |

| 5 | 后端 `nginx/default.conf` | 登录 location 加同样三段 `if` |

| 6 | 后端 | 临时容器校验 → 重启 nginx 容器生效 |

### 11.4 环境坑：单文件 bind mount 被 inode 替换后失联

后端 nginx 的 `main.conf` / `default.conf` 是**单文件 bind mount**。
用 `install` / `mv` 覆盖会生成新 inode，容器仍指向「已删除的旧 inode」：

```text
现象：宿主机文件是新内容，容器内 grep 仍是旧配置；nginx -t 还通过（因为它测的是容器内旧文件）
处置：容器内生效必须原地写入，或重启容器重新绑定挂载（本次用重启）
```

→ 后续所有涉及后端 nginx 配置的变更都必须注意这一点。
