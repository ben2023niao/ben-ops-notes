# 2026-09-30 【运维记录】免限制白名单清单（支付 / SDK / 合作方 / 自动化测试机）

> 来源：本地项目文档 `game/youdianse-docker/main/docker-youdianse-php/docs/2026-09-30-【运维记录】免限制白名单清单-支付SDK合作方测试机.md`
> 整理：2026-11-09。仅复制到知识库，未改动原项目文件；敏感凭据已脱敏。

环境标签：线上环境（正式）
背景：当天新上「UA 真实性」与「刷量封禁」防护后，连续误伤了正常业务调用：

| # | 受影响方 | 现象 | 原因 |

| --- | --- | --- | --- |

| 1 | 1game 的 auth 服务器 | `checkTokenV2` 返回 502，玩家登录失败 | 服务端调用 UA 为 `python-requests`/`Go-http-client`，被 UA 真实性规则拦成 444 → CloudFront 转 502 |

| 2 | 支付方回调 | 几百单无法回调 | 回调 UA 为 `Go-http-client`，同样被 UA 规则拦 |

| 3 | 游戏 SDK 接口 | `/api/sdk/*` 502 | SDK 由游戏服务端调用，UA 非浏览器 |

| 4 | 自动化测试机 | 全量接口报告 106/127 失败 | 测试机 UA 为 `python-requests/2.34.2`，被 UA 规则拦 |

## 一、免限制规则（触发即整体放行）

命中以下**路径**的请求：不做 UA 真实性判断、不计入限流、不做 IP 黑名单拦截（支付/SDK 是钱与接入的事）：

```text
/api/(v1/)?(callback|pay|payment|order|withdraw|recharge|cashier|settle)/*
/api/sdk/*
/customer/*   /channel/*   /sdk/*        （合作方服务端接口）
```

命中以下**来源 IP** 的请求：不做 UA 真实性判断、不计入限流、不封禁：

```text
自有基础设施（SELF_IPS，14+2 条）：
  203.0.113.1 / 203.0.113.1 / 203.0.113.1 / 203.0.113.1 / 203.0.113.1 / 203.0.113.1
  203.0.113.1 /.139 /.249 / 203.0.113.1 / 203.0.113.1
  203.0.113.1 / 203.0.113.1 / 203.0.113.1 / 203.0.113.1 / 203.0.113.1
合作方 / 自有测试服务器（PARTNER_EXTRA_IPS）：
  203.0.113.1  1game auth（AWS 新加坡）
  203.0.113.1 1game auth / 支付回调来源
  203.0.113.1  自动化测试机（Allure / 全量接口回归，UA python-requests/2.34.2）
拨测监控出口段：2a02:4780::/32（UA DomainSecurityMonitor）
```

| 守卫（ben-bot） | `state/self_ips.txt` + 生成器 `PARTNER_EXTRA_IPS` | 保证守卫不会再把这些 IP 当刷量源 |

## 三、新增白名单的标准动作（避免再误伤）

1. 路径类（新的合作方接口）：加到 `$yds_pay_path` map（宝塔 + 网关）
2. 来源 IP 类（新的合作方/测试服务器）：加到 `PARTNER_EXTRA_IPS`（生成器）**和** `state/self_ips.txt`（守卫）
3. 加完必须：重新生成三方白名单 → 守卫跑一轮 → 三处 reload → **用对方的 UA + IP 实测一次**
4. 校验要点：白名单 IP + 非浏览器 UA 应 200；非白名单 IP + 非浏览器 UA 应仍被拦

## 五、运维注意

- 白名单是"双向"的：**路径 + IP 两套**，缺一处仍会被拦（本次测试机就是漏了网关的 IP 白名单）
- 守卫的清单重写必须每轮执行（见 `cfcf018`），否则手工清理状态后清单不会更新
- 现有清单见上表；新接入合作方请按第三节流程登记，并同步更新本文档

## 六、补充：测试机首轮复跑仍有 68 条失败 → 后端白名单两个隐藏 Bug（已修复）

第一轮修复后测试机通过率从 20 → 58 条，但仍失败 68 条（运营反馈"登录 502"）。逐层排查（探针 + 日志）发现
**后端（203.0.113.1）的三方白名单从未生效**，两个原因：

1. **map key 用了 `$binary_remote_addr`**：这是 IP 的**二进制**形式，而 map 里写的是文本 IP，
   两者永远不相等 → 白名单恒不命中（后端登录接口把合作方/测试机全当陌生人拦掉）
2. **依赖 realip 后的 `$remote_addr` 不可靠**：后端开了 `real_ip_recursive on`，
   多跳 XFF 中只要有一跳不在信任列表（CloudFront 边缘、内网测试客户端等），
   `$remote_addr` 就会被解析成那一跳，白名单同样命中不了

修复（`render_backend_block()`）：

```text
map $http_x_forwarded_for $yds_be_client {      # 统一取 XFF 第一跳（与宝塔侧一致）
    default $remote_addr;
    "~^(?<be_first>[^,]+)" $be_first;
}
map $yds_be_client $yds_is_3rd_party { ... }
map $yds_be_client $yds_3rd_game    { ... }
map $yds_be_client $yds_tp_login_key { ... }    # 合作方/测试机 → 空 key（不限流）
```

同时把 `PARTNER_EXTRA_IPS`（1game auth ×2 + 自动化测试机）也写进后端区块（此前只写了宝塔，后端缺失）。

验证（探针 `location = /__probe` 打印变量 + 三种 XFF 链）：

| 检查项 | 结果 |

| --- | --- |

| 后端 `3rd=` 变量（测试机 IP） | 修复前 `0` → 修复后 `1` |

| 后端登录接口：测试机 IP，XFF 单跳 / 双跳 / 三跳（含 203.0.113.1） | 修复后均**非 444**（返回业务 404，因测试请求缺少加密参数） |

| 后端登录接口：非白名单 IP | 仍被拦（000） |

| 网关 / 宝塔 / 后端 全链路：测试机 IP 打 `/api/v1/system/info`、`userProduct/getProductList`、`community/gameFollow`、`user/info` | 全部 **200** |

## 七、第三轮：测试仍 68 条失败 → 后端登录路由本身 404（与防护无关）

第二轮复跑仍 58 通过 / 68 失败（与上一轮**完全相同的数字**，说明是稳定失败而非偶发拦截）。
从 Allure 报告取到失败用例详情，根因不在防护：

```text
用例：账号登录1（/api/v1/Login/account）
报错：ValueError: 响应体不是合法 JSON（HTTP 404），
     原始内容：'<html>…<center><h1>404 Not Found</h1></center><hr><center>nginx</center>…'
```

即：**登录请求拿到的是 nginx 默认 404 页面**，不是业务 JSON → 用例 broken →
「签到/积分/任务/收藏/预约/个人信息/关注/绑定邮箱」等 **60+ 依赖登录态的用例全部级联失败**。

排查与修复：

```text
① 后端（203.0.113.1）default.conf 里为登录接口单独加的
   location ^~ /api/v1/Login/account { … try_files $uri $uri/ /index.php?_url=$uri&$args; }
   在该 ^~ location 内不会回退到 index.php（对照实验：无 if 的同样写法一样 404；
   而同一条 try_files 放在 location / 内工作正常）→ 该路径恒 404。
   （对照实验已清理：/api/v1/__t1、__t2、__t3）
② 修复：该 location 内改为直接 fastcgi 到前端控制器（与 location ~ \.php$ 等价）：
   include fastcgi_params; fastcgi_pass web:9000;
   fastcgi_param SCRIPT_FILENAME /var/www/html/youdianse-php/public/index.php;
   fastcgi_param HTTP_VERSION 2.1.1;
```

验证：

| 检查项 | 结果 |

| --- | --- |

| 后端 `/api/v1/Login/account`（Dart / python-requests） | 修复前 nginx 404 → 修复后 **200 + 业务 JSON** |

| 宝塔转发 `/api/v1/Login/account` | **200** |

| 网关转发 `/api/v1/Login/account`、`/api/v1/user/info`、`/api/v1/system/info` | 全部 **200** |

| 公网 App 路径登录（Dart UA） | **200** |

| 测试机近 250 条 / 后端近 400 条请求状态 | 全部 **200**，零拦截 |

> 注意：该 404 是**本次防护改造时新增的登录专用 location 引入的**，属于我们自己引入的回归；
> 之前该接口走 `location /`，所以自动化测试早期是能通过的。
