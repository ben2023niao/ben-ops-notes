# 【优化】后端日志三层保留策略：24h 明文 → 本地压缩 7 天 → 超 7 天 S3

> GitHub 仓库源文件：[点击打开网页渲染版](https://github.com/ben2023niao/ben-ops-notes/blob/main/doc/md/202610150000-%E6%B8%B8%E7%82%B9%E6%B6%A9%2BShell%2BPython-%E3%80%90%E4%BC%98%E5%8C%96%E3%80%91%E5%90%8E%E7%AB%AF%E6%97%A5%E5%BF%97%E4%B8%89%E5%B1%82%E4%BF%9D%E7%95%99%E7%AD%96%E7%95%A5%EF%BC%9A24h%20%E6%98%8E%E6%96%87%20%E2%86%92%20%E6%9C%AC%E5%9C%B0%E5%8E%8B%E7%BC%A9%207%20%E5%A4%A9%20%E2%86%92%20%E8%B6%85%207%20%E5%A4%A9%20S3.md)

> 整理日期：2026-10-15 00:00｜日期依据：文件名日期

- 日期：2026-10-15
- 环境：**线上后端** 16.209.16.108（`/opt/docker-youdianse-php/runtime/app-logs`）
- 触发：后端反馈「日志同步像是规则被改了，只能从 12 点开始查，之前没有」→ 要求「保持最近一周全天可查」
- 定稿策略（运维要求）：**24 小时内保持 `.log` 明文；超过 24 小时压缩留在服务器；超过 7 天丢 S3**

---

## 一、现象与根因

### 1.1 现象

```text
· 后端查日志时，当天只有最近几小时的记录（"12 点之前的日志没有"）
· 期望：最近一周任意时段都能查
```

### 1.2 根因（实测）

| # | 事实 | 影响 |
| --- | --- | --- |
| 1 | `api_request/api_response/big_data_click` **只有 logrotate 在轮转**（每小时切割脚本只处理 `php/php-fpm` 子目录，顶层文件不在其扫描范围） | 轮转策略 = 唯一决定本地可查窗口 |
| 2 | 该 logrotate 配置为 `size 500M` + **`rotate 3`**，而业务量约 5G/天、每天轮转 4~5 次 | 本地只留 **3 代 ≈ 不到 1 天** |
| 3 | S3 归档脚本只处理后端 **nginx-logs**（`backend/` 前缀），**不含 app-logs** | 更早的日志既不在本地、也不在 S3 |

→ 于是「当天只能查到最近几小时」；更早的（含 12 点前）已经轮转删除，**不可找回**。

---

## 二、实现（三层）

### 2.1 分层规则

```text
① 24 小时内      → 保持未压缩 .log（直接 grep）
② 超过 24 小时   → 压缩成 .gz 留在服务器（zgrep 可查）
③ 超过 7 天      → 移入 runtime/app-logs/.s3-pending/ → 归档脚本上传 S3 后删除本地
```

### 2.2 为什么压缩不放在 logrotate 里

logrotate 只能表达「压最近一轮（delaycompress）」或「全压（compress）」，**无法按 24 小时年龄分层**：

- 只开 `compress`：几小时前的就被压了，不满足「24h 内明文」；
- 完全不开：本地攒 5G/天 × 7 天 = 35G，网关根盘放不下。

因此拆成两件事：**logrotate 只负责"切"**，**压缩/交接由分层脚本按年龄决定**。

### 2.3 改动清单

| 文件 | 作用 |
| --- | --- |
| `ops/production/logrotate/youdianse-backend-applogs` | 轮转策略：`size 500M` / **`rotate 40`** / **`maxage 7`** / **不再 compress**（压缩交给分层脚本） |
| `ops/production/scripts/youdianse-app-log-tier.py` | **新增**：①>24h 的 `.log` → gzip；②>7 天的 `.gz` → `.s3-pending/`；有动作时通知群。cron `*/15 * * * *` |
| `ops/production/scripts/youdianse-backend-log-s3-archive.sh` | **新增到仓库并扩展**：原来只归档后端 nginx 日志；现在同时归档 `app-logs/.s3-pending/` → `s3://<bucket>/backend-applogs/`，成功才删本地。cron `27 */6 * * *`（监控机） |

> 分层脚本覆盖 **app-logs 顶层全部 `*.log`/`*.gz`**（api_request / api_response / big_data_click /
> big_data_app_log / big_data_spend / balance / game_notify / error / 每日主日志 …），
> 不含 `queue/`（队列自身机制管理）与 `.hourly-rotated/`（切割脚本工作目录）。

### 2.4 容量估算

```text
未压缩窗口（24h）≈ 5G ｜ 压缩后 ≈ 340MB/天 × 6 天 ≈ 2G  → 稳态约 7G
网关根盘 49G（实测可用约 27G），余量充足。
```

## 三、验证（生产实测）

```text
1) logrotate 配置语法/行为：logrotate -d 无报错，且不会误删现有归档（removing old log = 0）
2) 分层脚本干跑：识别 54 个文件、其中 8 个超 24h 待压缩
3) 分层脚本实跑：compressed=8（api_request/api_response/big_data_click/主日志，约 4.2GB → 压缩后数百 MB）
   放宽范围后再跑：compressed=12（balance / big_data_app_log / big_data_account_detail /
   big_data_download / big_data_game_register / big_data_recharge / big_data_register /
   big_data_register_attr / big_data_spend / check_token / error / game_notify）
4) 结果核对：
   24h 内未压缩 .log = 32 个 ✅
   超 24h 仍未压缩的**非空**文件 = 0 个 ✅（剩余 19 个都是 0 字节空文件，按规则跳过）
   顶层 .gz = 33 个 ✅ ｜ .s3-pending = 0（尚无 >7 天数据）
5) 通知链路自测：造一个 2 天前的测试日志 → 脚本压缩并成功通知（跑通后已清理，无残留）
6) S3 归档脚本：`bash -n` 通过；试跑输出两个来源
   （prefix=backend nginx 日志 / prefix=backend-applogs 业务日志）均「无超期日志，跳过」
```

## 四、本次一次性补发（历史日志打包）

后端反馈时，更早的日志已不可得（见第一节），因此按需求把**现存的全部**打包发到上线群：

```text
· 内容：api_request / api_response / big_data_click / 每日主日志，2026-10-13 ~ 10-15（现存全部）
· 形式：backend-app-logs-2026-10-13_to_10-15.tar（925MB）→ 45MB 分片 × 21
· 说明：分片已全部发送成功（20 成功 + 1 个因 SSL 中断补发成功），文案里 @booter23
· 用法：cat backend-app-logs.part* > logs.tar && tar -xf logs.tar && zgrep ...
```

**这对后续不再需要**：本地已有 7 天窗口，直接上服务器 grep/zgrep 即可。

## 五、运维命令

```bash
# 看分层脚本做了什么
sudo tail -20 /var/log/youdianse-app-log-tier.log
sudo tail -20 /var/log/youdianse-app-log-tier.cron.log
# 干跑（不实际压缩/移动）
sudo python3 /opt/docker-youdianse-php/ops/production/scripts/youdianse-app-log-tier.py --dry-run
# 手工触发一次分层
sudo /bin/sh -c '. /opt/docker-youdianse-php/cicd-web/runtime/secrets.env 2>/dev/null; TG_CHAT_ID=-4929911895 exec python3 /opt/docker-youdianse-php/ops/production/scripts/youdianse-app-log-tier.py'
# 查日志（本地 7 天窗口）
cd /opt/docker-youdianse-php/runtime/app-logs && grep <关键字> api_request-2026-10-15.log* && zgrep <关键字> api_request-2026-10-13.log*.gz
# 看 S3 归档进度
sudo tail -20 /var/log/youdianse-backend-log-archive.log      # 监控机 52.79.252.255
sudo ls -la /opt/docker-youdianse-php/runtime/app-logs/.s3-pending/   # 后端
```
