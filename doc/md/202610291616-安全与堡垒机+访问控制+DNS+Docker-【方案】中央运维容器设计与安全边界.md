# 【方案】中央运维容器设计与安全边界

## 一、目标

把当前静态运维发布页升级为可从网页选择步骤、执行并实时查看结果的中央运维控制台。

目标：

1. 每个命令块可展开查看，也可点击执行。
2. WebSocket 实时返回 stdout/stderr、阶段状态和退出码。
3. 巴西发布固定 01 金丝雀，健康检查通过后才允许批量发布。
4. 香港固定 01 金丝雀，02/未来 03/04/05 只能进入同一批量组。
5. 全程有登录身份、操作审计和失败记录。
6. 不依赖某个人的 Mac 在线。
7. 容器故障或网络中断不能导致所有业务节点同时下线。

## 二、非目标

第一版不提供：

- 浏览器任意 Shell 输入框；
- 任意 SSH 目标/端口；
- 任意 Docker 命令；
- 自动修改 DNS、Cloudflare、防火墙；
- 自动删除服务器、容器、磁盘或数据库；
- 无确认的生产回滚。

## 三、总体架构

```text
浏览器
  │ HTTPS + WebSocket
  ▼
访问层（Cloudflare Access 或内网/VPN）
  │
  ▼
bizops-ops-console（巴西 03）
  ├── Web UI / 发布页
  ├── FastAPI
  ├── WebSocket 日志流
  ├── 发布 Recipe 状态机
  ├── 服务端健康检查
  └── SSH 执行器
        ├── 03：pull / build / image 检查
        ├── BR01 → verify
        ├── BR02 → BR04 → BR05
        ├── HK01 → verify
        └── HK02 / 未来 HK03/04/05
```

容器不挂载 `/var/run/docker.sock`。对本地 03 的 Docker 操作同样通过 SSH 执行，避免控制台获得宿主机 root 等价权限。

## 四、技术选型

| 层 | 选择 | 原因 |

| --- | --- | --- |

| 后端 | Python FastAPI + Uvicorn | 与现有运维脚本一致，异步 WebSocket/子进程支持成熟 |

| 前端 | 现有 HTML + xterm.js | 保留操作台，终端输出支持 ANSI、进度条和颜色 |

| 执行 | Python async subprocess + OpenSSH/rsync | 复用现有脚本，能实时读取输出 |

| 状态 | 内存任务 + SQLite WAL | 轻量、可审计、便于断线恢复 |

| 部署 | Docker Compose | 便于固定版本、健康检查和日志轮转 |

| 访问 | HTTPS + Cloudflare Access（推荐） | 多用户身份、MFA、统一访问控制 |

备用访问方式：现成 Nginx Basic Auth + 来源 IP 白名单。仅在对端固定 IP 且无法配置 OIDC 时使用。

## 五、执行模型

### 5.1 白名单 Recipe

浏览器只提交：

```text
recipe: precheck | pull | build | deploy-br-canary | deploy-br-bulk |
        verify-br | deploy-hk-canary | deploy-hk-bulk | verify-hk |
        rollback-host | health
version: 用户输入版本号
vendors: 白名单厂家
dry_run: true/false
```

禁止提交任意 command、host、shell、path 或 Docker 参数。

### 5.2 每个执行为一个 Job

```text
job_id
recipe
operator
version
region
vendors
targets
dry_run
status = queued/running/passed/failed/cancelled
current_stage
started_at/finished_at
exit_code
```

所有 Job 写入 SQLite；结构化事件同时进入审计日志。

### 5.3 WebSocket 事件

```json
{"seq":42,"type":"stdout","stage":"deploy-br-01","data":"..."}
{"seq":43,"type":"check","stage":"verify-br-01","ok":true}
{"seq":44,"type":"complete","status":"passed","exit_code":0}
```

事件应保留序号，断线重连后从 `after_seq` 续传，不丢失过程输出。

## 六、发布状态机

### 6.1 巴西

```text
PRECHECK
 → BR01_PULL
 → BR01_STOP_SYNC_START
 → BR01_VERIFY
      ├─ 失败：停止，锁定 bulk
      └─ 通过：BULK_READY
 → BR02 → BR04 → BR05（逐台执行）
 → BR_ALL_VERIFY
```

批量组外层 `set -e`；任一台失败后不再操作后续节点。已正常运行的节点保持服务，01 在整个批量期间保持在线。

### 6.2 香港

```text
PRECHECK
 → HK01_PULL
 → HK01_STOP_SYNC_START
 → HK01_VERIFY
      ├─ 失败：停止
      └─ 通过：BULK_READY
 → HK02 → HK03 → HK04 → HK05（未来节点按配置顺序）
 → HK_ALL_VERIFY
```

批量节点列表由服务端 `BACKEND_TARGETS.hk.bulk` 维护；以后增加 HK03/04/05 不需要改页面布局。

## 七、每一步的校验

### 7.1 发布前

- 当前只有一个 Job 获取发布锁。
- 至少两个 Nginx 活跃后端处于健康状态。
- 03 拉取到目标版本，`share.so` MD5 与开发值一致。
- 镜像 tag 和 registry 可达。
- 目标主机 SSH 可达。
- 批量列表不包含 01 金丝雀。

### 7.2 主机启动后

- 目标容器全部 Up。
- `RestartCount` 不增加。
- 容器实际 Image ID 与目标镜像 ID 一致。
- 端口监听正常。
- 内网 `/health` 或业务探针正常。

### 7.3 全量完成

- BR01/02/04/05 全覆盖检查。
- Nginx 活跃 upstream 至少保留一条。
- 页面入口抽测通过。
- 任何失败都保留在 Job 结果和审计记录中。

## 八、失败与回滚

| 阶段 | 策略 |

| --- | --- |

| 拉代码失败 | 不停止任何容器 |

| 镜像构建失败 | 不停止任何容器 |

| 01 拉取/同步失败 | 恢复 01 服务，禁止批量 |

| 01 启动失败 | 标记失败，提供“恢复上一镜像”操作 |

| 批量中某台失败 | 停止后续主机操作，保留 01 和其他正常节点 |

| 页面/健康检查失败 | 不发“可以测试”，提供回滚按钮 |

| WebSocket 断开 | 后台 Job 继续运行，重连恢复日志 |

自动回滚默认关闭；只提供明确、单主机、可审计的回滚操作，避免错误版本扩散。

## 九、鉴权与审计

### 9.1 推荐鉴权

首选 Cloudflare Access：

- 登录身份：Google Workspace 或邮箱 OTP；
- 用户白名单；
- MFA；
- 只允许 HTTPS；
- 不公开裸 IP:端口。

如果短期没有 Access：

- Nginx Basic Auth；
- 来源 IP 白名单；
- 限定内网/VPN；
- 先只开读模式。

### 9.2 权限

| 角色 | 权限 |

| --- | --- |

| viewer | 查看状态和历史日志 |

| operator | dry-run、拉代码、构建、发布、验证 |

| admin | 回滚、Nginx/维护操作、访问管理 |

生产发布至少 operator。回滚和 Nginx 修改至少 admin。

### 9.3 审计内容

- operator 用户名、IP、浏览器会话 ID；
- job_id、recipe、参数和 dry_run；
- 实际执行的主机、阶段、命令模板；
- stdout/stderr（必须脱敏）；
- 每步退出码和最终状态；
- 开始/结束时间、取消和回滚操作。

## 十、Secret 管理

- GitLab、SSH 密码和部署凭据从 HTML 完全移除。
- 容器读取 `/run/secrets/*` 或 root-only env 文件。
- 页面只显示脱敏后的命令预览。
- 日志在落库前执行脱敏过滤：
  - `sshpass -p`
  - URL 内嵌账号密码
  - Authorization / Bearer / Token
  - JWT/长 token
  - 已知 Secret 值
- 环境变量和 Secret 文件加入 `.gitignore`。

## 十一、容器运行配置

```text
name: bizops-ops-console
host: 巴西 03
restart: unless-stopped
cpu: 1
memory: 512MiB
rootfs: read-only
writable: /data, /tmp
cap_drop: ALL
security_opt: no-new-privileges
docker_socket: 不挂载
healthcheck: GET /api/health
```

目录：

```text
/opt/bizops-ops-console/
├── compose.yml
├── app/
├── static/
├── recipes/
├── data/audit.db
├── data/jobs/
└── secrets/          # 0600，本机保存
```

## 十二、API 草案

```text
GET  /api/health
GET  /api/catalog
POST /api/jobs
GET  /api/jobs
GET  /api/jobs/{id}
POST /api/jobs/{id}/cancel
WS   /api/jobs/{id}/events?after_seq=N
POST /api/rollback
```

关键要求：

- `POST /api/jobs` 只接受 recipe 名称和白名单参数。
- 服务端生成 true 命令，前端只能查看脱敏预览。
- 发布锁、金丝雀门禁、失败中止均在后端完成，不依赖前端 JS。
- WebSocket 只发只读事件或控制当前 Job，不提供任意命令通道。

## 十三、实施阶段

### Phase 1：只读 POC

- FastAPI/静态页/WebSocket/xterm.js；
- 执行 `docker ps`、`docker images`、`/health`；
- 鉴权和审计；
- 不提供写操作。

### Phase 2：拉取、构建与检查

- 03 拉代码、`build.sh`；
- share MD5、镜像 ID、香港 configs 同步；
- dry-run 与实际构建。

### Phase 3：发布状态机

- BR01 金丝雀 → BR02/04/05；
- HK01 金丝雀 → HK02/未来 03/04/05；
- 服务端门禁、失败中止、日志续传。

### Phase 4：生产硬化

- Cloudflare Access/VPN；
- 回滚按钮和演练；
- Beszel 健康监控；
- 审计保留和备份；
- 进行一次低峰发布演练。

## 十四、验收标准

1. 浏览器不能提交任意 Shell 字符串。
2. WebSocket 可实时显示每一行命令输出。
3. 01 未通过时，服务端拒绝批量发布。
4. 批量任一台失败后，不继续后续主机。
5. 01 在整个批量期间保持在线。
6. 页面和审计记录不出现密码/token。
7. 刷新或断线后能续看当前 Job 日志。
8. 容器重启后 Job 历史仍可查询。
9. 只读版在 03 上稳定运行并由 Beszel 监控。
10. 正式发布前有 dry-run 和人工确认。

## 十五、待确认项

1. 访问域名：建议独立内部域名，不直接暴露裸 IP:端口。
2. 鉴权：建议 Cloudflare Access；无权限时先用 Nginx Basic Auth + IP 白名单。
3. 第一批用户和角色名单。
4. 是否允许 operator 直接发布，还是必须具备 admin 二次确认。
5. 审计保留期：建议 90 天。
