# 【优化方案】后端 / 前端 / 数据库流量优化实施指南（逐步可执行）

> 来源文件：`~/Projects/work/game/youdianse-docker/main/docker-youdianse-php/docs/2026-10-17-0120-【优化方案】后端前端数据库流量优化实施指南（逐步可执行）.md`

> 整理日期：2026-10-17 01:20｜日期依据：文件名日期

- 时间：2026-10-17（北京时间）
- 面向对象：后端（PHP）、前端（Nuxt H5/PC）、DBA/运维
- 依据：`docs/2026-10-17-0040-【问题排查】线上后端与数据库流量猛涨取证及异常日志汇总.md` 的只读取证
- 目标（三周内）：主库对外发送 107 MB/s → **< 30 MB/s**；主库 query 535/s → **< 150/s**；扫描/返回放大 ~280 倍 → **< 20 倍**；应用慢接口日志 1,792 条/天 → **< 200 条/天**；日志 13.9 GB/天 → **< 4 GB/天**

---

## 零、先看这张「问题地图」（一句话版）

| 层 | 现象 | 根因 |
| --- | --- | --- |
| 后端 | PHP web 容器入 104 MB/s、出 7.8 MB/s | 每个请求都在从 Mongo 拉配置/列表数据 |
| 数据库 | 出 107 MB/s、入 1 MB/s；每秒扫 128 万索引键只返回 5,752 文档 | 小集合被亿级重复查询 + 大量无索引扫描 |
| 前端 | 用户侧只有 7 MB/s，但静态资源单请求 200~800 KB | 大 chunk 与未压缩图片、埋点单事件单请求 |
| 共同 | 日志 24h 新增 13.9 GB | api_request/api_response 全量落盘 |

**最扎眼的一条**：`user_sign_config` 集合只有 **1 个文档 1.2 KB**，却被查询 **1.33 亿次**；`game_category` 只有 **123 个文档 112 B/条**，却被查询 **14.41 亿次**。这类集合全部加起来不到 1 MB，完全应该走缓存。

## 一、后端（PHP）优化：7 步

> 通用背景：应用已有缓存层 —— `cache()->get/set/delete`（`CacheKey.php` 定义了 80+ 个键，全项目引用 289 处），后端存储为 **Redis `203.0.113.1:6379` db=3、prefix=`ph_`、默认 lifetime=3600**。所以问题不是"没有缓存能力"，而是**热点路径绕过了缓存**。

### 步骤 B1：把「配置型集合」全部收进缓存（收益最大、风险最低）

按实测查询量排序，逐个落到具体代码：

| 集合 | 文档数 / 体积 | 累计 queries | 建议缓存键（已存在则复用） | 建议 TTL | 失效点 |
| --- | --- | ---: | --- | --- | --- |
| `game_category` | 123 个 / 112 B | 14.41 亿 | `CacheKey::GAME_CATEGORY_OPTIONS`（已存在，`GameCategoryService.php:60/102`） | 1800s | 后台增删改分类时 `cache()->delete()` |
| `game` | 743 个 / 11.8 KB | 2.70 亿 | 新增 `game:list:{lang}:{filterHash}` | 600s | 后台改游戏时按语言后缀删 |
| `user` | 1,163 万个 / 17 GB | 2.24 亿 | 不动配置缓存，改「投影 + 从库」（见 B3/B4） | — | — |
| `adv` / `adv_pos` | 272 / 14 个 | 2.19 亿 / 3,052 万 | `CacheKey::ADV`、`CacheKey::ADV_APP`（已存在） | 600s | 后台广告位变更 |
| `user_task_list` | 15 个 / 399 B | 1.42 亿 | `CacheKey::TASK_LIST_DAILY` / `TASK_LIST_NEWBIE`（已存在，`UserTaskService.php:154/199`） | 1800s | 任务配置变更 |
| `app_version` | 11 个 / 500 B | 1.39 亿 | 新增 `CacheKey::APP_VERSION` | 300s | 发版时删除 |
| `user_sign_config` | **1 个 / 1.2 KB** | 1.33 亿 | `CacheKey::SIGN_CONFIG`（已存在，`UserTaskService.php:66`） | 1800s | 签到配置变更 |
| `article` | 588 个 / 26.6 KB | 8,169 万 | `CacheKey::ARTICLE`（已存在） | 600s | 后台发文 |
| `game_sdk` | 85 个 | 4,635 万 | 新增 `CacheKey::GAME_SDK` | 1800s | SDK 配置变更 |
| `user_product` | 58 个 | 4,177 万 | `CacheKey::USER_PRODUCT*`（已存在） | 180~600s | 商品变更 |
| `channel_package` | 787 个 | 3,850 万 | 新增 `channel_package:{channel}` | 600s | 渠道包变更 |

**为什么"已经有缓存却还打 1.33 亿次"？** 因为直接调用 Model 的地方太多，绕过了走缓存的那条路径：

```
GameCategoryModel 直接调用   8 处
AppVersionModel   直接调用  24 处
UserSignConfigModel 直接调用 27 处   ← user_sign_config 只有 1 个文档却查了 1.33 亿次
UserTaskListModel 直接调用  10 处
AdvModel          直接调用   9 处
GameModel         直接调用 199 处
Controller 层直接查库        68 处（例：ApiV1/RechargeController.php、NotifyController.php、TrackingController.php）
```

**动作**：先按上表把「走缓存」的入口补齐，再逐个把直接调用改成走 Service/Repository 方法（见 B7）。

**验收（只读命令）**：

```bash
# 主库查询速率（在 web 容器内执行，前后各跑一次对比）
php -r '$m=new MongoDB\Driver\Manager("mongodb://server.db1.com:27017");
$f=fn()=>$m->executeCommand("admin",new MongoDB\Driver\Command(["serverStatus"=>1]))->toArray()[0]->opcounters->query;
$a=$f(); sleep(20); $b=$f(); printf("query %.1f /s\n",($b-$a)/20);'
```

期望：`query` 从 **535/s 降到 150/s 以下**，`top` 命令里上表集合的 queries 增速趋近于零。

### 步骤 B2：消除同一请求内的重复查询（N+1）

典型代码：`app/Services/User/UserTaskService.php` 里 `UserSignConfigModel::findFirst(['_id' => 1])` 出现在 70、42、225、1144 等多个方法；一次任务列表请求会反复取同一份配置。

**动作**：

1. 给这类「单文档配置」加**进程内请求级缓存**（`static` 数组或单例），一次请求只查一次：

```php
// 建议形态（示意）
private static array $cfgMemo = [];
$cfg = self::$cfgMemo['sign'] ??= UserSignConfigModel::findFirst(['_id' => 1]);
```

2. 列表型数据用**一次 `find` 取全量 + 内存过滤**替换循环里的 `findFirst`。
3. `UserTaskService.php:158/330/496` 三处 `UserTaskListModel::find(...)` 条件接近，合并为一次查询后内存分组。

**验收**：php-fpm slow.log 中 `MongoDbConnection::executeCommand` 出现次数下降；`scannedObjects/returned` 比值下降。

### 步骤 B3：加投影（projection）与分页，砍掉无用大字段

实测大对象：`game` 平均 **11.8 KB/条**、`article` 平均 **26.6 KB/条**；接口侧 `/api/v1/game/detail` **98 KB/次**、`/api/v1/modules/home` **278 KB/次**。

**动作**：

1. 所有列表接口只取前端真正用到的字段：

```php
// 示意：游戏列表只需要卡片字段
GameModel::find($where, ['_id'=>1,'name'=>1,'icon'=>1,'tags'=>1,'hot'=>1], $limit, $offset);
```

2. 富文本类（文章正文、帖子正文）**拆成详情接口按需拉取**，列表里只返回摘要。
3. 首页 `/api/v1/modules/home` 拆成「首屏必需」+「非首屏懒加载」两段。
4. 所有列表接口强制 `limit` + 游标分页（`_id` 或时间字段），禁止无 limit 的 `find`。

**验收**：网关日志中 `/api/v1/modules/home`、`/api/v1/game/detail` 的平均 KB/次下降 30%+。

### 步骤 B4：把只读流量切到从库（代码已有能力，几乎没用）

代码里已有：`app/Core/Mongodb/MongoModel.php:39`（`AbTestConfigModel::on('slave1')->find(...)`）和 `app/Constants/CommonConstKey.php:12-13`（`MONGODB_SLAVE_1/2`），但全项目 `->on('slave` 用法**几乎为零**；而 `.env` 里 `default` 与 `channel` 都指向主库 `server.db1.com`，从库 `server.db2.com` 没承接读。

**动作**：

1. 先确认 `slave1`、`slave2` 指向 `server.db2.com` 的两个从库，并复核复制延迟：

```javascript
// 在主库执行（只读）
rs.printSecondaryReplicationInfo()
```

2. 把「只读 + 可容忍毫秒级延迟」的查询切到从库：配置类（B1 表）、游戏列表、文章列表、广告位。
3. **保留在主库**：写后立即读（下单、支付回调、任务完成后的状态查询）、事务相关。
4. 高风险提示：切换后要做一次「下单 → 立即查订单」的回归，防止复制延迟导致偶发查不到。

**验收**：主库 `bytesOut` 从 107 MB/s 降到 30 MB/s 以下；从库带宽上升；应用无「刚写读不到」报错。

### 步骤 B5：支付链路加超时（`recharge/create` 是慢接口第一名）

证据：应用 error 日志 **99% 是 `slow_api`**，10-16 共 1,792 条，其中 `recharge/create` 1,532 条；php-fpm slow.log 里 `curl_exec` 2,054 次，栈为 `CommonUtil.php:278 → PaymentService.php:954(httpJson) → :1021(sharkPayment) → RechargeController.php:138`。

**动作**：

1. 第三方支付 HTTP 调用统一设置 `CURLOPT_CONNECTTIMEOUT`（建议 2s）与 `CURLOPT_TIMEOUT`（建议 5s），失败快速返回并给前端明确错误码。
2. 加熔断/重试（最多 1 次，指数退避），避免请求堆积占用 php-fpm 进程（当前 `pm.max_children=64`）。
3. 下单接口把「支付通道调用」与「订单落库」解耦：先落库返回订单号，通道调用异步补偿。

**验收**：应用 error 日志 `slow_api` 从 1,792 条/天降到 200 条以下；`recharge/create` P95 耗时下降。

### 步骤 B6：日志降采样（一天少写 9 GB）

写入点在 `app/Controller/BaseApiController.php:208`（`api_request`）与 `:259`（`api_response`）；另有 `BaseCustomerController.php:112/129`。

**动作**：

1. 默认**不写全量**：仅记录「耗时 ≥ 200ms」「非 2xx」「白名单接口（支付/登录/下单）」。
2. 其余按 1/20 采样（可用请求 id 哈希取样，保证可复现）。
3. `api_response` 只记 `size`、`elapsed`、`status`，**不记完整 body**。
4. 观察一周后把 `api_request` 从 6.1 GB/天降到 1 GB/天以内。

**验收**：`du -sh /opt/docker-youdianse-php/runtime/app-logs` 的 24h 增量从 13.9 GB 降到 <4 GB。

### 步骤 B7：把 Controller 里的直连数据库收敛到 Service/Repository（结构治理）

当前 Controller 层直接查库 **68 处**（`grep -rn "Model::\(find\|findFirst\|insert\|update\)" app/Controller`）。这会让「缓存、投影、读分离」无法统一治理。

**动作**：按接口批次（先支付/通知类，再埋点类）把查询下沉到 Repository；每下沉一个 Controller，就顺手补上 B1 的缓存与 B3 的投影。

## 二、前端（Nuxt H5/PC）优化：6 步

> 实测（网关 20 万请求窗口，按响应字节排序）：

| 资源 | 次数 | 平均大小 | 小计 |
| --- | ---: | ---: | ---: |
| `/_nuxt/C8I3s652.js` | 1,056 | **822.8 KB** | 848.6 MB |
| `/api/v1/modules/home` | 1,930 | 278.3 KB | 524.5 MB |
| `/api/v1/game/detail` | 3,026 | 98.4 KB | 290.7 MB |
| `/images/index-new/G.svg` | 383 | **623.6 KB** | 233.2 MB |
| `/_nuxt/5-gpfbcI.js` | 992 | 226.2 KB | 219.1 MB |
| `/_nuxt/BgNepA1g.js` | 959 | 101.6 KB | 95.2 MB |
| `/images/mine/footer-bg.webp?v=2` | 272 | 248.2 KB | 65.9 MB |
| `/api/v1/system/info` | 5,908 | 10.0 KB | 57.7 MB |
| `/images/signup/tips.png` | 281 | 140.9 KB | 38.7 MB |
| `/og/home.jpg`（另测） | — | **2,120 KB** | — |
| `/images/mine/vip-daily-icon.svg`（另测） | — | **2,127 KB** | — |

### 步骤 F1：静态资源瘦身与缓存策略

1. `C8I3s652.js` 823 KB —— 按路由做代码分割，把「非首屏组件（活动、商城、社区）」移出主 chunk；检查是否把 icon 库/大组件全量打进主包。
2. `G.svg` 623 KB、`vip-daily-icon.svg` 2.1 MB、`og/home.jpg` 2.1 MB —— **SVG 里内嵌了大图**，改为压缩后的 webp/avif（或外链小尺寸图），按展示尺寸（2x）导出。
3. `tips.png` 141 KB → 转 webp（预计 <30 KB）。
4. 确认 CDN 开启 **brotli/gzip** 与 **长缓存**（`Cache-Control: public, max-age=31536000, immutable`，文件名带 hash 已在做）。
5. 首页预加载只保留首屏必要的 2~3 个 chunk（`<link rel="preload">`）。

**验收**：网关日志中这些路径的「KB/次」下降 30%+，首屏流量下降。

### 步骤 F2：首屏请求合并（一次拿全"配置包"）

首屏会并发打：`system/info`、`configDict/getConfigDict`、`AppVersion/latestVersion`、`modules/home`、`game/topPromotion`、`User/info`…

**动作**：

1. 后端提供一个聚合接口（如 `/api/v1/bootstrap`），一次返回：系统配置 + 配置字典 + 版本信息 + 签到配置 + 首页模块（首屏部分）。
2. `/api/v1/modules/home` 拆「首屏」与「非首屏」，非首屏用 IntersectionObserver 懒加载。
3. 同一次会话内配置类数据缓存在 `sessionStorage`/`localStorage`（带 TTL，例如 10 分钟，或用服务端返回的 `etag`/`maxAge`）。
4. 冷启动时先渲染骨架屏，避免为等配置而串行请求。

**验收**：`system/info`、`configDict/getConfigDict`、`AppVersion/latestVersion` 三个接口调用量下降 70%+。

### 步骤 F3：埋点类接口批量上报（当前是「一个事件一个请求」）

实测窗口内：`tracking/record` 42,133 次、`Tracking/recordPageVisit` 39,803 次、`exposureCollect/report` 28,438 次。

**动作**：

1. 前端维护上报队列：**每 20 条或每 5 秒**合并成一次请求（后端提供批量入口）。
2. 页面 `visibilitychange → hidden`、`beforeunload` 时 flush（用 `sendBeacon`）。
3. 曝光采集去重：同一元素同一会话只上报一次；滚动节流 ≥500ms。
4. 路由切换才记一次页面访问，页面内锚点跳转不算。

**验收**：三个接口调用量下降 80%+；后端 `tracking` 相关写入与日志同步下降。

### 步骤 F4：轮询改退避/长轮询

`/api/v1/UserLsjAi/getAiSessionStatus` 在采样窗口内 12,195 次。

**动作**：改成 1s → 2s → 4s 指数退避，最长 15s；或改服务端长轮询/SSE；页面切到后台时停止轮询。

### 步骤 F5：静态资源不要走 API 网关回源

取证发现 `/_nuxt/*.js`、`/images/*` 在**网关**上被大量请求（单文件上千次、数百 KB），也就是静态资源走了 SSR/网关回源路径。

**动作**：

1. `_nuxt` 构建产物与 `images` 静态资源统一从 CDN/对象存储直出（S3 + CloudFront），网关只处理 API 与 HTML。
2. 检查 Nuxt 配置 `build.publicPath` / `cdnURL` 是否指向 CDN 域名；`/images/*` 是否被 Nginx location 误路由到 SSR。
3. 复核 SSR 内部到底渲染在做什么，避免 SSR 资源请求走 SSR 渲染链路（自放大）。

**验收**：网关日志里 `/_nuxt/*`、`/images/*` 的命中次数归零或降到极小。

### 步骤 F6：给接口加 `Cache-Control` / `ETag`

配置类 GET 接口（`configDict/getConfigDict`、`AppVersion/latestVersion`、`system/info` 的静态部分）由后端返回 `Cache-Control: public, max-age=300` + `ETag`，让客户端与 CDN 承担重复请求。

## 三、数据库（MongoDB 主库 56.155.42.18）优化：6 步

### 步骤 D1：打开慢查询采样（先拿数据再优化，需走变更审批）

当前 `profiling` 关闭（level 0、slowms 100），所以**看不到慢查询形状**。建议在低峰期开启采样 1~2 小时：

```javascript
// 主库执行（临时，采样结束后恢复）
db.setProfilingLevel(1, 200)      // 只记录 >=200ms 的操作（capped 集合，开销可控）
// 采样后分析
db.system.profile.aggregate([
  {$group: {_id: {ns: "$ns", op: "$op", plan: "$planSummary"}, n: {$sum: 1}, ms: {$avg: "$millis"}}},
  {$sort: {n: -1}}, {$limit: 30}
])
db.setProfilingLevel(0)           // 恢复
```

**注意**：这是线上配置变更，需要运维/负责人确认后执行，并在低峰窗口。

### 步骤 D2：索引核查（重点看"有索引但没用"和"没有索引"）

```javascript
// 1) 看每个索引到底有没有被用过（自重启累计）
db.game_category.aggregate([{$indexStats: {}}])
db.article.aggregate([{$indexStats: {}}])
// 2) 看实际执行计划（把 profiler 抓到的查询形状拿来跑）
db.game_category.find({...}).explain("executionStats")   // 关注 totalDocsExamined / nReturned
```

现状要点：

- `user_sign_config` 只有 1 个文档、`user_task_list` 15 个文档 —— 亿级查询即便是 COLLSCAN 也快，但**每秒百万级扫描会白吃 CPU 与缓存**，应优先从应用层缓存解决（B1）。
- `article`：588 个文档、平均 **26.6 KB**、**只有 1 个索引** —— 建议按列表筛选/排序字段（分类、发布时间、状态）补索引，并做 projection。
- `user`：1,163 万文档、**17 GB**、14 个索引 —— 关注索引膨胀与写入放大，结合 B3 投影使用。
- 判断标准：`explain` 中 `totalDocsExamined / nReturned > 100` 即为读放大可疑点。

### 步骤 D3：读分离 + 连接复核

1. 与 B4 配套：从库承接只读，主库只负责写与复制源。

## 6.1 体检结论：基础健康，但有一个 P0 隐患

**健康的部分（`203.0.113.1:6379`，应用使用 db1=业务 / db2=队列 / db3=缓存）**

| 指标 | 实测值 | 判断 |
| --- | --- | --- |
| 版本 / 运行时长 | Redis 6.2.20 / 130.1 天 | 正常 |
| 内存 | used 1.01 G，峰值 1.17 G，碎片率 0.99，淘汰键 0 | 正常 |
| 命中率 | hits 32.28 亿 / misses 2.70 亿 = **92.29%** | 正常（缓存确实在生效） |
| 客户端 | connected 8、blocked 0、累计连接 19.7 亿、拒绝连接 0 | 正常 |
| 延迟 | PING 0.61 ms、GET(未命中) 0.58 ms | 正常 |
| 持久化 | RDB 最近保存 00:59、状态 ok；save 策略 `3600 1 300 100 60 10000` | 正常 |
| 安全 | 6379 在三台 DB 公网 IP 与后端/网关/宝塔 均不可达 | 未暴露，正常 |
| 应用报错 | 近 24h 无 RedisException / 连接拒绝 / LOADING | 正常 |

**P0 隐患：业务代码用 `KEYS` 做前缀删除，单线程 Redis 被周期性阻塞**

```
SLOWLOG 128 条构成：KEYS 126 条 + DEL 2 条
每条 KEYS 耗时 0.32 ~ 0.64 秒，平均每 153 秒出现一次（时间跨度 5.3 小时）
来源 IP：全部来自后端主机 203.0.113.1（即 16.209.16.108）

按业务分类：
  99 次  登录"多点登录踢下线"    pattern = [敏感内容已脱敏]
  11 次  统计任务 tracking_guest_dl:{date}:*
  10 次  统计任务 tracking:{date}:*:pv
   6 次  统计任务 product_click:*
```

根因链路：

1. `redis()`（`[redis] index = 1`）所在 **db1 有 1,771,045 个键**，抽样 20 万键中 **96% 是 `[敏感内容已脱敏] 19.2 万），其余为 `tracking_page_visit`、`growth`、`tracking`、`vip_received_coin`、`msg_click_uv` 等。
2. `KEYS` 是**全库遍历**，177 万键 ≈ 0.5 秒；Redis 单线程，这 0.5 秒内 session（db0）、queue（db2）、cache（db3）**全部排队阻塞**。
3. 最频繁的触发源是**用户登录**：`app/Services/User/UserService.php:1861` 在多点登录模式下，每次登录都会 `KEYS [敏感内容已脱敏] 再逐个删除旧 token。

影响面：登录越密集，阻塞越频繁；阻塞期间所有接口的 Redis 调用（会话、验证码、缓存、队列）都要等几百毫秒。这也可能是后端 nginx 日志中 642 次 `recv() failed`、15 次 `upstream timed out` 的一个隐藏来源。

## 6.2 修复方案（按优先级，一步一步）

### 修复 R1（必须改）：登录踢下线不再用 KEYS

**文件**：`app/Services/User/UserService.php:1861`（多点登录删除该用户全部 token）

推荐做法（改动小、立即见效）——**用 Set 维护"用户 → token 列表"索引**：

```php
// 登录时：写入 token 的同时登记索引
redis()->setex("[敏感内容已脱敏], $ttl, $tokenValue);
redis()->sadd("[敏感内容已脱敏], "{$tokenId}");
redis()->expire("[敏感内容已脱敏], $ttl);

// 踢下线时：按索引精确删除，不再全库扫描
foreach (redis()->smembers("[敏感内容已脱敏] as $tid) {
    redis()->del("[敏感内容已脱敏];
}
redis()->del("[敏感内容已脱敏];
```

低成本兜底（不改数据结构，先把阻塞去掉）：

```php
// 用 SCAN 游标分批替代 KEYS，每次 500~1000，非阻塞
$cursor = '0';
do {
    $res = redis()->scan($cursor, "[敏感内容已脱敏], 500);
    $cursor = $res[0] ?? '0';
    foreach ((array) ($res[1] ?? []) as $key) { redis()->del($key); }
} while ($cursor !== '0' && $cursor !== 0);
```

> 注意：本项目 phpredis 设置了客户端前缀 `ph_`，`SCAN` 的 pattern 会被自动加前缀；不要手写 `ph_ph_*`。

### 修复 R2：统计类任务同样换成 SCAN

把这 4 个文件的 `redis()->keys($pattern)` 全部替换为 SCAN 分批（模式同上）：

| 文件:行 | 用途 |
| --- | --- |
| `app/Services/Common/TrackingService.php:116` | `tracking:{date}:*:pv` 汇总 |
| `app/Services/Common/TrackingService.php:359 / 419 / 601` | `tracking_guest_dl:{date}:*` 等 |
| `app/Services/Common/ProductClickStatService.php:34` | `product_click:*` 落库 |
| `app/Services/Common/MessageService.php:683` | `msg_click_uv:*` 去重统计 |
| `app/Services/Sdk/UserService.php:1589` | 同上（SDK 侧） |

### 修复 R3：给 Redis 加上限与内存告警

当前 `maxmemory=0`（未设置）+ `noeviction`，内存没有上限：一旦键数继续涨，可能触发 OOM Kill。

```bash
# 建议值（按实际内存评估后执行）：给缓存/会话留出余量，超出后按 LRU 淘汰
CONFIG SET maxmemory 4gb
CONFIG SET maxmemory-policy allkeys-lru
# 并写入 redis.conf 持久化（重启后仍生效）
```

同时把 `used_memory`、`evicted_keys`、`keyspace_hits/misses`、`SLOWLOG` 长度纳入每日体检（与 `docs/2026-10-17-0040` 的数据侧体检合并）。

### 修复 R4：持久化与单点

- AOF 当前关闭、无副本（`role=master`、`connected_slaves=0`）：崩溃或重启最坏丢最近 1 小时数据，session 丢失会导致用户大面积掉线。建议开 `appendonly yes` + `appendfsync everysec`，或加一个副本。
- 复核 token TTL：抽样看到最长 **1,866,051 秒（约 21.6 天）**、常见约 2.5 天。TTL 越长，db1 键数越多，`KEYS`/`SCAN` 成本越高，建议按业务安全要求收敛。

## 7.1 实测拓扑

```
203.0.113.1 = ip-172-31-44-11 = Beszel「游点涩-数据库-从库01」(公网 15.168.164.29)
  └─ 同时跑着：MongoDB 从库（server.db2.com）+ Redis 6.2.20（应用 cache / queue 入口）
```

也就是 **Redis 与应用的主要读库在同一台机器上**。读分离改造后，这台机器的网卡发送量从平均 14 MB/s 涨到 77 MB/s（峰值 93.6 MB/s），而 Redis 本身只占其中约 1.4 MB/s（≈1.5%）。

风险：一旦 Mongo 读把该机 CPU/网卡打满，Redis 的 P99 延迟会跟着恶化，进而影响缓存与队列，表现为"数据库慢带着 Redis 一起慢"，排查时容易误判成 Redis 的问题。

## 7.3 建议

1. 读流量按 `slave1` / `slave2` 均分（当前只落到从库01，从库02 处于空闲）。
2. 中期考虑把 Redis 独立到单独主机，或至少不要与承接主要读流量的从库同机；短期先给该机加"网卡 + CPU + Redis P99 延迟"的联合告警。
3. 副本角色/容量变化后，重新评估 Redis 的 `maxmemory`（当前未设置）与该机内存余量。
