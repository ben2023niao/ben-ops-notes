# 契约测试规则

> GitHub 仓库源文件：[点击打开网页渲染版](https://github.com/ben2023niao/ben-ops-notes/blob/main/doc/md/202606040109-%E5%B0%8F%E8%93%9D%E7%9B%B4%E6%92%AD%2B%E8%87%AA%E5%8A%A8%E5%8C%96%2B%E6%95%85%E9%9A%9C%E6%8E%92%E6%9F%A5-%E5%A5%91%E7%BA%A6%E6%B5%8B%E8%AF%95%E8%A7%84%E5%88%99.md)

> 整理日期：2026-06-04 01:09｜日期依据：文件创建/修改时间

OpenAPI 是合同，必须能继续向下驱动 mock、后端实现、前端 mock 和接口文档。乌托邦 的契约测试至少覆盖四层：

1. OpenAPI 静态校验：recursive `$ref`、operationId、responses、`x-prd-id`、breaking change。
2. Mock server 合约：mock handler 和 fixture 必须来自 OpenAPI operation 和 schema。
3. 后端响应合约：真实服务的状态码、响应体、错误结构、鉴权行为必须符合 OpenAPI。
4. 前端 mock 来源：前端 mock 或 fixture 必须说明来自 OpenAPI、mock server 或测试环境接口，不能静态编字段冒充完成。

## 1. 证据入口

契约测试证据写入：

```text
docs/qa/contract-test-evidence.json
```

每条证据必须能追踪到：

1. 需求 ID。
2. OpenAPI operationId。
3. OpenAPI path 文件。
4. mock server 状态。
5. 后端 conformance 状态。
6. 前端 mock 来源。
7. 测试命令或报告。

## 2. 状态

| 状态 | 含义 |
| --- | --- |
| `pending` | 契约已定义，但实现或测试未完成。 |
| `pass` | mock、后端响应和前端 mock 来源均已验证。 |
| `fail` | 当前证据证明契约不一致。 |
| `not-applicable` | 该 operation 不需要此类测试，必须写明原因。 |

`pass` 必须有自动化测试命令或报告路径。`not-applicable` 必须写 `reason`。

## 3. MR 要求

涉及 `packages/contracts/openapi/**` 的 MR 必须：

1. 通过 `npm run check:openapi`。
2. 通过 `npm run check:contract`。
3. 如果新增或修改业务 operation，更新 `docs/qa/contract-test-evidence.json`。
4. 如果后端尚未实现，只能把状态写为 `pending`，不能宣称接口闭环完成。
