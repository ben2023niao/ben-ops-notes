# 容器化项目增删运维手册

> GitHub 仓库源文件：[点击打开网页渲染版](https://github.com/ben2023niao/ben-ops-notes/blob/main/doc/md/202606040150-%E5%B0%8F%E8%93%9D%E7%9B%B4%E6%92%AD%2BLinux%2BShell-%E5%AE%B9%E5%99%A8%E5%8C%96%E9%A1%B9%E7%9B%AE%E5%A2%9E%E5%88%A0%E8%BF%90%E7%BB%B4%E6%89%8B%E5%86%8C.md)

> 整理日期：2026-06-04 01:50｜日期依据：文件创建/修改时间

本文面向后续运维接手，覆盖当前 Docker Compose + `dev-cicd.sh` 发布方式下，新增或删除前端 / 后端项目时需要改哪些文件、按什么顺序验证、哪里不能放密钥。

## 1. 当前边界

当前容器化发布采用以下原则：

- 前端容器内不跑 nginx；`web-prod` 运行 Nuxt SSR，`admin-prod` / `live-host-prod` 用 Node 静态服务监听端口。
- 宝塔在服务器外层做反向代理，只需要代理到容器暴露端口。
- `web-prod` / `admin-prod` / `live-host-prod` 共用 `kickoff-frontend:${BUILD_ENV}` 镜像，避免三端重复构建。
- `docker compose --profile deploy` 是部署模式；普通 `docker compose up --build` 是本地 dev 模式。
- 真实密钥只放部署机 `.env` / `.cicd.env`，不写进 git；根目录不再要求 `.env.stg` / `.env.prod`。
- `.ai-framework/`、`docs/`、`scripts/validate-*` 等工程期产物不能进入运行时镜像。

当前服务端口：

| 服务 | Compose service | 容器名 | 端口 | 说明 |
| --- | --- | --- | --- | --- |
| C 端 Web | `web` / `web-prod` | `kickoff-web` / `kickoff-web-prod` | `3000` | Nuxt SSR |
| 主播端 | `live-host` / `live-host-prod` | `kickoff-live-host` / `kickoff-live-host-prod` | `3030` | Nuxt 静态 SPA |
| 运营后台 | `admin-web` / `admin-prod` | `kickoff-admin-web` / `kickoff-admin-prod` | `5174` | Vite 静态 SPA |
| Public API | `api` | `kickoff-api` | `8080` | Go API |
| Admin API | `admin-api` | `kickoff-admin-api` | `8081` | Go Admin API |
| MySQL | `mysql` | `kickoff-mysql` | `13306` | 本地映射端口 |
| Redis | `redis` | `kickoff-redis` | `16379` | 本地映射端口 |

## 2. Telegram 通知配置

`dev-cicd.sh` 会自动读取部署机本地的 `.cicd.env`：

```bash
cd /opt/xiaolan_watches_the_game_at_night
install -m 600 /dev/null .cicd.env
vi .cicd.env
```

内容示例：

```bash
[敏感内容已脱敏]
TG_CHAT_ID="<TG_CHAT_ID>"
```

如果发布任务把脚本放到其他目录，可以通过 `CICD_ENV_FILE` 指定：

```bash
CICD_ENV_FILE=/etc/kickoff/dev-cicd.env sh dev-cicd.sh
```

注意：

- `.cicd.env` 不提交 git。
- 不把 `.env`、`.cicd.env` 发到 Telegram。
- 机器人 token 泄露后必须立刻在 BotFather 重置。

## 3. 新增前端项目流程

新增前端前，先确认这些信息：

| 项目 | 示例 |
| --- | --- |
| 目录 | `apps/ops-dashboard` |
| package name | `@kickoff/ops-dashboard` |
| 本地端口 / 部署端口 | `3040` |
| 产物类型 | Nuxt SSR / Nuxt 静态 SPA / Vite 静态 SPA |
| 对外域名 | 宝塔反向代理域名 |
| API base | Public API 或 Admin API |

### 3.1 准备应用包

`apps/<name>/package.json` 至少需要这些脚本：

```json
{
  "name": "@kickoff/ops-dashboard",
  "scripts": {
    "dev": "nuxt dev --host 0.0.0.0 --port 3040",
    "build:stg": "nuxt generate --dotenv .env.stg",
    "build:prod": "nuxt generate --dotenv .env.prod"
  }
}
```

如果是 SSR 项目，`build:stg` / `build:prod` 使用 `nuxt build`；如果是纯静态项目，使用 `nuxt generate` 或 `vite build`。

### 3.2 增加 dev Compose 服务

在 `docker-compose.yml` 的 `FRONTEND (DEV MODE)` 下增加服务：

```yaml
  ops-dashboard:
    <<: *frontend-dev-service
    container_name: kickoff-ops-dashboard
    environment:
      <<: *frontend-dev-env
      NUXT_PUBLIC_API_BASE: https://api-dev.example.com
      NUXT_PUBLIC_APP_NAME: 小蓝运营看板
    command: sh -c "pnpm --filter @kickoff/ops-dashboard exec nuxt dev --host 0.0.0.0 --port 3040"
    ports:
      - "3040:3040"
    depends_on:
      frontend-deps:
        condition: service_completed_successfully
      api:
        condition: service_started
```

如果项目调用 Admin API，把依赖改成 `admin-api`，并让浏览器请求对应 Admin API 域名。

### 3.3 增加 deploy Compose 服务

如果是静态 SPA，使用 `static-server.mjs`：

```yaml
  ops-dashboard-prod:
    profiles: ["deploy"]
    image: kickoff-frontend:${BUILD_ENV:-stg}
    build:
      context: .
      dockerfile: infra/docker/frontend-prod.Dockerfile
      args:
        BUILD_ENV: ${BUILD_ENV:-stg}
    container_name: kickoff-ops-dashboard-prod
    working_dir: /workspace
    ports:
      - "3040:3040"
    command: node infra/docker/static-server.mjs apps/ops-dashboard/.output/public 3040
    restart: unless-stopped
    depends_on:
      api:
        condition: service_started
```

如果是 Nuxt SSR，命令改成：

```yaml
    command: node apps/ops-dashboard/.output/server/index.mjs
```

### 3.4 更新前端部署镜像

在 `infra/docker/frontend-prod.Dockerfile` 的 build 阶段增加：

```dockerfile
RUN pnpm --filter @kickoff/ops-dashboard run build:${BUILD_ENV}
```

runtime 阶段增加 package manifest 和产物：

```dockerfile
COPY apps/ops-dashboard/package.json ./apps/ops-dashboard/package.json
COPY --from=build /workspace/apps/ops-dashboard/.output ./apps/ops-dashboard/.output
```

如果产物是 Vite `dist`：

```dockerfile
COPY --from=build /workspace/apps/ops-dashboard/dist ./apps/ops-dashboard/dist
```

### 3.5 更新 `dev-cicd.sh`

新增环境 URL：

```sh
PROD_OPS_DASHBOARD="http://203.0.113.1:3040"
DEV_OPS_DASHBOARD="http://203.0.113.1:3040"
```

在分支判断中赋值：

```sh
OPS_DASHBOARD_URL=$PROD_OPS_DASHBOARD
# 或
OPS_DASHBOARD_URL=$DEV_OPS_DASHBOARD
```

把 deploy 服务加入列表：

```sh
DEPLOY_SERVICES="mysql redis migrate api admin-api web-prod admin-prod live-host-prod ops-dashboard-prod"
```

增加健康检查：

```sh
check_url "运营看板" "$OPS_DASHBOARD_URL/"
```

Telegram 成功报告里补访问地址。

### 3.6 宝塔配置

在宝塔里新增站点或反向代理：

| 项目 | 值 |
| --- | --- |
| 目标协议 | `http` |
| 目标 IP | 部署机内网 IP 或 `203.0.113.1` |
| 目标端口 | `3040` |
| WebSocket | 只有实时连接需要时才开启 |

### 3.7 前端新增验证

```bash
sh -n dev-cicd.sh
docker compose config --quiet
docker compose build ops-dashboard
BUILD_ENV=stg docker compose --profile deploy build web-prod
BUILD_ENV=stg docker compose --profile deploy up -d --no-build ops-dashboard-prod
curl -fsS http://203.0.113.1:3040/
```

验证通过后更新：

- `README.md`
- `infra/deploy/README.md`
- 本文档中的当前服务表
- `docs/agents/logs/<日期>-<任务>.md`

## 4. 删除前端项目流程

删除前端项目前，先确认外部入口已经下线：

1. 在宝塔停用或删除对应反向代理。
2. 确认没有发布任务、监控、第三方回调仍引用该域名。
3. 通知业务确认可删除。

代码和部署侧按以下顺序处理：

1. 从 `dev-cicd.sh` 删除 URL 常量、分支赋值、健康检查、Telegram 展示。
2. 从 `docker-compose.yml` 删除 dev 服务和 `*-prod` deploy 服务。
3. 从 `infra/docker/frontend-prod.Dockerfile` 删除 `RUN pnpm --filter ... build:${BUILD_ENV}`、package manifest COPY、产物 COPY。
4. 从 `pnpm-workspace.yaml` 或相关 workspace 配置删除包引用，前提是该包已从仓库删除。
5. 删除或归档 `apps/<name>`。
6. 更新 README、运维文档、Agent 工作日志。
7. 执行验证：

```bash
sh -n dev-cicd.sh
docker compose config --quiet
BUILD_ENV=stg docker compose --profile deploy build web-prod
```

示例：删除 `live-host`

- 删除 `live-host`、`live-host-prod`。
- 删除端口 `3030` 的宝塔反向代理。
- 删除 `dev-cicd.sh` 中 `LIVE_HOST_URL` 和健康检查。
- 删除 `frontend-prod.Dockerfile` 中 `@kickoff/live-host` 的 build 与产物 COPY。

## 5. 新增后端项目流程

新增后端项目前，先确认它属于哪种类型：

| 类型 | 建议方式 |
| --- | --- |
| 新 HTTP API | 在 `services/go-app/cmd/<name>` 增加新入口，复用现有配置、日志、DB、Redis |
| 后台管理能力 | 优先接入现有 `admin-api`，并更新 OpenAPI / contracts |
| 异步任务 | 增加 `worker` 或 cron 型入口，不暴露公网端口 |
| 实时服务 | 独立端口，明确 WebSocket / TCP / UDP 协议与反代方式 |

### 5.1 后端代码要求

如果新增 HTTP 服务，必须具备：

- `/healthz` 健康检查。
- 配置从 env / yaml 读取，不能硬编码密钥。
- 需要 DB 时走 migration，已上线 migration 不直接改。
- 涉及接口时同步 `docs/api/openapi.yaml` 和 `packages/contracts/`。
- 涉及资金 / 审计 / RBAC 时按 `AGENTS.md` 红线执行。

### 5.2 增加 Compose 服务

示例：新增 `realtime-api`，监听 `8090`：

```yaml
  realtime-api:
    build:
      context: .
      dockerfile: infra/docker/go-dev.Dockerfile
    container_name: kickoff-realtime-api
    working_dir: /workspace/services/go-app
    environment:
      <<: *go-env
      APP_HTTP_ADDR: :8090
    volumes:
      - .:/workspace
      - go_mod_cache:/go/pkg/mod
      - go_build_cache:/root/.cache/go-build
    command: sh -c "go mod download && go run ./cmd/realtime"
    ports:
      - "8090:8090"
    depends_on:
      migrate:
        condition: service_completed_successfully
      redis:
        condition: service_healthy
```

如果部署态需要独立镜像，优先复用现有 Go Dockerfile 模式；不要把 docs、framework、源码无关文件复制进 runtime。

### 5.3 更新 `dev-cicd.sh`

新增 URL：

```sh
PROD_REALTIME_API="http://203.0.113.1:8090"
DEV_REALTIME_API="http://203.0.113.1:8090"
```

加入服务列表：

```sh
DEPLOY_SERVICES="mysql redis migrate api admin-api realtime-api web-prod admin-prod live-host-prod"
```

增加健康检查：

```sh
check_url "Realtime API" "$REALTIME_API_URL/healthz"
```

如果这个后端服务需要暴露公网，在宝塔或网关补反向代理；如果只给内网服务调用，不要开放公网入口。

### 5.4 后端新增验证

```bash
go test ./...
sh -n dev-cicd.sh
docker compose config --quiet
docker compose build realtime-api
docker compose up -d realtime-api
curl -fsS http://203.0.113.1:8090/healthz
```

如果新增接口：

```bash
npm run check:openapi
npm run check:contract
```

## 6. 删除后端项目流程

删除后端前，先做下线确认：

1. 确认没有前端、第三方、定时任务、内部服务仍调用。
2. 停掉宝塔 / 网关入口。
3. 如果有数据库表，不直接删生产数据；先走归档、冻结、灰度下线。
4. 如果有消息队列或定时任务，先清理消费者和计划任务。

代码和部署侧按以下顺序处理：

1. 从 `dev-cicd.sh` 删除 URL、服务名、健康检查、报告展示。
2. 从 `docker-compose.yml` 删除服务。
3. 删除对应 Dockerfile 构建入口或镜像 COPY 逻辑。
4. 删除 systemd / 宝塔 / 监控 / 告警配置。
5. 如果删除 API，更新 OpenAPI、contracts、前端 API client。
6. migration 不直接回滚已上线历史；新增 down migration 只用于新迁移回滚，不用于删除生产历史表。
7. 执行验证：

```bash
go test ./...
docker compose config --quiet
sh -n dev-cicd.sh
```

示例：删除旧 `admin-api`

- 先确认 `apps/admin` 已迁移到新 Admin API。
- 宝塔停止旧 `/api/v1/admin` 反向代理。
- 删除 `admin-api` 健康检查和 compose 服务。
- 更新 `VITE_PROXY_TARGET`、OpenAPI、README。
- 跑 `go test ./...` 和 `docker compose config --quiet`。

## 7. 发布前后检查清单

发布前：

```bash
git fetch origin
git status --short
git rev-list --left-right --count HEAD...@{upstream}
./devtools/framework status
python3 scripts/validate-runtime-environment.py
python3 scripts/validate-prd.py
python3 scripts/validate-engineering-standards.py
python3 scripts/validate-capability-gates.py
python3 scripts/validate-completion-claims.py
sh -n dev-cicd.sh
docker compose config --quiet
```

发布后：

```bash
docker compose --profile deploy ps
curl -fsS http://203.0.113.1:8080/healthz
curl -fsS http://203.0.113.1:8081/healthz
curl -fsS http://203.0.113.1:3000/
curl -fsS http://203.0.113.1:3030/
curl -fsS http://203.0.113.1:5174/
```

镜像边界检查：

```bash
docker run --rm kickoff-frontend:stg sh -c 'test ! -e /workspace/docs && test ! -e /workspace/.ai-framework'
docker run --rm kickoff-frontend:stg find /workspace -name "*.go" 2>/dev/null | head
docker images kickoff-frontend:stg --format "{{.Size}}"
```

`find` 不应输出 Go 源码；如果输出源码或 docs/framework 文件，先修 `.dockerignore` / Dockerfile，再发布。
