# 堡垒机 2222 网络故障与 DOCKER-USER 持久化修复

> 公开版脱敏说明：JumpServer 公网地址、容器私网地址、运维来源 IP 和巴西测试机出口 IP 均已替换为占位符。记录保留故障链、命令结构和验证方法，便于复盘 Docker 转发规则持久化问题。

## 故障结论

本次 JumpServer SSH 入口不可用由两类问题叠加造成：

1. 宿主机 `FORWARD` 默认策略为 `DROP`，容器端口映射对应的转发流量被拦截。
2. 最初使用按来源 IP 写入的临时 `FORWARD` 规则恢复连接，但宿主机重启后规则会丢失。
3. 后续用于持久化规则的 helper 脚本存在 shell 语法错误，启动时没有顺利执行。
4. 排查命令把 `echo helper_rc=0` 的退出码误认为 helper 自己的结果，导致故障判断被误导。

最终使用 Docker 官方扩展链 `DOCKER-USER` 持久化 SSH 映射端口的入向和返程放行规则，并通过“先删除手工规则、再重启 Docker”的方式验证规则确实自动恢复。

## 环境与链路

故障环境的关键组成如下：

| 项目 | 状态 |
|---|---|
| 入口 | JumpServer SSH，公网 TCP 2222 |
| 容器 | `jms_koko`，内部 TCP 2222 |
| 宿主机转发 | `ip_forward=1` |
| 宿主机 `FORWARD` | 默认 `DROP` |
| Docker 防火墙后端 | nftables |
| 固定来源控制 | 云安全组 |

完整流量链路：

```text
外部客户端
  → <JUMP_HOST_IP>:2222
  → JumpServer 宿主机 DNAT
  → <KOKO_CONTAINER_IP>:2222
  → FORWARD
  → DOCKER-USER
  → DOCKER-FORWARD
```

`DOCKER-USER` 是 Docker 保留给用户的过滤链。Docker 在启动过程中创建并遍历该链，因此适合放置容器映射端口所需的持久转发放行规则。

## 故障现象

从巴西打包机访问 JumpServer 的 TCP 2222 超时，而宿主机上的容器运行正常。检查确认：

- `jms_koko` 监听 `0.0.0.0:2222`。
- Docker 端口映射存在：`2222/tcp`。
- `jms_*` 容器均处于运行状态。
- 宿主机 `ip_forward=1`。
- `INPUT` 链为 `ACCEPT`。
- Docker 的 DNAT 规则存在，目标为 `jms_koko` 容器。
- `FORWARD` 默认策略为 `DROP`。
- `DOCKER-USER` 链存在但没有放行规则。

因此问题不在容器监听、端口映射或 DNAT，而在宿主机对转发流量的默认拒绝和持久放行规则。

## 临时恢复

紧急恢复可以按来源 IP 临时添加入向和返程规则：

```bash
iptables -A FORWARD \
  -s <CLIENT_IP>/32 -d <KOKO_CONTAINER_IP>/32 \
  -p tcp -m tcp --dport 2222 \
  -m conntrack --ctstate NEW,ESTABLISHED -j ACCEPT

iptables -A FORWARD \
  -s <KOKO_CONTAINER_IP>/32 -d <CLIENT_IP>/32 \
  -p tcp -m tcp --sport 2222 \
  -m conntrack --ctstate ESTABLISHED -j ACCEPT
```

这种方式可以快速恢复业务，但不能作为最终方案：

- 每组来源都需要两条规则，维护成本高。
- 规则位于默认 `FORWARD` 链，宿主机重启后会丢失。
- 来源 IP 变更后容易误判为同一类故障。

临时规则只用于争取排查时间，持久化修复完成后应删除。

## 定位 helper 执行失败

最初用 systemd Drop-in 在 Docker 启动后调用 helper：

```ini
[Service]
ExecStartPost=/usr/local/sbin/jumpserver-koko-forward
```

`systemctl show docker -p ExecStartPost` 能看到配置，但 `DOCKER-USER` 仍为空。使用 shell 跟踪执行后，发现循环写法错误：

```text
for _ in 1
2
3
...
30; do
```

Shell 在遇到单独的数字 `2` 时把它当作命令，随后报：

```text
syntax error near unexpected token `2'
```

正确写法是：

```bash
for _ in {1..30}; do
  ...
done
```

### 为什么 `helper_rc=0` 会误判

错误排查方式：

```bash
/usr/local/sbin/jumpserver-koko-forward
echo helper_rc=0
```

无论 helper 是否成功，后面的 `echo` 都会成功并打印 `0`。这里的 `0` 不是 helper 的退出码。

正确记录方式：

```bash
/usr/local/sbin/jumpserver-koko-forward
rc=$?
echo "helper_rc=$rc"
```

或者直接依赖脚本中的 `set -euo pipefail` 和 systemd 的 `ExecStartPost` 退出状态。

## 持久化修复

helper 需要等待 Docker 创建 `DOCKER-USER`，然后用可重复执行的检查插入两条规则：

```bash
#!/usr/bin/env bash
set -euo pipefail

PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

for _ in {1..30}; do
  iptables -nL DOCKER-USER >/dev/null 2>&1 && break
  sleep 1
done

# Docker 30 秒内没有创建扩展链时必须失败。
iptables -nL DOCKER-USER >/dev/null

if ! iptables -C DOCKER-USER \
  -p tcp --dport 2222 \
  -m conntrack --ctstate NEW,ESTABLISHED -j ACCEPT 2>/dev/null; then
  iptables -I DOCKER-USER 1 \
    -p tcp --dport 2222 \
    -m conntrack --ctstate NEW,ESTABLISHED -j ACCEPT
fi

if ! iptables -C DOCKER-USER \
  -p tcp --sport 2222 \
  -m conntrack --ctstate ESTABLISHED -j ACCEPT 2>/dev/null; then
  iptables -I DOCKER-USER 1 \
    -p tcp --sport 2222 \
    -m conntrack --ctstate ESTABLISHED -j ACCEPT
fi
```

规则具有以下特点：

- 只放行 JumpServer SSH 映射端口。
- 入向允许 `NEW,ESTABLISHED`，返程只允许 `ESTABLISHED`。
- 使用 `iptables -C` 检查后再插入，重复执行不会无限追加。
- 来源白名单继续由云安全组维护，不在宿主机 helper 中写死具体 IP。

将脚本保存到 `/usr/local/sbin/`，设为可执行后再启用 systemd Drop-in。建议先执行：

```bash
bash -n /usr/local/sbin/jumpserver-koko-forward
systemd-analyze verify /etc/systemd/system/docker.service.d/99-jumpserver-koko-forward.conf
```

## 有效验证方法

不能只检查“当前规则还在”，因为手工添加的规则可能让验证假通过。正确流程是：

1. 手工确认当前连接可用。
2. 删除 `DOCKER-USER` 中手工插入的规则。
3. 只重启 Docker，不手工补规则。
4. 检查 `DOCKER-USER` 是否由 `ExecStartPost` 自动恢复。
5. 检查 systemd 中 helper 的最终退出状态。
6. 从实际客户端重新验证 TCP 和 SSH 协议。

重启前应确认：

```text
-N DOCKER-USER
```

仅重启 Docker 后，期望看到：

```text
-N DOCKER-USER
-A DOCKER-USER -p tcp -m tcp --sport 2222 -m conntrack --ctstate ESTABLISHED -j ACCEPT
-A DOCKER-USER -p tcp -m tcp --dport 2222 -m conntrack --ctstate NEW,ESTABLISHED -j ACCEPT
```

并确认：

- Docker 服务重新进入 `active (running)`。
- `ExecStartPost` 的实际结果为 `status=0/SUCCESS`。
- `jms_*` 容器在 Docker 重启后重新启动。

## 清理临时规则

持久化验证通过后，删除所有按来源 IP 手工添加的 `FORWARD` 入向和返程规则。清理后应只剩 Docker 的通用转发入口：

```text
-P FORWARD DROP
-A FORWARD -j DOCKER-USER
-A FORWARD -j DOCKER-FORWARD
```

放行逻辑集中在 `DOCKER-USER`，来源控制集中在云安全组，避免两处同时维护不同白名单。

## 两层连通性复测

最终验证至少要覆盖两层。

### 第一层：TCP 端口连通

```bash
nc -zv -w 5 <JUMP_HOST_IP> 2222
```

期望：

```text
Connection to <JUMP_HOST_IP> 2222 port [tcp/*] succeeded!
```

### 第二层：SSH 服务身份

```bash
ssh -vv -p 2222 <TEST_USER>@<JUMP_HOST_IP> true
```

看到远端返回 JumpServer SSH banner，才能证明流量到达正确服务，而不是只建立了到某个代理或中间设备的 TCP 连接。

本次从巴西打包机复测连续三次均成功，近距离连接耗时约 310–320 ms，SSH 协议层返回 JumpServer 远端软件标识。同机访问该主机的 80/443 不开放，与安全组边界一致，不影响 2222 的恢复结论。

## 后续白名单维护

新增或删除 JumpServer SSH 来源时，只需修改云安全组中的 TCP 2222 入站规则。以下内容都不应因单个来源变化而修改：

- helper 脚本。
- Docker systemd Drop-in。
- `DOCKER-USER` 端口规则。
- JumpServer 容器配置。

每次修改后从实际来源执行 TCP 和 SSH 两层验证。

安全组必须保持最小来源范围。不要把 2222 直接开放给全网，除非有明确业务依据和额外访问控制。

## 防复发清单

1. 判断命令结果必须看真实退出码，不能把后续 `echo` 的成功码当成目标命令结果。
2. 持久化验证前必须移除手工规则，否则无法证明自动恢复。
3. Docker 端口映射不要依赖临时 `FORWARD` 规则，优先使用 `DOCKER-USER`。
4. 来源 IP、目标公网 IP、容器私网 IP 必须分开记录，避免测试到错误地址。
5. 多行 shell 脚本不要直接依赖聊天软件复制，执行前先做 `bash -n`。
6. 连通性验证至少覆盖 TCP 和 SSH 服务身份两层。
7. 主机安全组负责来源白名单，宿主机规则负责容器转发，职责要明确。
