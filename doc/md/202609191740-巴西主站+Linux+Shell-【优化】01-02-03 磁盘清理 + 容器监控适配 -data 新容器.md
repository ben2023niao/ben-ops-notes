# 【优化】01-02-03 磁盘清理 + 容器监控适配 /data 新容器

> 来源文件：`~/Projects/work/game/pgserver/master/docs/history/2026-09-19-1740-【优化】01-02-03磁盘清理与容器监控适配新容器记录.md`

> 整理日期：2026-09-19 17:40｜日期依据：文件名日期

时间：2026-09-19（北京时间 17:40 / UTC 09:40）
对象机器：后台 01 `203.0.113.1`、后台 02 `203.0.113.1`、压测 03 `203.0.113.1`、
　　　　　备用入口机 `34.151.249.53`（203.0.113.1）、宝塔 `35.247.205.6`（203.0.113.1）
触发原因：01/02/03 磁盘使用率连续告警（>70%，01 一度 95.3%）；同时清理旧容器后，
　　　　　容器监控还在按旧容器名报警（`容器缺失：dbqp-pg-release-01` …），需要改成监控新容器。
结果：三台各释放 190G~440G 不等；容器监控改为监控 `/data` 下的 `game-service-*-prod`，
　　　并且新增「滚动发版宽限」避免误报；已实测 dry-run 与真实定时任务均为 0 报警。
**本轮未通知飞机群。** 全程未影响线上用户（改的都是监控脚本与磁盘，未动 nginx 与后端进程）。

## 二、清理了什么

### 1. 01 / 02 / 03 三台的旧容器与旧镜像

```text
01：删除 8 个已停止的旧容器 dbqp-<厂家>-release-01（26.3G）
    删除被替代的镜像 panda/pp/api 的 20260916-ben-cb8f2c55（约 3.6G）
    镜像总量 52.85G -> 15.39G
02：删除旧容器 + 被替代镜像 + pgserver:master-1516f8dd（5.84G）
03：删除 pgserver:master-1516f8dd（5.85G）+ dbqp-browser-test（2.4G，随后已重建并推送到本地私服）
```

### 2. 01 / 02 / 03 三台的老结果集 `/opt/game_results_datas`

```text
01：253G
02：237G
03：190G
合计约 680G（这是本轮释放量的大头，也是 01 从 96% 直接掉到 34% 的原因）
```

三台现在的项目目录都在 `/data` 下（`/data/pgserver`、`/data/server-runtime`），
`/opt` 下的老结果集已不再被任何容器挂载。

## 三、删老结果集前的三重确认（删除前实测）

破坏性操作前的确认证据，留档以便复盘：

```text
1）7 天内无写入：02/03 的 /opt/game_results_datas 最后写入停在 2026-09-08；
2）无运行中容器挂载：docker inspect 全部容器，挂载点只有 /data/server-runtime(/data/pgserver)，
   没有任何容器挂载 /opt/game_results_datas；
3）无脚本/定时任务引用：01/02/03 的 crontab 与 /etc/systemd/system 中
   grep "/opt/game_results_datas" 命中 0 处。
```

## 四、为什么入口机和宝塔的 `/opt/pgserver` **没有删**（重要）

入口机 `/opt/pgserver` 1.5G、宝塔 `/opt/pgserver` 1.8G 都**不能删**，因为机器人容器
把整个目录 bind mount 进去了（不是缓存，是运行依赖）：

```text
入口机 容器 dbqp-ben-bot-standby：
  /opt/pgserver                      -> /workspace/pgserver            (rw)
  /opt/pgserver/docker/ben-bot/data/upload  -> /app/data/upload          (rw)
  /opt/pgserver/docker/ben-bot/data/scripts -> /app/data/scripts        (rw)
  /opt/pgserver/docker/ben-bot/app/benbot/{home,help_center,plugin_registry}.py -> /app/app/benbot/... (ro)

宝塔 容器 dbqp-ben-bot：同样挂载以上全部路径
```

`fuser -m /opt/pgserver` 在入口机上能看到大量进程在占用该目录，佐证它是活依赖。
所以本轮只在三台后台清理 `/opt`，入口机与宝塔的 `/opt/pgserver` 原样保留。

## 五、容器监控改造（本次主要需求）

### 1. 问题

2026-09-18~19 三台的发布容器已经从「按机器号命名」换成「按厂家统一命名」，
但监控脚本 `docker/scripts/container_health_monitor.py` 还按旧名字找容器，
于是每 2 分钟报一次假警（用户收到的就是这一类）：

```text
【DBQP 容器监控｜报警】时间：2026-09-19 17:04:01
- 容器缺失：dbqp-pg-release-01（203.0.113.1）
- 容器缺失：dbqp-tada-release-01（203.0.113.1）
…
```

### 2. 新旧容器命名对照（01/02/03 三台已统一，不再带机器号）

| 服务 | 旧容器名（已下线） | 新容器名（现在监控的） |
| --- | --- | --- |
| PG | `dbqp-pg-release-*` | `game-service-pg-prod` |
| TADA 接口 | `dbqp-tada-release-*` | `game-service-tada-prod` |
| TADA 实时 WS2 | 同 `dbqp-tada-release-*` | `game-service-tada_ws-prod`（01/03）／`game-service-tada-ws-prod`（02） |
| PP | `dbqp-pp-release-*` | `game-service-pp-prod` |
| PPK / POPOK | `dbqp-popok-release-*` | `game-service-ppk-prod` |
| PlaySon | `dbqp-playson-release-*` | `game-service-playson-prod` |
| Panda | `dbqp-panda-release-*` | `game-service-panda-prod` |
| platform-api | `dbqp-platform-api-release-*` | `game-service-api-prod` |
| G759 | （无旧容器） | `game-service-g759-prod` |

注意两处名字不一致的坑：**POPOK 的容器名是 `ppk`**、**platform-api 的容器名是 `api`**。

### 3. 脚本改动

文件：`docker/scripts/container_health_monitor.py`（同时部署到入口机
`/opt/pgserver/docker/scripts/container_health_monitor.py`，由 crontab 每 2 分钟调用）

```text
① 期望容器清单换成 game-service-*-prod（含新增的 g759 与 TADA WS2）；
   TADA WS2 用「候选名列表」，下划线/连字符两种写法都算正常。
② 每台后端可以有各自的「已知缺口」（BACKEND_MISSING_OK）：
   03 备用机当前没有 game-service-tada-prod，列进去不再误报（其它 8 个照常监控）。
③ 容器缺失从「一次采样就报警」改为「连续 MISS_THRESHOLD 次（默认 3 次 ≈ 6 分钟）才报警」：
   开发滚动发版时容器会 stop/rm/run，中间 1~2 分钟查不到是正常的，老版本会立刻误报。
   恢复时如果之前报过警，会补一条「容器恢复」通知；宽限期内自己恢复的则静默。
④ --dry-run 不再写状态文件：老版本 dry-run 也会 save_state()，
   跑一次 dry-run 就把「缺失」写进状态，导致后面真正的报警被吞掉（本次实际踩到）。
⑤ 自动清理状态文件里的历史遗留键（例如 `203.0.113.1:dbqp-pg-release-01`），避免状态越滚越大。
```

新增可调环境变量：`DBQP_CONTAINER_MISS_THRESHOLD`（默认 3，即约 6 分钟）。

### 4. 验证（本次实测）

```text
① 语法检查：python3 -m py_compile 通过。
② 部署一致性：本地与入口机 md5 一致 d03bb9a684625926ea3c2fba2dd1cc9b。
③ dry-run：`[dry-run] 期望容器 29 个 | alerts=0 recovers=0`，且不再生成状态文件。
   29 = 01(10 个) + 02(10 个) + 03(9 个，少 TADA 主服务)。
④ 真实跑一次：`OK 2026-09-19 17:29:59 期望容器 29 个全部正常`。
⑤ 定时任务：17:30:01 那一次 cron 也已经打到
   `OK 2026-09-19 17:30:01 期望容器 29 个全部正常`（/var/log/dbqp-container-health.log）。
⑥ 逻辑回归（本地假数据，不动线上）：
   · 容器消失 1 次 → 静默；第 2 次 → 静默；第 3 次 → 报警；容器回来 → 发「容器恢复」。
   · 03 缺 tada 主服务 → 不报警；历史遗留键 `dbqp-pg-release-01` → 自动被清掉。
   · 报警正文示例：
     「- 容器缺失：game-service-g759-prod（203.0.113.1 / 01）连续 3 次采样（约 6 分钟）未找到，
        候选名：game-service-g759-prod」
```

## 六、遗留问题（需要开发确认，未处理）

**03 备用机缺 TADA 主服务 `game-service-tada-prod`（9096）。**

```text
证据：03 上 `docker ps -a` 只有 game-service-tada_ws-prod，没有 game-service-tada-prod；
      `ss -ltnp` 在 03 上也看不到 9096 端口；03 的容器都是 2026-09-18 08:19 那次
      `sh start.sh all` 起的（start.sh 的 ALL_VENDORS 里是有 tada 的），但 tada 不在。
影响：03 目前是备用机，nginx 三台 vendor upstream 的 03 都是 down，**不影响线上用户**；
      但 03 真要顶上来时，TADA 游戏会在 03 上没有后端。
补起来的命令（开发/运维在 03 上执行，需要先确认版本号）：
      cd /data/server-runtime
      sh start.sh tada <版本号>          # 版本号照 01/02 上 tada 容器用的镜像 tag
补起来之后，记得把 container_health_monitor.py 里 BACKEND_MISSING_OK 的
"203.0.113.1": {"game-service-tada-prod"} 那一行删掉（或改成空集合）。
```

## 七、回滚方法

```text
容器监控脚本（入口机 34.151.249.53）：
  # 回到「新容器名但无宽限」的中间版本
  cp -a /opt/pgserver/docker/scripts/container_health_monitor.py.bak-20260919-172925-before-data-container-optimize \
        /opt/pgserver/docker/scripts/container_health_monitor.py
  # 回到最老的「按机器号 release 容器」版本
  cp -a /opt/pgserver/docker/scripts/container_health_monitor.py.bak-20260919-090829-before-new-container-names \
        /opt/pgserver/docker/scripts/container_health_monitor.py

监控状态文件（入口机）：
  /var/tmp/dbqp-container-health.json.bak-20260919-092950   # 本次重置前的状态（含历史键与一次误报）
  /var/tmp/dbqp-container-health.json.bak-20260919-090829   # 更早一次备份
  回滚后直接覆盖回 /var/tmp/dbqp-container-health.json 即可；删掉该文件则会重新建立基线。
```
