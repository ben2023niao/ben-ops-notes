## 1. 模块目标

竞猜是 Kickoff 的**核心商业引擎**，连接观赛流量与 GMV。本模块定义：

1. **活动配置与生命周期**：运营创建活动 → 4 个状态自动流转
2. **押注流程**：用户参与押注的完整闭环（含余额校验、限额、幂等、奖池累加）
3. **结算与派彩**：开奖后按选项命中向押中用户派彩
4. **多阵地一致性**：首页、直播间、竞猜 tab、赛事详情四个入口的押注行为统一

## 4. 业务规则

### 4.1 活动状态机

```text
[草稿]  运营创建 → 配置 → 发布
   │
   ▼
[未开始]  ── 到达"开盘时间" ──►  [进行中]  ── 到达"封盘时间" / 比赛结束 ──►  [待开奖]
                                                                                │
                                                                                ▼
                                                              结果写入 + 派彩  →  [已开奖]
   │
   └──── (运营异常处置) ────►  [已退单] ── 全部押注资金回退
```

**状态判定规则**：

| 状态 | 触发条件 | 用户可否押注 |
| --- | --- | --- |
| 未开始 | now < 开盘时间 | 否 |
| 进行中 | 开盘时间 ≤ now < 封盘时间 且 比赛未结束 | 是 |
| 待开奖 | now ≥ 封盘时间 OR 比赛已结束；但结果未公布 | 否 |
| 已开奖 | 结果已公布且派彩已完成 | 否（仅查看） |
| 已退单 | 运营标记异常 | 否（押注已回退） |

### 4.2 活动配置（运营后台输入项）

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 名称 | ✓ | 例如"世界杯半决赛 · 胜平负" |
| 关联比赛 ID | ✓ | 链接到具体 match |
| 市场类型 | ✓ | 胜平负 / 比分 / 总进球 / 让球 / 30 分钟进球 / 大小分 |
| 选项列表 | ✓ | 每个选项含 `name`、`rate`（赔率） |
| 开盘时间 | ✓ | 用户开始押注的时间 |
| 封盘时间 | ✓ | 用户停止押注的时间（一般 = 开赛时间，或上/下半场结束） |
| 展示直播间 | 否 | 在哪些直播间作为浮动卡展示；空 = 仅在通用入口 |
| 平台抽水 | ✓ | 默认 20%（即派彩池 = 总押注 × 80%） |

### 4.3 押注下单事务

**接口**：`POST /api/v1/predict/bet`

**必填字段**：`activity_id`, `option_key`, `amount`, `idempotency_key`

**事务序列**（强一致，单事务内）：

1. SELECT `predict_activity` FOR UPDATE → 校验状态 = "进行中" 且 now < 封盘时间
2. SELECT `user_wallet` FOR UPDATE → 校验钻石余额 ≥ amount
3. 校验活动和全局配置的单次上限 ≥ amount
4. 等级单次/单日上限已下线；如需日限额，必须走全局风控配置，不得按用户等级区分
5. UPDATE `user_wallet` SET diamond = diamond - amount
6. INSERT `predict_bet`（含订单号、idempotency_key、当前赔率快照、ip、ua）
7. UPDATE `predict_activity` SET pool_total = pool_total + amount, participant_count = 唯一参与人数
8. UPDATE `user_consume_total`（累计消费 += amount/10 RMB 等价）
9. INSERT `wallet_ledger`（账本表，op_type=BET_OUT）
10. INSERT `audit_log`（押注审计）

**幂等**：基于 `(user_id, idempotency_key)` 去重，重复请求返回首次结果。

**赔率快照**：押注时记录当时赔率到 `predict_bet.rate_at_bet`，派彩以快照为准（避免赔率后续变化导致争议）。

### 4.4 加注

- 同一用户、同一活动、同一选项可多次下单。
- 每次下单是**独立订单**，独立赔率快照。
- "我的押注"中显示该用户在该活动该选项的累计金额（聚合显示），但内部仍是 N 条记录。

### 4.5 派彩计算

**派彩池**：`pool_total × (1 - 抽水率)`（默认抽水 20%，派彩池 80%）

**单用户派彩**：

- 命中：`payout = bet_amount × rate_at_bet`（即"押 X 钻石 + 赔率快照"）
- 未命中：`payout = 0`，损失押注本金

**总派彩控制**：理论上所有命中者派彩总和 ≤ 派彩池。
- 若 `Σ(命中 bet × rate)` ≤ 派彩池：按赔率派彩，差额平台留存
- 若 `Σ(命中 bet × rate)` > 派彩池（极端情况）：按比例缩放派彩（每人 × `派彩池 / Σ`）；前端文案"高赔率市场极端结果可能按比例缩放"

**派彩事务**：批量更新 `user_wallet`、写 `wallet_ledger`（op_type=BET_IN）、更新 `predict_bet.payout` 与 `predict_bet.status`。

### 4.6 限额体系

| 限额 | 取值 | 校验位置 |
| --- | --- | --- |
| 单次最低 | 100 💎 | 客户端 + 服务端 |
| 单次最高 | 以活动 `max_bet_diamond` 和全局 `biz.predict.max_bet_diamond` 为准，不按等级区分 | 客户端 + 服务端 |
| 单日总押注 | 等级日限额下线；如需启用需新增全局风控配置 | 服务端 |
| 单活动单用户总押注 | 默认无限（受单日总押注约束） | 服务端 |

#### 4.6.1 单日总押注（默认）

等级日限额已下线。历史 L0-L6 日限额表不再作为实现依据。

### 4.7 多阵地一致性

| 阵地 | 展示规则 | 押注弹窗 |
| --- | --- | --- |
| 首页"热门竞猜" | 进行中 + 未开始，按奖池倒序，4 条 | 跳竞猜中心或赛事详情 |
| 直播间浮动卡 | 仅"进行中"，主推 1 张，绑定该直播间 | 直接唤起弹窗 |
| 直播间"查看全部" | 所有"进行中"活动 | 直接唤起弹窗 |

## 5. 边界与异常

| 场景 | 系统行为 | 提示/状态 |
| --- | --- | --- |
| 余额不足 | 阻止下单 | "余额不足? 前往充值 →"（跳充值，回来后恢复弹窗上下文） |
| 单次超活动/全局上限 | 阻止下单 | "押注金额超出限制" |
| 单日超总押注上限 | 阻止下单 | "今日押注已达上限" |
| 封盘瞬间下单 | 阻止下单 | "活动已封盘" |
| 比赛被取消 / 活动被退单 | 钻石回退到下单前 | 系统消息 + 邮件/站内信 |
| 幂等键重放 | 返回首次订单结果 | 不重复扣款 |
| 网络抖动二次提交 | 服务端通过幂等键去重 | 不重复扣款 |
| 后端事务中钱包变更失败 | 整体回滚 | 提示"系统繁忙，请稍后重试" |
| 极端情况派彩缩放 | 按比例派彩 | "高赔率市场极端结果，派彩已按比例缩放" |

## 6. 权限与风控

1. **登录强制**：押注、加注、查看"我的押注"需登录。
2. **审计日志**：每次押注、派彩、退单 → 强制审计。
3. **风控规则**（仅列原型评审版已定义）：
   - R-301（单笔大额押注）：单笔 ≥ ¥10,000 等值 → 财务复核
   - 单用户密集刷量、单一高赔率集中下注 属技术架构识别的潜在缺口，**原型评审版未定义**，待产品评审后再补入并分配规则 ID
4. **资金一致性**：押注、派彩走**强一致**事务；账本 + 钱包 + 订单 三表同事务。
5. **资金审计**：每日 T+1 跑批校验 Σ(押注流入) - Σ(派彩流出) - Σ(平台抽水) = 0（容差 ≤ 0.01 元）。

## 10. 测试要求

1. **单元测试**：状态机判定、限额校验、派彩计算（含极端缩放）、幂等去重
2. **集成测试**：完整押注事务（含失败回滚）、并发押注（同用户 100 并发应只 1 个生效）、派彩批处理
3. **混沌测试**：押注过程随机注入数据库失败，验证事务回滚一致性
4. **E2E**：购物车风格的完整闭环 — 押注 → 加注 → 等待开奖 → 派彩 → 钱包到账 → 累计消费升级
5. **压测**：单活动 500 押注/s 持续 5 分钟，P99 < 500ms
6. **对账测试**：跑批 1 个完整活动结算，校验 Σ流入 - Σ流出 = 平台抽水
