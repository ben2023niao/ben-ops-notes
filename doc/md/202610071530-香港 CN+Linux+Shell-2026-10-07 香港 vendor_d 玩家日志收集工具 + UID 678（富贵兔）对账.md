## 一、需求

```text
测试（Patti）反馈：vendor_d 11 富贵兔，初始金额 1000、投注 5、旋转 554 局后余额不足，输 996.2，
问「是否正常」（UID：678）。
开发要求：发一下香港 vendor_d 的日志。
用户要求：**整理的日志和原始日志都要发飞机群**。
```

## 二、定位到的会话

```text
香港 vendor_d 两台后端（prod-01 192.0.2.16 / prod-02 192.0.2.17）各自处理了一部分请求，
同一天日志分别在 /data/server-runtime/logs/vendor_d/2026-10-07.log（容器内 /app/vendor_d/logs）。

账号 = ONCNYTEST_678（UID 678 拼在账号里；后端日志里 user_info.id 是 209354，与平台 UID 不是一回事）。
会话窗口：2026-10-07 06:43:54 ~ 07:22:35 UTC = **北京 14:43 ~ 15:22**。
单台行数：01 = 3,713 行；02 = 3,727 行；合并去重后 7,440 行（两台互补，不是重复）。
```

## 三、做法：新增可复用收集工具

```text
docker/deploy/hongkong/collect_game_user_logs.py（纯标准库，符合「docker/ 下不放 shell」的仓库规则）

  # 线上直连两台后端抓取（密码走 SSHPASS，与 hk_sync.py 同一约定）
  SSHPASS=... python3 collect_game_user_logs.py --vendor vendor_d --user ONCNYTEST_678 --date 2026-10-07
  # 离线合并（已经把日志拉到本地时）
  python3 collect_game_user_logs.py --user ONCNYTEST_678 --from-dir /tmp/hkops --out-dir /tmp/hkops/out

产出三个文件：
  merged.log   两台合并、按时间排序、去重（每行前缀 [host]，便于追溯来源）
  rounds.csv   解析 [SPIN_RESPONSE_AUDIT] 的逐局明细：time,round,bet,win,free_spins,start,end,wallet,buy_feature
  summary.md   对账摘要：局数、总投注、总赢、净变动、首尾余额、余额链是否连续、单局极值、RTP

只读操作；日志含 token，外发前确认接收方（本次是发到项目内部飞机群）。
```

## 四、对账结果（两队日志合并后）

| 项目 | 数值 |
| --- | --- |
| 游戏 | `prosperity-rabbit`（富贵兔，game 11） |
| 逐局审计条数 | 551 条 spin / **525 个唯一 round**（免费旋转会让 round 少于 spin，测试说的「554 局」口径不同） |
| 每局投注 | 5.00（551 局全部一致，无买免费 buyFeature=False） |
| 总投注 | 2755.00 |
| 总赢 | 1758.80 |
| **净变动** | **-996.20** ← 与测试反馈的「输 996.2」完全一致 |
| 余额 | 开局 1000.00 → 末局结束 **3.80**（不足 5 元继续下注 → 「余额不足」） |
| 余额链 | 逐局 start/end 首尾相接，**0 处缺口**（账目无漏记/错记） |
| 单局分布 | win>0 184 局 / win=0 367 局 / win<投注 470 局；单局 win 区间 [0.00, 200.00] |
| 本次会话 RTP | **63.84%**（总赢/总投注） |
| 风控配置（日志内） | 命中池「杀60%」脚本：`BASE_RATE 960`、`KILL_RATE 600`、`GIVE_RATE 1400`、`DYNAMIC_SCRIPTS [502,503,504]`、`AUTO` 见表 |

```text
结论：**账目是准的**（总赢、净变动、余额首尾都能与测试口径对上，且余额链连续）；
本次会话输得多（RTP 63.84%）与该玩家命中「杀60%」风控脚本、以及单次会话波动有关，
是否算「正常」请开发/游戏侧按该玩家的风控脚本与目标 RTP 判定。
```
