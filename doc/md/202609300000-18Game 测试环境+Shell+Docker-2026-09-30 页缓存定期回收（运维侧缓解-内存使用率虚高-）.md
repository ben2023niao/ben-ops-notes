# 2026-09-30 页缓存定期回收（运维侧缓解"内存使用率虚高"）

> GitHub 仓库源文件：[点击打开网页渲染版](https://github.com/ben2023niao/ben-ops-notes/blob/main/doc/md/202609300000-18Game%20%E6%B5%8B%E8%AF%95%E7%8E%AF%E5%A2%83%2BShell%2BDocker-2026-09-30%20%E9%A1%B5%E7%BC%93%E5%AD%98%E5%AE%9A%E6%9C%9F%E5%9B%9E%E6%94%B6%EF%BC%88%E8%BF%90%E7%BB%B4%E4%BE%A7%E7%BC%93%E8%A7%A3-%E5%86%85%E5%AD%98%E4%BD%BF%E7%94%A8%E7%8E%87%E8%99%9A%E9%AB%98-%EF%BC%89.md)

> 整理日期：2026-09-30 00:00｜日期依据：文件名日期

## 背景

Docker / Beszel 等监控把 **page cache 计入"已用内存"**，导致线上多台机器长期显示 80%+，
而 `MemAvailable` 一直很充裕（真实占用很低）。国庆前开发不发版、无法从应用侧减少日志写入量
（后端 `api_request` + `api_response` 每天约 5G），因此运维侧用定时回收页缓存来缓解。

实测（处理前 → 处理后，含 cache 口径）：

| 主机 | 处理前 | 处理后 | 真实占用 |
| --- | --- | --- | --- |
| 后端 16.209.16.108 | 88% | 19% | 9% |
| 网关 16.208.38.88 | 82% | 51% | 40% |
| 前端 13.208.101.121 | 58% | 41% | 35% |
| 宝塔 16.208.5.147 | 85% | 16% | 12% |

## 方案

脚本：`devops/scripts/youdianse-mem-cache-reclaim.sh` → 部署到 `/usr/local/sbin/`
cron：`7 * * * * /usr/local/sbin/youdianse-mem-cache-reclaim.sh`（每小时）
日志：`/var/log/youdianse-mem-reclaim.log`

**不是无脑清缓存**，只有同时满足以下条件才动手：

1. 「缓存计入后的使用率」≥ `MEM_RECLAIM_THRESHOLD`（**默认 50%**，2026-09-30 由 70% 下调）
2. 「真实可用内存」≥ `MEM_RECLAIM_MIN_AVAILABLE`（默认 15%）—— 确认没有真实内存压力
3. 先 `sync` 落盘，再 `echo 1 > /proc/sys/vm/drop_caches`（只回收 page cache）

否则记一条 `skip` 日志（已验证：占用降到 15% 时会正确跳过，不做无谓 I/O）。

### 阈值调整记录

| 日期 | 阈值 | 原因 |
| --- | --- | --- |
| 2026-09-30 初始 | 70% | 只在明显虚高时动手，尽量减少无谓 I/O |
| 2026-09-30 调整 | **50%** | 阈值 70% 时，含 cache 使用率长时间停在 60~65% 就永远不触发；运维侧要求提早就把数字拉回来 |

调整后同一时段（后端 16.209.16.108 实测）触发情况：
· 调整前：18:07 65%、19:07 65% → 连续 skip
· 调整为 50% 后：同样 65% 会直接触发回收（缓存 16.9G → 0.5G，可用内存 10G → 26G）

## 已部署

- 后端 16.209.16.108、网关 16.208.38.88、前端 13.208.101.121、宝塔 16.208.5.147（共 4 台）
- **未覆盖**：数据库主机（Mongo 主/从、Redis，内网 172.31.x，当前跳板不可直连）。
  如这些机器也出现"内存虚高"，需按同一脚本部署（或从可直连的机器上跳过去执行）。

## 注意事项

1. 这是**缓解手段**：缓存清掉后仍会随文件读写重新增长，只是每小时被拉回一次
2. 对 I/O 有轻微影响（热点文件需重新从磁盘读），阈值+可用内存双判断已把无谓回收降下来
3. **根治仍要开发侧**（节后）：减少 `api_request` / `api_response` 的日志量或采样
4. 若长期仍频繁触发回收，建议同时把监控告警口径从 `(总-空闲)/总` 改为 `总-可用`
