# 2026-09-25 香港 g759 等厂商端口不可达：GCP 防火墙端口范围修复记录

> 来源文件：`~/Projects/work/game/pgserver/cn/docker/doc/2026-09-25-1345-【修复Bug】香港g759等厂商端口不可达-GCP防火墙端口范围修复记录.md`

> 整理日期：2026-09-25 13:45｜日期依据：文件名日期

## 一、现象

```text
用户反馈：香港 g759 有点问题，怀疑 nginx 端口没映射对。
实测：https://g759-games.hkcloudplay06.com/ 、/health 均 502；
      standby nginx 错误日志：no live upstreams / upstream timed out（upstream 为 203.0.113.1:9019）。
```

## 二、排查过程（逐步排除）

```text
1) nginx 端口映射——**正确**：
   香港 standby：upstream dbqp_hk_standby_g759 -> 203.0.113.1:9019 / 203.0.113.1:9019
   巴西参照：upstream g759_game_backend -> 203.0.113.1:9019 / 203.0.113.1:9019
   server_name ~^g759-games\.hkcloudplay0[67]\.com$、proxy_pass 指向正确。
2) 容器与端口——**正常**：
   prod-02 game-service-g759-prod：status=running、restarts=0、发布 0.0.0.0:9019->9019；
   nsenter 进容器网络：4 个 worker 均 LISTEN 0.0.0.0:9019；
   容器日志有正常业务输出（User Sync 租期、total_rounds/total_bet 统计、Leader 竞选）。
3) 从 standby 探测后端端口——**9018/9019/9020 全部不可达**，而 9090 可达：
   => 问题在「standby -> 后端」的网络放行，而不是 nginx 或应用。
```

## 三、根因

```text
GCP 防火墙规则 dbqp-hk-allow-standby-to-backends（2026-09-24 创建）当时只放行：
  tcp:8765, tcp:9090-9104
其中 9090-9104 覆盖 api(9090)/pg(9091)/jili(9093)/ppk(9098)/pp(9099)，
但**没有覆盖 9018-9020**：
  panda 9018、g759 9019、playson 9020
=> 这三个厂商的域名从 standby 访问必然 502/504（g759 即用户反馈的现象）。
```

## 四、修复

```bash
gcloud compute firewall-rules update dbqp-hk-allow-standby-to-backends \
    --allow=tcp:8765,tcp:9018-9020,tcp:9090-9104

结果：allowed 由 "tcp:8765,tcp:9090-9104" 变为 "tcp:8765,tcp:9018-9020,tcp:9090-9104"
      （source 203.0.113.1/32、target tag hk-backend 不变）
```

## 五、验证

| 验证项 | 结果 |
| --- | --- |
| standby → 203.0.113.1 / 203.0.113.1 的 9018 / 9019 / 9020 | 全部**可达** |
| `https://g759-games.hkcloudplay06.com/health` | **200** |
| `https://g759-games.hkcloudplay07.com/health` | **200** |
| `https://g759-games.hkcloudplay06.com/`（根路径） | 404（应用形态，属正常） |
| `https://panda-games.hkcloudplay06.com/health` | **200** |
| `https://g759-static.hkcloudplay06.com/favicon.ico` 静态 | 200 |

说明：pg(9091) / ppk(9098) / pp(9099) 端口虽在放行范围内但仍不可达，
原因是这三个厂商容器在重启循环（数据库权限未开通），与本次防火墙问题无关；
api(9090) 一直正常。

## 六、遗留与建议

```text
1. 老入口机的规则 dbqp-hk-allow-baota-to-backends 同样是 tcp:8765,tcp:9090-9104，
   未含 9018-9020。老入口机目前走外部双后端（老域名现网）不受影响；
   若将来老入口机也切到自建后端，需要同样补 9018-9020（否则 g759/panda/playson 会 502）。
2. 新建后端相关防火墙规则时，端口范围应与 start.sh 的厂商端口表对齐：
   api 9090 / pg 9091 / jili 9093 / ppk 9098 / pp 9099 / panda 9018 / g759 9019 /
   playson 9020 / tada 9096 / tada_ws 8765。
3. 数据库权限开通后复查 pg/ppk/pp 是否恢复监听。
```

## 七、追加：香港防火墙统一开放（2026-09-25 13:10，用户要求「香港的都开一下防火墙」）

```text
把后端相关入站规则统一为「香港子网 -> hk-backend 全厂商端口」：
  gcloud compute firewall-rules update dbqp-hk-allow-baota-to-backends \
      --source-ranges=203.0.113.1/20 \
      --allow=tcp:8765,tcp:9018-9020,tcp:9090-9104
=> source 由 203.0.113.1/32 扩大为整个香港子网（覆盖入口机、standby、两台后端互访、
   以后新增的机器）；端口与 start.sh 的厂商端口表对齐。
  （standby 专用规则 dbqp-hk-allow-standby-to-backends 保留，内容相同，冗余但无害。）
```

最终香港 VPC 入站规则：

| `dbqp-hk-allow-standby-to-backends` | `203.0.113.1/32` | `hk-backend` | tcp:8765, 9018-9020, 9090-9104 |
| `dbqp-hk-allow-internal-admin` | `203.0.113.1/20` | `hk-baota,hk-backend` | tcp:22 |
| `dbqp-hk-allow-icmp` | `203.0.113.1/20` | `hk-baota,hk-backend` | icmp |
| `dbqp-hk-allow-beszel-agent` | `0.0.0.0/0` | `hk-baota,hk-backend` | tcp:45876 |
