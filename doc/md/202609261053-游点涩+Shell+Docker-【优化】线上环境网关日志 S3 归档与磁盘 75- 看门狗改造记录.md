## 一、背景与问题分析

```text
2026-09-26 网关 nginx 日志曾把 49G 根盘打满（100%），导致 HTTPS 回源中断、拨测连环告警。
当时已做两件事：清理日志 + logrotate 改为 daily+maxsize 2G+rotate 3。

复盘发现「日志归档」这条长期链路实际是空跑的：
· 归档脚本（ben-bot 宿主机 /usr/local/bin/youdianse-nginx-log-archive.sh）按 -mtime +7 取文件，
  即只归档「7 天前」的 .gz；
· 而网关 logrotate 是 maxsize 2G（当时每天 12-13G，约 6-7 次轮转/天）+ rotate 3，
  → 文件在 1-2 天内就被 logrotate 自己删掉了，永远等不到「7 天」；
· 归档日志佐证：连续多日输出「无 7 天前日志，跳过」。

因此本次目标：
· 日志长期留存到 S3，本地只留 1-2 天；
· 增加网关磁盘 >75% 自动清理看门狗 + 两群告警，避免再次打满。
```

## 二、改造一：日志落 S3 + 本地只留 1-2 天

```text
1. 网关 /etc/logrotate.d/nginx：rotate 3 → rotate 16
   备份：/root/logrotate-nginx-backup-20260926-024653.conf
   （保留足够多轮转文件供归档脚本上传；本地实际留存由归档脚本删除控制）
2. 归档脚本 /usr/local/bin/youdianse-nginx-log-archive.sh：-mtime +7 → +1（24 小时前）
   备份：/root/nginx-log-archive-backup-20260926-104653.sh
3. 归档频率：root cron `5 3 * * *` → `5 */6 * * *`（每 6 小时一次，平滑）。
4. 仓库同步：devops/scripts/youdianse-nginx-log-archive.sh（注释与阈值同步更新）。

验证（手动执行一次 /usr/local/bin/youdianse-nginx-log-archive.sh）：
  [02:47:03] 已上传 S3 并删除本地：error.log.6.gz（http=200）
  [02:47:23] 已上传 S3 并删除本地：access.log.3.gz（http=200，480MB）
  [02:47:25] 已上传 S3 并删除本地：error.log.7.gz（http=200）
  [02:47:26] 已上传 S3 并删除本地：error.log.8.gz（http=200）
  [02:47:28] 已上传 S3 并删除本地：error.log.5.gz（http=200）
  → 网关 /var/log/nginx 仅剩当前日志与最近轮转件，磁盘 46% → 38%
```

## 三、改造二：磁盘 >75% 自动清理看门狗

### 3.1 网关本地看门狗

```text
脚本：/usr/local/sbin/youdianse-gateway-disk-guard.sh（源文件同步至仓库 devops/scripts/）
cron：root `*/10 * * * *`（每 10 分钟）
日志：/var/log/youdianse-disk-guard.log

分级处置逻辑（当前使用率 <75% 时直接退出，不产生任何动作）：
  1) 删除旧压缩日志（*.gz）只保留最新 6 份；未压缩轮转件只保留最新 2 份；
  2) 仍 ≥75% → journalctl --vacuum-size=500M；
  3) 仍 ≥75% → 逐个截断「大于 1MB」的历史轮转日志（最多 10 轮，且校验截断确实生效）；
  4) 仍 ≥90% → 先取样本（tail 20 万行压缩到 /root）再截断当前 access.log + nginx -s reopen，
     并执行 docker builder prune --filter until=24h（只清构建缓存，不动运行容器）。
```

### 3.2 两群告警接入（CC 守卫）

```text
文件：devops/scripts/cc_guard/youdianse_cc_guard.py（ben-bot 运行机同名路径）
· gateway_metrics() 增加 disk 指标（df -P /）；
· 新增磁盘告警：≥75% 时向 18game运维 + 18GAME_ 上线群（正式環境）发送告警，冷却 1 小时
  （阈值可用环境变量 CC_DISK_ALERT_PERCENT 调整）；
· CHECK 日志新增 disk=xx% 字段，便于长期观察。
备份：/root/cc_guard-backup-20260926-105243.py
```

### 3.3 验证

```text
1. 真实阈值运行（38% < 75%）：无任何动作，exit=0
2. 临时目录强制测试（THRESHOLD=1，LOGDIR=/tmp/dg-test）：
   正确识别 5MB 历史日志 → 截断 → 正常退出（exit=0），未误删当前日志
3. 告警分支验证（临时把阈值降到 10%，拦截 telegram 输出，未真发群）：
   收到 1 条「【线上环境｜磁盘告警】网关根盘使用率过高 … disk=38%（阈值 10%）」
4. 守卫实跑：CHECK … disk=38% … 无告警（符合预期）
```

### 3.4 过程失误与修复（如实记录）

```text
首版看门狗脚本在「临时低阈值」测试时出现死循环：反复截断已经是 0 字节的轮转文件
（使用率永远 ≥1%，脚本无法收敛），持续约 4 分钟，产生了 2.1MB 日志、CPU ~10%。
处置：
  · 立即 pkill 终止脚本、清空被撑大的看门狗日志；
  · 确认影响范围：nginx active、业务容器未受影响、磁盘 38%、仅一个历史轮转件被截断；
  · 修复：只截断「大于 1MB」的文件、最多 10 轮、截断后校验文件确实变小才继续、
    新增 LOGDIR 变量以便用临时目录安全测试。
复盘：破坏性自测必须先在沙箱目录验证，不能直接对生产路径跑低阈值。
```

## 四、回滚

```text
· 网关 logrotate：恢复 /root/logrotate-nginx-backup-20260926-024653.conf → logrotate -d 校验
· 归档脚本：恢复 /root/nginx-log-archive-backup-20260926-104653.sh → 还原 cron 为 5 3 * * *
· 看门狗：删除网关 root crontab 中 `*/10 … youdianse-gateway-disk-guard.sh` 一行；
  必要时删除 /usr/local/sbin/youdianse-gateway-disk-guard.sh
· 守卫磁盘告警：把 CC_DISK_ALERT_PERCENT 设大（如 999）或恢复 /root/cc_guard-backup-20260926-105243.py
```
