## 一、整体技术方案（分层架构）

```text
用户（H5/PC/APP/SDK游戏）
  │
  ▼
CDN 入口（AWS CloudFront / 腾讯 EdgeOne·CDN，HTTPS 终止，回源按域名分流）
  │
  ▼
入口/网关层
  ├─ 线上新网关 16.208.38.88（nginx 按 UA 分流：手机→H5 3003、电脑→PC 3004；
  │     /api|channel|customer 反代宝塔内网 203.0.113.1）
  ├─ 线上宝塔 16.208.5.147（老 H5/PC、admin 后台、域名证书 vhost、/api 反代后端）
  └─ 日本前置 138.252.248.139（备用回源候选）
  │
  ▼
应用层（容器）
  ├─ H5 Nuxt SSR（3003） / PC Nuxt SSR（3004）—— 前后端分离，SSR + S3 静态
  ├─ PHP API（Phalcon 7.4，web 容器 8088→9000）—— 业务接口、SDK、支付、后台
  └─ cron 容器 —— 定时任务、队列消费、大数据上报、小时报告
  │
  ▼
数据层（线上独立主机）
  ├─ MongoDB（用户/订单/游戏/配置/日志集合）
  ├─ Redis（缓存/会话/token/队列，db 分 index）
  └─ 大数据上报：logbus2 → big_data_job 队列 → 入库/报告（Spug 调度）
```

**发布链路**：GitLab（web/h5/pc 仓库）→ Webhook → CICD 平台（自研 Python/Tornado/PyWebIO）→ Docker 构建 → 多环境容器发布 → 版本/接口回传群。

**自动化/工具层**：ben-bot（Telegram 机器人：发布入口、域名维护、SSL 续签、值班、文档）、域名维护脚本、磁盘清理定时任务、监控告警、日志持久化。

## 二、技术栈与技能矩阵（尽量写全）

### 2.1 云平台与网络
| 技术 | 技能点 | 深度 |
| --- | --- | --- |
| AWS | EC2 实例/机型选择与扩容、S3 静态桶、CloudFront 分发/回源/缓存、VPC/内网、快照/AMI、IAM 最小权限 | 必需 |
| 腾讯云 | COS、CDN/EdgeOne 刷新与回源、备案 | 必需 |
| DNS/域名 | DNSPod、Gname/注册商、Cloudflare、A/CNAME/NS、TXT 校验、**防链路风险验证（域名锁/双因素/变更审计）** | 必需（重点） |
| 网络排查 | TCP/TLS/HTTP2、连接/端口/TIME_WAIT、回源链路、丢包/延迟、curl/dig/openssl/mtr | 必需 |

### 2.2 Linux 与容器
| 技术 | 技能点 | 深度 |
| --- | --- | --- |
| Linux | Ubuntu/Debian、systemd、用户/权限、磁盘/LVM、日志轮转、文件句柄/内核参数（sysctl：端口范围/tw_reuse/file-max） | 必需 |
| Docker | Dockerfile 优化、Compose 编排、镜像构建/缓存/清理、容器网络/端口、日志、健康检查、重启策略 | 必需 |
| 发布流水线 | GitLab CI/Webhook、多环境镜像 tag、蓝绿/回滚思路、发布日志与守护 | 必需 |

### 2.3 Web 与中间件
| 技术 | 技能点 | 深度 |
| --- | --- | --- |
| Nginx | server/location/反代/分流（UA）、SSL/SNI/证书链、X-Forwarded-For/realip、worker_connections/rlimit、缓存、sub_filter、rewrite/301、健康检查 | 必需（重点） |
| PHP | PHP-FPM 调优（pm/opcache/memory）、Phalcon 框架运维、composer 依赖、慢日志/错误日志 | 必需 |
| Node | Nuxt/Nitro SSR 部署、PM2、SSR 缓存（SWR）与用户 IP 透传、前端构建（pnpm） | 加分/需配合前端 |
| MongoDB | 慢查询/索引、聚合、备份/恢复、oplog、连接数、副本集思路 | 必需 |
| Redis | 缓存设计、大 Key/热 Key、连接池/端口治理、持久化、Lua 基础 | 必需 |
| 队列/任务 | big_data_job 消费、幂等/去重、Spug 定时调度、失败重试与积压监控 | 必需 |

### 2.4 自动化与开发
| 技术 | 技能点 | 深度 |
| --- | --- | --- |
| Python | 运维脚本、requests/urllib、subprocess、JSON/YAML、定时任务、Web 小工具 | 必需（优先） |
| Shell | bash 脚本、ssh/scp 批处理、cron、日志处理 | 必需 |
| Telegram Bot | bot API、按钮/回调、群通知、消息编辑/分页 | 加分（已自建） |
| Web 小系统 | Tornado/PyWebIO/Flask 一类，能维护 CICD 控制台 | 加分 |
| 版本管理 | Git 分支/合并/revert、GitLab API、Webhook 签名 | 必需 |

### 2.5 监控、日志与安全
| 技术 | 技能点 | 深度 |
| --- | --- | --- |
| 监控 | Beszel（现有）、CPU/内存/磁盘/网络告警、拨测（页面/接口/支付成功率） | 必需（可补强） |
| 日志 | 应用/nginx/容器日志、持久化与轮转、关键字告警、慢日志分析 | 必需 |

### 2.6 软技能与值班
- 7×24 值班意识、15 分钟内响应、独立处置常见故障；
- 文档沉淀（每次故障必写复盘）；
- 跨部门协作（前端/后端/发行/HR/老板）；
- 抗压、冷静、善于复盘与改进。

## 三、高级运维 JD（完善版）

### 岗位名称
高级运维工程师 / 运维开发工程师（SRE 方向）

### 岗位职责
1. 负责平台线上环境（H5/PC/后台/SDK 游戏）稳定运行：发布、监控、故障、值班；
2. 持续建设自动化：CICD 发布、域名/证书、巡检、告警、值班机器人、运维看板；
3. 容量与性能：QPS/CPU/内存/Redis/Mongo 瓶颈定位与调优、扩容与压测；
4. 安全与容灾：DNS/注册商加固、证书、备份快照、故障演练、备用通道；
5. 参与 7×24 值班，独立处置常见故障，重大事件 30 分钟内升级；
6. 每起故障输出复盘文档，持续完善 SOP。

### 任职要求
**硬性（必需）**
1. 3 年以上 Linux 运维 / SRE 经验，熟练 Python 或 Shell 编写自动化；
2. 精通 Nginx 反代/分流/SSL 与 PHP-FPM 调优，能独立定位 500/超时/连接打满问题；
3. 熟悉 Docker/Compose 与 CI/CD（GitLab 或 Jenkins 一类）；
4. 熟悉 MongoDB 与 Redis 运维（慢查询、索引、大 Key、连接治理）；
5. 熟悉 DNS/TLS/CDN 与云平台（AWS 或腾讯云），有域名安全/防链路风险验证意识；
6. 能接受排班值班，文档习惯好，响应快、抗压。

**加分项**
- Telegram 机器人 / 监控平台（Prometheus/Grafana/Beszel）落地经验；
- Nuxt/Node SSR、Phalcon/PHP、大数据上报链路经验；
- 自研过发布平台或运维控制台；
- 有游戏/支付类业务运维经验。

### 薪资与职级建议
- 按市场高级运维/运维开发区间（建议 HR 按当地行情给范围，可因“要能独立处理问题 + 会写自动化”适当上浮）；
- 试用期考核：能否独立完成一次发布、一次故障定位、一个自动化脚本。

## 五、缺失与短板（需要人补/需要招的方向）

1. **自动化/运维开发**（最缺）：能写脚本/维护 CICD 与机器人，把人工操作继续工具化；
2. **深度故障定位**：能独立啃“连接/内核/中间件”类疑难（如本次 Redis 端口、nginx 打满）；
3. **监控/可观测性**：拨测、告警分级、值班联动；
4. **安全方向**：DNS/注册商加固、凭据管理、事件响应演练；
5. **值班人力**：4 人排不满 24h，需补人后真正 7×24 覆盖。

## 六、可优化点清单（按优先级）

### P0（建议尽快）
1. **DNS/注册商加固**：开启域名锁/两步验证、DNS 变更审计与告警、备用权威 DNS（防再次链路风险验证）；
2. **24h 值班落地**：按 0900 文档排班方案试排，补人前先“组长监督 + 两组轮值 + 问题升级”；
3. **发布门禁**：分支/版本强校验、正式包禁止测试域名（8-20 教训）、一键回滚按钮。

### P1（重要）
4. 后端/网关高可用：备机或容器编排，快照演练；
5. 业务级拨测：页面/核心接口/支付回调成功率，告警转群；
6. 慢查询与大 Key 巡检自动化（Mongo/Redis）；
7. 老 H5 4C/8G、ben-bot 4C/8G 升级。

### P2（持续）
8. Prometheus/Grafana 落地（可选，与 Beszel 并存）；
9. 每月容灾演练 + 故障手册；
10. 值班看板与一键 SOP 按钮；
11. 文档与知识库持续完善。

## 七、招聘补充建议

- **优先补 1 名“运维开发/自动化”**（会 Python + CICD + 机器人），直接缓解自动化与人手矛盾；
- **其次补 1 名“SRE/高级运维”**（Linux/Nginx/PHP/中间件深度），补齐疑难故障与 24h 值班；
- 有安全背景者优先（DNS/防链路风险验证/事件响应）；
- 试用期以“独立发布 + 独立定位一次故障 + 交付一个自动化脚本”为验收标准。

## 八、会议口径（补充）

1. 开场先摆“技术方案 + 自动化 + 监控 + 容灾 + 复盘”，展示完成度；
2. 再给“缺失与可优化清单”（第五节/第六节），口径是“方向明确、可优化空间有限且可量化”；
3. 24h 值班给出真实缺口与排班方案，说明“先排、排不过来再招”；
4. 招聘按第三节 JD，强调“能独立处理问题 + 会写自动化”；
5. 中台对外：名义两边管理，实际靠制度与监控完善自保（见 0900 文档第十一节）。
