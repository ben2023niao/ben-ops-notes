# 【优化+问题排查】结果集权限被改坏的原因定位 + 权限自愈监控上线

> 公开版脱敏说明：公司、平台、节点、账号、地址和业务对象均已替换为示例标识；替换后的名称仅用于公开复盘。

> 来源：本地项目文档 `game/pgserver/master/docs/history/2026-09-24-1540-【优化+问题排查】结果集权限被改坏原因定位与权限自愈监控上线记录.md`
> 整理：2026-11-09。仅复制到知识库，未改动原项目文件；敏感凭据已脱敏。

时间：2026-09-24 15:40（北京时间）/ 07:40（UTC）
对象机器：后台 01 `192.0.2.1`、后台 02 `192.0.2.1`（打包机 03 `192.0.2.1` 按用户要求**不装**）
问题：开发反馈「两台后台都没一个游戏能玩，看着像文件夹权限没对」
结论：**发版/补数据时用 `rsync -a` 从打包机 03 拉 `/data/server-runtime`，
　　　把源端的 `root:root` + 644/755 权限一起覆盖到 01/02；而容器里的业务进程
　　　是以 `appuser(uid=1000)` 跑的，SQLite 需要结果集目录可写（建 -wal/-shm、写 .db），
　　　属主变成 root 后写不进去 → 所有厂家游戏都下不了注。**
处置：① 已修复 01/02 权限；② 上线「权限自愈 + 飞机群告警」定时任务（01/02，每 2 分钟）。
用户明确要求：**只装 01/02，不动 CDN 上的 Worker**。

---

## 一、现象与结论

```text
现象：01、02 两台全部厂家游戏无法下注（不是单个游戏、不是单个厂家）。
结论：结果集目录 /data/server-runtime/game_result_datas 的属主/权限被改成了 root:root，
      容器内以 uid 1000(appuser) 运行的业务进程失去写权限。
点名验证：容器里 `docker exec game-service-pg-prod id` → uid=1000(appuser) gid=1000(appuser)。
```

## 二、根因：从打包机 rsync -a 把 root:root 覆盖了过来

### 1. 直接触发动作（人为操作，非自动任务）

```text
02 上执行的命令（补结果集/发版流程）：
  rsync -avz --delete --exclude 'logs' --exclude '*.db-shm' --exclude '*.db-wal' \
        root@192.0.2.1:/data/server-runtime /data/

rsync 的 -a 隐含 -rlptgoD，其中 -p 保留权限、-o/-g 保留属主属组；
以 root 身份执行时，就会把源端（打包机 03）的 root:root 与 644/755 原样写到 01/02。
```

### 2. 证据

```text
① 打包机 03（源端）本身就是 root:root，权限更严：
     drwxr-xr-x root:root  /data/server-runtime/game_result_datas
     drwxr-xr-x root:root  /data/server-runtime/game_result_datas/pg
     -rw-r--r-- root:root  /data/server-runtime/game_result_datas/pg/pg_1.db   (644)
② 01/02 同步后同样出现大批 root:root 条目：
     01：game_result_datas 1006 个条目里 742 个属主不是 uid1000
     02：game_result_datas 1106 个条目里 882 个属主不是 uid1000
③ 时间线对得上：
     03 上 share.so / server_configs 的 ctime = 2026-09-23 08:35（打包完成）
     01 上同两个文件 ctime = 2026-09-23 08:37:59 → 说明 01 是在这个时刻被 rsync 覆盖的
④ 今天早上有人把权限手工改回了 777（ctime = 07:00:55(01) / 07:00:28(02)），
   所以现在看到的是 777，但**属主仍然是 root**，属于“能用但不规范”的临时状态。
```

### 3. 这个坑以前就踩过，仓库里早有记录

```text
docker/scripts/sync_game_results_data.py 里的注释原文：
  「容器内业务进程以 appuser(uid=1000) 运行，SQLite WAL 需要在结果集目录创建 -wal/-shm。
    若目录/文件属主不是 uid1000 或目录不可写，会出现 “attempt to write a readonly database /
    建立只读连接失败”。本函数在每次 rsync 后自动 chown/chmod，避免再次出现同类线上问题。」
它给 rsync 加了 --chown=1000:1000，并在同步后执行 chown -R 1000:1000 + chmod -R u+rwX,go+rX。
—— 本次出问题的命令是手写 rsync，没带 --chown，也没有后续 chmod，所以又踩了一遍。
```

## 三、处置一：先把 01/02 修好

```text
把 /data/server-runtime/game_result_datas 与 /data/server-runtime/logs
修成「属主 1000:1000 + 至少 owner 可读写」：
     chown -R 1000:1000 <目录>
     chmod -R u+rwX    <目录>
结果：01 修复 742 个异常条目、02 修复 882 个，修复后剩余 0；回归验证全部正常。
```

## 四、处置二：上线「权限自愈 + 飞机群告警」定时任务（只装 01/02）

### 1. 脚本

```text
仓库：docker/scripts/fix_result_perms.sh
部署：01/02 的 /opt/bizops-scripts/fix_result_perms.sh（0755）
（03 的脚本副本已按用户要求删除；03 目前无该定时任务）
```

行为：

```text
· 每 2 分钟检查 /data/server-runtime/game_result_datas 与 /data/server-runtime/logs
  （maxdepth 3，约 1000 个条目，find 毫秒级）；
· 只有发现「属主不是 1000:1000」或「目录缺 owner-x / 文件缺 owner-w」才动手修：
      chown -R 1000:1000 <目录> && chmod -R u+rwX <目录>
  —— 只加不改：不缩小 group/other 位，避免影响其它读取方；
· 一旦发生修复，**立即发飞机群告警**（@运维 @Ben_Bird @benb6879），带上机器/目录/异常条目数/样例行；
· 同一台机器 10 分钟内最多发一条（NOTIFY_MIN_INTERVAL），避免反复被改时刷屏；
· 一切正常时不写日志、不动元数据，只每小时留一条心跳。
```

### 2. 定时任务（systemd）

```text
/etc/systemd/system/bizops-result-perms.service   （Type=oneshot，调脚本）
/etc/systemd/system/bizops-result-perms.timer     （OnBootSec=2min + OnUnitActiveSec=2min）
已执行：systemctl daemon-reload && systemctl enable --now bizops-result-perms.timer
两份 unit 文件同时存仓库：docker/scripts/systemd/bizops-result-perms.{service,timer}
```

## 六、运维手册（手动操作）

```text
# 看当前有没有异常（只看不改）
DRY_RUN=1 /opt/bizops-scripts/fix_result_perms.sh ; tail -5 /var/log/bizops-result-perms.log

# 立刻修一遍（不等定时器）
/opt/bizops-scripts/fix_result_perms.sh

# 只想验证飞机群通道能不能收到（发一条“测试”，不改权限）
TEST_NOTIFY=1 /opt/bizops-scripts/fix_result_perms.sh

# 想看告警在群里的样式（用【同一套模板】的假数据发一条“模拟演练”，不改权限、不写限流状态）
SIMULATE=1 /opt/bizops-scripts/fix_result_perms.sh
# 还可以自定义演练内容，例如演示“没修干净”的那种
SIMULATE=1 SIM_DIR=/data/server-runtime/logs SIM_BAD=3 SIM_TOTAL=65 SIM_LEFT=12 \
  /opt/bizops-scripts/fix_result_perms.sh

# 临时不告警（比如已知在做迁移，不想刷屏）
NOTIFY=0 /opt/bizops-scripts/fix_result_perms.sh

# 看定时器 / 看历史
systemctl list-timers bizops-result-perms --no-pager
journalctl -u bizops-result-perms -n 50 --no-pager
tail -20 /var/log/bizops-result-perms.log

# 临时停用 / 恢复
systemctl stop bizops-result-perms.timer && systemctl disable bizops-result-perms.timer
systemctl enable --now bizops-result-perms.timer
```

## 七、顺带发现 / 建议（未执行，等确认）

```text
1) 更彻底的修法（推荐）：发版同步命令统一加 --chown=1000:1000，
   或直接用仓库里的 docker/scripts/sync_game_results_data.py（它自带修正逻辑）。
   现在有自愈兜底，属主被覆盖后 2 分钟内会自动改回来，但“报警+自愈”毕竟是被动补。
2) 也可以把打包机 03 的 /data/server-runtime 同名目录一起纳入自愈，
   这样源头就是 uid1000，同步过去天然正确（本次按用户要求只在 01/02 装）。
3) 权限位现状：结果集目录目前是 777（世界可写）。自愈脚本只加不减，没动它。
   若要收紧，建议对齐官方写法 chmod -R u+rwX,go+rX（属主 1000，别人只读）。
4) 域名 pg4-static.* 抽查：22 个根域名逐个测，只有 pg4-static.m6xv8q.cyou
   第一次请求超时（curl http=000），复测 200 但耗时 7.1s（其它域名 2~3s 内），
   证书正常（CN=m6xv8q.cyou，有效期到 2026-11-08）。属偶发/冷启动偏慢，
   如需深挖要在 Cloudflare 侧看该域名命中情况——**Worker 是开发维护的，本次未做任何改动**。
```
