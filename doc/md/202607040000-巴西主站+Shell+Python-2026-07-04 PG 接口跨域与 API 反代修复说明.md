# 2026-07-04 PG 接口跨域与 API 反代修复说明

> 公开版脱敏说明：公司、平台、节点、账号、地址和业务对象均已替换为示例标识；替换后的名称仅用于公开复盘。

## 这份文档解决什么问题

这份 prompt 给后续 AI / 运维同学快速接手 PG 麻将胡了（PG65 / Mahjong Ways）“未能成功启动 / N1000PHFIYR04 / CORS / 520”问题使用。

核心结论：

- `pg-games.<root>` 的游戏页面和 `pg4-static.<root>` 静态资源已经正常。
- 真正导致 PG65 启动失败的是新版 PG 客户端从 `pg-games.xqv9m8.icu` 跨域请求 `api.xqv9m8.icu` 的 verify 接口。
- 修复前 `api.xqv9m8.icu` 没有被当前宝塔活跃 Nginx 站点接住，Cloudflare 返回 520，浏览器表现为 CORS 缺失。
- 已通过 Docker 运维侧修复：PG 活跃反代站点同时接 `pg-games.*` 和 `api.*`，并统一补 CORS。

注意：不要在群里、文档里、提交里粘贴 JWT、ticket、cookie、商户密钥、用户 login token。需要说明时只写脱敏摘要。

## 用户侧现象

游戏弹窗：

```text
未能成功启动
未能连接到服务器，请检查您的网络或重试。
错误代码：N1000PHFIYR04
```

浏览器 Console 关键报错：

```text
Access to XMLHttpRequest at
https://api.xqv9m8.icu/web-api/auth/session/v2/verifyOperatorPlayerSession?traceId=...
from origin https://pg-games.xqv9m8.icu
has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.

Failed to load resource: net::ERR_FAILED
https://api.xqv9m8.icu/web-api/auth/session/v2/verifyOperatorPlayerSession?traceId=...

Failed to load resource: the server responded with a status of 520
https://api.xqv9m8.icu/api/report/timing
```

容易误判的噪音：

```text
https://pg-games.xqv9m8.icu/cdn-cgi/rum? -> 404
```

`/cdn-cgi/rum` 是 Cloudflare Browser Insights / RUM 埋点，不是 PG 登录或 verify 业务接口。它会在 Console 里红，但不是这次“未能连接到服务器”的主因。

## 根因

新版 PG 客户端有这个行为：

- 页面入口：`https://pg-games.xqv9m8.icu/65/index.html?...`
- 静态资源：`https://pg4-static.<root>/65/...`
- verify 接口：`https://api.xqv9m8.icu/web-api/auth/session/v2/verifyOperatorPlayerSession?...`
- report 埋点：`https://api.xqv9m8.icu/api/report/timing`

宝塔当前活跃站点在修复前是：

```text
/www/server/panel/vhost/nginx/pg-games.xqv9m8.icu.conf
```

该站点只包含：

```text
pg-games.* 22 个域名
```

历史 `api.*` 站点文件存在，但文件名是禁用态：

```text
api.xqv9m8.icu.conf.category-split-disabled-20260612_174254
api.q7m9v8.icu.conf.category-split-disabled-20260612_174254
...
```

这些 `.category-split-disabled-*` 文件不会被 Nginx 加载。

因此 `api.xqv9m8.icu` 请求经过 Cloudflare 到源站时，没有有效活跃 Nginx server block 接住，表现为 Cloudflare 520；浏览器自然拿不到 `Access-Control-Allow-Origin`，于是报 CORS。

### 域名同步脚本

文件：

```text
docker/线上服务器信息/baota/scheduled-tasks/sanitized/sync_all_game_domains_to_baota.py
```

新增逻辑：

```text
PG_API_PREFIX = "api"
```

PG game 站点域名从：

```text
22 个 pg-games.*
```

扩展为：

```text
22 个 pg-games.* + 22 个 api.*
```

当前 PG 活跃站点 id：

```text
35
```

修复后宝塔 `site.db` 中：

```text
22 个 api.* 全部 pid=35
```

注意：`platform-api/conf/domains/pg.json` 的 `game_hosts` 仍然只应是 `pg-games.*`。`api.*` 是 PG 客户端内部 verify/API host 兼容，不应作为 launcher host 暴露给用户。

### 公共反代配置

文件：

```text
docker/线上服务器信息/baota/nginx/panel-vhost-nginx/common/all-games-proxy.conf
```

新增/调整点：

1. `api.*` host 路由到 `pg_game_backend`。

```nginx
if ($host ~ "^api\.") { return 418; }
```

2. `OPTIONS` 预检直接返回 204。

```nginx
if ($request_method = OPTIONS) {
    add_header Access-Control-Allow-Origin "*" always;
    add_header Access-Control-Allow-Methods "GET, POST, OPTIONS" always;
    add_header Access-Control-Allow-Headers "*" always;
    return 204;
}
```

3. `@pg_game_backend` 统一补 CORS 响应头，并隐藏上游已有 CORS 头，避免重复或 `Allow-Credentials` 与 `*` 冲突。

```nginx
proxy_hide_header Access-Control-Allow-Origin;
proxy_hide_header Access-Control-Allow-Methods;
proxy_hide_header Access-Control-Allow-Headers;
proxy_hide_header Access-Control-Allow-Credentials;
add_header Access-Control-Allow-Origin "*" always;
add_header Access-Control-Allow-Methods "GET, POST, OPTIONS" always;
add_header Access-Control-Allow-Headers "*" always;
```

4. `/api/report/timing` 直接返回 204，消除 Console 里的 520 噪音。

```nginx
location = /api/report/timing {
    add_header Access-Control-Allow-Origin "*" always;
    add_header Access-Control-Allow-Methods "GET, POST, OPTIONS" always;
    add_header Access-Control-Allow-Headers "*" always;

    if ($request_method = OPTIONS) {
        add_header Access-Control-Allow-Origin "*" always;
        add_header Access-Control-Allow-Methods "GET, POST, OPTIONS" always;
        add_header Access-Control-Allow-Headers "*" always;
        return 204;
    }

    return 204;
}
```

## 修复后复测结果

```bash

  -X OPTIONS 'https://api.xqv9m8.icu/web-api/auth/session/v2/verifyOperatorPlayerSession?traceId=TEST' \
  -H 'Origin: https://pg-games.xqv9m8.icu' \
  -H 'Access-Control-Request-Method: POST' \
  -H 'Access-Control-Request-Headers: content-type'
```

结果：

```text
access-control-allow-origin: *
access-control-allow-methods: GET, POST, OPTIONS
access-control-allow-headers: *
```

### Verify 空参数 POST

命令：

```bash
curl -sS -D - -o /dev/null \
  -X POST 'https://api.xqv9m8.icu/web-api/auth/session/v2/verifyOperatorPlayerSession?traceId=TEST' \
  -H 'Origin: https://pg-games.xqv9m8.icu' \
```

## 后续排查提示

如果测试仍反馈 PG65 进不去：

1. 先让测试刷新浏览器缓存或无痕窗口重试。
2. Network 里先排除 `/cdn-cgi/rum?`。
3. 重点看第一条非 RUM 红色请求：
   - `api.<root>/web-api/auth/session/v2/verifyOperatorPlayerSession`
   - `api.<root>/web-api/auth/session/v2/verifySession`
   - `pg-games.<root>/game-api/<slug>/v2/GameInfo/Get`
   - `pg-games.<root>/game-api/<slug>/v2/Spin`
4. 如果 verify 已经 200，但游戏仍失败，把 verify 响应体脱敏后检查：
   - `dt.gm[0].gid` 是否为当前 `gi=65`
   - `dt.geu` 是否指向当前 API/game host
   - `dt.bau` / `dt.lau` 是否是当前 host

另一个开发侧疑点：

```text
pg/data/operator/65/verifyOperatorPlayerSession.json
pg/data/verifySession/65/verifySession.json
```

模板内 `gm[0].gid` 当前固定为 `1543462`，不是 `65`。`pg/server.py` 里 operator verify 的动态覆盖代码仍是注释状态：

```python
# verify_data["dt"]["gm"][0]["gid"] = gameid
```

如果新版 PG 客户端校验 `gm[0].gid`，这会继续导致 PG65 或其他 PG 游戏异常。这个属于开发业务代码修复范围，运维侧不应直接改 `pg/server.py`，除非用户明确授权。
