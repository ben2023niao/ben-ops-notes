## 一、为什么必须"迁桶"而不是"改 Worker"

巴西玩家访问静态资源慢，根因是桶在日本。Cloudflare Worker 的 `BUCKET_MAP` 只能指定桶名，
不能指定区域；GCS **不支持修改桶的区域，也不支持桶改名**。所以只能：

```text
1) 新建 <桶名>-sa（巴西南美东1）
2) 删除 <桶名>（日本大阪）
3) 把 -sa 复制成 <桶名>（巴西；GCS 不支持改名，只能同区复制）
4) 删除 <桶名>-sa
→ 最终只保留巴西的同名桶，Worker / CDN 域名 / 桶名全部不用改
```

已经在巴西的厂家（历史迁移过一部分的）：**只做「校验 + 补全」，绝不删桶**，避免把线上桶删成空桶。

## 二·补、迁移后的全量校验（S3 ETag ↔ GCS md5，零数据搬运）

用 `s3_gcs_sdk_sync.py --verify-only` 对 17 家做了元数据全量比对，结论：

```text
· 全部 17 家：迁移本身零丢失 —— 迁移前后同名桶对象数一致，-sa 删除前都做过集合包含校验
· 与 AWS S3 源比对后做了一次「查缺补漏」：只补"S3 有、GCS 完全没有"的对象
    tada-statics 补 420 个、playson-static 补 1 个，其余 15 家 0 缺失；补完再跑一遍
    17 家全部「无差异，已是最新」，缺失对象清零（新增 s3_gcs_sdk_sync.py --only-missing）
· 仍然存在、但**故意没有动**的差异（属于内容新旧版本不一致）：
    tada-statics 5801、pp-static 5125、tada-statics1 444、tada-statics2 136、
    tada-statics3 13、ppk-static 25、pg6-static / playson-static / panda-static 各 1
  为什么不自动覆盖：迁移是服务端 rewrite，会把对象的 GCS 更新时间刷成"今天"，
  已经没有可靠的时间戳判据来判断 S3/GCS 谁更新；而业务上既存在「开发传 S3、我们同步 GCS」，
  也存在「开发直接传 GCS」两种情况，盲目以 S3 覆盖可能把新版本回退。
  要覆盖的话执行（会把 S3 版本推到 GCS，并补 health.json）：
      bash /opt/dbqp-scripts/gcs-br/gapfill_all.sh      # 只补缺失（安全，默认用这个）
      docker run ... s3_gcs_sdk_sync.py --prefix <厂家> --apply   # 全量覆盖
```

## 四、踩坑记录（重点，别再犯）

1. **`Blob.rewrite` 的调用方向会搞反，且失败得非常隐蔽**
   - 语义：`A.rewrite(B)` 是 **把 B 搬到 A**（参数才是源对象），不是 A→B。
   - 后果：写成 `src.rewrite(dst)` 时，实际是"读 dst、写 src"。如果 dst 是刚建好的空桶，
     就会 100% 404 失败；如果 dst 里恰好有同名对象，就会**看起来有进度、实则什么都没搬**。
   - 本次实测证据：`src.rewrite(dst)` 报
     `404 .../b/<dst>/o/<obj>/rewriteTo/b/<src>/o/<obj>: No such object: <dst>/<obj>`。
   - 对策：`br_vendor_move.py` 增加 **搬运方向自检（金丝雀）**——正式搬运前先搬 1 个对象，
     确认目标桶真的出现了该对象才开跑；两种方向都试，哪个能写进目标就用哪个，都不行直接报错退出。

2. **SDK 默认 HTTP 连接池太小，直接把吞吐压死**
   - `google-cloud-storage` 用 requests 的 `HTTPAdapter(pool_maxsize=10)`；
     几十个线程并发时只有 10 条连接被复用，其余每条请求都要重做 TLS 握手。
   - 对策：把 `client._http` 的 adapter 换成 `pool_connections=64+, pool_maxsize=256`。
   - 修复后：**20 对象/s → 320~340 对象/s（约 16 倍）**。

3. **`gsutil -m rm` 会 fork 大量子进程，多厂家并发能把 8 核打满**
   - 15 家同时 `gsutil -m rm` → load 41、CPU 饱和，把关键路径的复制拖到 20 对象/s。
   - 对策：改用**编译版** `gcloud storage rm -r --quiet`（单进程、轻量），并把收尾并发降到 3。

4. **`client.batch()` 在 google-cloud-storage 3.x 已经坏了**
   - 调用直接抛 `KeyError: "Cannot get('items', default=()) on a future"`。
   - 对策：不要用 batch 删除；逐对象删只作为兜底。

5. **删桶前必须先清空对象**
   - 桶非空时 `buckets.delete` 会失败（或被静默吞掉），留下"空壳桶"，
     后续"重建同名桶"直接跳过 → 假完成、线上 404。
   - 对策：清空（清空后**再数一遍**确认 0）→ 删桶 → **再确认桶不存在** → 才继续下一步。

6. **`pkill -f <关键字>` 会把自己那条 SSH 命令一起杀掉**
   - 因为模式字符串出现在自己的命令行里（踩了 4 次以上，表现是"命令莫名消失、任务没起"）。
   - 对策：优先用 `docker kill <cid>`；必须用 pkill 时，用变量拼接把关键字拆开
     （`X="gs""util"; pkill -f "$X"`）。

7. **后台任务必须 `setsid`，且不要用 `$!` 判断存活**
   - 只 `nohup` 会被 SSH 会话带走；`setsid cmd &` 时 `$!` 可能立刻失效。
   - 对策：用 `docker ps`/状态文件判断存活，不要用 pid 文件。

8. **限流会让"列举对象"返回空 → 误判"全部缺失"**
   - 所有列举都要带重试，否则会把"限流"当成"桶里没东西"。

9. **迁移与"补全脚本"不能同时跑**
   - 一边删桶重建、一边从暂存桶回填，两边互相打架，曾出现 CDN 桶被清成 0（玩家 404）。
   - 对策：同一时刻只跑一条链路；补全要在迁移结束后统一做。

10. **发群通知里 `%d` 拿到 None 会直接崩掉整个迁移进程**
    - 本次真实事故：步骤2 删完日本桶后，把 `region()`（返回 None）覆盖到了 `left` 变量，
      通知格式化 `%d` 抛 TypeError → 进程退出，任务停在"日本桶已删、巴西桶未建"的中间态。
    - 对策：中间态必须可续跑（本工具已支持"日本桶不在、暂存桶在 → 直接进步骤3"）。

11. **小文件多不是 CPU 高的根因，"每文件起进程"才是**
    - 老实现每个文件起 3 个进程（aws cli + 2×gsutil），4000 个对象 ≈ 1.2 万次进程启动；
      新实现全程 SDK 直连 + 服务端 rewrite，本地只发 API 调用。

12. **`Blob.exists()` 会误判 False（自检假失败的真凶）**
    - `Blob` 对象一旦被 `delete()` 过、或带上了 `generation`，`exists()` 会带着这个
      generation 去查（`?generation=N`），查到的是已不存在的旧版本 → 永远返回 False。
    - 本次真实事故：自检先删了目标对象再复制，复制其实成功了，但 `dst.exists()` 报 False，
      于是判定"方向不对"直接中止；panda 因此停在"日本桶已删、巴西桶刚建"的中间态。
    - 对策：判存在统一用 `client.bucket(b).get_blob(name) is not None`（每次都是新查询）。

13. **`gsutil -m cp` 回填很慢且不透明**
    - 实测只有约 85 对象/s，且不显示目标路径，排查困难。
    - 结论：GCS→GCS 同区复制用服务端 rewrite（320+ 对象/s）比 CLI 回填快 4 倍。

14. **新建 / 重建的 GCS 桶默认私有 → Worker 匿名回源 403 → 被边缘缓存成 7 天**
    - 这是本轮最严重的事故（用户进不去游戏），详见上一节「线上事故」。
    - 迁移、扩容、重建桶的脚本都必须**建桶后立刻** `add-iam-policy-binding allUsers:objectViewer`。

## 四·补、⚠️ 线上事故：新桶默认私有，导致"用户进不去游戏"（2026-09-14 20:30~21:00）

**现象**：迁移完成后有用户反馈进不去游戏；部分老资源能进、新资源进不去。

**根因**（不是 Worker 代码、不是国家白名单）：

```text
1) 本轮迁移把「删大阪桶 → 在巴西重建同名桶」做了一遍，
   而 GCS 新建桶默认是**私有**的 —— 17 个桶全部缺 allUsers:objectViewer
2) Cloudflare Worker 回源 GCS 用的是**匿名请求**：
   https://<bucket>.storage.googleapis.com/<path>
   → 拿到 GCS 的 403：Anonymous caller does not have storage.objects.get access ...
3) Worker 的 fetch 开了 cacheEverything + cacheTtl 604800，
   **这个 403 被 Cloudflare 边缘缓存了 7 天**
   → 已缓存过的老资源还能命中缓存（能进），没缓存过的新资源直接 403（进不去）
```

**修复动作**：

```bash
# 1) 17 个桶全部补公开读
gcloud storage buckets add-iam-policy-binding gs://newgg2-dbqp-gcs-<前缀> \
  --member=allUsers --role=roles/storage.objectViewer
# 2) 匿名直读逐个验证：17/17 返回 200
curl -s -o /dev/null -w '%{http_code}' https://newgg2-dbqp-gcs-<前缀>.storage.googleapis.com/health.json
# 3) 对 23 个静态 zone 做 purge everything（补权限前一次、补完后再一次，清掉期间产生的 403）
#    宝塔上：bash /tmp/cf_purge_all.sh   （token 有 IP 白名单，必须从宝塔刷）
# 4) 复验：origin 随机抽样 136/136 全 200；走 CDN 抽样 102/102 全 200
```

**永久防复现**：`br_vendor_move.py` 新增 `make_public()`，**建桶/复用桶之后立刻加
`allUsers:objectViewer`**，失败会打日志并提示手工命令。
以后任何"新建桶/重建桶"的脚本都必须带这一步。

**用户侧提示**：Worker 给 200 响应打了 `Cache-Control: public, max-age=604800`，
浏览器也会缓存 7 天；用户手机若缓存过错误响应，清缓存/隐私窗口打开一次即可。

**另一个潜在坑**：线上 Worker 有 `ALLOWED_COUNTRIES = ["BR","SG","HK","AE"]`，
非白名单国家的 IP 会拿到 403 页面 —— 排查"同一台手机换网络有的能进有的不能进"时，
先让用户打开 `https://<static-domain>/cdn-cgi/trace` 看 `loc=` 是不是 BR。

## 五、同步链路（现状）

```text
AWS S3（大阪）  dbqp-s3-<前缀>-static / dbqp-s3-tada-staticsN
      ↓（03 上容器内 s3_gcs_sdk_sync.py，boto3 ↔ google-cloud-storage SDK 直连）
GCS（巴西）     gs://newgg2-dbqp-gcs-<前缀>      ← 现在**只有这一套桶**
      ↓
Cloudflare Worker（static-gcs-proxy，BUCKET_MAP 前缀→桶名）
      ↓
玩家
```

`BUCKET_MAP` 里 17 个前缀现在全部指向**同名巴西桶**（桶名没有后缀变化），
所以本次迁移不需要改 Worker，也不需要改域名，只需按需刷 CDN 缓存。
