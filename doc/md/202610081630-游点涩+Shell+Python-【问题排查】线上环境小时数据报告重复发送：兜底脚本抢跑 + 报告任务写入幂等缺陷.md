# 【问题排查】线上环境小时数据报告重复发送：兜底脚本抢跑 + 报告任务写入幂等缺陷

- 触发反馈：番子反馈「最近的小时报告会偶发重复发送，怀疑是兜底机制误触发」

## 一、结论（先看这里）

**是兜底机制误触发**，而且兜底与报告任务之间存在真实的并发窗口：

1. 报告任务 `HourlyStatsMonitorJob` 的执行顺序是
   **「先查重 → 采集统计（实测约 2 分钟）→ 写记录 → 发报告」**；
2. Spug 任务 `HourlyStatsMonitor monitor` 在整点后 :07 触发，通常 :09 前后才写入记录；
   而兜底脚本 v1 固定 **:09** 检查，正好落在这段「采集窗口」内 → 判定「记录缺失」→ 自己也跑一遍；
3. 两个进程于是**各发一条同一小时的报告** —— 重复发送；
4. 更要命的是：写重复 `_id` 时 `MongoModel::insert()` **不抛异常**，只写一条错误日志并 `return null`，
   而 Job **不检查返回值**，照样往下执行 `TgNotifyService::sendMessage()` → 重复消息真实发出。

即：**兜底抢跑是触发条件，报告任务"写入失败仍发送"是让重复消息真正落地的原因。**

## 二、证据

### 2.1 兜底日志：几乎每小时都在补跑

```text
2026-10-08 08:09:01 WARNING record missing, backfill: 2026-10-08_07   → 08:11:04 backfill done
2026-10-08 09:09:01 WARNING record missing, backfill: 2026-10-08_08   → 09:11:06 backfill done
2026-10-08 10:09:01 INFO    record exists,  skip:   2026-10-08_09
2026-10-08 11:09:01 WARNING record missing, backfill: 2026-10-08_10   → 11:11:04 backfill done
2026-10-08 13:09:01 WARNING record missing, backfill: 2026-10-08_12   → 13:11:09 backfill done
2026-10-08 14:09:01 WARNING record missing, backfill: 2026-10-08_13   → 14:11:07 backfill done
2026-10-08 15:09:01 WARNING record missing, backfill: 2026-10-08_14   → 15:11:05 backfill done
2026-10-08 16:09:01 WARNING record missing, backfill: 2026-10-08_15   → 16:11:10 backfill done
```

补跑耗时稳定在 **约 2 分钟**（08:09:01 → 08:11:04），正好印证「采集很慢」这一点；
而 Spug 是 :07 触发 —— :09 检查时它多半还没写记录。

### 2.2 代码层面（两个关键点）

`app/Jobs/Monitor/HourlyStatsMonitorJob.php`：

```php
$existing = HourlyStatsMonitorModel::findFirst(['_id' => $id]);
if (!empty($existing)) { echo "已存在记录: {$id}，跳过\n"; return; }   // ← 查重
$currentData = self::collectStats(...);                              // ← 约 2 分钟（并发窗口）
HourlyStatsMonitorModel::insert($record);                            // ← 写记录（返回值被忽略）
...
TgNotifyService::sendMessage($reportMsg, 'monitor');                 // ← 照样发送
```

`app/Core/Mongodb/MongoModel.php`：

```php
$result = self::connect()->executeCommand($cmd);
if ($result[0]['n'] == 0) {
    $cmd['error'] = ...;
    LogUtil::error($cmd);            // 只记日志
}
return $result[0]['n'] > 0 ? $document['_id'] : null;   // 不抛异常
```

即：**重复键不会中断流程**，第二个进程照样把报告发出去。

## 三、修复（本次已上线）

### 3.1 兜底脚本 v2（我方代码，已部署并生效）

文件：`ops/production/scripts/youdianse-hourly-report-guard.py`

| 项 | v1 | v2 |
| --- | --- | --- |
| 检查时间 | 每小时 **:09** | 每小时 **:25**（给 Spug :07 任务留足时间） |
| 缺失时的动作 | 直接补跑 | 先做**在跑检测**，有实例则等待后复检 |
| 在跑检测 | 无 | 宿主机 `docker top` 查 cron/web 两容器命令行里有无 `HourlyStatsMonitor` |
| 等待预算 | 无 | `--wait 30 --retries 20`（≈10 分钟），预算内一直在跑则**跳过并告警**（宁晚不重） |
| 安全开关 | 无 | 新增 `--dry-run`、`--hour`，值班可安全演练 |

> 注：容器内没有 `ps`/`pgrep`（PHP 镜像精简），因此用**宿主机** `docker top -o pid,args` 做检测，实测可用。

## 五、遗留与建议（需后端/流程侧配合）

1. **报告任务写入幂等（根因，建议后端修）**：把插入结果用起来，写入失败（重复 `_id`）时不要继续发送：

```php
$inserted = HourlyStatsMonitorModel::insert($record);
if ($inserted === null) {
    echo "记录写入失败（可能已被其它进程写入），跳过本次发送: {$id}\n";
    return;
}
```

   更彻底的做法是「原子占位」：先 `findAndModify` 带 `upsert` 抢占该小时的记录（占位），
   抢到才采集与发送，从机制上消灭并发窗口。
2. **Spug 任务配置失败重试**：Spug 侧给该任务加失败重试，减少对兜底的依赖。
3. **发布窗口避开整点 :00-:10**：避免重建容器与 :07 执行窗口重叠（这是当初报告缺失的原因）。
4. 兜底仍保留：本次只解决「重复」，不降低「缺报兜底」能力。
