# 3. 直播链路架构（双方案并存）

> 来源文件：`~/Projects/work/game/xiaolan-watches/dev/docs/architecture/live-streaming-architecture.md`

> 整理日期：2026-05-22 00:00｜日期依据：正文日期

> 对齐 PRD：[`kickoff-live.md`](../prd/modules/kickoff-live.md)、[`kickoff-h5.md`](../prd/modules/kickoff-h5.md)、[`kickoff-admin.md`](../prd/modules/kickoff-admin.md) §3.3' 直播间管理
>
> **本文档保留两个方案**，ADR-0003 决策时基于团队能力、成本、上线时间窗选定其一。两方案 API 契约对业务层一致。
>
> **v0.2 变更（2026-05-22）**：原 PRD 主播端 5 步流程废弃；主播仅用 OBS 推流，**不使用任何 web 端**。所有 web 端监控/配置职能（房间标题、关联比赛、弹幕监控、大 R 在场、强制关播、推流凭据管理）由"房间管理员"在运营后台承担（详见 `kickoff-admin.md §3.3' 直播间管理`）。主播大 R 接待通过房间管理员的 TG/电话外部通知。

## 3.1 共同需求（与方案无关）

- OBS（RTMP）推流
- 1080p / 720p / 480p 三档 ABR
- HTTP-FLV 优先 + HLS 兜底
- 录制（DVR）至 OSS
- 截图每 30s → AI 鉴黄
- 时移（DVR 回看）24h 滚动
- 推流鉴权 + 播放鉴权（短 token）
- 防盗链（四重防护）
- CDN 边缘分发（双 CDN GSLB）
- 主播多设备并发禁止（PRD R-108）
- 断流自动重连
- 监控：推流稳定性、首帧、卡顿、回源率

## 3.2 流量与压力归属（10k CCU）

| 流量 | 量级 | 谁承担 |
| --- | --- | --- |
| 视频拉流出站 | **20 Gbps**（1080p × 10k × 2 Mbps） | CDN 边缘 ≥ 95% |
| CDN miss 回源 | 1-2 Gbps | 直播 Pull Edge |
| OBS 推流入站 | 50 主播 × ~5 Mbps = 250 Mbps | 直播 Push Edge |
| HLS m3u8 / ts 请求 | ~30w QPS | CDN 边缘 |
| FLV 长连接 | 10k 并发 | CDN 边缘 |

**关键结论**：推流入口压力极小（50 路），出站带宽才是真正瓶颈，必须由 CDN 边缘承接。

## 3.3 方案 A：SRS 自建源站

### 3.3.1 拓扑

```
                  推流域名 push.kickoff.tv（DNS GSLB）
                              │
                ┌─────────────┴─────────────┐
                ▼                           ▼
       [ SRS Push Edge A ]          [ SRS Push Edge B ]
       (8c/16GB/1Gbps)              (active-active)
                │                           │
                └─────────────┬─────────────┘
                              │ srs forward / cluster
                              ▼
                ┌─────────────┴─────────────┐
                ▼                           ▼
        [ SRS Origin A ]            [ SRS Origin B ]
        (16c/32GB/1Gbps + NFS)      (互备)
                │
                ├──HTTP hook on_publish───► go-srs-hook (开播校验+授权)
                ├──HTTP hook on_unpublish─► go-srs-hook (关播+session 结束)
                ├──HTTP hook on_dvr───────► worker-realtime (录制完成→上传OSS)
                │
                ├──RTMP pull──► [ 转码集群 FFmpeg × 4 ]
                │                  ├─ 1080p 原码
                │                  ├─ 720p 转码
                │                  └─ 480p 转码
                │                  └─► RTMP push 回 SRS Origin（新流名）
                │
                ├──DVR FLV/MP4──► 本地共享存储 NFS/Ceph
                │                  └─► worker-cron 5min 扫描→上传 OSS
                │
                └──snapshot──► 截图 worker (每 30s)→OSS→鉴黄 API
                              │
                              ▼
                  ┌───────────┴───────────┐
                  ▼                       ▼
          [ SRS Pull Edge × 4 ]   (公网域名 cdn-origin.kickoff.tv)
              │ 仅暴露给 CDN，IP 白名单
              ▼
       [ 腾讯云 CDN ]   [ 火山引擎 CDN ]
              │             │
              └──────┬──────┘  GSLB DNS 加权
                     ▼
            play.kickoff.tv → 用户播放器
```

### 3.3.2 关键决策

| 决策项 | 选择 | 理由 |
| --- | --- | --- |
| 源站软件 | **SRS 5.x** | 活跃维护；内置 RTMP/HLS/HTTP-FLV/WebRTC/SRT；HTTP API + callback；集群成熟 |
| 拓扑分层 | **Push Edge / Origin / Pull Edge 三层分离** | 推流接入、转码处理、CDN 回源 各自专责 |
| 推流协议 | RTMP（OBS 默认） | 兼容最广；v1.1 可加 SRT 兜底弱网 |
| 拉流协议-Web | HTTP-FLV 主 + HLS 兜底 | FLV 1-3s 延迟接近"直播感" |
| 拉流协议-H5 | HLS 唯一 | iOS Safari 不原生支持 FLV |
| 转码 | **独立 FFmpeg 集群**（不让 Origin 扛 CPU） | v1 软转；v2 可上 NVENC GPU |
| 录制 | SRS DVR FLV → worker 转 MP4 → OSS | 内置 hook 触发，异步上传 |
| 截图 | SRS on_publish + FFmpeg 每 30s 抓帧 → OSS → 阿里云内容安全 | 鉴黄输入 |
| 时移 | SRS DVR 24h 滚动；前端独立"回看"入口 | 赛事复盘场景 |
| CDN | 双 CDN GSLB（腾讯云 + 火山） | 单 CDN 故障切换 |

### 3.3.3 容量规划（10k CCU）

| 组件 | 规格 | 数量 | 单机承载 |
| --- | --- | --- | --- |
| SRS Push Edge | 8c/16GB/1Gbps | 2 | 100 主播 / 500 Mbps 推流入站 |
| SRS Origin | 16c/32GB/1Gbps + NFS | 2 | 同步全部推流；50 路转码触发 |
| 转码集群 FFmpeg | 16c/32GB（v1 软转）/ T4 GPU（v2） | 4 | 12 路 1080p→720p+480p 软转 |
| SRS Pull Edge | 8c/16GB/**10 Gbps** | 4 | 5000 并发回源 / 10 Gbps 出口 |
| 录制 / 截图 worker | 4c/8GB | 2 | 50 路并发处理 |
| 共享存储 | NFS / Ceph 5TB | 1 cluster | DVR + 转码中转 |

CDN 回源率假设 ≤ 10%，回源 ~2 Gbps → 4 × 10 Gbps Edge 容量充足。

### 3.3.4 推流鉴权（SRS HTTP hook）

```
1. 主播在 streamer-portal 完成 5 步流程，点"一键开播"
2. go-api 校验：主播状态 + 班次 + 房间冲突（PRD R-108 单设备并发）
3. go-api 生成 push_key:
   push_key = HMAC-SHA256(secret, streamer_id || session_id || expire_at)
   推流 URL = rtmp://push.kickoff.tv/live/{stream_name}?key={push_key}&t={expire_at}
4. go-api 写入 Redis: live:push:{stream_name} = { streamer_id, expire_at }
5. 返回 URL 给主播端 (OBS 配置)
6. OBS 推流到 SRS Push Edge
7. SRS 触发 on_publish hook → go-srs-hook:
   - HMAC 验签
   - 校验 expire_at > now
   - 查 Redis 确认 session 有效
   - 返回 200 允许 / 403 拒绝
8. SRS Edge forward 到 Origin，转码 / 分发开始
```

### 3.3.5 播放鉴权（短 token + Nginx + Lua）

SRS 自身 hook 在 CDN 长连接复用场景下不可靠，鉴权前置到 SRS Pull Edge 前面的 **Nginx + Lua**：

```
1. 用户进入直播间 → 前端调 GET /api/v1/live/room/{id}/token
2. go-api 校验：登录 + 房间状态 LIVE
3. 颁发 [敏感内容已脱敏], room_id || user_id || expire_at_30s)
4. 返回 play URL:
   https://play.kickoff.tv/live/{stream_name}.flv?敏感凭据：[已脱敏]
5. CDN 边缘命中 → 直接返回
6. CDN miss → 回源 SRS Pull Edge → Nginx + Lua 校验 token HMAC 通过 → SRS 返回流
7. 前端每 20s 调 /api/v1/live/room/{id}/refresh-token 续期
```

### 3.3.6 防盗链四重防护

| 层 | 校验 | 失败行为 |
| --- | --- | --- |
| 1. URL token | HMAC 验签 + 时效（30s） | 403 |
| 2. Referer 白名单 | 仅允许 *.kickoff.tv | 403 |
| 3. UA 黑名单 | 拦截已知盗播工具 UA | 403 |
| 4. IP 频次 | 单 IP 拉流 > 3 个房间/分钟 | 限速 |

### 3.3.7 断流重连

- **当前 ZEGO/WebRTC 口径**：ZegoCloud `stream_publish.stop` 回调是第一优先级，收到后立即结束会话并推送 `room.status.ended`。
- **主播端业务心跳兜底**：主播端开播成功后通过 `/ws/v1/streamer` 每 15s 发送 `streamer.live.heartbeat`，后端写入 `live_sessions.last_heartbeat_at`。
- **自动下播阈值**：worker 每 15s 扫描一次，若直播中 session 连续 60s 没有业务心跳，则把 `live_sessions` 标记为 `ABORTED`，把 `live_rooms.status` 改为 `ENDED`，并广播 `room.status.ended`。
- **连接心跳区别**：`client.ping` 只证明 WS 连接活着，不作为直播状态依据；前端必须单独发送 `streamer.live.heartbeat`。
- **前端表现**：收到 `room.status.ended` 且 `reason=streamer_heartbeat_timeout` 时，停止播放器并切到"主播已下播/直播流暂不可用"兜底页。
- **SRS 侧**：on_unpublish 后 30s 内若新 publish 同 stream_name → 视为重连，session 继续；超 30s → 关闭 session
- **客户端**：FLV 播放器自动重连 3 次（1s/3s/5s），失败切 HLS，最终失败显示"主播已离线"
- **WS 广播**：`room.disconnected` / `room.recovered` / `room.ended` 三种事件给所有观众
- **录制连续性**：同 session 内多次推流合并为一个录制文件

### 3.3.8 SRS HTTP Callback 与业务集成

| Hook | 触发时机 | go-srs-hook 动作 |
| --- | --- | --- |
| `on_publish` | 主播开始推流 | HMAC 验签 + 状态校验 → 登记 `live_sessions` |
| `on_unpublish` | 推流断开 | 标记 session 结束 + 推 WS `room.ended` |
| `on_play` | CDN 首次回源 | 仅记日志（鉴权前置到 Nginx） |
| `on_dvr` | DVR 文件写完 | 上传 OSS + 写 `live_recordings` |
| `on_record_begin` | 录制开始 | 登记开始时间 |
| `on_record_end` | 录制结束 | 触发转码 / 截图后处理 |

### 3.3.9 SRS 方案优劣

| 维度 | 评价 |
| --- | --- |
| 成本 | 中期成本低（无单价×流量）；服务器+带宽成本可控 |
| 控制力 | 高（自有源站，定制空间大） |
| 上线时间 | **慢**（需 SRS 集群、转码集群、Nginx+Lua、录制管线、监控全栈搭建） |
| 团队能力要求 | 高（需熟悉 SRS、FFmpeg、流媒体协议） |
| 故障责任 | 自承 |
| 弹性扩缩 | 受限（带宽签约、IDC 容量） |
| 合规 / 内容安全 | 自接 AI 鉴黄 + 人工审核 |
| 适合阶段 | 团队有流媒体经验、长期持有用户、对成本敏感 |

## 3.4 方案 B：云直播托管

### 3.4.1 拓扑

```
[ 主播 OBS ]
     │ RTMP
     ▼
[ 云直播 服务（腾讯云 LVB / 火山引擎视频云 / 阿里云直播）]
   ├─► 转码（1080p / 720p / 480p 多档）
   ├─► 录制（自动存对象存储 OSS）
   ├─► 截图（每 30s 一张）
   └─► 边缘分发
       ├─► HLS（兼容性最好）
       └─► HTTP-FLV
           │
           ▼
   云厂商内置 CDN（可叠加第二家 CDN 互备）
           │
           ▼
   用户播放器（Web flv.js / hls.js；H5 hls.js）
```

### 3.4.2 关键决策

| 决策项 | 选择 | 理由 |
| --- | --- | --- |
| 云直播商 | 腾讯云 LVB（主） + 火山引擎（备） | 双厂商互备避免单点 |
| 推流接入 | 云直播提供的 push domain | 无需自建源站 |
| 转码 | 云直播在线转码 3 档 | 厂商管理，按量计费 |
| 拉流 | 云直播 + 自带 CDN | 同厂商无回源费 |
| 录制 | 云直播录制 → 厂商 OSS → 同步到自有 OSS | 同区域同步免流量费 |
| 截图 | 云直播截图回调 | 推到自有 worker 鉴黄 |
| 鉴权 | 云直播提供的 key+timestamp+sign 鉴权 | 厂商自带 |
| 防盗链 | 云直播 token + 自定义 referer 白名单 | 厂商自带 |

### 3.4.3 容量规划

云直播是 SaaS，**无需容量规划**，按实际推/拉流量计费。
- 推流单价：~10 元/路·小时（含转码）
- 拉流单价：~0.2 元/GB（含 CDN）
- 录制单价：~0.05 元/分钟
- 截图单价：~0.05 元/张

### 3.4.4 推流鉴权（云直播）

```
1. go-api 调用云直播 SDK 生成推流 URL：
   rtmp://push.live.kickoff.tv/live/{stream_name}?[敏感内容已脱敏]
2. 返回主播端
3. OBS 推流到云直播
4. 云直播校验 txSecret + txTime → 允许 / 拒绝
5. 同时云直播回调 go-srs-hook（云直播也支持 webhook）→ 业务侧登记 session
```

### 3.4.5 播放鉴权（云直播）

```
1. 用户进入直播间 → 前端调 GET /api/v1/live/room/{id}/token
2. go-api 调用云直播 SDK 生成播放 URL：
   https://play.live.kickoff.tv/live/{stream_name}.flv?[敏感内容已脱敏]
3. 返回前端，播放
4. 云直播 CDN 校验 txSecret + txTime
```

### 3.4.6 与 go-srs-hook 的集成

云直播提供 webhook 给业务侧推送以下事件：
- 推流开始 / 结束
- 录制完成
- 截图完成
- 内容安全审核结果

业务侧 `go-srs-hook` 服务**对外接口与 SRS 方案一致**，仅内部适配层不同。

### 3.4.7 云直播方案优劣

| 维度 | 评价 |
| --- | --- |
| 成本 | 流量大时贵；GMV 800w 量级，推/拉流费用估算 ~50-100w（赛季 32 天） |
| 控制力 | 低（依赖厂商功能与稳定性） |
| 上线时间 | **快**（1-2 周可完成接入与联调） |
| 团队能力要求 | 低（仅需 SDK 接入） |
| 故障责任 | 厂商主责，SLA 保障（99.9%） |
| 弹性扩缩 | 极佳（无容量上限，按量计费） |
| 合规 / 内容安全 | 厂商自带 AI 鉴黄 + 我方人工复审 |
| 适合阶段 | 上线时间紧、团队无流媒体经验、对成本不敏感 |

## 3.5 双方案对比与决策维度

| 维度 | SRS 自建 | 云直播托管 |
| --- | --- | --- |
| 上线时间 | 4 周 | 1-2 周 |
| 团队技能门槛 | 流媒体 + Linux 网络 + FFmpeg | SDK 接入即可 |
| 32 天赛季成本 | ~30-50w（服务器+带宽） | ~50-100w（按量） |
| 故障责任 | 自承 | 厂商 SLA |
| 长期成本曲线 | 平缓 | 线性增长 |
| 可定制性 | 高（私有协议、转码参数） | 低 |
| 弹性扩容 | 受限（IDC / 带宽） | 极佳 |
| AI 鉴黄 | 自接 | 厂商内置 |
| 出海延迟 | 自有节点不足 | 厂商节点覆盖好 |
| 主播无感切换 | 不支持 | 支持（多接入点） |

### 3.5.1 推荐决策路径（ADR-0003 输入）

| 团队/项目实际情况 | 推荐方案 |
| --- | --- |
| 有流媒体老手 / 上线时间充裕 / 预算紧 / 长期持有 | **SRS 自建** |
| 无流媒体经验 / 上线时间紧 / 重业务轻基建 / 32 天后转型 | **云直播托管** |
| 介于两者 | **第 1 阶段云直播托管上线，第 2 阶段并行搭 SRS 灰度迁移** |

### 3.5.2 业务层抽象

`internal/infra/live/` 提供统一接口：

```go
type LiveService interface {
    GeneratePushURL(streamerID, sessionID int64, ttl time.Duration) (string, error)
    GeneratePlayURL(roomID, userID int64, ttl time.Duration) (string, error)
    KickPublisher(streamName string) error
    GetSessionStats(streamName string) (*SessionStats, error)
}

// 两个实现：
// 1. internal/infra/live/srs/srs.go
// 2. internal/infra/live/cloud/{tencent|volcengine|aliyun}.go
```

业务层完全解耦，切换方案只改 DI 注入。

## 3.6 监控指标（两方案通用）

| 指标 | 阈值 | 来源 |
| --- | --- | --- |

| 卡顿率 | > 5% | 播放器埋点 |
| 录制失败次数 | > 0 | hook 回调统计 |
| 截图鉴黄异常 | 单房间 1h ≥ 1 次 | AI 内容安全 API |
