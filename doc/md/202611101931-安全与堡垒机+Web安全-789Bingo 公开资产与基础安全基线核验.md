# 789Bingo 公开资产与基础安全基线核验

> 本记录只描述公开面的被动核验和配置风险评估。未执行登录态越权、输入注入、支付操作、用户数据访问或漏洞利用；公开版不记录可直接复用的基础设施地址和攻击步骤。

## 评估范围

本次检查覆盖主域名公开 DNS、HTTP/HTTPS 跳转、TLS、证书、浏览器安全响应头、`robots.txt`、`sitemap.xml`、首页 HTML 和公开静态资源指纹。目标是判断公开边界与基础安全配置，而不是证明业务接口存在漏洞。

评估时尚未获得可执行的登录态测试范围和账号，因此所有结论都限制在公开证据和静态指纹层面。

## 公开边界

- 主域当前由 Cloudflare 代理，公网响应来自边缘节点。
- HTTP 和 `www` 入口会跳转到主域 HTTPS。
- TLS 证书有效，覆盖主域及相关公网子域。
- 主站使用 React 单页应用；独立博客目录使用 WordPress。
- 公开静态资源使用内容哈希命名，未发现 `sourceMappingURL`。
- `robots.txt` 和 `sitemap.xml` 可正常读取。
- 安全联系文件没有提供有效内容，返回的是单页应用回退页面。

## 正向控制

主站在传输层和浏览器侧具备多项基础控制：

- 全站使用 HTTPS，证书链有效。
- 启用了 HSTS。
- 已设置 `X-Content-Type-Options: nosniff`。
- 使用严格来源的 Referrer Policy。
- 对麦克风、USB、串口和蓝牙等权限做了浏览器策略限制。
- Cloudflare 挑战 Cookie 使用 Secure、HttpOnly、SameSite 和 Partitioned。
- 正常跨域请求没有返回宽松 ACAO，未观察到开放 CORS。
- 未发现公开目录列表、源码映射或调试页面。

这些控制降低了常见传输层、Cookie 读取和跨域数据暴露风险，但不能替代业务接口鉴权。

## 后台归属判断

公开资源可以确认博客目录使用 WordPress，因此其管理入口属于内容管理系统，主要用于文章、页面、媒体和 SEO 管理。它不能直接等同于游戏运营、订单、支付、财务或客服总后台。

评估未通过口令猜测、目录爆破或登录绕过继续验证后台。客户端代码中与聊天室管理相关的角色字段只说明存在聊天管理能力，也不能据此推断完整运营后台的公开入口。

## 配置面风险

### CSP 防护不完整

现有 CSP 主要限制页面嵌入和对象加载，对本页脚本执行的限制不足。它不等同于已经存在 XSS，而是意味着当业务出现注入缺陷时，浏览器侧缺少一道有效缓解。

建议先以 Report-Only 模式盘点 GTM、分析脚本、内联样式和第三方域名，再逐步收紧 `default-src`、`script-src`、`style-src`、`connect-src`、`img-src` 和 `frame-src`。切换前必须做灰度验证，避免直接破坏支付跳转、图片和统计。

### 域名治理

本次未观察到 DMARC、CAA 和 DNSSEC DS 记录。三项控制的侧重点不同：

- DMARC 降低发件域名仿冒和钓鱼邮件成功率。
- CAA 限制可为主域签发证书的 CA。
- DNSSEC 为权威 DNS 响应提供签名链保护。

建议先进入 DMARC 监控阶段，确认全部合法发信源后再提升隔离策略；CAA 应按实际证书供应商配置；DNSSEC 应在注册商与权威 DNS 两侧同步启用并验证 DS 链。

### HSTS 与安全联系渠道

HSTS 当前没有声明 `includeSubDomains` 和 `preload`。启用前必须确认所有子域均长期支持 HTTPS，否则会把局部配置问题扩展成整域访问故障。

安全联系文件应指向真实可用的安全邮箱、响应流程和漏洞披露边界，不应由前端路由返回 HTML 首页。

### 第三方统计标识

页面公开配置中的分析服务标识属于浏览器可见的统计 Key，不是后台管理凭据。其主要风险是统计事件被伪造、访问量或来源数据被污染，不能据此读取用户、订单、资金或运营数据。

仍应确认该标识只允许指定站点和统计接口使用，并为异常事件量设置监控。

## CVE 匹配边界

本次没有发现能够证明目标命中具体 Nginx、React、DNS 或业务依赖 CVE 的完整证据。仅有框架名称、响应头或第三方包名不足以判定漏洞命中。

可信的 CVE 判断至少需要：

1. 精确组件和版本。
2. 受影响功能和请求路径。
3. 当前配置是否满足触发条件。
4. 在授权测试窗口内完成非破坏性验证。

## 优先建议

1. 建立分阶段 CSP 发布计划。
2. 发布 DMARC 监控策略，再逐步收紧。
3. 按实际 CA 和 DNS 架构启用 CAA、DNSSEC。
4. 提供真实的安全联系渠道和漏洞披露流程。
5. 监控 NS、A、TXT、MX 和证书变更，防止域名劫持或错误签发。
6. 登录态、越权、支付回调、限流和 WebSocket 鉴权必须在书面授权和隔离账号下测试。

## 结论

789Bingo 的公开基础防护整体完整，Cloudflare 边界、HTTPS、证书、跳转和主要安全头工作正常，没有从公开证据确认可直接利用的高危 CVE 或未授权业务数据访问。

当前更适合按“防御纵深”处理：补齐 CSP、域名治理和安全联系流程，同时继续把高风险业务验证限制在授权测试范围内。
