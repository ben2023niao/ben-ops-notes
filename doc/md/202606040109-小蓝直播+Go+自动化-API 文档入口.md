## API 分组

| 分组 | 说明 |
| --- | --- |
| Auth | 登录、会话、鉴权。 |
| User | 用户资料。 |
| Admin | 后台管理，详见 `docs/api/admin-api.md`。 |
| System | 健康检查、配置、基础能力。 |

## 契约规则

1. OpenAPI 是客户端、后台和服务端之间的事实来源。
2. 接口字段命名、错误码、分页、鉴权方式必须统一。
3. 高风险接口必须幂等。
4. 后台接口必须有角色权限和审计日志。
5. 前后端分离后台必须在 OpenAPI 中标明 owner service，允许 `services/go-app` 或 `services/laravel-app` 承接。
6. 每个 OpenAPI operation 必须写 `x-prd-id`，追踪到 `docs/prd/requirements.md`；确实不对应业务需求时写 `x-prd-not-applicable: true`。

## OpenAPI 的四个身份

OpenAPI 不是只给后端看的 yaml 文件。它同时承担：

1. 接口合同：前端、后台、后端、测试围绕同一份契约协作。
2. Mock 源头：前端和测试从契约生成 mock，不能凭空编字段。
3. 契约测试依据：服务端响应、错误结构、鉴权和分页必须符合契约。
4. 接口文档源头：Swagger UI、Scalar、Redoc 或内部文档站应由 OpenAPI 生成或引用。

`docs/api/**` 可以解释模块边界、鉴权、错误码、owner service、调用流程和文档站入口，但不能手工维护一份与 `packages/contracts/openapi/**` 冲突的接口真相。

## OpenAPI 拆分

OpenAPI 必须从项目早期就按模块拆分，避免多人同时修改一个大文件。

入口：

```text
packages/contracts/openapi/index.yaml
```

模块：

```text
packages/contracts/openapi/paths/
packages/contracts/openapi/schemas/
```

开发顺序：

```text
PRD 模块确认 -> 需求 ID 登记 -> OpenAPI 模块更新 -> 前端 mock / 后端实现 / 测试用例并行
```

推荐发布链路：

```text
packages/contracts/openapi/**
  -> lint / bundle / breaking check
  -> mock server
  -> contract test
  -> docs/api 文档站
  -> CI / MR gate
```
