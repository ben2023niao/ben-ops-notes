> GitHub 仓库源文件：[点击打开网页渲染版](https://github.com/ben2023niao/ben-ops-notes/blob/main/doc/md/202605251234-%E5%B0%8F%E8%93%9D%E7%9B%B4%E6%92%AD%2BShell%2BGo-%E6%97%A5%E5%BF%97%E8%81%9A%E5%90%88%20%2B%20%E5%AE%9E%E6%97%B6%E5%91%8A%E8%AD%A6%E6%8E%A5%E5%85%A5%E6%8C%87%E5%8D%97.md)

> 状态:v0.3.3 后端已就绪;部署侧 fluent-bit / Sentry 配置由 ops 完成。
> 部署形态:**docker-compose 两机方案**(不上 k8s,见下方决策)。

## 部署架构决策(为什么不上 k8s)

当前规模:**2 台机器**。

| 维度 | k8s 单机/小集群 | docker-compose 两机 |
|---|---|---|
| 控制面开销 | api-server + etcd + scheduler + kubelet 至少吃 1.5G 内存 + 1 核 CPU | 0(docker daemon 即可) |
| 学习/运维成本 | 高(YAML 海 + Helm + Ingress + StorageClass) | 低(docker-compose up -d) |
| 故障半径 | k8s 控制面挂 = 业务全挂 | 单 service 挂 = 单 service 挂 |
| 适用场景 | ≥ 5 节点 + 多服务弹性伸缩 | 2-3 节点 + 几个服务 + 手动切流量 |

**结论**:2 台机器上 k8s 是显著过度设计,选 docker-compose。等真到 5+ 节点 + 多服务编排需求再考虑 k3s/k8s。

## 两机部署架构

| 机器 | 角色 |
|---|---|
| **机 A**(主) | nginx + go-app(api + admin) + redis-master + fluent-bit |
| **机 B**(从) | mysql + redis-replica + 定时备份 + fluent-bit |

故障切换:**手动**(写 `runbook.md`),5 分钟内切流量到机 B 临时降级,牺牲短暂可用性换运维简单。

## 总体架构

```
┌───────────┐  stdout JSON  ┌──────────────┐  push  ┌──────────────┐
│  go-app   │ ────────────► │  fluent-bit  │ ─────► │  Grafana     │ ◄── 业务看板 + 告警
│           │     (zap)     │  (compose)   │        │  Cloud Loki  │
│           │                └──────────────┘        └──────────────┘
│           │       Error+ 级别                      ┌──────────────┐
│           │  ─────────────────────────────────────►│  sentry.io   │ ── Telegram bot + 邮件
└───────────┘     (sentry-go SDK,异步)              └──────────────┘
```

两条独立链路:
- **聚合查询 / 业务看板**:Loki(SaaS),索引全量日志,Grafana 看板
- **实时错误告警**:Sentry(SaaS),Error+ 自动 capture + 栈帧聚合 + 通知

## 后端就绪情况(无需运维改动)

### 1. 结构化日志

`zap.NewProductionConfig()` 输出 JSON 到 stdout,docker `json-file` driver 即可被 fluent-bit 抓取。

字段约定:
```json
{
  "ts": "2026-05-25T12:34:56.789Z",
  "level": "error",
  "msg": "AES decrypt failed, holder name fallback to empty",
  "trace_id": "...",
  "request_id": "...",
  "user_id": 184,
  "event_type": "wallet.bank_account.decrypt_failed",
  "severity": "critical",
  "finance_risk": "critical",
  "biz_id": "BANK_ACC_123",
  "cipher_len": 128,
  "error": "..."
}
```

### 2. 标准字段工厂

新代码统一用 `pkg/logger` 工厂,避免 key 拼写漂移:

```go
import "kickoff/go-app/internal/pkg/logger"

logger.L(ctx).Error("decrypt failed",
    logger.Event(logger.EventFinanceRiskDecrypt),
    logger.Sev(logger.SeverityCritical),
    logger.FinanceRisk(logger.SeverityCritical),
    logger.BizID(orderNo),
    zap.Error(err))
```

事件类型清单见 `internal/pkg/logger/fields.go`。新增事件必须在此登记。

### 3. Sentry 自动推送

`logger.InitWithSentry()` 已接通,DSN 非空时:
- Error/Warn 自动推 Sentry(`min_level` 可调)
- `event_type` / `severity` / `finance_risk` / `biz_id` / `trace_id` 等自动成 Sentry tag
- 其余字段进 `zap_fields` context
- 进程退出 `FlushSentry()` 兜底

## 部署侧配置

### A. fluent-bit(docker-compose)

机 A 的 `docker-compose.yml`:

```yaml
services:
  go-app:
    image: kickoff/go-app:v0.3.3
    container_name: go-app
    restart: unless-stopped
    environment:
      - APP_APP_ENV=production
      - APP_APP_LOG_LEVEL=info
      - APP_APP_SENTRY_DSN=${SENTRY_DSN}
      - APP_APP_SENTRY_ENVIRONMENT=production
      - APP_APP_SENTRY_RELEASE=${GIT_TAG}
      - APP_APP_SENTRY_MIN_LEVEL=error
      - APP_APP_SENTRY_SAMPLE_RATE=1.0
      - APP_APP_SENTRY_FLUSH_TIMEOUT_MS=2000
    logging:
      driver: json-file
      options:
        max-size: "100m"
        max-file: "5"
        tag: "{{.Name}}"

  fluent-bit:
    image: fluent/fluent-bit:3.0
    container_name: fluent-bit
    restart: unless-stopped
    volumes:
      - /var/lib/docker/containers:/var/lib/docker/containers:ro
      - ./fluent-bit.conf:/fluent-bit/etc/fluent-bit.conf:ro
      - ./parsers.conf:/fluent-bit/etc/parsers.conf:ro
    depends_on: [go-app]
```

`fluent-bit.conf`:

```ini
[SERVICE]
    Parsers_File parsers.conf
    Flush 5
    Log_Level info

[INPUT]
    Name tail
    Tag docker.go-app
    Path /var/lib/docker/containers/*/*-json.log
    Parser docker
    Refresh_Interval 5
    # 只抓 go-app 容器的日志(按 attrs.tag 过滤)
    Path_Key file

[FILTER]
    Name grep
    Match docker.go-app
    Regex file go-app

[FILTER]
    Name parser
    Match docker.go-app
    Key_Name log
    Parser json
    Reserve_Data On

[OUTPUT]
    Name loki
    Match docker.go-app
    Host logs-prod-006.grafana.net   # Grafana Cloud Loki endpoint
    Port 443
    Tls On
    Http_User ${GRAFANA_USER}
    Http_Passwd ${GRAFANA_API_KEY}
    Labels job=go-app,host=${HOST_NAME},env=production
    LabelKeys event_type,severity,finance_risk,level
    LineFormat json
```

`parsers.conf`(标准):

```ini
[PARSER]
    Name docker
    Format json
    Time_Key time
    Time_Format %Y-%m-%dT%H:%M:%S.%LZ
    Time_Keep On
```

机 B 同样部署一份 fluent-bit(读 mysql/redis docker 日志),`Labels host=mach-b`。

### B. Sentry 接入

1. **sentry.io 后台**:创建项目(选 Go),拿 DSN
2. **服务端 env**(写 `.env`,加 `.gitignore`):
   ```bash
   SENTRY_DSN=https://<key>@o123456.ingest.sentry.io/<project>
   GIT_TAG=v0.3.3
   ```
3. **Sentry Alert Rules**(后台 → Alerts → Create Alert):
   - `tag:event_type=wallet.recharge.amount_mismatch` → Telegram + 邮件(立即页人)
   - `tag:finance_risk=critical` → Telegram + 邮件
   - `tag:event_type=payment.callback.state_stuck` 任意 → Telegram 开发群
   - Issue count > 10/min → 邮件
4. **集成 Telegram bot + 邮件**:
   - **Telegram**:`@BotFather` 建 bot 拿 token;`@kickoff_alerts` 群把 bot 拉进去拿 chat_id
     - Sentry 用 generic Webhook,target URL:`https://api.telegram.org/bot<TOKEN>/sendMessage?chat_id=<CHAT_ID>`
     - 或在 Sentry 外加一层中转(`scripts/sentry-to-tg.sh`,把 Sentry JSON body 转成 Markdown 推 TG),格式更好看
   - **邮件**:Sentry 后台 → User Settings → Notifications → 加邮件订阅,critical 走邮件,error 仅看板
   - **可选 PagerDuty / Opsgenie**:夜间 critical 自动电话(本期不上,留 critical 双通道兜底即可)

### C. Grafana / Loki 业务看板

**Grafana Cloud 免费档**(50 GB Loki + 14 天保留 + Grafana 看板,3 用户),够 2 机初期用。

注册 → 拿到 `GRAFANA_USER` / `GRAFANA_API_KEY` 填上面 fluent-bit.conf。

基于日志规则(LogQL)告警:

```
# 24h 内 finance_risk 事件总数 > 5 触发
sum(rate({job="go-app"} | json | finance_risk != "" [24h])) > 5

# 充值失败率 > 5%
sum(rate({job="go-app"} | json | event_type=~"wallet.recharge.*" | level="error" [5m]))
/
sum(rate({job="go-app"} | json | event_type=~"wallet.recharge.*" [5m])) > 0.05
```

详细告警规则模板:后续 ops 在 Grafana 后台落地。

## 推荐 SaaS 选型(避免自建)

| 组件 | 自建成本 | 推荐 SaaS | 免费档够用度 |
|---|---|---|---|
| 日志聚合 | Loki + Grafana + 对象存储 ≈ 半台机 | **Grafana Cloud** | 50 GB/月,2 机用足够 |
| 错误告警 | Sentry self-hosted 至少 4G 内存 | **sentry.io** | 5k events/月,初期足够 |
| 国内备选 | — | **阿里云 SLS / 腾讯云 CLS** | 按量 ¥10-50/月,延迟更低 |

**结论**:除非合规强制要求数据不出境(目前 PRD 没要求),否则**全部走 SaaS**。两机的运维心智负担足够低,可专注业务。

## 关键事件 → 告警通道对照

| event_type | severity | 通道 | 处理 SLA |
|---|---|---|---|
| `wallet.bank_account.decrypt_failed` | critical | Telegram + 邮件 | 1h |
| `wallet.recharge.amount_mismatch` | critical | Telegram + 邮件(抄送财务) | 4h(人工对账) |
| `payment.callback.state_stuck` | error | Telegram 开发群 | 8h |
| `payment.callback.malformed_json` | warning | Sentry 看板 | 24h |
| `wallet.recharge.third_party_match_failed` | error | Telegram 开发群 | 8h |
| `wallet.recharge.order_leaked_to_sweeper` | warning | Sentry 看板 | 24h |
| `config.enc_key.invalid` | critical | 启动失败 + Telegram + 邮件 | 启动即查 |

## 字段保留约定

**改字段名 = 破坏告警**。新增字段随意,改名 / 删除需要同步运维侧告警规则。
受影响 key:
- `event_type` / `severity` / `finance_risk` / `biz_id`(Loki/Sentry 索引)
- `trace_id` / `request_id` / `user_id`(链路追踪)
- `trade_no` / `order_no` / `cb_id` / `channel`(资金对账)

完整清单见 `internal/pkg/logger/sentry_hook.go` `sentryTagKeys`。

## 扩容信号(什么时候才上 k8s)

满足以下**任一**条件再考虑 k3s/k8s,否则保持 docker-compose:

- 节点数 ≥ 5
- 微服务数 ≥ 6 且需要相互调用编排
- 业务出现"早晚高峰需 3x 弹性扩容"的需求
- 团队有专职 SRE(1 人以上)
