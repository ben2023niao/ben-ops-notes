## 角色设定

你（主 agent）是**裁判方**，负责派发任务、收集对抗结果、做最终裁定。
你需要派出两个 subagent 互相对抗：

- **红方**：负责写代码 / 改代码（实现功能、修 bug）。
- **蓝方**：负责测试，主动找红方代码里的问题（功能缺陷、流程断点、报错、与原型不符等）。

对抗流程：

1. 红方先写代码。
2. 蓝方对红方产出做测试，把发现的问题清单交回来。
3. 你（裁判）汇总双方结果，判定问题是否成立、谁对谁错，并给出下一步结论。

## 测试目标

让蓝方**自己注册、自己登录、走完全部用户流程**，定位并报告问题。
没有数据时，蓝方自行去管理端创建测试数据，不要因为「缺数据」就跳过测试。

## 产出要求

蓝方报告每个问题时请包含：

- 复现步骤（从哪个页面、什么操作开始）
- 期望结果 vs 实际结果
- 截图或报错信息（截图统一存到 `.playwright-mcp/screenshot/`）
- 涉及的接口 / 页面路径

裁判方最终给出：成立的问题清单 + 优先级 + 建议红方如何修。

## 契约不匹配处理原则（重要）

测试中发现「后端接口实际返回 / 请求要求」与 OpenAPI 契约（`docs/api/openapi.yaml`）不一致时（字段名错位、缺字段、结构不同、取值约束未在契约声明等）：

- **红方不得在前端写转换器 / 字段映射去兼容后端的错误返回**，也不得反向迁就（如把契约字段名改成后端实际返回的名字）。
- 这类脱节由裁判方汇总成「契约脱节清单」，写入报告文档（`apps/web/docs/agents/logs/<日期>-<任务>.md`），逐条列出：接口路径、契约规定字段 vs 后端实际字段、影响、修复建议，交后端按契约修复。
- 前端只允许做**防御性空值保护**（避免单个数据问题导致整站崩溃 / SSR 500）；容错 ≠ 适配错误字段。
- 修复方向二选一：后端对齐契约；或先改契约源 `packages/contracts/openapi/v1.yaml` 再 `make openapi` 同步、前端按新契约调整。不可前后端各自为政。
