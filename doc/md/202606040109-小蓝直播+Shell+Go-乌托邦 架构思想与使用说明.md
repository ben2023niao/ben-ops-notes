# 乌托邦 架构思想与使用说明

> GitHub 仓库源文件：[点击打开网页渲染版](https://github.com/ben2023niao/ben-ops-notes/blob/main/doc/md/202606040109-%E5%B0%8F%E8%93%9D%E7%9B%B4%E6%92%AD%2BShell%2BGo-%E4%B9%8C%E6%89%98%E9%82%A6%20%E6%9E%B6%E6%9E%84%E6%80%9D%E6%83%B3%E4%B8%8E%E4%BD%BF%E7%94%A8%E8%AF%B4%E6%98%8E.md)

> 整理日期：2026-06-04 01:09｜日期依据：文件创建/修改时间

本文是 乌托邦 的核心说明文档。它解释框架为什么这样设计、各层如何协作、团队如何在新项目中落地，以及后续如何维护和升级。

## 1. 定位

乌托邦 不是业务脚手架，也不是某一个产品项目的代码模板。它是一套 AI 原生工程框架，用来约束团队、AI Agent、文档、契约、测试、Git 和交付流程。

它解决的问题是：

1. AI Agent 容易只看局部代码，不看 PRD、契约和验收标准。
2. 前端、后端、测试容易各写各的，接口联调时才发现不一致。
3. 项目初期速度很快，但规则、日志、ADR、质量门禁没有沉淀，后期难以复制。
4. 公共规则和项目规则混在一起，导致每个新项目都要重新讨论一遍工程规范。
5. 框架更新后无法安全同步到已有项目，团队只敢复制，不敢升级。

乌托邦 的回答是：

```text
公共框架仓库
  -> 作为业务项目的 .ai-framework 子仓库
  -> init 生成项目骨架
  -> sync 只更新受管工具和可审查规则
  -> 项目 Overlay 保存项目差异
  -> CI/质量门禁强制验收
```

## 2. 核心思想

### 2.1 框架不是一次性复制物

早期脚手架常见做法是复制一个目录，然后在新项目里手工改。这个模式会导致两个问题：

1. 复制后公共框架和业务项目断开关系，框架修复无法传播。
2. 项目会不断修改公共规则，最后公共能力被业务细节污染。

乌托邦 使用 `.ai-framework` 子仓库模式：

```text
business-project/
  .ai-framework/      # 乌托邦 公共框架仓库
  apps/               # 当前业务项目应用
  services/           # 当前业务项目服务
  packages/           # 当前业务项目契约和公共包
  docs/               # 当前业务项目 PRD、架构、QA、日志
```

公共框架继续由自己的 Git 仓库维护。业务项目只引用一个版本，并通过 `devtools/framework plan/apply` 把允许同步的文件更新到项目。

完整手册和文档站不放进 `.ai-framework`。它们属于独立 `utopia-handbook` 学习层，用于团队培训和思想传播；Core 只同步执行规则、模板、validator 和可审查工程约束。这样可以避免 Agent 在业务项目中把长教程当成硬规则误读。

### 2.2 公共规则和项目规则必须分层

乌托邦 只管通用工程底线：

1. Monorepo 目录边界。
2. AI Agent 工作流。
3. PRD、契约、测试、日志、ADR 的沉淀方式。
4. 代码规范、数据表设计规范、运维就绪、OpenAPI、UI、性能、验收证据等质量门禁。
5. Git 分支、MR、CODEOWNERS、发布和升级流程。

业务项目自己决定：

1. 具体 PRD。
2. 具体接口和数据模型。
3. 具体设计图和 UI 验收标准。
4. 具体第三方服务。
5. 具体部署环境和密钥。
6. 当前项目允许的例外。

项目差异写入：

```text
docs/project/README.md
docs/project/presets.md
docs/project/constraints.md
docs/project/acceptance.md
docs/project/environments.md
docs/project/third-party.md
```

这就是 Project Overlay。公共框架负责底线，Project Overlay 负责当前项目的自由度。

### 2.3 契约优先是并行开发的前提

乌托邦 不鼓励先让前端猜页面、后端猜接口。标准顺序是：

```text
PRD
  -> Requirement ID
  -> OpenAPI / Event / DTO / Error Code
  -> Frontend mock
  -> Backend implementation
  -> API tests
  -> E2E / acceptance
```

核心资产是：

```text
docs/prd/**
docs/prd/requirements.md
packages/contracts/openapi/**
packages/contracts/events.md
packages/contracts/errors.md
docs/qa/**
```

当前端、后端、测试和 AI Agent 都围绕同一份契约工作，才可以真正并行。

`docs/prd/requirements.md` 是需求总账。每个可开发需求必须拥有 `AUTH-001` 这类稳定 ID，并在模块 PRD、OpenAPI operation、验收证据、测试说明和 Agent 日志中复用。这样 Review 时不是问“这个页面像不像做完了”，而是检查某个需求 ID 是否从 PRD 到上线证据全链路闭环。

### 2.4 文档采用双视图模型

乌托邦 把文档拆成两种视图：

1. 人可读文档：解释业务背景、范围、边界、流程、决策和协作方式。
2. AI/工具可读控制文件：承载需求 ID、OpenAPI、schema、状态、owner、验收证据和门禁输入。

这不是要求每个项目都维护两份重复文档，而是要求同一个事实源能同时服务人和机器。具体项目需要哪些文档，由 PRD、项目复杂度和 `docs/project/**` 决定。详细规则见 `docs/architecture/documentation-model.md`。

OpenAPI 因此不只是接口说明。它同时是接口合同、Mock 源头、契约测试依据和接口文档站源头。面向人看的 Swagger UI、Scalar、Redoc 或内部文档站应由 `packages/contracts/openapi/**` 生成或引用，不能手工维护一份与契约冲突的接口真相。

### 2.5 AI 规则必须从提醒升级为门禁

只写“请认真测试”“请看设计图”是不够的。AI Agent 很容易把口头规则当作提醒，而不是硬约束。

乌托邦 把规则拆成三层：

1. 文档规则：告诉 Agent 应该怎么做。
2. 命令门禁：用 `npm run check` 验证必须满足的条件。
3. 证据沉淀：要求日志、截图、验收记录、红蓝 Review 结果留档。

因此框架不只要求“你要测试”，还要求“你必须给出可检查的测试证据”。

PRD 约束也必须进入门禁：`npm run check:prd` 校验产品 PRD、需求总账、模块 PRD 和模板；`npm run check:openapi` 校验每个 operation 的 `x-prd-id`；`npm run check:ai-gates` 校验 Agent 日志引用了具体需求 ID。

代码和数据表也属于框架底线。`docs/quality/code-standards.md` 定义跨端、Go Gin、Laravel、测试和 Review 规范；`docs/architecture/database-design-standards.md` 定义 MySQL 表命名、主键、字段、索引、迁移、账本和审计规范。`npm run check:engineering-standards` 确保这些规范、模板和 Review/Agent 日志入口没有缺失。

复杂业务必须进入架构能力门禁。`docs/architecture/capability-gates.md` 定义异步、缓存、CDN、统计、搜索、推荐、高可用、可观测性、数据一致性、权限安全和迁移判断；`npm run check:capability-gates` 校验结构化证据、MVP 边界、高风险触发项和红蓝结论。

运维约束同样进入门禁。`docs/operations/ops-readiness.md` 定义环境、部署、回滚、密钥、备份恢复、观测和故障处理；`npm run check:ops` 确保项目具备上线前最小可恢复性，而不是只把服务跑起来。

### 2.6 Git 是框架运行的一部分

乌托邦 不是单纯的目录约定。它假设所有工程行为都进入 Git：

1. 业务项目通过 MR 合并。
2. 框架通过版本号和 tag 发布。
3. 项目通过 submodule commit 锁定框架版本。
4. 框架同步通过 manifest 控制可更新文件。
5. 重大技术决定通过 ADR 记录。
6. 每个 Agent 任务通过日志交接。

没有 Git 约束，AI Agent 会很难判断哪些内容是公共规则、哪些内容是业务实现、哪些变更可以安全同步。

## 3. 整体架构

### 3.1 公共框架仓库

公共框架仓库只保存可跨项目复用的工程资产：

```text
乌托邦/
  AGENTS.md
  README.md
  FRAMEWORK_VERSION
  CHANGELOG.md
  framework.config.json
  framework.lock.json
  framework.sync.json
  devtools/
  scripts/
  framework/
  docs/
  apps/
  services/
  packages/
  infra/
```

其中 `apps/`、`services/`、`packages/` 在框架仓库里是结构基线和 README 说明，不应该放业务实现。

`apps/web` 在 Core 中只是 Web surface 结构占位，不承载 乌托邦 文档站。乌托邦 自身文档站位于 `utopia-handbook/apps/web`。

### 3.2 业务项目仓库

业务项目是实际开发、部署、上线的地方：

```text
business-project/
  .ai-framework/          # 乌托邦 子仓库
  AGENTS.md               # 当前项目 Agent 规则，可在公共规则上加本项目约束
  README.md               # 当前项目入口
  project.config.json     # 当前项目 preset、质量级别、技术栈选择
  framework.lock.json     # 当前项目锁定的框架信息
  apps/
    mobile/
    web/
    admin/
  services/
    go-app/
    laravel-app/
    realtime/
    worker/
  packages/
    contracts/
    ts/
    go/
    php/
    ui/
  docs/
    prd/
    architecture/
    api/
    qa/
    agents/
    decisions/
    operations/
    project/
  infra/
```

项目仓库可以根据 preset 裁剪目录，但不要破坏职责边界。

### 3.3 框架分层

```text
framework/
  core/
  profiles/
  quality-gates/
  examples/
```

`core` 是所有项目必须具备的最小集合。它包含 Agent 规则、基础目录、核心校验脚本、同步工具和项目 Overlay 说明。

`profiles` 是项目类型预设：

```text
mobile-app
nuxt-web
go-gin-api
laravel-app
fullstack-monorepo
custom
```

兼容别名 `web-platform`、`go-gin-app`、`go-gin-laravel` 仍保留给旧项目升级使用；新项目优先使用上面的正式名称。

`quality-gates` 是按需启用的质量门禁，例如 capability、UI visual、performance/SLO。

`examples` 是参考样例，不进入项目运行时代码，也不作为 managed sync 的目标。

### 3.4 同步模型

同步由 `framework.sync.json` 控制：

```text
managedFiles   # 可以由框架安全替换的受管工具
advisoryFiles  # 只能提示人工 review，不能自动覆盖的规则或模板
```

受管文件通常是：

1. `devtools/framework`
2. `scripts/sync-framework.sh`
3. 各类 validator/self-test 脚本
4. 框架运行依赖说明

人工审查文件通常是：

1. `AGENTS.md`
2. `README.md`
3. 规则文档
4. 模板文档
5. 架构策略文档

这样可以避免框架升级直接覆盖项目已经本地化的业务规则。

## 4. Monorepo 目录思想

乌托邦 默认使用 Monorepo，因为 AI 原生团队需要让 PRD、契约、前端、后端、测试、部署和 Agent 日志在同一个上下文里协作。

### 4.1 apps

```text
apps/
  mobile/        # 移动 App
  web/           # 官网、下载页、PC/H5/Public Web，默认 Nuxt 4 + Tailwind CSS v4
  admin/        # 后台管理前端
```

`apps/*` 只放真实可运行应用。PRD、接口映射、设计覆盖矩阵不能放在 `apps/*` 里冒充实现。

### 4.2 services

```text
services/
  go-app/        # Go Gin 核心应用服务：Public API、Admin API、领域逻辑
  laravel-app/   # Laravel 完整应用：Web/API/Filament/Console/Jobs
  realtime/      # WebSocket、IM、在线状态、事件
  worker/        # 异步任务、回调、定时任务
```

Go Gin 适合高并发核心 API、实时前置、网关和轻量服务。Laravel 适合完整后台、内容运营、Filament、复杂管理功能、Console 和 Jobs。

如果项目只需要 Laravel，可以启用 `laravel-app` preset。若项目需要 Go + Laravel 双栈，可以启用 `fullstack-monorepo`。

Go Gin 推荐内部结构：

```text
services/go-app/
  cmd/
    api/                  # Public API 入口，给 mobile/web 使用
    admin/                # Admin API 入口，可选；当 OpenAPI owner 指向 services/go-app 时使用
    migrate/              # 迁移或维护命令，可选
  internal/
    config/
    http/
      public/
      admin/
      middleware/
    application/
    domain/
    repository/
    infrastructure/
    observability/
  migrations/
  tests/
```

Laravel 推荐内部结构：

```text
services/laravel-app/
  app/
    Console/Commands/
    DTO/
    Enums/
    Exceptions/
    Filament/
    Http/
      Controllers/
      Requests/
      Resources/
    Jobs/
    Models/
    Services/
    Support/
  config/modules/
  database/
    migrations/
    seeders/
    factories/
  routes/
    web.php
    api.php
    api/
  tests/
```

`apps/admin` 是统一后台前端，不是 Go 或 PHP 服务端。它可以调用 `services/go-app` 或 `services/laravel-app` 提供的 Admin API；具体接口 owner 必须写入 `docs/api/admin-api.md` 和 OpenAPI。若项目采用 Laravel Filament 一体后台，则可以不启用 `apps/admin`，直接使用 `services/laravel-app/app/Filament`。

### 4.3 packages

```text
packages/
  contracts/      # 跨语言契约：OpenAPI、事件、错误码、DTO 规范
  generated/      # 根据 contracts 生成的 TS/Go/PHP 类型或客户端
  ts/             # 前端、Node、React Native 共享包
  go/             # Go 服务共享包
  php/            # Laravel/PHP 共享包
  ui/             # mobile/web/admin 分层 UI 资产
```

`packages/shared` 这种模糊命名容易把不同语言的公共包混在一起。乌托邦 更推荐按平台拆分：`ts`、`go`、`php`、`ui`、`generated`。

### 4.4 docs

```text
docs/
  prd/
  architecture/
  api/
  qa/
  agents/
  decisions/
  operations/
  project/
  templates/
```

`docs/` 不是补充材料，而是 AI 协作的主工作区。Agent 开发前必须读取，开发后必须更新。

### 4.5 infra

```text
infra/
  ci/
  deploy/
```

CI/CD、部署策略、环境说明和基础设施脚本放在 `infra/`。业务代码不要混进 `infra/`，部署配置不要散落到应用目录外无法追踪。

## 5. 标准工作流

每个需求按这个顺序推进：

```text
Read
  -> Clarify
  -> PRD
  -> Contract
  -> Plan
  -> Implement
  -> Verify
  -> Log
  -> Review
```

### 5.1 Read

先读项目规则、PRD、OpenAPI、架构、设计和现有代码。

### 5.2 Clarify

发现需求不清、契约缺失、权限不明、第三方配置不确定时，先记录待确认，不把推测写成事实。

### 5.3 PRD

把业务目标、范围、不做什么、验收标准写进 `docs/prd/**` 或任务卡，并把可开发需求登记到 `docs/prd/requirements.md`。PRD 团队成员说明和需求总账必须互相引用，避免只写长文档而没有机器可追踪入口。

### 5.4 Contract

影响前后端协作时，先改：

```text
packages/contracts/openapi/**
packages/contracts/events.md
packages/contracts/errors.md
docs/api/**
```

`packages/contracts/openapi/**` 是机器可读事实源；`docs/api/**` 是人可读说明和文档站入口。OpenAPI 变更后，必须同步确认接口文档视图、mock、契约测试和 `x-prd-id` 追踪关系。

### 5.5 Plan

把任务拆成可验证的小切片。涉及 UI、资金、权限、实时通信、大流量、第三方服务时必须标风险。

### 5.6 Implement

按契约实现。前端可以基于 OpenAPI mock 并行，后端按同一份 OpenAPI 实现，测试按同一份 OpenAPI 写用例。

### 5.7 Verify

至少执行项目定义的：

```bash
npm run check
```

根据改动类型追加构建、接口测试、E2E、截图验收、压测或手工验证。

### 5.8 Log

每次 Agent 工作写入：

```text
docs/agents/logs/YYYY-MM-DD-<task>.md
```

日志必须说明读取了什么、改了什么、为什么、如何验证、剩余风险是什么。

### 5.9 Review

重要任务必须做红蓝对抗：

1. 红队找问题：需求漏项、契约不完整、UI 偏差、安全风险、假测试、假功能。
2. 蓝队修复或解释：补测试、补文档、补验收证据。
3. 未完成事项进入日志和任务卡。

## 6. 质量门禁

乌托邦 的默认门禁由 `package.json` 串联：

```bash
npm run check
```

主要覆盖：

1. 框架版本和发布规则。
2. 框架价值模型。
3. framework/core/profile/quality-gate 分层。
4. sync manifest。
5. 项目 Overlay。
6. 文档双视图模型。
7. 架构能力门禁。
8. 技术栈和 Web 支持策略。
9. 大流量治理模板。
10. packages 边界。
11. 设计覆盖矩阵。
12. UI 验收证据。
13. OpenAPI 递归引用、兼容性检查和文档站生成。
14. 测试环境。
15. 项目验收。
16. 红蓝 Review。
17. AI 完成门禁。

### 6.1 架构能力门禁

复杂业务、核心流程、高风险模块和生产发布必须先回答：这个需求是否只是 CRUD，是否涉及异步、缓存、CDN、统计、搜索、推荐、高可用、可观测性、数据一致性、权限安全或迁移。如果某项能力不涉及，也要写“不适用”及原因。

MVP 可以不上完整能力，但必须写清当前边界、未来迁移成本和升级触发指标。涉及资金、订单、扣费、收益、权限、审核、处罚、用户数据或生产发布时，还要追加高风险门禁。

### 6.2 UI 项目门禁

有设计源的项目必须逐页建立：

1. 页面验收卡。
2. 设计图映射。
3. 截图证据。
4. 视觉差异说明。
5. 移动端和桌面端视口矩阵。

快速 MVP 没有设计源时，可以不启用强视觉 diff，但必须在 `docs/project/constraints.md` 说明 UI 验收标准。

### 6.3 大流量项目门禁

大流量项目必须补：

1. SLO。
2. 压测计划。
3. 容量评审。
4. 观测指标。
5. 降级和限流策略。

MVP 项目可以先保留模板，但不能把未验证性能说成已上线可承载大流量。

## 7. Git 维护模型

### 7.1 公共框架仓库

公共框架仓库维护 乌托邦 本身：

```bash
git clone <UTOPIA_REPO_URL> utopia
cd utopia
npm run check
```

框架改动必须符合：

1. 不写入具体业务项目名称、PRD、设计图或密钥。
2. 不破坏既有项目初始化。
3. 不把项目本地规则强行变成公共规则。
4. 改动后跑 `npm run check` 和 `npm run check:init`。
5. 发布前更新 `FRAMEWORK_VERSION` 和 `CHANGELOG.md`。

### 7.2 业务项目仓库

业务项目通过 submodule 锁定框架版本：

```bash
git submodule add <UTOPIA_REPO_URL> .ai-framework
```

项目提交里会包含 `.gitmodules` 和 `.ai-framework` 指向的 commit。这样每个项目可以选择何时升级框架。

### 7.3 框架升级

```bash
git submodule update --remote .ai-framework
devtools/framework status
devtools/framework plan
devtools/framework apply
npm run check
```

`plan` 用来查看将要同步什么，`apply` 才真正写入受管文件。

### 7.4 分支建议

业务项目：

```text
main                  # 稳定主干
develop               # 可选开发集成分支
feature/<scope>       # 功能
fix/<scope>           # 修复
docs/<scope>          # 文档
infra/<scope>         # 基础设施
framework/<scope>     # 框架升级或规则调整
```

公共框架：

```text
main
feature/<framework-scope>
fix/<framework-scope>
release/vX.Y.Z
```

不要让前端、后端长期固定在不同分支。分支按任务切，不按岗位切。前后端并行依靠 OpenAPI 契约，不靠长期分支隔离。

## 9. 日常开发使用方式

### 9.1 做一个新功能

1. 新建任务分支。
2. 读取 `AGENTS.md`、相关 PRD、OpenAPI、架构和 QA 文档。
3. 更新 PRD 或任务卡。
4. 更新 OpenAPI/事件/错误码。
5. 前端基于契约做 mock 和页面。
6. 后端基于契约实现接口。
7. 测试基于契约写用例。
8. 跑 `npm run check` 和必要的应用测试。
9. 写 Agent 日志。
10. 发 MR，附验证结果和风险。

### 9.2 改接口

先改：

```text
packages/contracts/openapi/**
docs/api/**
```

再改：

```text
apps/**
services/**
tests/**
```

如果是 breaking change，必须记录兼容策略。

### 9.3 改 UI

有设计图时：

1. 更新设计覆盖矩阵。
2. 对照页面验收卡。
3. 跑截图或视觉验收。
4. 记录未对齐项。

没有设计图时：

1. 在 `docs/project/constraints.md` 写明 UI 目标。
2. 至少提供关键视口截图。
3. 不能把 MVP UI 宣称为像素级完成。

### 9.4 改后台或权限

必须检查：

1. 登录鉴权。
2. RBAC 权限。
3. 审计日志。
4. 敏感操作二次确认。
5. 后台接口测试。

### 9.5 改资金、订单、扣费、收益

必须检查：

1. 幂等。
2. 强一致或补偿策略。
3. 账本记录。
4. 审计日志。
5. 回滚和异常处理。
6. 服务端测试。

## 10. 如何区分改框架还是改项目

应该改 乌托邦：

1. 多个项目都会受益的规则。
2. 初始化器、sync、validator、quality gates。
3. Monorepo 标准目录。
4. Git/MR/CI 通用流程。
5. 可复用的模板和检查脚本。

应该改业务项目：

1. 当前产品 PRD。
2. 当前接口内容。
3. 当前数据模型。
4. 当前 UI 设计覆盖。
5. 当前部署环境。
6. 当前第三方密钥和配置。
7. 当前项目特有例外。

如果不确定，先把判断写进 Agent 日志的“风险与待办”，不要偷偷把业务规则沉进公共框架。

## 12. 成熟度路线

乌托邦 当前重点是让 AI 原生团队稳定复制工程方法。后续演进方向：

1. preset 初始化继续增加业务型 preset，例如 crawler、content-web、SaaS admin。
2. sync manifest 继续细分 advisory 类型和人工 review checklist。
3. 契约测试从 evidence gate 继续升级为真实 HTTP conformance runner。
4. UI 视觉 diff runner 接入真实截图基线服务。
5. 压测 runner 和 SLO 数据接入真实监控系统。
6. 框架升级报告继续增加风险评分和 breaking-change 摘要。
7. 多项目框架采用情况统计。

评价 乌托邦 是否成功，不看文档写得多不多，而看它是否让团队在多个项目中持续做到：

1. 新项目启动更快。
2. AI Agent 更少漏读需求。
3. 前后端联调更少返工。
4. 测试和验收证据更完整。
5. 框架问题能回流公共仓库。
6. 项目之间能共享工程经验，而不是复制业务垃圾。
