# 游点涩项目运维快速上手

> GitHub 仓库源文件：[点击打开网页渲染版](https://github.com/ben2023niao/ben-ops-notes/blob/main/doc/md/202610270000-%E6%B8%B8%E7%82%B9%E6%B6%A9%2BLinux%2BShell-%E6%B8%B8%E7%82%B9%E6%B6%A9%E9%A1%B9%E7%9B%AE%E8%BF%90%E7%BB%B4%E5%BF%AB%E9%80%9F%E4%B8%8A%E6%89%8B.md)

> 整理日期：2026-10-27 00:00｜日期依据：文件名日期

- 适用对象：第一次接手游点涩/18game 平台运维的开发、运维和值班同学
- 适用环境：游点涩线上环境，测试环境作为对照
- 目标：先看懂系统，再做只读巡检；确认安全后，再按标准流程发布和排障

## 一、先用一句话理解这个项目

用户访问游戏网站时，请求会经过 CDN/Nginx、H5/PC 页面、PHP API，最后访问 MongoDB 和 Redis。运维要保证这条链路一直通，并在发布、故障和容量变化时安全处理。

```text
用户
  -> DNS / CloudFront / 其他 CDN
  -> H5/PC 统一网关（Nginx + Nuxt）
  -> 后端 Nginx
  -> PHP-FPM / php-cron
  -> MongoDB + Redis
```

你不需要第一天就记住全部机器。先记住这条主链路，再按故障位置往下查。

## 二、三个仓库不要搞混

| 仓库 | 放什么 | 谁经常改 |
| --- | --- | --- |
| `docker-youdianse-php` | Docker、Nginx、PHP、CICD、监控脚本和运维文档 | 运维 |
| `youdianse-php` | PHP 业务代码 | 后端开发 |
| `docker-youdianse-php-config-main` | `.env.prod`、SDK 白名单、平台密钥 | 运维，通过配置发版 |

### 最重要的规则

1. 业务代码只在业务仓库改。
2. 容器、Nginx、CICD、运维脚本只在 `docker-youdianse-php` 改。
3. env 和 `alb_white*.txt` 只在配置仓库改。
4. 不要在线上服务器直接 `vi`、`echo >>` 或 `docker cp` 修配置。
5. 任何变更先备份、再验证，最后发群说明。

## 四、第一次需要拿到的内容

向负责人申请：

- GitLab 仓库只读或开发权限
- 线上 SSH 私钥，或 Spug 堡垒机账号
- Telegram 机器人使用权限
- CICD 发布权限
- Beszel 监控查看权限

密钥、密码、Token 只放在本机或服务器受控目录。不要发到群里，不要提交 Git，不要写进文档。

## 五、第一次进入项目：按这个顺序读

```text
1. workbench/START_HERE.md
2. workbench/CURRENT_TASK.md
3. workbench/CURRENT_STATE.md
4. workbench/MACHINE_ACCESS_MATRIX.md
5. workbench/PROJECT_RUNTIME_CHAINS.md
6. README.md
7. 本次任务相关 docs/
```

记住两个原则：

- 先看“当前状态”，再看历史文档。历史文档描述的是当时发生了什么，不一定等于现在的配置。
- 聊天记录只能提供线索。真正操作前必须上机器做只读核验。

## 七、机器人怎么用

在群里发送：

```text
/start
```

首页分成：

- 测试发布区
- 线上发布区
- 功能分类区
- 运维任务编排
- 帮助和联系人

第一次只做三件事：

1. 点“运维任务编排”，看当前任务和负责人。
2. 点“运维值班表”，确认今天谁值班。
3. 点“帮助”，熟悉菜单，不急着发布。

发布前必须确认：平台、环境、前后端类型、Git commit、开发/测试负责人、发布说明。

## 八、后端发布怎么做

### 1. 开发提交业务代码

开发把业务代码提交到 `youdianse-php` 的 `main`，取得 commit id。

### 2. 运维确认发布信息

至少确认：

- 环境是线上
- 后端仓库和 commit id 正确
- 已说明发布内容
- 开发和测试负责人已确认
- 当前没有其他发布占用

### 3. 从 CICD 或机器人发布

发布过程会自动：

```text
拉取指定 commit
  -> 构建 youdianse-php 镜像
  -> 准备运行配置
  -> 重建 web / nginx / cron
  -> 同步白名单
  -> 校验宿主机与容器 sha256
  -> 发送 Telegram 结果
```

### 4. 发布后必须检查

```bash
sudo docker ps --filter name=youdianse-main-php \
  --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'

cd /opt/docker-youdianse-php
sudo cicd-web/runtime/venv/bin/python cicd-web.py check-app-local
curl -sS -o /dev/null -w '%{http_code}\n' \
  https://www.youdianse.com/api/v1/system/info
```

还要看：

- H5 和 PC 首页是否 200
- API 是否 200
- Beszel CPU、内存、load 是否异常
- `runtime/app-logs/error-今天.log` 是否新增错误
- 白名单和配置 sha256 是否 PASS

命令成功不等于业务正常。页面、接口、日志和监控四项都要看。

## 九、前端发布怎么做

前端发布主要跑 H5/PC 构建和容器切换：

```text
选择提交
  -> 拉取前端代码
  -> 构建 Docker 镜像
  -> 启动新的 3003 或 3004
  -> 校验页面和版本文件
  -> 发布成功后失效旧静态缓存
```

发布后检查：

- 首页 200
- `/version.json` 的 git id 正确
- `_nuxt` 和图片没有大面积 404
- 网关 Nginx 无持续 502/104
- 静态缓存 MISS 后再次请求应 HIT

## 十、配置发布怎么做

线上配置仓库固定维护三类核心文件：

```text
env/.env.prod
app-local-files/alb_white.txt
app-local-files/alb_white_secret.txt
```

不要把服务器上的临时文件反拷回 Git。不要写“服务器我改好了”，然后忘记配置仓库。

配置发布后必须确认：

- 配置仓库版本正确
- 宿主机文件版本正确
- web/cron 容器内文件版本正确
- `check-app-local` 为 PASS
- 容器是只读挂载

### 新游戏登录/回调失败先查白名单

```bash
sudo grep -a check_host_sign_failed \
  /opt/docker-youdianse-php/runtime/app-logs/error-$(date +%F).log \
  | tail -20
```

- `host_not_in_whitelist`：游戏 Host 不在 `alb_white.txt`
- `decrypt_host_sign_empty`：平台密钥不在 `alb_white_secret.txt`

处理方式是修改配置仓库并走配置发布，不在容器里手工追加。

## 十一、故障来了怎么判断

### 第一步：确认影响范围

```text
一个域名还是一批域名？
只有页面还是 API 也挂？
所有地区还是某一条线路？
是否刚发布、刚重建或刚好整点？
```

### 第二步：按链路排查

#### 页面打不开

1. DNS 和证书
2. CloudFront/CDN 是否 502
3. 网关 Nginx
4. H5/PC 3003/3004
5. 后端 API
6. MongoDB/Redis

#### API 慢或 500

1. 后端 PHP-FPM 是否 busy
2. `error-今天.log`
3. `api_request/api_response` 是否暴涨
4. Mongo 主从连接是否正常
5. Redis Slowlog

#### 502 / upstream 104

```bash
sudo tail -200 /var/log/nginx/error.log
sudo docker ps
sudo docker logs --tail 100 <容器名>
```

重点区分：

- Nginx 到不到上游
- 上游进程是否重启
- PM2 是否因内存阈值重启
- PHP-FPM 是否打满
- API 上游是否长时间超时

#### 磁盘高

```bash
df -hT /
docker system df
du -xh --max-depth=2 /var/lib/docker /var/log 2>/dev/null | sort -h | tail -30
```

先判断是日志、镜像、构建缓存、数据库还是业务文件。不能解释的文件不要删。

#### 内存高

```bash
free -h
ps -eo pid,user,pmem,rss,etimes,cmd --sort=-rss | head -20
docker stats --no-stream
```

MongoDB 占用内存不一定是泄漏，可能包含 WiredTiger 缓存。先看趋势、告警和进程构成。

#### 大量请求/疑似 CC

先看：

- SYN_RECV 是否暴涨
- established 是否异常
- 全站 QPS
- 来源是否集中
- 444/429/403 比例
- UA 和路径是否异常

不要看到 load 高就直接说被 抗压能力测试。真实业务、爬虫、静态资源回源、应用循环也可能把机器打高。

## 十二、排障时必须保留证据

至少保留：

- 发生时间
- 域名和接口
- HTTP 状态
- 服务器 hostname
- 容器状态
- 关键日志前后各 100–200 行
- Beszel 同期 CPU/内存/load
- 最近一次发布或配置变更

日志太大时，按相同小时取 `api_request` 和 `api_response`，不要只拿全天总量对比。

## 十三、任何线上变更前的 8 项检查

- [ ] 环境是线上还是测试
- [ ] 仓库和分支正确
- [ ] 本地与远端最新提交已确认
- [ ] 工作区改动均已解释
- [ ] 改动已备份
- [ ] 已通知群和相关负责人
- [ ] 已准备验证命令
- [ ] 已准备回滚办法

## 十四、推荐的第一次实操

第一次不要直接改线上。按以下顺序练：

### 练习 1：只读巡检

登录后端，确认 hostname、容器、CICD、磁盘和日志路径。

### 练习 2：看一次发布

旁听一次完整后端或前端发布，记录每一步：

```text
发布申请 -> 检查版本 -> 发布 -> 容器状态 -> 页面/API -> 日志 -> 群通知
```

### 练习 3：查一次白名单

在测试环境查 `check_host_sign_failed`，理解白名单和平台密钥分别解决什么问题。

### 练习 4：跟一次告警

从 Beszel 告警进入对应机器，确认趋势、进程、日志和结论，不在没有证据时重启。

### 练习 5：做一次回滚演练

只做文档演练也可以。明确：

- 上一版本 git id 是什么
- 配置文件备份在哪
- 回滚后看哪些页面和接口
- 谁确认业务恢复

## 十五、常见错误

| 错误 | 正确做法 |
| --- | --- |
| 在服务器直接改 env/白名单 | 改配置仓库并走配置发布 |
| 只看容器 Up 就说正常 | 还要看接口、页面、日志、监控 |
| 看到 CPU 高就重启 | 先确认业务、进程、上游、监控口径 |
| 所有日志整天下载后比较 | 用相同小时、相同接口比较 |
| 发布后不看回调错误 | 检查白名单、密钥和业务日志 |
| 把密钥发群或提交 Git | 只通过受控密钥目录/堡垒机使用 |
| 没备份就改 Nginx | 改前复制并记录时间戳 |

## 十七、上手标准

能独立值班前，应能做到：

- 看懂用户请求主链路
- 分清三个仓库和环境
- 只读检查页面/API/容器/日志/监控
- 知道白名单问题怎么查
- 知道发布前后检查什么
- 知道什么时候停下来找老运维

不确定时先停手。正确地说“我需要确认”比错误地重启生产安全得多。
