## 1. 这次要解决什么

把新的备案域名 `hbazuua.cn` 也接入测试环境，先做三条测试域名：

- `test-img.hbazuua.cn`：后端 uploads 图片反代域名
- `test-pc.hbazuua.cn`：测试 PC 页面入口
- `test-h5.hbazuua.cn`：测试 H5 页面入口

目标是让 `hbazuua.cn` 和已有的 `hbabaxb.cn` 都能作为测试备案域名使用。后续图片加载可以做成多域名候选：谁快用谁；两个腾讯备案图片域名都不可用时，再回退到 AWS CloudFront 老图片地址。

## 8. “谁快用谁 + AWS 兜底”的推荐做法

浏览器不会自动在两个图片域名之间赛跑。后端返回一个字符串 URL 时，浏览器只会请求这一个 URL。

要实现“谁快用谁”，需要前端图片组件或统一图片加载工具做候选列表。

推荐顺序：

```text
1. https://test-img.hbabaxb.cn/uploads/xxx?敏感凭据：[已脱敏]
2. https://test-img.hbazuua.cn/uploads/xxx?敏感凭据：[已脱敏]
3. https://d1rct3ku9n07y3.cloudfront.net/uploads/xxx
```

注意：

- 前两个腾讯备案域名走防盗刷签名。
- AWS CloudFront 作为最后兜底，不加密。
- token 当前只按 path 和时间计算，不按 host 计算；同一张图可以把 host 替换成另一个 `test-img` 域名复用同一组 `token/t`。
- 不建议每张图都无脑并发请求两个腾讯域名，会把流量翻倍。

更稳的实现：

1. 页面初始化时分别请求两个 `test-img` 域名的轻量探测文件或同一张小占位图。
2. 记录哪个域名更快。
3. 本页图片默认使用更快的域名。
4. 单张图片加载失败时，再切到另一个腾讯域名。
5. 两个腾讯域名都失败，最后切 AWS CloudFront。

这样既能做到“用户面前谁快用谁”，又不会把每张图请求都翻倍。
