## 一、结论

按用户要求只启动 BR01 全部业务容器，BR02/BR04/BR05 始终保持停止。
BR01 初始创建了 9 个容器，但随后 8 个 Sanic 业务容器出现自动重启，
启动验证未通过。

用户随后确认：Redis 已被手动关闭，DBA 网络尚未放通。这是维护恢复的前置
条件，未满足前不得继续启动容器。BR01 已再次执行全停，静置 30 秒后四台
巴西后端的 `game-service*` 运行数全部为 0。

## 三、BR01 启动过程

执行：

```text
cd /data/server-runtime
sh start.sh all 20261029-ben
```

首次创建结果：

```text
容器：9/9 创建成功
端口：9090/9091/9096/9098/9099/9020/9018/9019/8765 均监听
镜像：20261029-ben
```

短时间复核发现：

```text
8 个 Sanic 容器 RestartCount 上升到 2～5
vendor_a WS2 保持 RestartCount=0
健康探测出现连接重置或 5 秒超时
```

因此群消息 775 中的“启动验证通过”仅代表创建和端口初检，已被后续稳定性
复核推翻；最终结论必须以后续重新全停和 Redis/DBA 门禁为准。

## 四、关键日志与资源

典型日志：

```text
Main ERROR: Not all workers acknowledged a successful startup. Shutting down.
Sanic worker startup threshold is 30.0s.
ConnectionResetError: [Errno 104] Connection reset by peer
```

同批次启动时资源状态：

```text
CPU：8 核
内存：31 GiB，总使用约 5 GiB
Disk：/ 使用 37%，剩余约 309 GiB
Load average：约 10.75（8 个 Sanic 同时初始化时）
```

内存和磁盘均未耗尽。为排除并发启动本身的影响，随后在 BR01 内停止全部
业务容器，只单独启动 PG；PG 仍发生 1 次以上重启，说明外部依赖未恢复是
继续启动的硬阻塞，不能靠重复启动或继续拉起其他厂家解决。

## 五、用户确认的恢复前置条件

```text
1. Redis 重新启动并确认可用；
2. DBA 完成网络放通；
3. 用户明确通知可以恢复；
4. 才允许重新启动 BR01。
```

以上任一项未完成，四台巴西后端业务容器全部保持停止。

## 六、最终状态

停止 BR01 全部业务容器后，等待 30 秒再次复核：

| 节点 | `game-service*` 运行数 |
| --- | ---: |
| BR01 | 0 |
| BR02 | 0 |
| BR04 | 0 |
| BR05 | 0 |

服务器主机保持在线，监控代理保持运行，不执行系统重启。

## 七、恢复门禁

Redis 和 DBA 网络确认恢复后，仍只先启动 BR01：

1. 启动 BR01 全部 9 个业务容器；
2. 至少观察 60 秒，要求 RestartCount 持续为 0、OOMKilled=false；
3. 核对 9 个端口、镜像 ID 和容器状态；
4. 核对日志无 Redis、数据库、钱包超时和 worker 启动失败；
5. 通过后再单独确认 BR02；不得自动扩展到 04/05。

任一门禁失败立即停止 BR01，并继续保留其他节点停止状态。
