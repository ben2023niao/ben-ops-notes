# 文档双视图模型

> 来源文件：`~/Projects/work/game/xiaolan-watches/dev/docs/architecture/documentation-model.md`

> 整理日期：2026-06-04 01:09｜日期依据：文件创建/修改时间

乌托邦 是 AI 原生工程框架，因此文档不能只服务人阅读，也不能只服务脚本校验。框架采用双视图模型：

1. 人可读文档：让产品、研发、测试、运营、运维、管理者理解背景、范围、流程和决策。
2. AI/工具可读控制文件：让 Agent、CI、生成器、契约测试和 Review 门禁稳定读取事实源。

这不是要求每个项目为每件事都维护两份重复文档，而是要求同一个事实源能被人和机器分别消费。具体项目需要哪些文档，由 PRD、项目复杂度、团队分工和 Project Overlay 决定。

乌托邦 自身的长篇使用手册属于 Handbook 学习层，不属于 Core 执行层。Core 仓库只保留可执行规则、模板、validator、Project Overlay 和必要说明；`docs/manual/**`、`docs/learning/**`、`docs/overview/**` 与文档站实现由独立 `utopia-handbook` 项目维护。业务项目接入 `.ai-framework` 时，不默认引入 Handbook，避免 Agent 把教程案例误读成硬规则。

## 1. 核心原则

| 原则 | 说明 |
| --- | --- |
| 一份事实源，多种视图 | 业务事实只能有一个主来源，可以生成或引用出多种阅读视图。 |
| 团队可读文档解释背景 | 团队可读文档负责讲清楚为什么、边界、例外、流程和业务语义。 |
| 控制文件承载约束 | 控制文件负责稳定字段、ID、路径、状态、owner、schema 和验收结果。 |
| 双向追踪 | 团队可读文档要引用需求 ID、契约和验收；控制文件要能追踪回 PRD 和 owner。 |
| 项目决定深度 | 快速 MVP 可以少文档，但不能丢失需求 ID、契约、验收和日志的最小闭环。 |
| 禁止重复真相 | 如果团队可读文档和控制文件表达同一事实，必须明确谁是源头，另一方只能解释或生成。 |

## 2. 文档分层

| 资产 | 人可读视图 | AI/工具可读控制层 | 最小要求 |
| --- | --- | --- | --- |
| PRD | `docs/prd/product-prd.md`、`docs/prd/modules/*.md` | `docs/prd/requirements.md`、需求 ID、状态、owner、验收引用 | 每个可开发需求必须有稳定 ID。 |
| API | `docs/api/**`、Swagger UI、Scalar、Redoc 或内部文档站 | `packages/contracts/openapi/**`、event、error code、DTO schema | OpenAPI 是接口事实源，文档站是阅读视图。 |
| 数据模型 | `docs/architecture/data-model.md`、ERD、字段说明 | migrations、schema、table template、审计字段约束 | 表结构变更必须能追踪到需求或 ADR。 |
| UI/体验 | 页面验收卡、截图、录屏、设计说明 | 设计矩阵、截图基线、视觉 diff 结果 | 有设计源的项目必须可对照；无设计源的 MVP 要写清 UI 验收标准。 |
| 测试 | `docs/qa/**`、测试计划、回归记录 | test report、coverage、contract test、E2E evidence | 不能只写“已测”，必须有可检查证据。 |
| 运维 | 部署说明、runbook、故障处理流程 | 环境矩阵、SLO、备份恢复记录、告警配置引用 | 上线前必须具备回滚、密钥、备份恢复和事故响应入口。 |
| Agent 日志 | 工作日志、交接、风险说明 | 固定字段、需求 ID、验证命令、框架摩擦记录 | 日志是审计记录和框架改进输入。 |
| 框架手册 | `utopia-handbook` 文档站、手册、学习材料 | 不进入 Core 执行上下文；如需改变规则，必须回到 Core MR | 手册解释思想，不能替代 `AGENTS.md`、Core rules 和 validator。 |

## 3. PRD 的定位

PRD 不是单纯长文档，而是需求数据库的入口。

团队成员需要读：

```text
docs/prd/product-prd.md
docs/prd/modules/*.md
```

AI 和工具需要读：

```text
docs/prd/requirements.md
docs/prd/requirements.index.json
需求 ID
状态
owner
契约引用
验收引用
测试引用
```

项目可以根据 PRD 复杂度决定模块文档粒度。简单 MVP 可以只有少量模块 PRD；复杂项目必须拆分模块、角色、权限、边界、异常、验收和待确认问题。

## 4. OpenAPI 的定位

OpenAPI 在 乌托邦 中有四个身份：

1. 接口合同：前端、后台、后端、测试围绕同一份契约协作。
2. Mock 源头：前端和测试可以从契约生成 mock，不凭空编字段。
3. 契约测试依据：后端响应和错误结构必须符合 OpenAPI。
4. 接口文档源头：面向人阅读的接口文档站应由 OpenAPI 生成或引用。

推荐链路：

```text
packages/contracts/openapi/**
  -> lint / bundle / breaking check
  -> mock server
  -> contract test
  -> docs/api 文档站
  -> CI / MR gate
```

`docs/api/**` 不应该手工维护一份与 OpenAPI 冲突的接口真相。它可以解释模块边界、鉴权策略、错误码约定、owner service、调用流程和文档站入口。

## 5. Project Overlay 的自由度

公共框架只规定最小约束：

1. 需求必须可追踪。
2. 契约必须可执行。
3. 验收必须有证据。
4. 日志必须可审计。
5. 运维必须可恢复。

具体项目决定：

1. 是否需要完整产品 PRD。
2. 是否需要接口文档站。
3. 是否需要设计稿和视觉 diff。
4. 是否需要压测和 SLO 门禁。
5. 后台是前后端分离，还是 Laravel Filament 一体后台。
6. Web、App、Admin、Go、Laravel 启用哪些目录。

项目选择和例外必须写入 `docs/project/constraints.md` 或对应 Project Overlay 文件。没有记录的例外，AI Agent 不能当作默认规则。

## 6. Agent 工作要求

Agent 开始任务时，必须先判断当前任务依赖哪一层事实源：

1. 改需求：先更新 PRD 团队成员说明和需求总账。
2. 改接口：先更新 OpenAPI，再更新或生成接口文档视图。
3. 改数据：先更新数据模型、migration 和表设计说明。
4. 改 UI：按项目是否有设计源选择截图验收或 MVP 验收标准。
5. 改部署：更新 runbook、环境变量、回滚和观测入口。

Agent 完成任务时，日志必须说明：

1. 读取了哪些团队可读文档。
2. 修改了哪些 AI/工具可读控制文件。
3. 是否存在团队成员视图和控制文件不一致。
4. 是否需要把项目经验沉淀回公共框架。
