## 一、改前的问题

```text
1) proxy_connect_timeout 60s
   后端"卡住但不拒绝连接"时，请求要干等 60 秒才失败 —— 这段时间客户端就是转圈。
2) 没有显式配置 proxy_next_upstream
   只能吃默认值（error timeout），失败后是否改投另一台不明确。
3) proxy_read_timeout 600s
   后端"静默消失"（进程被强杀/网络被丢包）时，nginx 复用的 keepalive 空闲连接
   不会立刻断开，请求要等到 600 秒才报错 —— 实测已经复现（见第四节）。
4) upstream max_fails=3 fail_timeout=10s
   坏节点要累计 3 次失败才被摘除，摘除慢一步。
```

## 二、改后的配置（两台机器一致）

### 1）后端层：`00.vendor-upstreams.conf`

```nginx
upstream tada_game_backend {              # 以 TADA 为例，其它厂家同理
    least_conn;                           # 按连接数最少的后端分发（双活要的就是它）
    server 203.0.113.1:9096 max_fails=2 fail_timeout=5s;          # 01 生效
    server 203.0.113.1:9096 max_fails=2 fail_timeout=5s;          # 02 生效
    server 203.0.113.1:9096 max_fails=2 fail_timeout=5s down;    # 03 备用
    keepalive 32;                         # 与后端保持最多 32 条长连接，省握手
    keepalive_timeout 10s;                # 空闲 10s 回收（避免复用"对端其实已经死了"的连接）
    keepalive_requests 1000;              # 每条上游连接最多复用 1000 次
}
```

变化点：

| 参数 | 改前 | 改后 | 为什么 |
| --- | --- | --- | --- |
| 生效机器 | 只有 02 | **01 + 02 同时** | 双活，单台挂掉仍有另一台 |
| max_fails | 3 | **2** | 更快摘除坏节点 |
| fail_timeout | 10s | **5s** | 摘除后更快重新探测 |
| keepalive_timeout | 无（默认 60s） | **10s** | 空闲连接快速回收 |
| keepalive_requests | 无（默认 1000） | 1000（显式） | 明确复用上限 |

### 2）代理层：`all-games-proxy.conf`（每个厂家 location 都一样）

```nginx
location @tada_game_backend {
    proxy_pass http://tada_game_backend;
    # 双后端容灾：连接失败/超时/网关错误时自动改投另一台（最多 2 次、总耗时 10s）
    proxy_next_upstream error timeout http_502 http_503 http_504;
    proxy_next_upstream_tries 2;
    proxy_next_upstream_timeout 10s;
    ...
    proxy_connect_timeout 5s;   # 容灾优化：原 60s -> 5s，后端卡住时快速切换
    proxy_read_timeout 60s;     # 容灾优化：原 600s -> 60s，后端静默挂掉时不至于卡 10 分钟
    ...
}
```

WebSocket 的两个 location（`/lifeservice/ws2`、`/ws2`）**保持 `proxy_read_timeout 3600s`**
（长连接本来就该长；它们也加了同一套 `proxy_next_upstream`，握手阶段失败会改投另一台）。

改后统计：`proxy_connect_timeout 5s` 共 9 处；`proxy_read_timeout 60s` 8 处、`3600s` 2 处（WS）；
`proxy_next_upstream` 规则 10 处；0 处仍是 600s/60s 连接超时。

## 三、参数为什么这样选

```text
· least_conn + 两台都不带 down        -> 真正的双活（按连接数分摊）
· proxy_next_upstream error          -> 连接被拒/网络不可达时，自动改投健康那台（客户端无感）
  timeout/502/503/504                -> 后端超时或网关错误也改投（只重试"基础设施错误"，
                                        不重试 500 这类业务错误，避免游戏 spin 重复下注）
  tries 2 / timeout 10s              -> 最多试 2 台、重试总耗时不超过 10s，故障不会被放大
· proxy_connect_timeout 5s           -> 内网互通 5s 足够；原来 60s，后端"半死"时客户要等 1 分钟
· proxy_read_timeout 60s             -> 正常请求都是秒级；静默挂掉时最多卡 60s（原 600s）
· upstream keepalive_timeout 10s     -> 空闲连接 10s 就回收，避免长期复用已死连接
· max_fails=2 / fail_timeout=5s      -> 坏节点 2 次失败就摘除，5s 后重试；减少"命中坏节点再重试"
```

## 四、故障切换实测（在入口机上做，用 iptables 模拟后端不可达）

测试方法：先把某台后端在入口机上 `iptables REJECT` 掉（等价于"这台机器没了"），
等 12 秒让空闲连接回收，然后连续请求真实游戏路径 `https://tada-games.xqv9m8.icu/`
（该路径会经 `error_page 419 -> @tada_game_backend` 走后端），统计状态码与耗时。

| 场景 | 请求数 | 结果 | 最大耗时 |
| --- | --- | --- | --- |
| 基线（01+02 都在） | 10 | 403 x10 | **0.01s** |
| **模拟 02 挂掉** | 20 | 403 x20 | **0.01s** |
| 恢复 | 10 | 403 x10 | 0.01s |
| **模拟 01 挂掉** | 20 | 403 x20 | **0.01s** |
| 全部恢复 | 10 | 403 x10 | 0.01s |
| 残留 iptables 规则 | — | 0 条 | — |

> 403 是后端对"本机 203.0.113.1 来源"的正常响应，说明**请求确实打到了后端**；
> 关键点是：**没有出现 502，也没有出现卡顿**，两侧各 20 次全部瞬间成功。

优化前同样测过：模拟 02 挂掉时 20 次里有 1 次卡满 10 秒（实际会卡到 600s 上限），
优化后该现象消失。

## 六、还需要知道的限制

```text
1) 最坏情况仍可能有几十秒延迟：后端不是"明确拒绝"而是"静默消失"（强杀/断网丢包）时，
   复用旧连接的那几个请求最多等 proxy_connect_timeout(5s) 或 proxy_read_timeout(60s)。
   我们已把上限从 600s 压到 60s，并把空闲连接 10s 回收，把影响面降到很低。
   要做到"完全零感知"需要主动健康检查（nginx plus / OpenResty 的 health check 模块），
   现在用的是 nginx 自带的被动健康检查（max_fails/fail_timeout）。
2) WebSocket（TADA WS2，8765）：后端挂掉时，已建立的实时连接会断开，客户端会重连；
   新连接会自动落到健康的那台（两个 location 都已配置 proxy_next_upstream）。
3) 游戏 spin 这类"非幂等"请求：我们只对"基础设施级错误"（连接错误/超时/502/503/504）重试，
   不对 500 业务错误重试，避免重复下注风险。
4) 入口机自身（34.151.249.53）仍是单点；如需入口高可用，需要再加一台入口 + DNS/Anycast 方案。
```
